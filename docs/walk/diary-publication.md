# 산책 보드의 첫 공개 마감

DEV #429 / APP #276에서 시작했고 DEV #443 / APP #311에서 20초 예산과 지도 우선 표시로 갱신했다.

## 계약

새 앱에서 종료한 산책은 종료 시각부터 20초의 초기 예산을 가진다. 원본 저장·인증·
좌표 전송·finalize·행동·사진 동기화에 쓴 시간도 포함한다. 앱은 남은 시간을
기존 storyboard POST의 `preparation_budget_ms`로 보낸다(정수 0~20000).
이는 새 `walk-diary-board-v1`에서만 허용한다.

인증된 capabilities의 `diary_publication.format`과 `budget_ms`로 협상한다.
앱은 광고된 상한과 남은 시간 중 작은 값을 사용한다. 기존 10초 요청과 저장된 예약은
계속 유효하며 새 요청/새로고침으로 기존 마감을 연장하지 않는다.
기존 요청에서 필드를 생략하면 기존 생성/lease 계약을 유지한다.
기존 저장 보드, 이전 형식, 사용자 수정본을 새 정책으로 재생성하지 않는다.

## 기존 저장 경로 사용

1. 기존 Walk 소유권 잠금과 입력 검증을 거친다.
2. 원본 기록·관측·동선 중간 지점·시작/종료로 기본 보드를 만든다.
3. 기존 `walk_storyboards.bundle` JSONB에 `walk-diary-preparation-v1`을 저장한다.
   시작 시각, 마감 시각, 완성된 기본 보드 receipt를 담는다.
4. 트랜잭션을 끝낸 뒤 기존 writer를 남은 시간 안에서 실행한다.
5. 제때 도착한 유효한 결과는 고정된 장면 core에 결합한다. 실패·시간 초과는 기본
   보드로 확정한다. 결과 채택도 기존 generation/revision/status 비교를 사용한다.

장면 topology는 앞선 기본 보드 정책을 그대로 사용한다. 타임아웃 때문에 장면 ID,
시간이나 위치를 다시 선정하지 않는다. 제목/본문은 같은 공개 계약의 완성된 값이다.

## 중단·재조회·경합

- 요청이 끊겨도 예약에 기본 보드와 원래 마감이 남는다.
- GET/같은 POST는 같은 준비를 읽는다. 마감이 지난 준비는 저장된 기본 보드로 확정한다.
- 마감 전에 반복 POST를 해도 예약과 타이머를 바꾸지 않는다.
- 마감 뒤 다른 연결이 먼저 확정했다면 기존 writer는 해당 행을 덮을 수 없다.
- 취소를 무시하는 provider task의 늦은 반환값은 DB에 쓰는 경로가 없다.
- 원본 기록이 바뀐 경우 이전 입력의 기본 보드를 새 원본인 것처럼 공개하지 않는다.
- 이미 저장된 보드는 배경/정책 버전만 달라졌다고 다시 쓰지 않는다.

새 worker·queue·DB migration은 없다. 서버 프로세스 중단 상태에서는 마감에 맞춰
별도 worker가 자동으로 행을 고치는 방식이 아니라, 다음 조회가 영속 예약을 확정한다.

## 기기 시간 예산과 서버 시간 예산

서버는 요청을 받아 생성 서비스에 들어온 시점부터 전달받은 나머지 예산을 적용한다.
네트워크 왕복·OS 스케줄링을 서버 시계로 보장할 수 없으므로 앱은 별도로 저장된
종료 마감을 판정한다. 서버 응답이 늦거나 아예 없으면 기기의 기본 보드로 공개한다.
20초는 정상적인 로컬 저장이 가능한 상태에서의 초기 준비 예산이며, 디스크 오류나
프로세스가 실행되지 않는 시간까지 화면이 열린다는 보장은 아니다.

앱은 저장된 지도와 동선을 먼저 표시하고 장면 영역만 준비 상태로 둔다. 장면은
완성된 보드로 한 번 공개하며, 공개 이후 늦은 AI 결과로 자동 교체하지 않는다.
배경 수집 `pending`은 예약 이전 상태다. 앱은 같은 마감 안에서 재조회/비갱신 POST를
반복하되, 기존 `running` 예약을 새로 만들거나 타이머를 연장하지 않는다.

기기 fallback과 사용자 편집은 현재 앱의 로컬 저장 범위다. 다른 기기에 동일한
로컬 확정본/편집본을 전송하는 API는 이번 작업에 포함하지 않는다.
