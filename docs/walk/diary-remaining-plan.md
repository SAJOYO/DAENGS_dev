# 산책 일기: 대화의 경위와 남은 기획

**후속 구현 — 2026-09-14 #508:** 동선·속도 통합 슬롯, 행동핀 없는 활동 작성,
LLM 전용 정규화, 모든 본문을 읽는 장면별 제목을 기본 카드 경로에 연결했다.
[결정 이유와 구현 범위](diary-activity.md)를 따른다. 아래 2026-09-13 대화·남은 기획은
당시 기준을 보존한다. 실제 LLM 품질·배포·실기기 검증의 완료를 뜻하지 않는다.

#512·#514의 패키징으로 바뀐 현재 경로는 [서비스](diary-service-package.md)와
[기획 규칙](diary-domain-package.md)의 이동표·의존 경계를
따른다. 아래 과거 커밋의 호출 경위·제품 결정은 보존하며 장면 정책을 변경한 작업은 아니다.

이 문서는 **왜 지금 구조가 되었고, 무엇을 더 확인해야 산책 일기 기획이 완성되는지**를 설명한다. 다음 담당자는 남은 작업 표만 보고 구현을 시작하지 말고 1~5절의 문제와 결정 이유를 먼저 읽는다.

작성 기준은 2026-09-13의 사용자 대화와 DEV `b1a5f8d4`다. 이 기준의 `dev`에는 [#498](https://github.com/SAJOYO/DAENGS_dev/pull/498)의 카드 작성 경로와 [#499](https://github.com/SAJOYO/DAENGS_dev/pull/499)의 공통 오케스트레이션 연결이 머지되어 있다. **코드 머지는 운영 서버 배포·실기기 실행·실제 LLM 품질 검증과 다르다.** 이 문서는 그 세 가지의 완료를 선언하지 않는다.

현재 실행 구조의 정본은 [카드 오케스트레이션](card-orchestration.md)이다. 이 문서는 그 구조를 다시 설계하는 문서가 아니라, 그 위에서 남은 공간 해석·슬롯 정책·서술 검증을 진행하기 위한 기획과 인계 기록이다. 사용자 요청은 문서화이며 아래 미완료 항목을 이번에 구현했다는 뜻이 아니다.

**코드를 수정하기 전에는 [9절: 실제 호출 경로와 혼동 방지](#handoff-paths)를 확인한다.** 기본 작성기·미리보기·과거 형식·저장본 읽기는 같은 경로가 아니다. 파일 이름이나 대역을 넣은 테스트 하나만으로 현재 서비스 연결을 판단하지 않도록 분기 조건과 확인 방법을 기록했다.

## 1. 사용자가 만들고 싶은 기능

산책을 마친 보호자가 지도를 보며 기록을 열었을 때, **어느 동네의 어떤 공간에서 남긴 기록인지 알 수 있고, 행동을 남긴 곳에는 실제 행동이 별도로 붙어 있는 일기**를 만드는 것이 목표다. 이름과 거리가 붙은 주변 시설 목록만으로는 그 장소가 어떤 공간인지 알기 어렵다.

한 카드에는 기록 시각과 위치 표시, 공간 본문, 핀이 있을 때의 행동 본문, 보존할 사용자 원문, 카드 제목이 연결된다. 이 요소가 같은 카드에 놓인다는 이유로 모두 한 번의 LLM 요청으로 작성하지 않는다. 읽기 화면을 반드시 별개의 여러 칸으로 쪼개야 한다는 뜻도 아니다.

사용자는 반복해서 다음을 요구했다.

- 산책의 공간을 구체화하되, 근처 시설을 줄줄이 나열하지 않는다.
- 피복은 공간 해석의 바탕이고, 공원·상권 등의 자료는 그 맥락을 구체화해야 한다.
- 강아지와 함께한 산책이라는 맥락을 유지하되 **강아지는 공간 서술에 등장하지 않는다.**
- 실제 행동이 없는 곳에 가상의 행위자나 행동을 만들지 않는다.
- SGIS 행정 위치를 기본 입력 경로에서 확보하고, 기존 정규화를 임의로 다시 만들지 않는다.
- 실험 스크립트만 만들지 않고 DEV·APP의 실제 작성·저장·읽기 경로를 사용한다.
- 제목의 표현 정책과 오케스트레이션 구조를 별개의 문제로 다룬다.

따라서 성공은 ‘API 세 개를 붙였다’, ‘슬롯 세 개를 채웠다’, ‘LLM이 문장을 반환했다’가 아니다. **실제 자료가 허용하는 공간 차이가 읽히고, 실제로 남긴 행동과 원문이 보존되는가**가 제품 목표다.

## 2. 무엇을 이야기했고 왜 방향이 바뀌었는가

### 2.1 공원 세 개·피복·상권을 병렬로 놓았더니 장소 나열이 됐다

초기 대화에는 공원 등록점 세 곳까지의 거리, ‘도로’ 피복, ‘여러 업종의 상가 분포’, 동선 형태가 같은 수준으로 놓인 입력이 등장했다. 사용자는 이 구성이 모델에게 여러 장소를 차례로 소개하도록 만들고 있다고 지적했다.

사용자의 문제 제기는 공공데이터가 부족하다는 것이 아니었다. **각 자료가 무엇을 설명하고 서로 어떻게 연결되는지가 없었다.** ‘공간 3개’라는 용량만 맞춰도 공간 맥락이 생기는 것은 아니다. 공원 두 곳을 빼고 대표 시설 하나만 강제로 남기는 것도 이 문제의 충분한 해결이 아니다.

그 결과 논의의 초점이 ‘가까운 시설 몇 개’에서 ‘현재 위치가 놓인 하나의 공간 맥락’으로 이동했다. 피복과 주변 관계로 공간 후보를 만들고, 그 후보를 구체화하는 데 필요한 자료를 선택하는 방향이다.

### 2.2 현재 지면과 주변 공간의 성격은 서로 다른 질문이다

기록 좌표의 피복이 도로여도 하천에 가까운 위치일 수 있다. ‘길’과 ‘하천 주변’ 중 하나를 지워야 하는 충돌이 아니다.

| 구분 | 답할 질문 | 설명용 예시 |
| --- | --- | --- |
| 행정 위치 | 어느 동네의 기록인가? | SGIS에서 확인한 행정동 |
| 현재 지면 | 기록 좌표의 피복은 무엇인가? | 길 |
| 주변 공간의 성격 | 이 지점을 어떤 공간 맥락으로 설명할 수 있는가? | 하천 가까이의 공간 |
| 구체적인 대상 | 그 맥락의 명칭이 확인됐는가? | 이름이 연결된 하천 |
| 국소 특성 | 이 부근을 다른 구간과 구별하는 것은 무엇인가? | 물길 방향의 풀밭 |

표는 목표 의미 구조이며, 모든 칸을 반드시 채우는 할당표가 아니다. 이름을 못 찾았다고 하천 피복까지 사라져서는 안 되고, 풀밭이 없는데 공간을 풍부하게 만들려고 넣어서도 안 된다.

### 2.3 하천은 대표 좌표 하나보다 형상과 이름의 연결로 다뤄야 한다

사용자는 하천이 긴 지형인데 대표 좌표와 반경으로만 설명하는 접근을 문제 삼았다. 논의한 방향은 **피복/하천 형상으로 공간 관계를 계산하고, 이름·코드는 사전 연결 자료로 구체화하는 것**이다.

전국 하천 API와 사용자가 제공한 「한국하천일람(권역별, 2021.12).xlsx」는 이름·코드 정합성 확인에 사용할 후보 자료로 논의됐다. 이것들이 장면 좌표의 정확한 하천 소속을 자동 증명하는 자료는 아니다. 하천 이름 연결에 사용할 형상의 단위, 피복 도형과의 대응, 합류부와 복수 후보 처리까지 확인해야 한다.

사용자는 자료가 오래됐다는 이유만으로 수변 실험을 미루지 말고 실제 수변 위치에서 어떤 재료가 만들어지는지 확인하라고 했다. 다음 작업도 연도 문제를 반복 논의하는 것으로 대체하지 않는다. 실제 매칭 충돌·좌표계·도형 대응이 발견되면 그 구체적인 문제를 기록한다.

사전 연결을 하더라도 매 장면에서 다시 계산할 것이 남는다. **하천 이름의 연속성과 현재 위치의 관계·주변 특성의 연속성은 다르다.** 같은 하천 코드라고 먼 구간의 풀밭·습지·시설 속성까지 이어받을 수 없다.

### 2.4 ‘초지·수변’ 같은 기술 용어가 본문을 딱딱하게 만들었다

사용자는 공간 데이터를 늘리는 것뿐 아니라 일상 언어로 변환하는 정규화를 요청했다. 현재 작성용 변환에는 도로→길, 자연/기타초지→풀밭, 하천→물길 등이 있다. 원래 분류 코드와 출처는 보존한다.

남은 문제는 단순한 단어 치환 이상의 의미 보존이다. 피복상 초지가 있다는 근거는 ‘푸르고 잘 관리된 잔디밭’의 근거가 아니다. 하천 분류를 ‘물길’이라고 불렀다고 현장 물소리나 현재 유량을 아는 것도 아니다. 일상 용어는 읽기 쉽게 하는 표현이지 새로운 속성을 추가하는 권한이 아니다.

### 2.5 재료 슬롯 옆에 관계를 두었지만, 관계 목록만으로도 충분하지 않았다

사용자는 ‘어디서·어떻게·무엇을’ 같은 재료와 별도로 관계 슬롯을 두는 안을 제시했다. 이후 피드백에서는 길·물길·풀밭과 관계들을 평평하게 나열하면 모델이 공간의 중심과 배치를 다시 추론해야 한다는 문제가 제기됐다.

대화에 제공된 실험 피드백에는 다음 종류의 오류가 보고됐다. **이 문서를 작성하면서 해당 실험의 원시 요청·응답을 다시 실행하거나 독립 평가한 것은 아니다.** 다음 실험에서 재현·점검할 실패 유형으로 보존한다.

- 독립적인 두 접촉을 하나의 공통 경계로 묶음.
- 두 대상과 각각 닿는다는 정보에서 ‘그 사이에 있다’는 배치를 만듦.
- 기준점에서 물길 가장자리까지 이은 짧은 구간의 교차를 길 전체와 하천 사이의 배치로 확대함.
- 비접촉 같은 검증 정보를 본문에 나열해 관계 판정 보고서처럼 작성함.

그래서 방향은 **계산 근거 → 작성용 장면 구조 → 생성 문장**으로 정리됐다. 계산 근거는 재현을 위해 충분히 남기되, 작성 입력에는 각 대상이 장면을 설명하는 역할과 확인한 관계의 범위를 함께 준다. 이것은 새 그래프 DB나 거대한 표현 계획기를 먼저 만들자는 결정이 아니다.

### 2.6 장면과 행동을 같이 쓰게 하니 없던 인과가 붙었다

대화에서는 공간 정보와 강아지 행동이 연결되며 ‘하천 쪽 냄새 때문에 코를 움직인다’ 같은 설명이 만들어지는 문제가 나왔다. 지도 자료로는 냄새의 출처나 행동의 동기를 알 수 없다.

사용자는 공간과 행동은 원래 별개의 서술이라고 정정했고, 이후 **공간은 기본 작업, 행동은 행동핀이 있을 때만 추가 작업**으로 나눴다. 두 결과는 코드로 같은 카드에 배치한다. 마지막에 LLM에게 본문을 다시 합치게 하지 않는다.

행동핀 없는 곳도 공간 본문을 만드는 제품 결정은 유지한다. 문장이 어렵다고 공간 작성 자체를 선택 기능으로 바꾸거나 현재 지면을 입력에서 삭제하는 것은 이번 합의가 아니다.

### 2.7 강아지 맥락은 필요하지만 보호자를 연기하는 지시는 다른 문제였다

사용자는 산책 시작 때 동행 강아지 정보가 주입된다는 점을 짚었고, 가상 이름 하나로 실험해 보자고 했다. 동시에 강아지가 공간 서술에 들어가면 안 된다고 명시했다.

이어진 피드백에서는 보호자 시점을 강조한 요청에서 걷기·발밑·시야·물소리 같은 현장 경험이 추가되는 문제가 보고됐다. 이름이 본문에 없다는 것만으로 행위자나 감각을 만들지 않았다고 평가할 수 없다는 뜻이다. ‘들려온다’도 소리와 청취 상황에 관한 주장이다.

따라서 작성 역할은 **보호자가 그곳에 있었던 것처럼 연기하기**가 아니라 **보호자의 산책 기록에 들어갈 공간 배경을 작성하기**로 잡았다. 공통 맥락은 누구의 기록인지, 공간 입력은 무엇을 아는지, 문체 설정은 어떻게 표현할지를 맡는다. 실제 행동의 행위자는 동행 명단을 보고 추정하지 않고 핀에 연결된 ID를 따른다.

### 2.8 SGIS 누락과 별도 실험 경로가 신뢰를 깨뜨렸다

사용자는 행정 위치를 SGIS에서 정적으로 확보해 제공해야 한다고 반복해서 지적했다. 공간 관계 실험에서 기존 SGIS 경로를 빠뜨리고 나중에 별도 스크립트로 보정하면, 실제 요청·카드 JSON·비교 화면이 서로 다른 실행을 보여줄 수 있다.

‘킁킁’ 같은 행동 라벨만 카드에 보이면 어디서 남긴 기록인지 알기 어렵다는 지적도 있었다. 여기에는 서로 다른 두 요구가 있었다. **확인된 위치를 기본 입력·표시에 연결하는 것**과 **카드 전체를 대표하는 제목을 생성하는 것**이다. 위치를 제목 모델이 알아서 언급할지에 맡기지 않는다.

기존 SGIS 정규화는 `sido / sigungu / dong`을 보존한다. APP의 기존 표시값은 `dong`이다. 표시 정책과 자료 보존을 혼동해서 ‘시 정보가 없다’고 설명하거나 새로운 주소 합성 규칙을 만들지 않는다.

자료 확보의 실패도 경로 누락과 다르다. 조회했지만 실패한 상태, 정상 응답이지만 해당 정보가 없는 상태, 의도적으로 제외한 실험 조건, 기본 경로 연결 자체가 빠진 상태를 구분해야 한다. 실험을 위해 별도의 축소 제품을 계속 만들지 않고 실제 변환·선정·요청 조립 경로를 통과시킨다.

### 2.9 오케스트레이션을 새로 만든 것과 기존 것에 연결한 것은 달랐다

처음 구현은 기존 일기 API와 발행·저장을 재사용했지만, 작성 작업의 실행 루프는 별도로 만들었다. 사용자가 기존 DEV 오케스트레이션에 연결했는지 물었을 때, 기존 API를 재사용했다는 설명만으로는 답이 되지 않았다.

기존 DEV를 분석한 결과, 어시스턴트는 계획 구성·어댑터 실행·코드 집계가 분리된 LangGraph였고, 일기 발행 서비스는 예약·마감·원본 버전 확인을 이미 갖고 있었다. 두 구조의 책임을 보존하며 연결하는 것이 필요했다.

[#499](https://github.com/SAJOYO/DAENGS_dev/pull/499)는 기존 어시스턴트와 일기가 `JobExecutor`를 공유하도록 바꾸고, 일기에는 별도의 명시적 LangGraph 흐름을 두었다. 기존 `walk` capability는 현재 산책 적합도 기능이므로 일기로 바꾸지 않았다. 일기 생성에 자연어 의미 라우팅을 새로 끼우지도 않았다.

이 경위 때문에 다음 작업도 ‘새 실험 실행기 하나’를 완료 결과로 삼으면 안 된다. 기존 실행 경계에서 입력·선정·작성 전략을 바꾸고, 실제 API 결과와 APP 표시까지 연결해 확인해야 한다.

### 2.10 제목보다 먼저 ‘실제로 사용할 본문’을 고정해야 했다

사용자가 제공한 리뷰는 아키텍처의 핵심을 LLM 개수보다 수정 권한의 분리로 짚었다. 공간 작성기는 공간 본문만, 행동 작성기는 해당 행동 본문만, 제목 작성기는 채택된 카드의 제목만 바꿀 수 있다.

본문 고정은 모든 모델 호출의 성공을 기다리는 단계가 아니다. 공간 성공·행동 기본 표현·주소 미확인처럼 각 부분에서 사용할 값이 정해지면 고정할 수 있다. 제목은 이 결과만 읽는다. 늦은 공간 결과나 주소를 제목 직전에 끼워 넣지 않는다.

입력 고정, 카드 본문 고정, 최초 공개 확정은 서로 다르다. 공개 마감과 최종 원본·사용자 수정 확인 권한은 기존 발행 경로가 처음부터 끝까지 갖는다. 제목의 구체적 문체와 평가 정책은 별도 과제로 남기며 공간 관계 실험의 변인으로 섞지 않는다.

## 3. 현재 가능한 것과 아직 가능한 것으로 보고하면 안 되는 것

| 항목 | 기준 시점의 상태 | 완료로 확대 해석하면 안 되는 것 |
| --- | --- | --- |
| 공통 실행 연결 | 기존 어시스턴트와 일기가 같은 실행 계층 사용, 일기 LangGraph 연결 | 운영 서버에서 새 코드가 실행 중이라는 주장 |
| 조건부 행동 | 핀이 있을 때 해당 카드의 행동 작업 실행 | GPS나 동행 이름만으로 행동을 추정하는 기능 |
| 본문·제목·발행 | 본문 고정 후 제목, 카드별 재사용·부분 실패·늦은 결과 차단·기존 저장 연결 | 모든 제목과 본문의 의미 정확성 |
| SGIS | 기존 정규화와 공간 요청·카드 위치 연결, APP 기존 표시 유지 | 위치만으로 공원 내부·하천변 통행성·현장 시야 확정 |
| 공간 입력 | 기존 WMS 점 피복·공원 등록점·상권 범위와 작성용 일상 어휘 사용 | 하천·풀밭의 국소 도형 관계를 전국에서 자동 선정하는 기능 |
| 환경 | 적격한 저장 관측을 사용하는 경로 존재 | 모든 실제 산책에서 성공한 날씨 관측을 확보했다는 주장 |
| 적재·퇴거 | 기존 재료별 적용 정책과 저장 동선 재생 실험 존재 | 공간 맥락 중심의 최종 적재·퇴거 정책 확정·운영 적용 |
| 검증 | API 경로와 저장·재조회·APP 계약 검증, 외부 공급자/모델은 대역 사용 | 실제 공급자 성공률·실모델 품질·운영 지연 검증 |

기존 [공간 정규화](space-normalization.md)와 [적용 정책](space-policy.md)의 ‘피복은 다른 자료의 상위 판정자가 아니다’라는 설명은 **현재 구현된 후보 적격성/재생 정책**이다. 앞으로 검토할 공간 맥락 선정과 구분한다.

두 책임은 함께 성립할 수 있다. 공원·상권 자료가 각자 유효하다고 해서 모두 본문에 들어가야 하는 것은 아니다. 반대로 피복 조회에 실패했다고 다른 유효한 원자료를 전부 삭제할 이유도 없다. **원자료의 유효성은 따로 판단하고, 작성할 공간 맥락은 피복과 주변 관계를 바탕으로 구성하는 것**이 이번 대화의 방향이다. 기존 실험 문서를 과거부터 이 정책이 구현돼 있던 것처럼 고치지 않는다.

## 4. 앞으로도 유지할 작성·자료 계약

| 경계 | 유지할 내용 | 필요한 이유 |
| --- | --- | --- |
| 공간 입력 | SGIS 위치, 공간 대상·속성·확인 관계, 적격 환경, 공통 산책 맥락 | 장소를 구체화하면서 행동 사실이 유입되는 것을 막음 |
| 공간 본문 | 장소와 환경만 서술. 강아지·사람의 행동·자세·감각·동기 생성 금지 | 행위자 이름을 숨겼다고 허구의 현장 경험이 사라지는 것은 아님 |
| 행동 입력 | 해당 핀의 실제 행위자와 기록된 행동 | 공간과 행동의 원인을 모델이 연결하지 않게 함 |
| 원문 | 공간·행동·제목 요청에서 제외하고 원래 내용 보존 | 사용자의 글을 환경 재료나 모델 재작성 대상으로 바꾸지 않음 |
| 제목 | 고정된 자기 카드 내용을 읽고 제목만 반환 | 묶음 호출이 다른 카드 사실을 가져오는 권한이 되지 않음 |
| 관계 | 대상 참조·관계 종류·근거·기준점·국소 범위를 보존 | 점의 관계를 길 전체 관계로 확대하지 않게 함 |
| 일상 어휘 | 원래 의미를 유지하며 기술 용어를 읽기 쉽게 투영 | 자연스러움을 이유로 색·정비 상태·분위기를 발명하지 않게 함 |
| 공개 | 기존 예약·하나의 마감·원본 확인·한 번 확정·편집 보존 | 작업용 캐시나 늦은 결과가 공개본을 바꾸지 않게 함 |

‘공간의 중심’ 같은 작성 우선순위는 지형에 관한 사실이 아니다. 모델이 그 표현을 본문에 그대로 쓰거나, 해당 대상이 넓게 펼쳐져 공간을 지배한다고 주장하면 실패다. 모델의 자유는 근거 내의 선택·생략·어휘·문장 순서에 둔다.

## 5. 남은 기획과 실험 순서

아래는 권장 작업 순서다. 각 단계의 완료 조건은 확인해야 할 결과이고, 새 기능이 이미 구현됐다는 체크 목록이 아니다. 수치 임계값·최종 슬롯 수·공간 분류명을 이 문서가 새로 확정하지 않는다.

### R1. 공간 대상과 관계를 실제 재료에서 구성하기

**질문:** ‘여러 시설이 근처에 있다’에서 ‘이 위치는 어떤 공간에 놓여 있다’로 바꾸려면 어떤 대상과 관계가 필요한가?

현재 지면, 주변 공간 후보, 확인된 명칭, 국소 특성을 구분한다. 피복별 API 고정 묶음보다 현재 맥락에서 비어 있는 질문을 먼저 정한다. 하천 피복은 확인됐지만 이름이 없으면 명명 자료를, 국소 차이가 없으면 주변 피복 관계를 확인한다. 가까운 공원이 있다는 이유만으로 자동 추가하지 않는다.

첫 범위는 기존에 논의한 수변 표본이다. 전국 공간 분류를 동시에 완성하려 하지 않는다. 사용자가 제외한 농촌과 너무 드물거나 커버 범위가 좁은 전용 범주는 이번 확대 대상에서 뺀다. 후속 대분류·소분류의 정확한 목록과 필요한 공급자 범위는 기존 자료를 확인해 별도로 명시한다.

필요한 작업:

1. 기존 양재천·유등천 등 실험의 좌표·도형·요청·응답이 있는지 확인하고 같은 표본을 재사용한다. 없으면 새 표본임을 명시하고 다시 확보한다. 대화 속 수치를 실측값처럼 복사하지 않는다.
2. 기록 위치와 하천 피복의 관계를 계산하고, 하천 형상·코드·이름의 사전 연결 가능성을 검증한다. 일치·복수 후보·미명명 상태를 남긴다.
3. 풀밭은 장면 조회 범위의 국소 부분으로 제한해서 관계를 계산한다. 큰 도형이 멀리서 하천에 닿는다는 이유로 현재 지점에서도 맞닿는다고 하지 않는다.
4. 공원 전체 등록 시설 정보와 장면 주변에 위치가 확인된 시설을 구별한다. 공원 등록점으로 경계나 내부 소속을 만들지 않는다.
5. 코드가 계산한 관계, 본문에 묘사할 관계, 검증에만 남길 조건을 구분해 기존 작성 입력에 전달한다.

**완료 조건:** 최소 세 수변 지점에서 현재 지면·하천 관계·이름의 근거·국소 특성을 재현할 수 있어야 한다. 같은 지점에서 물길 쪽 풀밭과 길 쪽 풀밭을 선택할 수 있다면 그 차이를 근거로 설명한다. 관계를 확인하지 못한 경우 비워 두는 결과도 정상 표본으로 보존한다. 여기서 확보한 명명 일치 사례를 전국 정확도로 보고하지 않는다.

### R2. 같은 사실의 전달 방식으로 공간 문장 비교하기

**질문:** 재료가 하나 더 있어서 문장이 좋아지는가, 그 재료가 무엇과 연결되는지 알 수 있어서 좋아지는가?

자료·좌표·모델·문체·공통 산책 맥락을 고정하고 다음 비교를 한다.

| 비교 | 전달하는 내용 | 확인할 차이 |
| --- | --- | --- |
| A | 현재 지면·하천 명칭/미명명·기록 위치와의 근접 관계 | 기본 공간을 알아볼 수 있는가 |
| B | A + 주변 풀밭/습지 등의 존재 | 명사 나열만 늘어나는가 |
| C | B + 확인된 국소 관계와 각 재료의 설명 역할 | 관계 차이가 정확하고 자연스럽게 읽히는가 |

비교군은 같은 제품 입력 준비 경로의 명시적인 투영 차이로 만든다. SGIS나 동행 맥락을 실수로 빼지 않는다. C를 풍부하게 보이게 하려고 확인하지 않은 관계를 가정하지 않는다. 과거 평평한 관계 목록과 작성용 위계의 차이를 확인할 필요가 있으면 사실 목록을 고정한 별도 대조로 둔다.

일상 용어 변환도 점검한다. ‘풀밭’이 ‘푸른 잔디밭’으로, ‘가까움’이 ‘안에서’로, 국소 접촉이 ‘길게 이어짐’으로 바뀌는지 문장의 주장 단위로 검토한다. 근거 ID가 형식상 존재하는 것만으로 통과시키지 않는다.

**완료 조건:** 실제 주입 프롬프트·입력·원문 출력과 문장별 근거 검토를 함께 남긴다. 자연스러움과 사실성을 따로 평가하고, 각 표본의 차이가 드러나는지 확인한다. 이름을 가린 관계도와 문장을 대응해 잘못된 배치를 떠올리게 하는지도 본다. 실패 출력도 보존하고 성공한 문장만 골라 완료를 선언하지 않는다. 자동 합격 점수나 통과율 목표는 아직 확정하지 않았다.

### R3. 공간 맥락의 적재·퇴거를 동선으로 검증하기

**질문:** 이동하면서 무엇을 계속 기억하고, 무엇을 현재 작성 입력에서 내려야 하는가?

기존 `diary_space_policy`·`diary_space_memory`와 [저장 동선 재생](space-policy.md)을 출발점으로 쓴다. 이미 해본 재료별 적용·용량 손실 실험을 다시 ‘앞으로 처음 할 일’로 쓰지 않는다. 남은 것은 관계를 가진 공간 맥락에 그 원칙을 적용하고 운영 작성 경로에서 검증하는 것이다.

다음 세 상태는 구별한다.

- **원자료 캐시:** 재사용할 수 있는 도형·이름·등록 자료.
- **현재 적용 재료:** 지금 좌표·시각에 유효한 대상과 관계.
- **작성/공개 스냅샷:** 그때 채택한 근거와 결과. 이후 상태 변화로 수정되지 않음.

진입 → 같은 하천에서 지면 변화 → 이탈 → 재진입을 재생하고, 중간에 위치 불명·조회 실패·합류부 명명 충돌을 넣는다. 위치 불명은 실제 이탈과 다르다. 하천 이름을 유지해도 거리·풀밭·습지는 새 위치에서 다시 계산한다.

진입·퇴거 거리를 달리하는 안정화나 연속 관측 조건은 **검토할 가설**이다. 대화의 60m·100m 예시는 확정된 제품 수치가 아니다. 관계 자체가 유효한 범위와 여러 후보 중 주 공간을 바꾸는 기준을 분리하고, 현재 유효하지 않은 관계를 표시 안정성 때문에 본문에 남기지 않는다.

**완료 조건:** 좌표별 적재·퇴거·유지·판정 불명·용량 제외의 사유를 재현할 수 있어야 한다. 재진입 시 원자료를 재사용하면서 현재 관계는 다시 계산하는지, 과거 스냅샷이 바뀌지 않는지 확인한다. 공간 3개 같은 기존 용량과 새 맥락 구조의 손실을 비교한 뒤 최종 용량/선정 정책을 정한다. 모든 좌표에서 LLM을 호출할 필요는 없고 대표 장면만 작성한다.

### R4. 기존 날씨 정책으로 실제 적격 환경을 넣기

**질문:** 날씨 API가 있다는 사실을 넘어서, 이 기록의 시각·위치에 어떤 환경을 말할 수 있는가?

기존 날씨 조회·정규화·적격성 정책을 먼저 따른다. 조회한 시각과 관측이 설명하는 시각, 지점과 지역 범위, 관측과 예보·구간 누적을 구분한다. 현재 산책 적합도 결과를 과거 장면의 날씨 원문으로 대체하지 않는다.

적격 관측 있음·정상 조회지만 값 없음·조회 실패·시공간 부적격 사례를 같은 공간 표본에서 비교한다. 시간 정보만 보고 햇살이나 어둠을 만들지 않고, 날씨가 있다는 이유로 강아지의 행동 원인을 설명하지 않는다.

**완료 조건:** 실제 성공 응답이 기존 변환과 적격성 검사를 거쳐 공간 작성 입력에 들어오는 사례를 확보한다. 부적격/미확보일 때 환경이 빠져도 공간·행동·원문은 유지돼야 한다. 실패 원인을 구분해 남기고 본문이 적격 범위 밖의 감각·상태를 추가하지 않는지 검토한다.

### R5. 실제 저장 산책을 DEV에서 생성해 APP에서 읽기

**질문:** 위 개선이 실험 결과만 좋아지게 한 것인가, 실제 사용자가 읽는 기록까지 이어졌는가?

같은 동선의 핀 없음/있음 시나리오, 여러 행동핀, 실제 화면에서 나오는 카드 수와 12개를 넘는 경우를 검증한다. 동행 이름은 서버가 읽은 맥락을 사용하고, 행동의 행위자 연결은 핀을 따른다. 구조 테스트의 대역 응답과 실제 공급자·LLM 응답을 별도 실행으로 구분한다.

실행마다 원본 기준 → 자료 확보 상태 → 선정 근거 → 실제 요청/응답 → 채택 결과 → 제목 입력 → 저장 카드 → APP 읽기 결과를 연결한다. 비교 화면이나 보고서는 이 실행의 저장 결과에서 만든다. 다른 요청에 이전 응답을 붙이거나 JSON만 보정하고 화면을 이전 실행으로 남기지 않는다.

재사용이 없을 때 호출 수는 대략 공간 카드 수 + 행동핀 수 + 제목 묶음 수다. 병행 실행된다는 사실만으로 공개 예산 안에 끝난다고 가정하지 않는다. 자료 조회·대기열·모델 응답·본문 고정·제목·최종 저장 시간을 구분해서 측정한다. 실제 제공자 실패나 늦은 응답도 숨기지 않는다.

**완료 조건:** 실제 저장 산책의 API 생성 결과를 APP에서 저장·재개방하고 위치·제목·본문·원문·사용자 편집이 같은 공개본을 가리키는지 확인한다. 생성 도중 원본 변경, 부분 실패, 늦은 결과, 재진입의 기존 보호가 유지돼야 한다. 사용한 서버 커밋·앱 빌드·실제 실행 범위를 기록한다. 별도 DB가 필요해 건너뛴 저장 검사와 실기기 미검증을 통과로 계산하지 않는다.

## 6. 실험 결과를 남기는 방법

각 결과에는 다음 항목을 함께 남긴다. 원본 좌표·사용자 기록은 기존 비공개 저장 위치를 참조하고, 인증키나 환경 파일 원문은 문서·PR에 복사하지 않는다.

| 항목 | 남길 내용 |
| --- | --- |
| 목적 | 이번에 바꾸는 한 가지와 고정한 조건 |
| 원본 | 저장 산책/기록 참조와 버전, 실제·합성 표본 구분 |
| 자료 | SGIS·EGIS·명명·환경의 확보 상태, 원자료/정규화 버전 |
| 선정 | 현재 지면·공간 후보·선택 대상·관계 범위·제외 이유 |
| 요청 | 정확한 시스템 지시와 입력, 모델·설정, 요청 식별 |
| 출력 | 실제 원문 응답, 실패/시간 초과, 채택·기본 결과·재사용 구분 |
| 검토 | 문장이 주장한 대상/관계와 대응 근거, 범위 확대·허구·자연스러움 |
| 공개 | 고정한 본문과 제목의 버전, 저장 결과 참조, APP에서 읽은 결과 |
| 판정 | 확인한 것, 확인 못 한 것, 다음 변경의 이유 |

‘강아지 이름이 안 나왔다’와 ‘행동·감각을 만들지 않았다’, ‘ID 검사가 통과했다’와 ‘그 ID가 문장의 뜻을 뒷받침한다’, ‘같은 출력이 반복됐다’와 ‘다른 장소에서도 정확하다’를 구분한다.

이름만 바꾸기, 하천 이름 가리기, 문체만 바꾸기, 특정 접촉 관계 제거는 유용한 대조다. 이름·문체 변경으로 공간 사실이 바뀌면 안 되고, 유일한 근거를 제거한 관계가 계속 본문에 나오면 안 된다. 예시 문장은 평가 표본과 분리한다. 같은 문장을 프롬프트에 넣고 재현됐다는 이유로 품질 향상이라고 보고하지 않는다.

같은 명확한 입력 계약에서도 오류가 반복되면, 입력 계층이나 금지 문구를 계속 늘리기 전에 동일 조건의 다른 모델을 진단 대조군으로 검토할 수 있다. 모델 교체가 확정됐다는 뜻은 아니다.

## 7. 다음 담당자가 처음 끝낼 단위

착수 전 [9절의 경로 확인](#handoff-paths)을 먼저 끝낸다. R1·R2의 실험 결과가 기본 작성 요청까지 전달되는지 확인할 기준이다.

첫 완료 단위는 **기존 수변 세 지점에서 현재 위치·하천·주변 풀밭의 관계를 실제로 구성하고, 같은 사실을 전달하는 방식의 차이가 공간 문장에 반영되는지 확인하는 것**이다. R1과 R2를 먼저 묶어 진행한다.

그 결과를 가지고 R3의 동선 재생에서 맥락 유지와 관계 갱신을 확인한다. 날씨는 기존 정책으로 별도 비교하고, 마지막에는 동일한 실제 서비스 경로로 APP에서 읽는다. 전국 전 범주·영속 공간 기억·제목 문체·전체 산책 요약을 첫 실험의 완료 조건으로 한꺼번에 넣지 않는다.

반대로 앞에서 완료한 조건부 행동 호출·공통 실행 연결을 다시 ‘앞으로 분리할 것’이라고 쓰지도 않는다. 후속 구현은 기존 접점을 사용한다.

- 입력/공간 수집: `walk_diary/preparation/input.py`, `walk_diary/collection/service.py`, 기존 SGIS·피복 정규화.
- 공간 후보·적용 실험: `daengs_walk.diary.space`, `daengs_walk.diary.slots`, 기존 `prepare_board_slots` 경로.
- 작성용 재료·검증: `walk_diary/writing/jobs.py`, 계약은 `walk_diary/contracts.py`, 조립은 `walk_diary/writing/assembly.py`(#507). 현재 모델·예산은 `walk_diary/writing/policy.py`, 전송은 `walk_diary/writing/provider.py`, 문체/역할은 기존 `walk_diary/writing/prompts.py`다. `walk_diary/runtime.py`는 그래프 호출과 기존 import 호환을 유지한다.
- 실행: `orchestration/runtime.py`, `diary.py`, 기존 채팅과 공유하는 `execution.py`.
- 발행/보존: `walk_diary/lifecycle/generation.py`가 `walk_diary/lifecycle/snapshot.py`의 준비·응답과 `walk_diary/lifecycle/reservation.py`의 예약·완료를 연결한다(#506). 공개 마감은 기존 `walk_diary/lifecycle/publication.py`, 저장은 기존 카드 영수증과 저장 경로를 유지한다.
- APP: 기존 `WalkDiarySync → ServerDiaryBoard → Room → WalkDiaryReader`.

코드 이름을 재사용했다는 것만으로 관계 선정을 완성했다고 보고하지 않는다. **이번 표본에서 어떤 재료를 얻었고, 왜 그 관계를 사용할 수 있으며, 실제로 어떤 문장이 나왔는지**를 보여주는 것이 다음 완료 보고의 중심이다.

## 9. 실제 호출 경로와 혼동 방지 — 후속 담당자의 착수 기준

이 절은 2026-09-14에 DEV `bc23d9aa32de5c2d3ee4a2434c6138adf1094ec0`, APP `802604d1fcf4d6bd3cc20aec2079ea9720745265`의 코드를 대조해 보완했다. 앞선 대화의 실험 설명을 옮긴 2절과 달리, 아래 경로·분기는 이 커밋에서 직접 읽은 내용이다. **이번 보완은 문서 검증이며 실제 공급자·LLM 호출이나 운영 서버 실행을 다시 수행한 기록이 아니다.** 이후 커밋에서 분기가 바뀌면 호출자부터 다시 확인한다.

2026-09-14 #502의 협상 후 기본 작성기 선택과 #504의 진입점 분리를 9.1·9.2·9.6에 반영했다.
기준은 #502 머지 커밋 `8acbe29385f684195ff450bc21ee14ef0e6a57cf` 위의 #504 코드·타겟 회귀이며, 외부 모델·배포 실측과는 구별한다.

### 9.1 작업하면서 혼동했던 네 지점

| 혼동 지점 | 왜 잘못 판단하기 쉬웠는가 | 현재 확인한 경계와 후속 작업의 기준 |

| 기존 오케스트레이션과 일기 발행 | 기존 API·예약·저장을 사용하면 기존 오케스트레이션까지 사용한다고 설명하기 쉬웠다. 실제로는 다른 책임이다. | 일기 그래프와 어시스턴트 그래프가 공통 `JobExecutor` 구현을 호출한다. 발행 권한은 기존 일기 서비스가 갖는다. 9.3의 양쪽 호출자와 공유 실행 테스트를 확인한다. |
| 기본 작성기와 실험·호환 작성기 | `slot`이라는 파일명, 과거 결합 작성 문서, `generate` 주입 테스트가 함께 남아 있었다. #504 전에는 인자에 따라 다른 작성기로 들어갔다. | 현재는 카드 `write_board`와 구형 `write_legacy_slot_board`로 구별한다. 요청 형식 → 저장 형식 협상 → 발행 재사용 여부 → 실제 작성 호출을 추적한다. 9.2의 분기표를 기준으로 검증 범위를 적는다. |
| 공간 후보의 적격성과 하나의 장면 선정 | 공원·상권·피복이 각각 유효하다는 사실을, 세 재료를 동등하게 나열해야 한다는 뜻으로 읽기 쉬웠다. | 후보를 사용할 수 있는지와 어떤 관계로 장면을 구성할지는 다른 판단이다. 피복을 해석의 바탕으로 삼는 후속 기획을 후보 유효성의 강제 종속 규칙으로 바꾸지 않는다. 9.5 참고. |
| SGIS 정규화와 APP 표시 | 화면에 동만 보이는 것을 원자료에서 시가 사라진 것으로 오해했다. 새 정규화 함수를 만들면 기존 의미까지 달라질 수 있다. | 기존 투영은 `sido`, `sigungu`, `dong`을 보존한다. APP 표시 추출은 `dong`을 읽는다. 9.4의 원자료 → 정규화 → 표시를 각각 확인한다. |

후속 담당자는 이 혼동을 해결하려고 새 작성기·주소 정규화·별도 실험 파이프라인을 먼저 만들지 않는다. **기존 코드에서 어느 단계가 문제인지 확인한 뒤 그 접점을 수정한다.**

### 9.2 기본 작성·미리보기·호환 경로를 구별하는 방법

현재 기본 카드 작성이 실제로 실행되는 경로는 다음과 같다. 일기 기능이 켜져 있고, 보드 형식이 선택되어 새 작성이 필요한 경우를 그린 것이다. 이미 공개된 결과나 진행 중 예약을 반환하는 요청은 작성 호출까지 내려가지 않는다.

```text
APP WalkDiarySync: capabilities의 제공 형식 선택
  → POST /app/walks/{walk_id}/storyboard
  → routers/walk_storyboard.get_diary_writer
      기본값 None: 작성기 선택을 협상 이후로 위임
  → services/walk_storyboard.generate
      existing_format으로 기존 저장 형식 보존
  → walk_diary.lifecycle.generation.generate_diary
  → walk_diary.lifecycle.reservation.reserve_diary
      협상된 형식의 입력 준비 → 원본/사진 버전 확인 → 기존 결과/예약 확인
      새 작성 필요 시 기존 context_pending을 기다리지 않고 예약 저장·commit
      → 예약된 예산 안에서 실행 (#505)
  → walk_diary.runtime.write_board(source, base)
      generate·collector 주입 여부와 무관하게 카드 그래프 실행
  → walk_diary.runtime.write_cards
  → orchestration/runtime.build_diary_orchestrator
  → orchestration/diary.DiaryOrchestrationService.run
      공간·조건부 행동 → 본문 고정 → 제목 → 코드 조립
  → walk_diary.lifecycle.reservation.complete_diary
      원본 재확인 → 만료 발행·generation 확인 → 기존 완료·저장/발행
  → APP ServerDiaryBoard → 기존 저장·읽기
```

첫 확인 파일은 [라우터](../../backend/src/daengs_backend/routers/walk_storyboard.py), [서비스 분기](../../backend/src/daengs_backend/services/walk_storyboard.py), [저장 형식 협상](../../backend/src/daengs_backend/services/walk_diary/lifecycle/negotiation.py), [생성·발행 서비스](../../backend/src/daengs_backend/services/walk_diary/lifecycle/generation.py)다. 작성기부터 읽고 진입 조건을 역으로 가정하지 않는다.

| 경우 | 실제 선택 조건·진입점 | 실행되는 것 / 증명할 수 없는 것 |
| --- | --- | --- |
| 기본 카드 새 작성 | 협상된 `walk-diary-board-v1`, 재사용 판정 후 새 작성, `write_board` | `generate(stage, payload, schema)`·`collector(board)`를 키워드로 주입해도 `write_cards → build_diary_orchestrator`를 실행한다. 수집은 예약 commit 이후 그래프에서 수행한다. |
| 과거 일기 형식 | POST의 `walk-diary-bundle-v1` 또는 board 요청에서 기존 bundle로 협상 | 생성 서비스가 준비 형식에 따라 `walk_diary.legacy.bundle.write_diary`를 선택한다. 과거 형식 작성은 아직 지원 경로이며 단순한 죽은 코드나 읽기 전용 코드로 취급하지 않는다. |
| 슬롯 미리보기 | POST `/app/walks/{walk_id}/diary-slots/preview`, `walk_diary_enabled`와 `walk_diary_slots_preview_enabled` 모두 활성 | `preview_saved_slots → write_slot_preview → write_slot_stamps`. 공개 storyboard의 생성·발행 경로와 별개다. 여기서 좋은 결과가 나와도 기본 카드 작성에 적용됐다는 증거는 아니다. |
| 기존 슬롯 계약의 명시적 작성 | `write_legacy_slot_board(source, base, generate=대역)` | `generate(payload, schema)`를 쓰는 `write_slot_stamps` 계약을 유지한다. 예약 전 수집은 `legacy_collector`, 기존 context job 완료 유예는 `legacy_context_wait=True`로 각각 명시한다. writer 래핑만으로 수집·대기가 활성화되지 않는다. |
| 이미 저장된 결과·진행 중 예약 | `reserve_diary`의 ready/running 재사용 분기, 기존 공개본 GET | 새 모델 호출 없이 기존 상태·결과를 반환할 수 있다. GET의 만료 복구와 과거 영수증 보완도 commit한다. 응답을 받았다는 사실만으로 새 프롬프트 실행을 주장하지 않는다. |
| 과거 저장 영수증 읽기 | `walk_diary.storage.board.load_board`, 저장 v1/v2와 영수증 종류 판독 | 저장 결과의 검증·복원이다. 과거 영수증을 읽었다고 과거 모델을 재호출한 것은 아니다. |

관련 구현: [기본 진입 함수](../../backend/src/daengs_backend/services/walk_diary/runtime.py)와 [과거 슬롯 진입](../../backend/src/daengs_backend/services/walk_diary/legacy/board_slots.py), [작업 입력·응답 검증](../../backend/src/daengs_backend/services/walk_diary/writing/jobs.py), [과거 일기 작성](../../backend/src/daengs_backend/services/walk_diary/legacy/bundle.py), [미리보기 라우터](../../backend/src/daengs_backend/routers/walk_diary_slots.py), [슬롯 작성](../../backend/src/daengs_backend/services/walk_diary/legacy/slots.py), [저장 형식 판독](../../backend/src/daengs_backend/services/walk_diary/storage/board.py).

#507 이후 저장 카드 영수증은 작성 입구 대신 `walk_diary.contracts`만 참조한다. 현재 그래프·모델 없이도 과거 저장본을 검증하는 경계와 변경 전후 표본은 [실제 카드 작성 경로](card-orchestration.md)의 저장 판독 절을 따른다.

**형식 협상에는 두 단계가 있다.** [APP의 WalkDiarySync](https://github.com/SAJOYO/DAENGS_APP/blob/802604d1fcf4d6bd3cc20aec2079ea9720745265/app/src/main/java/com/daengs/app/walk/sync/WalkDiarySync.kt)는 capabilities에 보드가 있으면 보드를, 없으면 과거 일기 형식을 선택하고 둘 다 없으면 legacy 경로를 검토한다. DEV의 `existing_format`은 보드 요청에서도 기존 일기 bundle이나 candidates 저장 형식을 보존할 수 있다. 따라서 APP가 보드를 선호한다는 사실과 특정 저장 산책에서 새 카드 작성기가 실행됐다는 사실은 다르다. 요청 형식만 기록하지 말고 반환 형식·저장 상태·실제 호출도 함께 남긴다.

또 `walk-diary-board-v1`은 공개 보드 형식이고, `walk-diary-board-storage-v1/v2`는 서버 내부 저장 형식이다. 저장 v2의 `writing_receipt`도 `StoredSlotWriting | StoredCardWriting`으로 구별된다. **공개 형식, 저장 형식, 작성 영수증 종류를 하나의 버전 번호로 읽지 않는다.** `complete_slot_board` 역시 `CardWritingResult`일 때 `complete_cards`, 그 외에는 기존 슬롯 조립으로 분기한다.

### 9.3 기존 오케스트레이션과 발행의 연결을 확인할 위치

| 책임 | 코드에서 확인할 연결 |
| --- | --- |
| 기존 어시스턴트 실행 | [runtime.py](../../backend/src/daengs_backend/orchestration/runtime.py)의 `build_orchestrator`와 [graph.py](../../backend/src/daengs_backend/orchestration/graph.py)의 `_execute_requests → JobExecutor` |
| 일기 실행 | 같은 `runtime.py`의 `build_diary_orchestrator` → [diary.py](../../backend/src/daengs_backend/orchestration/diary.py)의 공간·행동 합류 그래프 → 같은 [execution.py](../../backend/src/daengs_backend/orchestration/execution.py)의 `JobExecutor` |
| 생성 예약·최종 공개 | [walk_diary.lifecycle.reservation.py](../../backend/src/daengs_backend/services/walk_diary/lifecycle/reservation.py)의 예약·원본 재확인·채택, [walk_diary.lifecycle.generation.py](../../backend/src/daengs_backend/services/walk_diary/lifecycle/generation.py)의 작성·GET 연결, [walk_diary.lifecycle.publication.py](../../backend/src/daengs_backend/services/walk_diary/lifecycle/publication.py)의 기존 마감 |

공유하는 것은 **작업 실행 구현**이다. 어시스턴트와 일기가 한 그래프나 한 전역 세마포어를 공유한다는 뜻은 아니다. 현재 어시스턴트는 `JobExecutor(concurrency=1)`, 일기 실행은 모델 작업에 `concurrency=4`를 사용하며 자료 수집용 실행기는 별도로 둔다. 이 수치를 전체 서버의 전역 동시 호출 상한으로 설명하지 않는다.

일기는 기존 채팅의 의미 라우터나 응답 형식을 거치지 않는다. 기존 `walk` capability를 일기 생성 기능이라고 오해하지도 않는다. 일기 작업의 의존성은 이미 정해져 있고, 발행 예약에서 얻은 예산 안에서 실행된다. 공간과 행동 결과를 다시 섞는 최종 본문 작성기는 없다.

`JobExecutor`를 쓴다고 발행 권한이 그쪽으로 이동하지 않는다. 입력 고정, 채택 본문 고정, 최종 공개를 구별하고 사용자 원본·편집 검사와 늦은 결과 채택 방지는 기존 발행 흐름에서 확인한다. 실행 취소와 외부 제공자 요청의 물리적 종료도 같은 보장이 아니다.

### 9.4 SGIS의 ‘시’는 원래 정규화에 있다

기존 [walk_sgis.py](../../backend/src/daengs_backend/services/walk_sgis.py)의 응답을 [diary_public_background.py](../../backend/src/daengs_walk/diary/space/public.py)가 다음과 같이 투영한다. 새로 추가한 주소 규칙이 아니라 기존 매핑이다.

| SGIS 원자료 | 정규화된 `facts` | 의미 |
| --- | --- | --- |
| `sido_nm` | `sido` | 시도 명칭 |
| `sgg_nm` | `sigungu` | 시군구 명칭 |
| `emdong_nm` | `dong` | 행정동 명칭 |

투영은 `sgis-dong-v1`과 `address_type=administrative_dong`을 확인하며 행정 코드로 `source_ref`도 남긴다. ‘시’에 해당하는 명칭을 임의의 새 `city` 필드로 만들거나 이름에서 접미사를 지워 재정의할 이유가 없다.

반면 APP [ServerDiaryBoard.kt](https://github.com/SAJOYO/DAENGS_APP/blob/802604d1fcf4d6bd3cc20aec2079ea9720745265/app/src/main/java/com/daengs/app/walk/diary/ServerDiaryBoard.kt)와 과거 형식의 [ServerDiaryBundle.kt](https://github.com/SAJOYO/DAENGS_APP/blob/802604d1fcf4d6bd3cc20aec2079ea9720745265/app/src/main/java/com/daengs/app/walk/diary/ServerDiaryBundle.kt)는 위치 표시 추출에서 `facts.optString("dong")`을 사용한다. **원자료에 있는가 → 정규화에 보존됐는가 → 작성 요청에 들어갔는가 → 화면이 무엇을 골라 표시하는가**를 따로 확인해야 한다. 동만 표시된 화면은 시도·시군구가 정규화에서 빠졌다는 증거가 아니다.

후속 주소 문제가 생기면 원자료 응답과 `place_reference.facts`, 실제 작성 요청, 저장 카드, APP 표시값을 같은 기록 기준으로 대조한다. SGIS 조회 실패 상태와 조회 경로 자체의 누락도 구별한다. 이 보완에서 화면의 위치 표시 정책을 변경한 것은 아니다.

### 9.5 공간 적격성은 장면 구성의 완료 조건이 아니다

확인할 구현은 [수집](../../backend/src/daengs_backend/services/walk_diary/collection/service.py), [재료 정규화](../../backend/src/daengs_walk/diary/space/materials.py), [적용 정책](../../backend/src/daengs_walk/diary/space/policy.py), [슬롯](../../backend/src/daengs_walk/diary/slots/space.py)이다. 먼저 각 자료의 범위·위치·가용 상태를 보고 사용할 수 있는 후보를 만든다. 이 단계에서 피복 조회가 실패했다고 독립적으로 유효한 공원 자료까지 거짓이 되지는 않는다.

그다음 남은 기획은 현재 지면과 주변 피복으로 공간 맥락을 해석하고, 실제로 확인한 대상·관계가 그 맥락을 구체화하도록 선정하는 것이다. 공원·상권이 각각 적격이어도 둘을 반드시 본문에 쓰거나 같은 비중으로 나열할 필요는 없다. 반대로 ‘수변’이라는 해석만으로 가까운 공원을 같은 수변공원에 소속시킬 수도 없다.

특히 현재 `walk_diary.collection.service`의 기본 수집은 SGIS·공원·상권·피복 조회를 다루며 **전국 하천 형상 명명과 주변 풀밭의 국소 관계 계산을 모두 자동 연결한 수집기는 아니다.** EGIS 피복의 WMS 지점 조회가 연결됐다는 사실로 R1의 하천·풀밭 관계까지 완성됐다고 보고하지 않는다. GEO 실험 재료와 DEV 기본 수집에서 실제 확보한 재료를 구별한다.

R1·R2에서는 후보 적격성 검사와 장면의 대상·관계 선택을 각각 기록한다. 이 구별이 없으면 기존 정책 문서의 ‘공급자 간 강제 종속 없음’을 이유로 다시 평면 나열로 돌아가거나, 반대로 피복 결측 때문에 확보된 자료를 전부 버리게 된다.

### 9.6 다음 담당자의 확인 절차와 테스트 범위

1. 현재 DEV·APP 커밋과 해당 저장 산책의 요청/반환 형식을 기록한다. 기능 설정, 기존 공개본·예약 여부를 확인한다. 재현을 위해 사용자 공개본을 지우지 말고 통제된 테스트 산책을 사용한다.
2. 9.2의 라우터 의존성과 실제 작성 호출을 추적한다. `get_diary_writer`가 완성 결과를 돌려주는 대역이면 기본 그래프 검증으로 세지 않는다. `write_board(generate=..., collector=...)`는 외부 의존성만 교체하고 카드 그래프를 실행한다. 구형 슬롯 검증은 `write_legacy_slot_board`로 명시한다.
3. 같은 기록의 SGIS 원자료·정규화, EGIS 확보 범위, 공간/행동 요청, 채택 본문, 제목 입력, 저장 카드와 APP 읽기를 대조한다. 재사용과 새 생성, 실제 API와 대역 응답을 표시한다.
4. 수정한 책임에 해당하는 아래 테스트를 실행하고 결과·skip·미검증 범위를 남긴다. 이 문서 보완 자체에서는 아래 런타임 테스트를 재실행하지 않았다.

APP 응답·보존 계약을 수정한다면 `PublishedCardWritingTest`, `WalkDiarySpacePersistenceTest`, `WalkDiaryReaderTest`를 확인한다. 단위 테스트가 소비한 서버 응답 fixture의 출처와 버전도 확인한다. APP 루트에서 실행하는 예시는 다음과 같다.
