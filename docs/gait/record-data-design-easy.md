# 보행 기록 저장, 쉽게 설명 (2026-08-29)

정식 설계 문서는 `docs/gait-record-data-design.md`. 이 글은 그걸 쉬운 말로 풀어 쓴
것입니다.

## 뭘 하려는 건가요?

강아지 보행 영상을 분석하는 기능은 "한 번 찍고 끝"이 아니라 "이번 달에 찍고,
다음 달에 또 찍어서 뭐가 달라졌는지 보는" 기능입니다. 그러려면:

1. 찍은 영상을 지우지 않고 보관해야 하고,
2. 나중에 그 기록들을 목록으로 볼 수 있어야 하고,
3. 두 기록을 골라서 "뭐가 달라졌는지" 비교할 수 있어야 합니다.

이번 작업은 그걸 위한 **데이터 저장 설계**입니다. 실제로 서랍(DB)을 만들지는
않았고, "서랍을 만들 때 이렇게 만들자"는 도면만 그렸습니다.

## 왜 서랍(DB)을 아직 안 만드나요?

DAENGS 앱에는 아직 "이 사용자가 어떤 강아지를 키우는지"를 기록하는 서랍
자체가 없습니다. 강아지 서랍이 없는데 "강아지의 보행 기록" 서랍만 먼저 만들면,
나중에 강아지 서랍이 생겼을 때 서로 안 맞을 수 있습니다. 그래서 이번에는
도면만 그리고, 강아지 서랍이 정해지면 그때 실제로 만들기로 했습니다.

## 두 팀으로 나누는 이유

- **gait-analysis** (AI 분석 담당): 영상을 보고 "이 관절이 이렇게 움직였다"를
  계산하는 쪽. 계산이 오래 걸리고(영상 하나에 몇 분), 무거운 AI 모델을 씁니다.
- **daengs_backend** (서비스 담당): "이 기록은 누구의 어떤 강아지 것인지",
  "목록에 뭐가 있는지", "지워달라는 요청 처리" 같은 걸 맡습니다.

비유하면 gait-analysis는 **분석실**이고 daengs_backend는 **접수처**입니다.
분석실이 계산까지 다 하고 결과를 넘기면, 접수처가 그걸 서랍에 정리해 넣고
손님(앱 사용자)이 찾아올 때 꺼내 줍니다. 분석실이 직접 서랍 관리까지 하면,
분석하다가 문제가 생겼을 때 접수처(로그인 같은 다른 기능)까지 같이 멈출 수
있어서 나눴습니다.

## 영상 파일은 어디에 저장하나요?

영상 자체(수십 MB짜리 파일)는 **DB 안에 넣지 않습니다.** DB에는 "이 파일이
어디 있는지" 위치 정보만 적어 두고, 실제 파일은 서버의 파일 저장 공간(지금은
Docker volume)에 둡니다. 책으로 치면 도서관 서가에 책을 꽂아 두고, DB에는
"몇 번 서가"라고만 적어 두는 것과 같습니다.

## 지워달라고 하면 바로 지우나요?

바로 지우면 위험할 수 있어서 **"안 보이게 숨기기(소프트 삭제)"를 먼저 하고,
실제 파일 정리는 나중에** 하자고 제안했습니다. 이유는 분석실(gait-analysis)이
항상 켜져 있는 게 아니라서(평소엔 꺼둡니다), 지우려는 순간 분석실이 꺼져 있으면
파일을 못 지울 수 있기 때문입니다. 사용자 입장에서는 지운 즉시 목록에서
사라지니 차이를 못 느낍니다.

## 사진 말고 왜 영상만 업로드 용량 제한이 다른가요?

피부 사진 기능은 사진 한 장(12MB면 충분)을 받지만, 보행 분석은 영상 전체를
받습니다. 영상은 사진보다 훨씬 크죠. 그래서 이번에 **영상 업로드 한도를 새로
150MB로 정했습니다** — 실제 휴대폰으로 찍은 20~30초 영상이 넉넉히 들어갈
크기로 계산했습니다. 너무 크게 올리면 "영상이 너무 큽니다"라는 안내와 함께
거절합니다(전문 용어로 "413 에러").

## 이번에 실제로 코드를 고친 부분

- 영상이 너무 크면 거절하는 기능 (위 150MB 제한)
- 분석 기록에 "원본 영상이 어디 있는지" 정보를 추가 (전에는 결과 영상 위치만
  남고 원본 위치는 안 남아 있었습니다 — 빠뜨린 부분을 채웠습니다)

나머지(진짜 서랍 만들기, 목록/상세/삭제 화면이 실제로 동작하게 하기)는
이번에는 도면(설계)만 그리고, 강아지·사용자 서랍이 정해지면 다음 단계에서
만들기로 했습니다.
