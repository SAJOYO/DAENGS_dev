# 공간 작성기의 선택적 상세 조회

2026-09-14, DEV #520 후속 3단계.

## 결정

2단계의 [공통 근거 조회](diary-writing-context.md)에서 준비한 재료를 사용한다.
이번에는 `get_space_details` 한 종류만 공간 작성기에 연결한다.
위치·피복·지역 환경은 기본으로 공급하고, 주변 공간의 상세는 모델이 필요할 때 선택한다.
후보 선정·유효성 판정은 기존 룰베이스 슬롯에 남긴다.

기존 기본 `generate_card_prose`의 공간 경로에 들어갔으며, 저장 자료로 실행하는
실험도 같은 runtime을 쓰므로 동일하게 연결된다. DB·공공 API 수집기·행동 및 제목의
작성 조건·공개 시점은 변경하지 않는다. 실제 모델 비교는 [4단계 결과](diary-space-comparison.md)에
따로 남겼다. 도구 연결은 동작했지만 세 장면에서 서술 품질 개선은 확인하지 못했다.

## 모델에 공급하는 것

```text
공통 조회 → 기존 정규화 → 현재 카드의 전체 가용 재료 (서버)
                             │
                             ▼
                     초기 공간 모델 입력
              기본 materials + available_details
                   ┌─────────┴───────────┐
                   ▼                     ▼
                바로 서술         get_space_details 요청
                                  선택한 상세 최대 2개
                                         │
                                  서버 검증·내부 조회
                                         │
                                도구 결과를 받고 최종 서술
                   └─────────┬───────────┘
                        인용 검증·기존 카드 확정
```

기본 재료는 기존 정규화의 `location_label`, `point_land_cover`,
`regional_environment`다. 확보된 자료만 전달한다.
기존 공급자 확보·실패 상태를 새로 재분류하는 변경은 아니다.

나머지 공간 근거는 `available_details`에 짧은 ID와 조회 주제만 남긴다.
예를 들면 `{"id":"m2","topic":"주변 공원"}`이다.
이 목록은 조회 안내이며 아직 본문에 인용할 근거가 아니다.

```json
{"material_ids": ["m2"]}
```

이 요청을 받으면 서버가 이미 정규화한 해당 재료만 반환한다.
카드 ID·사용자 ID·좌표·공급자 이름·검색어를 인자로 받지 않는다.
현재 호출의 재료 사전만 접근하므로 다른 카드의 참조를 해석하거나 다른 산책을 조회할
경로가 없다. `m2`는 현재 호출에만 유효한 별칭이다.

반환값은 `{"status":"ok","materials":[...]}`이며 원시 응답·진단·메모를 포함하지 않는다.
동 이름과 일반적인 공원 배경 정책도 기존 정규화에서 적용된다.
공원과 숲을 함께 조회했다고 두 대상이 같은 공간이라는 새 근거가 생기지 않는다.

## 호출과 채택의 경계

- 추가 후보가 없으면 도구를 제공하지 않는다. 있더라도 `AUTO`로 제공해 생략할 수 있다.
- 모델 왕복 최대 2회, 도구 호출 최대 1회, 한 번에 상세 최대 2개다.
- 잘못된 ID·추가 필드·중복·상한 초과 인자는 근거 없이 `invalid_arguments`를 반환한다.
- 첫 응답에 여러 도구 요청을 하거나 다른 도구를 부르면 거절한다.
  마지막 응답에서는 도구를 다시 제공하지 않고 반복 요청도 거절한다.
- 초기 기본 재료와 실제 조회한 상세만 인용할 수 있다. 제공하지 않은 후보를 인용하면
  응답을 채택하지 않는다. 기존 공통 정규화기는 이 별칭을 내부 근거로 복원한다.
- 공간 도구는 행동·제목 작성기에 등록하지 않는다. 행동 핀이 있어야 행동 작업을 만들고,
  메모는 모든 생성 입력에서 제외하는 규칙을 유지한다.

도구는 동기적인 내부 자료 조회다. 추가 공공 API 호출은 0회다.
두 모델 왕복 전체가 기존 `JobExecutor`의 동일한 본문 마감 안에 들어간다.
도구마다 시간을 새로 주지 않는다. SDK가 취소를 삼키고 응답을 돌려줘도 취소된 작성기는
다음 모델 요청을 시작하지 않는다. 늦은 결과는 기본 본문·확정된 제목을 바꾸지 못한다.
실패 시 기존 공간 기본 결과와 발행 흐름으로 진행한다.

첫 요청은 도구 선택 또는 JSON 답변을 받을 수 있고, 조회 후 마지막 요청에는
도구 없이 기존 JSON 응답 스키마를 적용한다. 자동 함수 실행은 꺼두고 서버가 직접 실행한다.
Gemini의 네이티브 함수 호출 ID와 불투명한 서명은 다음 왕복에 원형 그대로 전달하며,
모델의 사고 내용이나 원시 응답 전체를 저장하지 않는다.
공식 [함수 호출 문서](https://ai.google.dev/gemini-api/docs/function-calling)와
현재 설치된 [Google Python SDK](https://github.com/googleapis/python-genai)의
`Content`·`FunctionCall`·`FunctionResponse` 계약을 기준으로 연결했다.

## 실행 기록·버전·기존 자료

`WritingJob.llm_request`는 정규화된 전체 가용 재료다.
3단계 공간 작성에서 이 묶음을 통째로 모델에 보내지 않는다.
선택적 `tool_trace`가 아래 실제 공급 내용을 기록한다.

- 초기 입력
- 실행한 도구와 허용된 인자, 실제 반환 재료 또는 실패 상태
- 모델 요청 횟수와 추가 공공 API 호출 횟수

이것은 개발자용 실행 기록이다. 사용자 일기 본문에 판정 사유나 도구 내역을 붙이지 않는다.
실험 뷰어의 디버그 영역도 전체 가용 재료 대신 초기 입력과 도구 결과를 표시한다.
마감으로 호출이 끝나지 못하면 완성된 trace가 없을 수 있다. 이를 호출 0회로 해석하지 않는다.

저장과 캐시 채택 때도 초기 입력·조회 결과·열람 후 인용 여부를 다시 확인한다.
재사용 시 기존 trace를 보존하며 새 호출로 세지 않는다.
실패 응답의 원시 오류·임의 인자는 저장하지 않는다.

작성 정책은 `shared-orchestration-card-writing-v8`이고 공간 전략 지문에
도구 정책 `diary-space-details-v1`과 짧은 사용 지침을 포함한다.
행동·제목 전략 지문과 입력 v6는 그대로다. 새로 생성할 때 공간 정책 변경을 구별하며,
과거 공개 일기를 자동 재생성하지 않는다.

`tool_trace`는 없으면 직렬화에서 제외하는 선택 필드다. 과거 저장본은 그대로 읽는다.
저장 독자는 순수한 `space_details.py` 검증만 사용하며 작성 런타임·SDK를 불러오지 않는다.
향후 도구 계약을 바꾸면 새 버전 분기를 추가하고 이 v1 판독 규칙은 보존해야 한다.

## 3단계 당시 확인 범위

실제 Gemini·새 공공 API·운영 DB·배포는 실행하지 않는다.
네이티브 SDK 대역으로 선택적 호출과 ID/서명 보존을 확인하고,
저장된 실제 공공자료와 가상 GPS로 실제 그래프·저장·캐시 연결을 검사한다.
서술 품질이나 Gemini가 적절한 후보를 고른다는 사실은 이번 검사로 입증하지 않는다.

제목 캐시 테스트는 메모 수정 시 재생성을 기대하던 옛 기대값을 제거한다.
HTTP 제목 정책 테스트에는 실제 생성 배경을 공급한다.
공간도 없고 메모만 있는 상황에서 메모를 제목의 근거로 쓰게 만들지 않는다.

10개 타겟 파일의 137개 사례 중 최초 129개가 통과했고, SDK 대역 형식·저장 테스트
반환형·옛 제목 기대값에서 8개가 실패했다. 해당 3개 파일을 수정한 뒤 59개를 재실행해
모두 통과했다. 변경 영향이 없는 나머지 78개 사례는 반복 실행하지 않았다.
