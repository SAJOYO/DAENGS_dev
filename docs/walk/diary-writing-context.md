# 일기 작성의 공통 근거 조회

2026-09-14, DEV #520 후속 2단계.

## 이유와 범위

서비스와 기존 실험의 LLM 입력은 이미 같은 `model_input.normalize()`를 사용했다.
다만 공간·행동 근거를 준비하는 코드가 작성 작업 생성 함수 안에 있어,
정규화 재료만 확인하려 해도 작업 생성이나 고정 응답 재생 경로를 거쳐야 했다.

이번에는 그 준비 코드를 `writing/context.py`로 옮겼다. 실제 작업과 생성 없는
실험 조회가 같은 함수에서 재료를 받는다. 후보 수집·슬롯 선정 정책은 추가하지 않는다.
1단계의 문장 예시는 아직 프롬프트에 넣지 않았다. 도구 등록·호출 루프는 3단계다.

## 연결

```text
현재 입력·선정 보드·고정 슬롯
    ├─ get_space_context(base, card_id)
    └─ get_action_context(base, card_id)
          ├─ 실제 작성: request/evidence → WritingJob → normalize → LLM
          └─ 실험 조회: llm_input → 같은 normalize → JSON 파일
```

조회 함수는 `PreparedSavedBaseBoard`를 받아 해당 보드의 카드와 스탬프를 찾는다.
보드·입력·슬롯 버전이 섞이거나 카드가 그 보드에 없으면 거절한다.
기존 작업 생성 진입점도 전달받은 장면과 스탬프가 현재 준비본에 속하는지 확인한다.
이는 준비본 내부의 연결 검사다. HTTP 회원 소유권 검사는 기존 API에 남아 있다.

반환하는 `WritingContext`에서:

- `request`: 작업 지문·인용 복원에 필요한 내부 요청. 원자료 ID와 위치 등 내부 정보가 있다.
- `evidence`: 원자료 추적용 정보. 모델에 보내지 않는다.
- `llm_input`: 기존 정규화기를 거친 서술 재료만 반환한다.

전체 반환 객체를 모델 입력으로 직렬화하지 않는다. 실험 파일도 `llm_input`만 담는다.
파일의 카드 ID는 사람이 결과를 대응시키는 외부 표지이며 LLM 재료에 포함되지 않는다.
출처별 가용 상태는 기존 내부 요청의 상태를 보존한다. 새 상태 분류를 도입하지 않았다.

## 유지하는 제품 규칙

- 행동 핀이 없으면 `get_action_context()`는 `None`을 반환한다.
  이동 재료가 풍부한 메모·사진·경로 카드에도 행동 작성을 열지 않는다.
- 핀이 있으면 기록된 행동과 그 시각의 이동 맥락 최대 1개를 준다.
  형상·되짚기·속도를 합치는 기존 규칙과 속도 기준을 그대로 사용한다.
- 메모는 어떤 서술 입력에도 넣지 않는다. 원문 보존·제목 의존성은
  [행동 핀과 독립 메모 계약](diary-action-boundary.md)을 따른다.
- 공간 재료는 동 이름과 일반적인 공원 배경을 유지한다.
- 조회는 재수집·재선정·글 생성·저장·발행을 하지 않는다.

유효한 준비본에 대한 기존 요청·지문·인용 정보는 유지한다.
입력 v6·작성 정책 v7·캐시·저장 영수증·프롬프트 버전을 올리지 않았다.
이미 저장된 일기를 조회 함수로 재처리하지 않는다.

## 생성 없는 실험

backend에서:

```powershell
uv run --no-sync python -X utf8 tools/preview_diary_context.py --source evals/diary_route_scenario/public-02 --output evals/diary_route_scenario/context-lookup-01
```

`--source`의 `input.json`과 `backgrounds.json`을 읽는다. gzip 파일도 지원한다.
기존 재생기의 입력 검증과 보드·슬롯 준비를 거친 다음 공통 조회 함수만 호출한다.
이 CLI에서의 최초 보드 준비와, 준비된 슬롯을 읽기만 하는 조회 함수는 구분한다.
기존 결과를 덮어쓰지 않으므로 재실행할 때는 새 출력 폴더를 지정한다.

출력은 `contexts.json`과 `summary.json` 두 개다. 본문·제목·가짜 생성 응답은 없다.
`space`에는 공간 입력, `action`에는 행동 입력 또는 `null`이 담긴다.
Gemini 키 파일이나 새 공공 API 호출이 필요하지 않다.

검사는 실제 작성기에 전달되는 입력과 직접 조회의 일치, 핀 없는 경우,
섞인 준비본·스탬프 거절, 메모·캐시·저장 읽기 경계를 대상으로 한다.
CLI 회귀 검사는 별도 프로세스에서 네트워크 연결과 작성 런타임 import를 차단한 채
저장된 공공자료를 읽어 이전 정규화 요청과 비교한다. 서술 품질 평가는 별도 4단계다.

이번 결과: 관련 7개 테스트 파일 91개 통과, 변경 Python 4개 파일 Ruff 통과.
양재 저장 자료에서 공간 입력 8개·행동 입력 1개를 추출했다.
기준 커밋 `b99a94b4`의 작업 생성 함수와 비교했을 때 9개 작업의 내부 요청·지문·인용 근거까지
동일했다. [조회 입력](../../backend/evals/diary_route_scenario/context-lookup-01/contexts.json)과
[요약](../../backend/evals/diary_route_scenario/context-lookup-01/summary.json)을 남긴다.
외부 호출과 본문·제목 생성은 모두 0회다. 전체 테스트·운영 DB·배포 검사는 수행하지 않았다.
