# 시설 검색 대화 평가

사용자 의도 → 제안된 변경 → 확정 필터 → 검색 결과 → 답변이 일치하는지 평가한다.
대상은 `facility-conversation-v2`이며 앱 UI 변경, 기존 v1의 동일 동작 보장은 범위 밖이다.

## 작업 목적: 출력 평가와 구조 재설계 연구

2026-09-10 사용자 지시: 실제 출력 평가와, 평가 결과에 근거해 구조를 다시 설계하는 연구를 함께 수행한다.
UI는 현재 상태로 고정한다. 산출물은 실행 결과, 실패 원인 분석, 구조 대안 비교, 채택 근거와 회귀 검증이다.

현재 구현의 동작을 보존하는 검사와 제품이 원하는 동작의 평가는 구분한다. 예를 들어
현 계약의 `clarify`/변경 배타 규칙을 준수해도, 매번 재질문해서 작업을 완료하지 못하면 제품 품질은 낮다.
미지원 요청의 정직한 처리는 평가하되 그 기능을 계속 미지원으로 둘지는 별도의 설계 판단이다.
23개 명세는 출발점이다. 연구로 정책이 바뀌면 변경 이유를 남기고 기준 버전을 올려 이전 기준도 보존한다.

## 진행 순서와 산출물

| 단계 | 작업 | 남길 근거 |
| --- | --- | --- |
| 1. 평가 연결 | 명세를 실제 상태/후보로 변환하는 실행 어댑터와 관측 기록 작성. 모델·엔진·답변·API 경합 경계를 구분 | 실행 명령, 재현 가능한 입력, 자동 판정 범위와 의미 검토 항목 |
| 2. 현재 기준선 | 현재 구조와 프롬프트에서 정상 흐름과 약한 경계를 먼저 실행한 뒤 23개로 확대 | 모델 원본 제안, 확정 전후 필터, receipt, 후보, 원본/최종 답변, 재시도·오류, 시간·호출 수 |
| 3. 원인 분해 | 실패한 모델 출력을 고정해 서버 경로를 재생하고, 유효한 계획을 넣어 실행·답변 경계를 대조 | 해석 오류 / 필요한 상태 누락 / 도구 표현력 한계 / 정책·원천 데이터 제약 / 상태 경합 / 답변 근거 오류 |
| 4. 구조 대안 | 관측된 원인을 설명하는 가설별로 작은 실험을 구성. 한 번에 바꾸는 축을 제한 | 현재 구조 대비 개선·퇴행, 추가 호출·지연·복잡도와 미해결점 |
| 5. 재설계 검증 | 동일 입력 비교와 튜닝에 쓰지 않은 표현·여러 턴 조합으로 검증 | 원문·변형별 결과, 기존 정상 동작의 회귀, 채택/기각 이유 |
| 6. 반영 | 근거가 있는 구조를 구현하고 해당 경계 회귀 테스트로 고정 | 설계 결정, 변경 PR, 재검증 결과 |

모델 반복 3회는 탐색용이다. 통계적 안정성이나 전체 자연어 정확도를 보증한다고 하지 않는다.
판정이 모호한 제품 정책은 사례와 가능한 동작을 제시해 사용자와 결정하고, 구현을 정답으로 역산하지 않는다.

## 연구할 구조 질문

- LLM이 조건 ID를 직접 편집하는 현재 방식과, 의미 요청을 내고 서버가 필터 변경으로 변환하는 방식의 차이.
- 전체 대화 이력 없이도 명확화 대상·원래 요구·확인할 선택지를 명시적으로 보존할 수 있는가.
- 지원 조건과 미지원 조건이 섞일 때 전체 재질문과 부분 적용/확인의 장단점. 사용자 동의 범위를 어떻게 표현할 것인가.
- 확인된 사실을 구조화해 답변에 전달할 때, 자유 문장·문구 조합·혼합 생성 방식의 근거 충실도와 표현 품질.
- 결과를 선택하거나 설명할 때 모델에 필요한 정보의 최소 범위와, 그 정보의 신선도/참조를 보장하는 방법.

위 항목은 실험 후보이며 채택된 설계가 아니다. 실패 기록에서 필요한 항목부터 검토하고,
외부 사례·기법 조사는 해당 설계 질문에 맞춰 진행한다. 초기 가설만으로 구조 전체를 교체하지 않는다.

평가에는 의도/필터 정확성, 원치 않은 변경, 작업 완료 여부, 확인 질문 횟수와 유용성,
답변의 근거 충실도, 시간·모델 호출·제공자가 반환한 사용량을 함께 기록한다.
사용량 정보가 없으면 비용은 미상으로 남긴다. fallback과 모델 원본 출력을 구분해
기본 문구가 모델의 실패를 가린 경우도 관측한다.

## 판정 원칙

- 필수 조건, 선호, 해제, 확인된 부정값, 미상은 별도로 판정한다.
- 언급하지 않은 조건은 유지한다. ID 순서보다 의미를 비교하되 중복 ID/중복 조건은 따로 검사한다.
- `clarify`는 현 계약상 필터 변경을 동반할 수 없다. 지원/미지원 요구가 섞이면 상태를 유지하며 확인한다.
- 허용 후보 집합을 기준으로 선택을 판정한다. 특정 장소 하나나 답변 문구의 완전 일치를 정답으로 고정하지 않는다.
- 검색을 하지 않은 `edit_only`, 과거 스냅샷 설명, 조건과 결과의 불일치를 성공한 신규 검색으로 표현하지 않는다.
- 모델이 안전하게 재질문했는지와 사용자가 원하는 작업을 완료했는지는 별도 지표다.
- 명확화 뒤 “응”은 실제 직전 질문에 맞춰 평가한다. 애매한 질문 뒤 재확인을 무조건 실패로 세지 않는다.
- 답변의 의미는 확인된 근거와 비교한다. 근거 ID·장소명·숫자 검사만으로 조용함·무료 같은 산문을 검증했다고 하지 않는다.
- 검색·계획·답변·API 상태 경합 실패를 분리한다. 외부 서비스 장애와 모델의 의미 오류를 합산하지 않는다.

## 먼저 확인할 약한 경계

- PC-E01/E02: 주차 필수 → 선호 → 해제와 주차 불가 요구의 차이.
- PC-E08: 명확화 원문이 이력에 추가되지 않는 현재 경로에서 짧은 후속 답변의 맥락 보존.
- PC-E09: 검색 중심 변경 도구가 없는 상태에서 지명 요청을 어떻게 처리하는가.
- PC-E11/E16: 미상과 근거 없는 서술에 대한 과도한 확신.

이는 코드로 확인한 검사 범위와 그로부터 세운 실패 가설이다. 실제 모델의 실패 횟수는 실행 기록에서 판단한다.

## 반복 검증 운영

1. 입력 문장, 초기 필터, 후보, 순서, 시각/캐시 나이를 동결하고 케이스 ID를 선택한다.
2. 각 독립 케이스는 초기 상태를 새로 만든다. 케이스 내부의 여러 턴만 상태를 이어간다.
3. 모델이 관여하는 케이스는 우선 같은 입력으로 3회 실행한다. 같은 모델·프롬프트·fixture·코드 버전을 기록한다.
4. 원문 결과를 남긴 뒤 각 기준을 판정한다. 자동으로 확인하지 못한 답변의 의미는 review_required로 남긴다.
5. 수정 후 실패한 ID를 먼저 재실행하고, 영향을 받은 관련 케이스를 추가한다. 무관한 전체 스위트를 반복하지 않는다.
6. 이전 결과는 덮어쓰지 않는다. 수정 전후 비교는 동일한 케이스/fixture 버전에서 한다.

케이스 문구 변형은 `PC-E01/a` 같은 variant_id로 구분하고 실제 입력 전체를 기록한다.
초기 상태·판정 의미가 바뀌면 데이터 버전을 올린다. 모델에 맞추려고 기대 결과를 몰래 완화하지 않는다.
