# 협업 규칙

2026-08-22 협업 특강(이동규 멘토)에서 가져온 기준을 이 프로젝트에 맞게 옮긴 것입니다.
강의 내용 중 이 프로젝트에 해당하지 않는 것(AWS 서버리스 구성, Jenkins / ArgoCD 현황)은
빼고 원칙만 남겼습니다. 강의 노트 원문은 이 저장소에 없습니다.

PR 본문 양식은 [`.github/PULL_REQUEST_TEMPLATE.md`](../.github/PULL_REQUEST_TEMPLATE.md),
되돌리기 번거로운 결정은 [decisions.md](decisions.md) 에 있습니다.

## 1. 역할 — 사람은 앞단과 뒷단에만

사람은 in the loop 가 아니라 **on the loop** 에 있습니다. 앞단(무엇을 먼저 할지)과
뒷단(나온 결과가 유효한지)만 사람이 잡고, 그 사이는 AI 에게 맡깁니다.

| 사람이 정하는 것 | AI 에게 맡기는 것 |
| --- | --- |
| **우선순위** (P0 / P1) | 프로덕트 백로그 쌓기 |
| Iteration 기간 | 태스크 쪼개기, PR 작업 목록 작성 |
| **결과물이 유효한지 검증** | 구현 · 커밋 · PR 본문 작성 |
| **작업이 섞이지 않았는지 확인** | 커밋 메시지 · PR 메시지 |
| 서버 상태 파악 (PM2 목록, 러너, 볼륨, 서버에만 있는 `.env`) | 인프라 설정 파일 작성 |
| 인프라를 어디에 어떻게 둘지 (자체 서버 / 클라우드) | 그 제약 안에서 코드 생성 |
| **회고** | — |

**우선순위는 AI 에게 위임하지 않습니다.** AI 는 검증에 과몰입하고 가끔 산으로 갑니다.

## 2. 우선순위 (P0 ~ P3)

Project 의 `Priority` 필드에 씁니다. **보수적으로 잡을수록** 일정이 다가올 때 조급함이 줄어듭니다.

| 등급 | 기준 | 예시 |
| --- | --- | --- |
| **P0** | 없으면 프로젝트가 **아예 동작조차 못 함** | compose · DB 스키마 · 배포 파이프라인 |
| **P1** | **메인 피처** — 없으면 프로젝트가 의미 없음 | 이 서비스가 존재하는 이유인 기능 |
| P2 / P3 | 나머지 | 대시보드, 관리 화면, 정산 |

- CI/CD 는 P0 이 아닙니다. 없어도 동작합니다.

## 3. Iteration 과 작업량

Iteration 은 **3~4일**입니다 (PR 템플릿 기준). **카드 하나 = PR 하나 = Iteration 하나.**

기간 전부를 구현에 쓸 수는 없습니다. 강의 기준으로 구현에 쓸 수 있는 시간은
기간의 절반이 못 됩니다. 나머지는 테스트 · 배포 · 검증 · 리뷰에 들어갑니다.

| 기간 | 워킹데이 | 실제 구현 가능 |
| --- | --- | --- |
| 2주 | 10일 | 3~4일 (최대 5~6일) |
| 1주 | 5일 | 2일 |
| **3~4일 (이 프로젝트)** | 3~4일 | **1~2일** |

이 숫자를 그대로 AI 에게 줍니다.

```
Iteration 이 4일이고 구현에 쓸 수 있는 건 2일이야.
2일 안에 끝낼 수 있는 단위로 쪼개서 PR 작업 목록으로 올려줘.
```

Iteration 을 짧게 잡은 이유: 한 달 프로젝트에 2주 스프린트면 회고를 한 번밖에 못 합니다.

**폭포수 자가진단** — 계획이 한 줄로 쭉 내려와서 보기 편하면 폭포수입니다.
기획하면서 설계하고, 설계하면서 개발하는 **병행**이 있는지가 판별 기준입니다.

## 4. PR 기준으로 일하기

**이슈는 쓰지 않습니다.** 이슈는 사람이 관리하는 것이었고, AI 가 관리하려면 코드에
붙어 있어야 합니다. GitHub 에서는 PR 도 이슈와 같은 번호 체계(`#13`)를 쓰므로,
Project 3 (`orgs/SAJOYO/projects/3`) 은 `Open Pull Requests` 기준으로 관리합니다.
이슈 템플릿도 두지 않습니다. 누가 이슈를 열면 PR 이나 Project 의 draft 카드로 옮기고 닫습니다.

**핵심 전환: PR 을 작업 "후"가 아니라 "전"에 엽니다.**

| | 기존 | 이 프로젝트 |
| --- | --- | --- |
| 시점 | 개발이 끝난 다음 | **할 일을 정리해서 먼저** |
| 내용 | 완료된 결과물 | **앞으로 할 일의 명세** |

### 순서

1. `dev` 에서 브랜치를 만들고 **draft PR 을 먼저 엽니다.** 제목이 곧 카드 이름입니다
   (`타입: 무엇을`, 타입은 feat / fix / docs / refactor / build / chore).
   빈 브랜치로는 PR 이 안 열리니 빈 커밋 하나를 올립니다.

   ```powershell
   git switch -c feat/walk-api dev
   git commit --allow-empty -m "feat: 산책 기록 API"
   git push -u origin feat/walk-api
   gh pr create --draft --base dev      # 제목을 묻고, 본문은 템플릿을 고릅니다
   ```

   ⚠️ **미리 열어 둔 카드에 착수할 때는 브랜치를 새로 파지 마세요.** 그 카드에는 이미 브랜치가
   있습니다. `git switch -c` 로 새 이름을 만들면 커밋이 전부 거기 쌓이고, PR 은 **원래의 빈
   브랜치를 그대로 머지**합니다 — 에러가 하나도 안 나고 `dev` 에는 아무것도 안 들어갑니다.
   2026-08-30 에 `#68` 이 그렇게 빈 채로 머지됐고, 작업 8커밋이 다른 브랜치에 남았습니다.
   착수 전에 **PR 이 쓰는 브랜치 이름부터 확인**하세요:

   ```powershell
   gh pr view <번호> --json headRefName -q .headRefName
   git fetch origin; git switch <그 이름>; git merge origin/dev
   ```

   `RAG-` 결정 번호나 랩(`lapN`)을 쓸 카드면 **`docs/decisions-rag.md` 머리의 "예약 중" 표에
   한 줄 넣습니다.** 카드를 미리 열어 두는 경우엔 여는 시점이 아니라 **착수할 때** 넣으세요 —
   열어 둔 사이에 다른 카드가 그 번호를 가져갑니다. PR 본문에만 적으면 먼저 머지하는 쪽이 이기고
   나중이 renumber 합니다 (#53 이 번호와 랩을 두 번 옮겼습니다. RAG-042).

   **`dev` 의 표만 보면 부족합니다** — 남이 예약해 둔 줄이 아직 그 사람 브랜치에만 있을 수 있습니다
   (RAG-045 ⑦ 에서 실제로 부딪혔습니다). 예약 커밋은 **제목을 `chore: 착수 — RAG-0NN 예약 (#카드)`
   로 고정**하고, 잡기 전에 열린 브랜치까지 한 줄로 확인하세요:

   ```powershell
   git fetch origin; git log --all --oneline --grep="예약"
   ```

2. Project 3 에 카드를 넣고 필드(담당자 / Priority / Size / Iteration)를 채웁니다.
   본문에는 필드가 담을 수 없는 것만 적습니다 — 두 군데가 되면 반드시 어긋납니다.
3. 작업 중 본문을 갱신합니다. 특히 `## 컨텍스트 메모` 는 다음 세션의 Claude 가 읽는
   유일한 인수인계입니다.
4. 끝나면 draft 를 풀고 리뷰 → `dev` 머지. **머지가 곧 배포**입니다.
5. 안 하게 됐으면 닫지 말고 Status 를 **Hold** 로 옮기고, 이유를 `## 컨텍스트 메모` 에
   한 줄 남깁니다.

### Project 필드

| 필드 | 기준 |
| --- | --- |
| Assignee | **카드를 열 때 작업자를 넣습니다.** 비어 있으면 "아무도 안 잡은 것"과 "적기만 안 한 것"이 갈리지 않습니다 |
| Priority | P0 ~ P3. **사람이 정합니다.** 프로젝트 자체 필드입니다 — 조직 issue field 에서 파생된 Priority(Urgent ~ Low)는 이슈에만 값이 들어가서 PR · draft 카드에는 못 씁니다 |
| Size | 나를 위한 게 아니라 **남을 위한 것.** 구현이 그려지면 XS / S, 설계도 안 떠오르면 L / XL. **Claude 가 판단해 넣습니다** — Priority 와 달리 사람 승인을 기다리지 않습니다. 구현이 그려지는지는 코드를 본 쪽이 압니다 |
| Iteration | 3~4일. 카드 하나가 하나의 Iteration 안에 끝나야 합니다 |
| Status | 아래 흐름을 따릅니다 |

#### Status 흐름

```
Todo ──────→ In progress ──────→ Done
 카드를 열 때    착수할 때           머지되면 (Projects 가 옮깁니다)
                     │
                     └──→ Hold   필요 없어졌거나 정의가 안 된 것
```

- **`Hold` 를 둡니다.** 필요 없어진 것과 정의가 안 된 것을 구분해 두면 리뷰 때 백로그로
  되돌릴지 정할 수 있습니다. 닫지 말고 Hold 로 옮기고 이유를 `## 컨텍스트 메모` 에 한 줄 남깁니다.
- **`In progress` 가 제일 잘 빠집니다.** 규칙이 없어서가 아니라 **그 순간에 이 문서를 읽는
  사람이 없기 때문**입니다 — 문서는 카드를 *열 때* 읽고, Status 를 바꿔야 하는 것은 며칠 뒤
  *착수할 때*라 시점이 어긋납니다. 그래서 PR 템플릿의 `## 착수 절차` 첫 칸에 두어 눈앞에 오게
  했습니다. 실제로 그 블록이 있던 카드는 지켜졌고 없던 카드에서 사고가 났습니다.
- **`Done` 은 손으로 옮기지 않습니다.** PR 이 머지되면 Projects 가 옮깁니다.
  ⚠ 다만 **Done 이 "작업이 dev 에 들어갔다"를 뜻하지는 않습니다** — 2026-08-30 에 `#68` 이
  빈 브랜치로 머지되면서 아무것도 안 들어갔는데도 Done 이 됐습니다 (RAG-047 ⑧).

- 다 같이 설계할 것은 **draft 카드**로 올립니다. 프로젝트 참여자 전원이 볼 수 있습니다.
- 여기까지 하면 WBS 를 따로 그리지 않아도 Roadmap 뷰에서 보입니다.
- `gh` 로 Project 를 읽고 쓰려면 `gh auth refresh -s project` 를 한 번 해 두어야 합니다.
  PR 템플릿이 Claude 에게 시키는 `gh project item-list` 도 이 권한이 있어야 돕니다.

### 브랜치

- 작업 브랜치는 `dev` 에서 따고 PR 로 `dev` 에 머지합니다. 머지된 브랜치는 자동 삭제됩니다 (저장소 설정).
- `main` 은 릴리즈 스냅샷입니다. 완성 단위마다 `dev → main` PR 로 올립니다. `dev` 가 default 라
  이 머지로 `dev` 가 지워지지는 않습니다 — **default 를 `main` 으로 바꾸지 마세요.**

## 5. 데일리 스크럼

세 줄이면 됩니다. **15~30분, 짧게.** 뒤에 기다리는 사람이 있어야 끝납니다.

1. 어제 뭐 했는지
2. 오늘 뭐 할 건지
3. **이슈가 뭐가 있는지**

PR 기준으로 확인합니다: 어제 PR 에 커밋이 올라갔는지, **안 올라갔으면 왜** 안 올라갔는지.

AI 로 좋아진 건 **생산의 속도**지, 공유를 안 해도 된다는 게 아닙니다.

## 6. 회고 — 열기구

Iteration 이 끝날 때마다 합니다. 한 사람당 포스트잇 **2장**이면 됩니다.

| 영역 | 무엇을 적나 |
| --- | --- |
| 🎈 **Hot air** | 잘된 점 |
| 🏋️ **Sandbag** | 아쉬운 점, 부족했던 점 |
| ☀️ Sunny day | (미래형일 때) 기대되는 것 |
| ⛈️ Storm cloud | (미래형일 때) 우려되는 것 |

1. 각자 붙이기 — **최대한 구체적으로**
2. 돌아가면서 왜 적었는지 설명
3. 이모지 · 스티커로 공감 투표
4. 공감 많이 받은 것 뽑기
5. 다음 Iteration 에 어떻게 반영할지 → **액션 카드.** Project 에 draft 카드로 올립니다.
6. **다음 회고 때 액션 카드가 지켜졌는지 먼저 확인**

도구: [Miro](https://miro.com) (보드 3개까지 무료), [FunRetrospectives](https://funretrospectives.com)

회고는 프로덕트를 만드는 것과 유일하게 무관한 단계라 안 하게 됩니다. 그런데 Iteration
루프에는 쉬는 타이밍이 없어서, **회고가 유일한 쉼표**입니다.

## 7. 인프라 — AI 에게 맡길 때

이 프로젝트의 인프라는 자체 서버(Windows PC, PM2 + nginx + compose)입니다. 강의의
AWS 서버리스 조합은 해당 없지만, 원칙 두 가지는 그대로 적용합니다.

- **첫 프롬프트에 아키텍처 제약을 줍니다.** 그냥 만들라고 하면 AI 는 자기 기본값을
  고릅니다(강의에서는 100% EC2 + CodeBuild/CodeDeploy). 여기서는 "자체 서버, compose 뒤의
  nginx, 포트는 nginx 만 연다" 같은 제약을 먼저 줘야 나중에 요구사항이 충돌하지 않습니다.
  이미 정한 것은 [decisions.md](decisions.md) 와 [CLAUDE.md](../CLAUDE.md) 에 있습니다.
- **설정 파일은 AI 가 쓰되, 상태는 사람이 압니다.** Terraform 이면 state 가 그렇고, 여기서는
  서버 PC 의 PM2 목록 · 러너 · 볼륨 · 서버에만 있는 `.env` 가 그렇습니다. 문제가 났을 때
  대응하는 건 사람입니다. 절차는 루트 [README.md](../README.md).
