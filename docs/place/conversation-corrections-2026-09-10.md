## 질문과 사전 기준

필터를 정확히 편집하는 기능이 사용자의 정정과 불만을 받아 다시 탐색하는 데도 충분한지 조사한다.
사용자가 제공한 다섯 문장을 그대로 연속/단독으로 사용하고, 에이전트가 작성한 조건 교정·수동 조작과 비교한다.
사용자가 실제 앱을 누르는 사용성 관찰이 아니라 **사용자 작성 발화의 합성 상황 재생**이다.

입력·기대값의 원본은 [corrections.v1.jsonl](../../backend/evals/place_conversation/corrections.v1.jsonl).
14개 흐름, 27단계(채팅 25, 수동 2)를 각 3회 실행한다. 기대값과 의미 검토 기준은 실행 전에 커밋했다.
모델에는 production query/current_state/history/selected/visible_order만 전달하고 기대값은 전달하지 않았다.

- 근거 충실도: 없는 사실·폐업 여부·새 후보·사용자 장기 기억을 만들어 내지 않는가.
- 작업 완료: 적용 결과가 원래 요청을 만족하거나, 요청을 풀 수 있는 구체적인 다음 질문을 했는가.
- 재탐색 진전: 검색을 다시 호출했다는 사실과 새 장소를 보여준 결과를 구분한다.
- 정책 선택: PC-U01 첫 턴·PC-U02의 “재미”는 정답이 미확정이다. 이번 사전 기준은 취향이 모호하면
  기존 업종을 유지하고 구체적으로 되묻는 보수적 안이다. 이 기준의 실패를 보편적인 해석 오답으로 보지 않는다.

기본 후보는 불투명 ID의 카페/음식점 6개다. PC-U01/U06/U09는 같은 반경의 카페 26개 중 20개만
처음 보이고 26번째만 주차 가능한 변형을 사용한다. 재미 요청으로 다른 업종으로 바뀌면 그 변형에 후보가 없어
0건이 되는 것은 fixture의 한계이며 실제 서비스의 검색 결과 수를 뜻하지 않는다.
연속 원문 PC-U01은 앞선 출력의 영향을 그대로 이어받으므로 단독 PC-U02~06과 함께 해석한다.

| 요청 | 실제 경로 | 의미 |
| --- | --- | --- |

| 더 보기 실패 → 주차 되는 카페만 | 전체 후보 검색으로 cafe-26 반환 | 검색 풀은 살아 있다. 재탐색 동작의 부재와 SQL/캐시 고장을 혼동하면 안 됨 |

실제 UI에서 답답함을 느꼈다는 관찰은 아니며, 제공 문구와 후속 행동 유무를 검토한 판단이다.

## 원인 분해와 대조

**1. 수동 undo는 프롬프트만으로 복구할 수 없는 정보 손실이다.**
[반사실 대조](../../backend/evals/place_conversation/runs/20260910T075627Z-7996e8c-6de532d692/undo-information-probe.json)는
실제 manual prepare와 Gemini 입력 생성 코드를 사용하고, 전송만 MockTransport로 대체했다(추가 모델 호출 0).

| 이전 상태 | 동일한 수동 입력 | 올바른 한 번 취소 |
| --- | --- | --- |
| cafe | cafe + restaurant | cafe |
| restaurant | cafe + restaurant | restaurant |

두 경로가 모델에 보내는 query/current_state/history/pending_question/selected/visible_order는 **완전히 동일하다**.
서로 다른 정답이 동일 입력으로 합쳐진다. 원문 history를 더 잘 읽게 해도 수동 이벤트에는 읽을 기록이 없다.
근거는 [service.py](../../backend/src/daengs_place/place/conversation/service.py)의 chat 전용 history 추가와
[provider](../../backend/src/daengs_place/place/providers/conversation_gemini.py)의 입력 구성이다.

**2. 더 보기와 제외는 실행할 수 있는 동작이 부족하다.**
[Interpretation](../../backend/src/daengs_place/place/conversation/intent.py)에 refresh는 있지만
다음 페이지/현재 결과 제외/사용자가 이미 아는 장소 제외 의미가 없다. 재검색은 같은 필터와 상한 20으로 시작한다.
선택 장소는 ID만, 목록도 ID 순서만 모델에 전달되며 이름 대응표와 잘림 여부는 전달되지 않는다.
따라서 명시적 상호 제외를 해석하더라도 검증된 ID로 연결해 실행할 경로가 없다.

**3. 미지원 의미가 여러 단계에서 소실된다.**
존재 여부/정보 오류 제보는 Attribute에 없고, 일반 explain에서 asked_attributes가 비면 서버가 selection_reason으로 바꾼다.
reference_index=0은 1부터 시작하는 계약에 위반되어 저장/실행 전에 막혔다.
이는 외부 제공자 통신 실패가 아니라 원본 도구 출력의 계약 위반이다.
서버 문구가 사실을 꾸미지 않은 것과, 사용자 질문을 처리했다는 것은 별개다.

**4. “재미”에는 사전 정답이 없다.**
현재 대분류 카탈로그로 재미를 놀거리/문화로 해석하는 것은 가능한 안이다.
이번 보수적 기준 대신 “일단 여러 놀거리로 넓혀 제안” 정책을 택하면 이 부분의 평가는 달라진다.
이 선택을 나머지 명백한 동일 목록 반복·제외 누락·수동 이력 손실과 섞어서 모델 정확도라고 보고하지 않는다.

## 후속 구조 제안 — 아직 구현하지 않음

유지할 것은 해석 → 서버 정책 → 실행 결과 → 근거 문구의 분리다.
추가할 것은 현재 탐색을 이어 갈 작은 상태와 명시적인 동작이다.

| 필요한 동작 | 서버가 보관/검증할 최소 정보 | 응답 방향 |
| --- | --- | --- |
| 불만 뒤 방향 조정 | 불만 대상과 아직 정하지 않은 탐색 기준 | “활동하는 곳이 좋아, 구경하는 곳이 좋아?”처럼 답할 수 있는 질문 |
| 이 장소 제외 | 이번 검색에서 제외한 source+ref, 적용된 검색 범위 | 특정 장소가 명확하면 이번 탐색에서 제외. 애매하면 선택 장소/목록 전체 중 무엇인지 확인 |
| 다음 후보 | 검색 조건 fingerprint, 결과 세대, cursor/정렬 기준, 이미 표시한 ID | 조건을 유지한 다음 후보. 소진되면 소진 사실과 반경·조건 변경 선택지 |
| 정보 오류 제보 | 사용자가 지칭한 source+ref, 제보 내용과 확인 상태 | “현재 자료로 폐업 여부는 확인할 수 없어.” 확인되지 않은 제보를 원천 DB 사실로 승격하지 않음 |
| 마지막 변경 취소 | 마지막 확정 변경의 before/after, actor(manual/chat), revision | 모델이 역연산을 새로 만들지 않고 저장한 변경을 서버가 되돌림 |

LLM에는 이런 **요청 의미**를 추가하고, 실행 허용과 ID·revision·조건 보존 검증은 서버에 둔다.
좌표/반경을 몰래 넓히지 않는다. 후보 제외와 페이징은 현재 20개를 화면에서 숨기는 데 그치지 않고
전체 후보에서 적용한 뒤 다음 결과를 가져와야 한다. 한 세션의 새 후보와 실제로 처음 방문하는 장소도 구별한다.

범위는 현재 검색의 짧은 상태로 한정한다. 평생 방문 이력이나 성향을 저장하는 장기 메모리는 근거가 없다.
지도/조건이 바뀔 때 제외·이미 본 장소를 유지할지는 명시적인 세션 정책으로 정하고,
undo는 최신 revision에 결합해 후속 수동 변경을 덮어쓰지 않도록 한다.

대안은 세 가지다. 프롬프트만 보강하면 불만 분류는 개선할 수 있어도 누락된 이력·페이징은 복구할 수 없다.
모든 응답을 자유 생성으로 돌리면 표현은 늘지만 앞서 제거한 근거 없는 사실 채널도 다시 열린다.
따라서 **현재 실행 정책 위에 재탐색 동작과 최소 상태를 보충하는 안**을 다음 구현 후보로 제안한다.
효과는 아직 검증하지 않았으며, 구현 뒤 같은 실패 사례와 처음 보는 표현을 함께 비교해야 한다.
