# 시설 검색 전용 LLM Judge

시설 입력의 해석과 실행 결과를 검토하는 오프라인 평가기다. 코드는 [place_conversation](../../backend/src/daengs_evals/place_conversation/README.md)에 있으며 실행 명령과 파일 설명은 그 README가 기준이다. 데이터는 [judge 안내](../../backend/evals/place_conversation/judge/README.md)를 따른다.

개발 세트 전체 실행과 Judge 대조 결과는 [시설 개발 세트 예비 평가](conversation-baseline.md)에 있다. 사용자 확인에 따른 운영 모델은 Flash-Lite다. 같은 모델의 합성 환경 측정과 실제 배포 경로 전체의 검증을 구분한다.

## 평가할 것

| 축 | 목적 |
| --- | --- |
| `intent_alignment` | 요청 조건 누락·임의 추가·AND/OR 변경·맥락 오용 찾기 |
| `scope_fit` | 시설 요청 오거절과 범위 밖 자유답변을 모두 찾기 |
| `result_faithfulness` | 실제 실행·반환 사실과 사용자 문구가 일치하는지 확인 |

기준은 [시설 범위 정책](scope-guardrails.md)과 [응답 정책](response-policy.md)이다. 고정 강아지 문구의 귀여움은 문구를 바꿀 때 검토한다. 매 실행마다 장문·친절함을 보상하는 문체 점수를 만들지 않는다.

의도·범위 축에는 현재 입력·필요한 이전 대화·실행 전후 상태·실제 반환 문구를 제공하며, 의도 축만 모델 계획도 본다. 결과 설명 축은 실행 전후 상태·실행 기록·표시 문구만 본다. 사용자 요청·이전 대화·모델 계획과 요청 수행 정책을 제외해 수행 실패가 사실성 감점으로 전파되지 않도록 한다. 요청과의 일치는 다른 두 축이 담당하고, 남은 관측만으로 문구의 진위를 판단할 수 없다면 `uncertain`이다. 모든 축에서 다른 사례·반복·변형의 맥락, 정답 라벨, 코드 점수, 기존 사람/Codex 리뷰를 제외한다.

결과는 `pass / fail / uncertain / not_applicable`와 짧은 사유·실제 입력 필드의 JSON Pointer 근거다. 자료 누락·선행 턴 실패·입력 상한 초과는 모델을 호출하지 않고 `unmeasured`로 남긴다. 관측을 임의 요약하거나 잘라서 완전한 자료인 것처럼 보이지 않는다.

루브릭 v3는 세 축을 독립적으로 평가한다. 명확한 요청을 못 하고 정직하게 실패를 알리거나 중립적으로 되묻기만 했다면 의도·범위는 실패여도 결과 설명은 통과할 수 있다. 미실행을 완료로 주장하거나, 반대로 실제 완료를 미실행으로 말하거나, 질문 속에 거짓 완료 전제를 넣으면 결과 설명도 실패다. 이를 확인하는 기본 대조 세트는 기존 12개를 포함한 `anchors.v3.jsonl` 22개다. v2의 판정 기준만 바꾼 재평가에서는 중복 감점 2건이 남아 입력·정책도 분리했다.

## 판정 소유권

코드 검사·LLM Judge·기존 리뷰를 별도 열로 표시한다. 모델 의견이 코드 검사 실패를 지우지 않는다. 자동 판정만 존재하면 의미 평가는 `review_required`로 유지한다. 기존 `reviews.jsonl`을 모델 판정으로 채우거나 수정하지 않는다.

Judge는 검토 보조다. 앵커 검사만으로 사람과의 일치도를 확보한 것이 아니므로 종합 품질 점수나 출시 자동 승인으로 사용하지 않는다. 제공자 오류·관측 누락·보류도 통과로 세지 않는다.

## 실행과 재현

기존 시설 `runner.py`·`checks.py`·`report.py`를 확장했다. DEV 공통 오케스트레이션의 `semantic.py`·`resolver.py`와 시설 Judge가 `daengs_backend/core/gemini.py`의 클라이언트 생성 코드를 함께 사용한다. 구조화 출력 설정·검증은 기존 `answer_quality/gemini.py`를 재사용한다. 공유 설정은 `GEMINI_API_KEY`, `GEMINI_TIMEOUT_MS`이며, Judge 모델만 `FACILITY_JUDGE_MODEL`로 선택한다. 기본값은 `gemini-3.1-flash-lite`다. OpenAI 키는 필요하지 않다.

오프라인 Judge가 전체 앱의 DB·암호화 키 설정에 묶이지 않도록 Gemini 키·타임아웃만 읽는 설정을 공통 생성 코드에 둔다. 운영 라우터와 리졸버는 기존 검증된 앱 설정 값을 생성 함수에 전달하며, 라우팅 모델·프롬프트·재시도 정책은 그대로다. Judge 요청에만 SDK 재시도를 1회 시도로 제한해 기존 호출 장부가 모든 시도를 기록한다.

시설 생성과 Judge는 같은 계열이므로 계열 독립성을 주장하지 않는다. 해당 사실은 메타데이터에 남기며, 사람의 기준과 일치도를 확인하기 전까지 검토 보조로 사용한다.

각 판정 실행은 별도 폴더에 입력·호출·결과·설정·해시를 보존한다. 모델·프롬프트·관측·앵커·평가 코드가 달라지면 새 실행이 필요하다. 동일 설정에서는 완료된 축을 제외하고 재개할 수 있다. 호출 상한은 앵커·재시도까지 포함하고, 최초 오류와 사용량을 남긴다. API SDK의 숨은 재시도는 사용하지 않는다.

기존 실행기 기본 모델도 현행 시설 설정 `FACILITY_CONVERSATION_MODEL`을 따르도록 연결했다. APP과 운영 서비스 요청 경로·DB는 변경하지 않았다.

첫 버전은 합성 검색과 서버 prepare/answer까지 관측한다. 공통 라우터·APP 실제 선택·회원 찜 저장 완료·Redis CAS·PostGIS 정확도는 별도 검증 대상이다. 추후 해당 관측 형식을 연결할 때 경계와 데이터 버전을 명시한다.

## 2026-09-12 구현 검증

시설 대화 회귀 검사 223개가 통과했고 기존 opt-in live 검사 1개는 건너뛰었다. 최종 대조 사례·리포트 변경 뒤 Judge와 평가기 타겟 검사 40개도 통과했다. Ruff, `uv run check`, CLI 도움말·사례 로딩, 문서 링크를 확인했다.

[실제 연결 시도 기록](../../backend/evals/place_conversation/runs/20260912T130753Z-670a13a-28eb2ff4c2/smoke-summary.json)은 5개 사례·6턴이다. Gemini 시설 실행 3턴의 관측을 얻었고 제공자 오류 2턴·선행 오류로 미실행 1턴을 구분했다. OpenAI Judge는 제공된 키의 HTTP 401로 앵커 단계에서 막혀 **실제 의미 판정은 0건**이다. Judge 품질이 검증됐다는 결과로 읽지 않는다.

최초 구현은 같은 인증 오류를 16회 기록했다. 이를 계기로 재시도 불가 4xx가 나오면 같은 실행의 추가 호출을 중단하도록 보완했다. 회귀 검사는 세 축의 시도 횟수가 1/0/0이 되는지 확인한다. 오류 기록은 그대로 보존했고 같은 키로 재호출하지 않았다. 당시 앵커는 8개였으며 Gemini 연결 정정 때는 12개였다. 이후 사용자의 운영 방식 확인에 따라 별도 OpenAI 연결을 제거하고 기존 Gemini 키·공통 생성 코드로 정정했다. 위 인증 오류는 이 정정 전 기록이다.

## Gemini 연결 정정 검증

공통 클라이언트·시설 Judge·의미 라우터·턴 리졸버·기존 answer-quality 평가기의 관련 테스트 **134개가 통과**했다. Ruff와 `uv run check`도 통과했다. 별도 프로세스에서 DB·암호화 설정과 OpenAI 모듈을 불러오지 않고 기존 Gemini 키만으로 Judge 클라이언트를 생성하는 것도 확인했다.

[Gemini 실험 요약](../../backend/evals/place_conversation/runs/20260912T130753Z-670a13a-28eb2ff4c2/gemini-summary.json)과 [판정 보고서](../../backend/evals/place_conversation/runs/20260912T130753Z-670a13a-28eb2ff4c2/judges/gemini-router-v1/report.md)에 실제 결과를 보존했다. 공통 오케스트레이션이 쓰는 `gemini-3.1-flash-lite`를 `--judge-model`로 명시한 실행에서 대조 사례 **12/12**, 관측이 완료된 **3턴의 9개 평가 축 모두 pass**였다. 앵커와 본 판정의 총 21회 호출에 제공자 오류는 없었다. 나머지 3턴의 9개 축은 원본 관측 오류·미실행 때문에 `unmeasured`다. 별도 의미 리뷰는 없으므로 최종 상태는 여전히 `review_required`다.

당시 Judge 기본값으로 잘못 선택했던 `gemini-3-flash-preview`는 먼저 5개 앵커를 정상 판정했지만 이후 HTTP 429로 막혔다. 10초 간격 재실행도 실패했고, 별도 진단 호출에서 하루 무료 요청 한도(`GenerateRequestsPerDayPerProjectPerModel-FreeTier`, 당시 값 20)를 확인했다. 이 두 실행의 실패 기록도 보존했다. 2026-09-13 사용자 정정에 따라 시설·Judge 기본값을 Flash-Lite로 맞췄다. Flash 한도 기록을 운영 모델의 한도나 Flash 재측정 필요성으로 해석하지 않는다.

## 결과 설명 축 분리 검증

기존 개발 세트 8턴을 Lite로 재평가해 Codex 검토와의 판정 일치가 v1 21/24 → v2 22/24 → v3 24/24였다. v2·v3 각각 대조 사례 22/22, 본 판정 24개 축, 총 46회 호출·제공자 오류 0회를 기록했다. 실제 기능 실패 3턴은 계속 실패이며 사람 검토로 바꾸지 않았다. 같은 개발 사례를 보고 수정했고 v3는 결과 설명 입력도 바꿨으므로 독립 정확도나 입력 고정 실험이 아니다. 사유 일부가 기존 목록과 이번 턴 실행을 모호하게 표현한 한계와 원본 재생·회귀 검증은 [기준선의 후속 검증](conversation-baseline.md#안내-문구judge-분리-후속-검증)에 있다.
