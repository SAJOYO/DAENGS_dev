## 2. 오케스트레이션 안에서 이 파트의 자리

계약·상태·라우팅은 `docs/orchestration/contracts.md` · `docs/orchestration/routing.md`(#80) 가 원본이다. 여기서는 **이 파트가 그 틀에
꽂히려면 무엇을 내야 하는가**만 적는다.

```
/assistant/query → LangGraph
   라우터(분류기) → RoutePlan{requests[], handoffs[], clarify}
   → LifeCapabilityAdapter.run(LifePayload)  ─in-process→ daengs_life.app.services.ask.ask()
     WalkCapabilityAdapter.run(WalkPayload)  ─in-process→ daengs_life.app.services.walk.walk()
   → CapabilityResult{OK | ABSTAINED | REFUSED | PENDING | ERROR | TIMEOUT}
   → 결정적 집계 → AssistantResponse
```

**용어 — Walk 가 둘이다.** 위 `WalkCapabilityAdapter` 와 능력 이름 `walk` 는 Life 의 **산책 적합도**(`daengs_life.realtime`, RT-)다.
`backend/src/daengs_walk/`(D-045 · D-046 · D-047)는 GPS 산책 **기록**·Cellophane·Capsule 이고 `/app/walks` 로 나가며, 오케스트레이션의
실행 대상이 아니다. 이 문서에서 "Walk" 는 전자다. HTTP 경로는 A4(#176)로 `/life/walk-conditions` 가 됐지만 **능력 이름 `walk` 는 09-21 전에
바꾸지 않는다** — 벤치마크 골드 80문항 · 앱이 읽는 `results[].capability` 가 그 값에 묶여 있다 (§5).

### 경계 — 주제가 아니라 **근거의 종류**로 긋는다

"생활"은 주제로는 끝이 없다. 이 파트의 실제 경계는 처음부터 하나였다: **출처를 인용할 수 있는 답만 한다** (KPI · `/life/ask` 의 404 ·
RAG-008 ③ 이 `care`·`emergency` 를 뺀 이유).

| Life 가 답한다 | 근거의 종류 |
| --- | --- |
| 규정 · 제도 · 절차 · 조건 · 요금 · 기한 | 법령 · 조례 · 고시 · 약관 · 기관 공식 안내 (`trust_level`: `law` > `official` > `guideline` — **`guideline` 은 아직 0건이다**, RAG-060 ⑥) |
| 지금/오늘의 조건 판정 | 공공 API 직조회 — `/life/walk-conditions`, (앞으로) 분실 조회 |

| Life 가 답하지 않는다 | 이유 | 어떻게 거절·넘기나 (2026-09-03 계약 실물에 맞춤) |
| --- | --- | --- |
| **이 개의 몸**에 대한 판단 — 증상 · 진단 · 용량 · 응급 | 문서가 아니라 판단 (RAG-008 ③) | **Life 가 REFUSED** — `refusal.code` = `medical_boundary` / `emergency_boundary` (A3a). 능력은 handoff 를 낼 수 없다 — `CapabilityResult` 에 그 필드가 없다 (contracts §4) |
| **이 개의 행동**을 바꾸는 계획 — 짖음 · 배변 · 입질 교정 | 〃 | 라우터가 `training` 을 EXECUTE 로 같이 고른다(다중 선택). Life 는 근거 없으면 `no_evidence` 기권 — **별도 핸드오프 불필요** |
| **어디** — 병원 · 카페 · 숙소 위치 | 장소 데이터는 place 소유 (D-026) | **라우터가 `place` 를 EXECUTE 로 고른다** (A3b). #196 이 능력·어댑터·planner 를 넣었지만 `ExecuteName` 은 아직 `training`·`life`·`walk` 라, 자연어 place 질문은 여전히 빈 선택 → 최상위 FAILED 다 |
| 근거 문서가 코퍼스에 없는 것 | — | 기권 `no_evidence` (넘길 곳 없음) |

이렇게 잡으면 ① 경계가 코드로 강제되고(코퍼스에 있는 것 = 경계) ② 골든셋 `expect: abstain` · `expect: refuse` 로 **테스트가 되며**
③ Life 를 라우터의 **기본 능력**으로 둘 수 있다 — 실패 방식이 정직(근거 없으면 기권)해서다. 핸드오프 식별자는 라우터 소유라
`place` 추가는 라우터 카드(A3b)다 — 이 파트는 필요를 적고 조율한다.

「이 파트가 내야 할 신호 — 현재 / 목표」 표는 전부 ✅ 라 보관 파일 §2 에 있다.

### 재적재와 GCP 동기화 — 위 표의 ✔ 에 붙는 값

재적재는 **집 서버 DB 만** 바꾼다. GCP 는 그 순간 안 바뀐다 — 적재도 성공하고 스모크도 통과하는데
앱에만 새 문서가 안 보이는 모양으로 만난다 (`docs/deploy/roadmap.md` §2-5).
반영하려면 **`documents` 테이블만** 갈아 끼운다 — 절차는 `runbook.md` §6 의 "Life 코퍼스만 동기화 (GCP)"
이고 `#290` 이 적었다. 🔴 **통째 덤프·복원으로 하지 말 것** — `vectordb` 한 DB 에 운영 테이블이 같이 있어
사용자 데이터를 덮어쓴다.

- **✔ 카드를 연달아 열면 GCP 동기화는 묶어서 한 번 낸다.** 카드마다 내면 손작업이 그 수만큼 늘어난다.
- `db/migrations/` 도 **두 DB 에 각각 손으로** 적용한다. 버전 테이블이 없어 어디까지 적용했는지는 사람이 안다.
- **구조적 해소가 §4 의 0번이다** (`docs/deploy/roadmap.md` §7-1 — 크롤러·코퍼스·적재 이전).
  2026-09-07 에 사람이 그 문서의 *"9/21 이후"* 칸에서 끌어올렸다. **위 손작업 전부가 그 카드까지의
  임시**이고, 그것이 이 표의 `✔` 표시가 실제로 뜻하는 값이다.
