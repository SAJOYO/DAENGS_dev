# Life 검색 — 무엇을 시도했고, 무엇을 버렸고, 왜 그랬나

`decisions-rag.md` 는 결정을 **시간 순**으로 쌓는다. 그래서 *"리랭커는 왜 안 썼어요?"* 같은
질문에 답하려면 9,990줄에서 `RAG-076` 을 찾아야 하고, 그 답이 `RAG-072` 의 산수와
`RAG-057` 의 스윕에 기대고 있다는 것은 세 곳을 다 읽어야 보인다.

이 문서는 그것을 **주제 순**으로 다시 세운 것이다. 규칙 둘:

- **기각한 것을 채택한 것과 같은 무게로 적는다.** 안 쓴 것들도 전부 수치를 갖고 안 썼다.
  그 수치가 이 프로젝트가 실제로 한 일이다.
- **수치에는 잰 환경을 붙인다.** 같은 것을 다른 환경에서 재면 결론이 뒤집힌다는 것을
  2026-09-10 에 실제로 겪었다 (§5.2).

정본은 여전히 `decisions-rag.md` 다. 각 절은 그쪽 번호를 단다.

## 1. `daengs_life` 가 무엇인가

### 1.1 두 개의 공개 경로

| 경로 | 하는 일 |
| --- | --- |
| `POST /life/ask` | 반려견 생활 법령·제도 질문에 **출처와 조항 번호를 달아** 답한다 |
| `GET /life/walk-conditions` | 기상청 실황·예보를 읽어 산책 적합도를 낸다 (이 문서 범위 밖) |

`/life/ask` 가 이 문서의 대상이다. KPI 는 처음부터 하나였다 —
**"답변에 출처 링크 + 조항 번호 인용"**. 잘 맞혔는지가 아니라 **인용할 수 있게 답했는지**로 잰다.
그 선택이 아래 모든 결정을 끌고 간다: 청킹 경계도, 지표도, 기각 사유도 전부 여기서 나온다.

### 1.2 오케스트레이션 안에서의 자리

앱이 실제로 부르는 것은 `/life/ask` 가 아니라 `POST /assistant/query` 다. 그 안에서:

```
POST /assistant/query
  └─ Orchestrator (orchestration/runtime.py)
       ├─ semantic.py    LLM 이 정하는 것은 단 하나 — 어느 능력을 실행할 것인가
       │                 (training · life · walk · place)
       ├─ planner.py     결정론적 RoutePlan 조립
       └─ graph.py       CapabilityName.LIFE → LifeCapabilityAdapter
                              └─ daengs_life  ← 이 문서
```

즉 `daengs_life` 는 **오케스트레이터가 부르는 하위 능력 하나**다. 이 경계가
검색 설계에 실제로 남긴 제약이 둘 있다:

- **`daengs_backend` 가 `daengs_life` 를 부르는 접점은 `main.py` 의 세 줄뿐이다** (D-021).
  등록 둘과 예열 하나. 검색·생성 정책은 어댑터가 **복사하지 않는다** —
  `adapters/life.py` 의 첫 줄이 *"without copying retrieval or generation policy"* 인 이유다.
- **검색 방식은 호출부가 모른다.** `search()` 의 시그니처는
  `(query, k, include_supplementary, category, conn)` 으로 고정돼 있고,
  교통 배제·지역 필터·인용 확장은 **전부 인자가 아니라 `query.text` 에서 읽는다**.
  인자로 빼면 CLI·평가·서빙이 각자 켜고 끄게 되고, 그 순간 **검문소에서 본 것과
  서빙이 하는 것이 갈린다.** 이 판단은 `RAG-040`·`RAG-052`·`RAG-063` 에서 **세 번** 반복됐다.

### 1.3 파이프라인 여덟 단계

```
크롤 ─→ 파싱 ─→ 청킹 ─→ 임베딩 ─→ 적재 ─→ 검색 ─→ 생성 ─→ 채점
 1       2       3        4        5       6       7       8
 └──── 서버가 매일 04:00 KST ────┘        └─ 서빙 ─┘   └ 골든셋·랩·judge
```

크롤부터 적재까지는 자동화돼 있다(GCP 쪽은 Cloud Run Job 하나가 전 구간을 돈다 — D-062).
**이 문서는 6번, 검색 이야기다.** 다만 검색 품질의 절반은 3·4번(청킹·임베딩)이
정하므로 그쪽부터 시작한다.

### 2.2 한 번의 질의가 하는 일

```sql
WITH dense AS (           -- ① 벡터 축
    SELECT id, row_number() OVER (ORDER BY embedding <=> :q) AS rn
    FROM documents WHERE embedding IS NOT NULL {필터}
    ORDER BY embedding <=> :q LIMIT 100
), lex AS (               -- ② 형태소 FTS 축
    SELECT d.id, row_number() OVER (ORDER BY ts_rank(d.content_tsv, q.q) DESC, d.id) AS rn
    FROM documents d, to_tsquery('simple', :tsq) AS q(q)
    WHERE d.content_tsv @@ q.q {필터}
    ORDER BY ts_rank(...) DESC, d.id LIMIT 100
), fused AS (             -- ③ 가중 RRF
    SELECT COALESCE(dn.id, lx.id) AS id,
           COALESCE(1.0/(60 + dn.rn), 0) + COALESCE(0.3/(60 + lx.rn), 0) AS rrf
    FROM dense dn FULL OUTER JOIN lex lx ON dn.id = lx.id
)
SELECT … FROM fused f JOIN documents doc ON doc.id = f.id
ORDER BY f.rrf DESC, doc.embedding <=> :q LIMIT :k
```

앞뒤로 붙는 것들:

```
질의 텍스트
  ├─ vocabulary.aliases()   사람 말 → 조문 말 확장 후 재인코딩   (§4.7)
  ├─ tokenize.tsquery()     Kiwi 형태소 → tsquery               (§4.2)
  ├─ transport.exclusions() 교통수단 배제 필터                   (§4.6)
  └─ region.orgs()          지역 org 필터                        (§4.6)
                              ↓
                         위 하이브리드 SQL
                              ↓
                    expand_citations()  인용 확장
```

`{필터}` 는 **dense·렉시컬 양쪽 CTE 에 똑같이** 붙는다. 한 축에만 걸면
RRF 가 다른 축에서 그 문서를 도로 끌어온다.

## 3. 코퍼스를 만드는 쪽

### 3.1 청킹 전략 — 네 가지를 비교하고 구조 기반을 골랐다 (`RAG-004`)

| 전략 | 판정 | 사유 |
| --- | --- | --- |
| Fixed-size | ✗ | N자 절단이 별표 논리 행 한가운데(`20 │ 40`)와 항 두문/호 사이를 끊는다 |
| Recursive (구분자 계층) | ✗ | 줄바꿈으로 구조를 *근사*한다. 태그로 **이미 가진** 정보를 버리는 것이고, `제101조제3항제4호` 인용 문자열을 텍스트 위치에서 복원할 수 없다 |
| Semantic (유사도 골짜기) | ✗ | 경계가 비결정적이라 조항 번호와 어긋난다. KPI 가 "조항 번호 인용"이라 치명적 |
| **구조 기반** | **✅** | 경계 = 인용 단위(조/항/호, 별표 행, Q/A). **청크 ID 가 곧 인용 문자열이 된다** |
| Docling | ⏸ | 원 소스가 이미 구조화된 XML/HTML 이라 쓸 자리가 없었다 |

**기준을 잡은 방법이 이 절의 값이다.** `300~800토큰` 같은 숫자에서 시작하면 참·거짓을
가릴 수 없어서 순서를 뒤집었다 — ① 사용자가 실제로 할 질문 7개를 적고 ② 그 답이 원문
**어디**에 있는지 손으로 찾고 ③ **찾은 조각의 자연 경계**를 청크 경계로 삼았다.

수집 28건 실측(2026-08-20):

| 단위 | 개수 | 중앙 | p95 | 최대 | 총량 |
| --- | --- | --- | --- | --- | --- |
| 조문 | 665 | 349자 | 1,336자 | 3,366자 | ~31만자 |
| 별표 | 69 | — | — | **52,862자** | 52만자 |
| 서식 | 126 | — | — | — | 69만자 |
| 부칙 | 224 | 232자 | 1,122자 | 6,014자 | ~9만자 |

이 표가 판정을 셋으로 갈랐다:

- 조문 2,000자 이상 = **665개 중 13개(2.0%)** → 긴 조 분할은 일반 규칙이 아니라 **예외 처리**
- 별표 8,000자 초과 = **69건 중 16건** → 별표 행 분할은 선택이 아니라 **필수**
- 별표+서식 121만자 vs 조문 31만자 → **별표가 조문보다 4배 크다**

확정 판정표:

| 단위 | 판정 |
| --- | --- |
| 조문 < 2,000자 | 1조 = 1청크 |
| 조문 ≥ 2,000자 (13건) | 항 두문 + 그 항의 모든 호 = 1청크. **호 단위 분할 금지** |
| 별표 69건 | 논리 행 단위 + 표제목·단위 표기·컬럼헤더 **3종 복제** |
| 서식 126건 | **인덱싱 제외** — 빈 양식 필드라 검색 노이즈 |
| easylaw 본문 | 소제목 단위(~700자/1주제). 대단위는 ~2,000자에 주제 4개라 기각 |

**호 단위로 쪼개면 안 되는 이유** — 금액이 항 두문에만 있다:

```
③ 다음 각 호의 … 100만원 이하의 과태료를 부과한다.        ← 금액
   4. 제15조제1항을 위반하여 … 등록하지 아니한 소유자      ← 금액 없음
```

**별표 헤더를 3종 복제해야 하는 이유** — `(단위: 만원)` 이 999줄짜리 표에 **단 한 번**
나온다. 빠뜨리면 `20` 이 20원인지 20만원인지 알 수 없다.

현재 청커 상수(`chunk.py`): `MAX_CHARS = 7,500`(넘으면 조용히 자르지 않고 **실패시킨다**) ·
`SOFT_CHARS = 2,000`(경고만) · `TABLE_WHOLE = 1,000` · `VERSION = 2`.

### 3.2 임베딩 모델 — 3파전을 사전 등록 규칙으로 판정했다 (`RAG-002` · `RAG-024`)

**후보 3종**은 한 축을 세 번 재지 않도록 골랐다:

| 모델 | 차원 | 컨텍스트 | 역할 |
| --- | --- | --- | --- |
| `BAAI/bge-m3` | 1024 | 8,192 | 기준선 |
| `nlpai-lab/KURE-v1` | 1024 | 8,192 | **통제 비교** — bge-m3 를 한국어 200만 쌍으로 파인튜닝한 모델 |
| `Qwen/Qwen3-Embedding-0.6B` | 1024 | 32,768 | 계열 다름 + 영어 |

**탈락시킨 후보와 그 이유:**

| 후보 | 기각 사유 |
| --- | --- |
| `multilingual-e5-large` | 1024차원이지만 **512 토큰 한계**. 조문 p95 가 1,336자(≈900~1,300토큰)라 **상위 10%가 조용히 잘린다.** 잘리는 게 보통 단서·예외 조항이라 법령 QA 에 치명적 |
| `gemini-embedding-001` | API 의존 + 3,072차원이라 pgvector HNSW 2,000차원 상한에 걸려 `halfvec` 우회 필요 |
| `jina-embeddings-v3` | **CC BY-NC** (비상업) |

**판정 규칙을 결과 보기 전에 못 박았다** — 이것이 이 절의 값이다:

```
1. 탈락선을 결과 보기 전에 고정한다
2. 탈락 후 남은 것들의 점수차는 읽지 않는다 — 15문항에서 그건 노이즈다
3. 남은 것이 둘 이상이면 bge-m3 (기준선 우선)
```

**지표는 Recall 이 아니라 `Hit@5`(문항 균등)** 를 탈락선으로 썼다. 이유 둘이 이 세트의
생김새에서 나온다 — ⓐ `Recall 0.62 vs 0.68` 은 15문항에서 노이즈지만
**`Hit@5 = 0` 은 노이즈가 아니다**("이 질문에 아예 답할 수 없다"). ⓑ Hit 은 문항 단위
이진값이라 **macro/micro 문제가 통째로 소멸한다** — 라벨 수가 층마다 달라(hand 7문항 12쌍
: easylaw 8문항 31쌍) micro 로 세면 세트가 사실상 "easylaw 벤치마크"가 된다.

**결과 (골든셋 15문항 · 청크 1,407 · 2026-08-24):**

| 모델 | Hit@1 | Hit@3 | **Hit@5** | Hit@10 | Recall@5 | MRR |
| --- | --- | --- | --- | --- | --- | --- |
| bge-m3 | 0.067 | 0.133 | 0.200 (3/15) | 0.467 | 0.150 | 0.177 |
| kure-v1 | 0.067 | 0.200 | 0.267 (4/15) | 0.467 | 0.183 | 0.179 |
| **qwen3-embedding-0.6b** | **0.133** | **0.267** | **0.400 (6/15)** | **0.600** | **0.211** | **0.257** |

`Hit@5` 가 6 : 4 : 3 이고 나머지 둘이 탈락선(2문항) 이상 낮아 **둘 다 탈락**,
승자는 `qwen3-embedding-0.6b`.

⚠ **사전 등록이 실제로 일을 했다.** 논의에서 추천하고 사람이 고른 것은 기준선(`bge-m3`)이었고,
`Qwen3` 은 *"운영 복잡도가 는다"*(질의에만 지시문을 붙이는 **비대칭 모델**)는 이유로
**기각했던 3순위**였다. 결과를 보고 규칙을 만들었다면 이 답이 안 나왔을 가능성이 크다.

**절대값이 낮다는 것도 그대로 기록됐다** — 승자조차 15문항 중 6이다. 덤프를 열어 본 원인 둘:

1. **easylaw Q/A 청크가 모든 질문의 top 을 점령한다.** 자연어 질문과 표면이 겹쳐서다
2. **`must` 는 법령 조문이라 질문과 표면이 안 겹친다.** Q2("언제까지 신고")의 정답
   `제15조` 는 **9위**였고 1위는 무관한 QA 청크였다

**하이브리드가 필요하다는 근거가 여기 있다.** dense 단독으로 조문에 닿지 못하는 것이
이 실측의 내용이다.

### 3.3 재인코딩과 재적재를 증분으로 (`RAG-064` · `RAG-084`)

품질이 아니라 **반복 비용**의 이야기지만, 반복 비용이 곧 실험 횟수라 품질에 직결된다.

**증분 임베딩** (`RAG-064`) — 청크가 한 줄만 바뀌어도 9,451건 전량을 다시 인코딩했고
`qwen3-embedding-0.6b` 로 **55분**이었다. 행별 `content_sha256` 을 실어 바뀐 것만 만든다.

착수 전에 *"배치 구성이 벡터를 바꾸나"* 부터 쟀다(청크 256건):

| | 비트 단위 동일 | 최대 절대차 |
| --- | --- | --- |
| A. 같은 입력 두 번 | **256/256** | **0** |
| B. 전량 256 vs 그중 16만 따로 | 9/16 | 5.0e-07 |
| C. 한 건씩 따로 (가장 극단) | 0/16 | **7.0e-07** |

**모델은 완전히 결정적이고(A), 배치 구성이 벡터를 바꾸긴 하는데 float32 잡음 수준이다.**
검색 점수의 순위 간격이 보통 `1e-3`~`1e-2` 이라 3~4자릿수 아래다.

> ⚠ **코사인으로 판정하면 안 된다.** A(비트 단위 동일)에서도 최소 코사인이 `0.99999988` 로
> 나온다 — float32 내적의 반올림 바닥이 `1.2e-7` 이라 그 아래를 구별할 수 없다.

**증분 적재** (`RAG-084`, 2026-09-09) — `UPSERT` 가 `ON CONFLICT DO UPDATE` 라 값이 하나도
안 달라져도 전 행에 새 튜플이 생겼다. `WHERE … IS DISTINCT FROM …` 세 줄을 달았다:

| | 시간 | 새 튜플 |
| --- | --- | --- |
| 변경 없음 (= 매일) | 9.22s → **1.62s** | 9,844 → **0** |
| 1행 변경 | 1.27s | `updated=1 · unchanged=9,843` |

증분화 전 코드로 '매일 적재'를 다섯 번 흉내 내니 dead tuple 이 **49,220**(살아 있는 행의 5배)
까지 쌓였다.

## 4. 찾는 쪽

### 4.1 하이브리드 검색 — dense + 형태소 FTS · 가중 RRF (`RAG-035`)

**착수 근거가 구체적이다.** 조례 208건 + 보조금24 37건이 들어오면서 같은 취지의 문서가
135개 지자체에 **거의 같은 문장으로** 쌓였다. 코사인으로는 서로 구별이 안 된다 —
`부산 동래구는 내장형 동물등록 비용을 지원해 주나요?`(S3)의 정답이 top-8 에도 없었다.

**결과 (골든셋 hand 12문항, top-5 안의 필수 라벨 수):**

| | dense 단독 | 하이브리드 |
| --- | --- | --- |
| S3 (판정 문항) | 0/1 | **1/1** |
| Q4 | 0/2 | **1/2** |
| 나머지 6문항 | 유지 | 유지 |
| **합계** | **6** | **8** |

**지표가 못 본 개선이 있었다** — 헤드라인(인용 8/12 · 컨텍스트 밖 조항 0)은 그대로인데
답이 달라졌다: S3 이 `제6조`(대전 서구 조례)에서 `제8조`(동래구 조례)로 바뀌었다.
전에는 **엉뚱한 지자체 조례로 답하면서도** "조항을 인용했다"에 잡히고 있었다.

#### 두 축을 어떻게 합치나 — RRF 와 `RRF_K`

**RRF = Reciprocal Rank Fusion.** 두 개의 검색 결과 목록을 하나로 합치는 방법이다.

**점수를 직접 섞을 수 없어서 생긴 방법이다.** 두 축이 내는 수는 **단위가 다르다**:

```
dense    코사인 유사도    0.82  0.79  0.77 …     ← 0~1 사이, 간격이 촘촘하다
렉시컬   ts_rank         0.0607  0.0304  … …    ← 상한이 없고 문서 길이에 딸린다
```

**`0.82` 와 `0.0607` 중 어느 쪽이 더 좋은 신호인지 말할 수 없다.** 정규화해서 섞는 길도
있지만, 그러면 *"각 축의 점수 분포가 어떻게 생겼나"* 라는 두 번째 가정이 생기고 코퍼스가
바뀔 때마다 그 가정이 흔들린다. **RRF 는 점수를 통째로 버리고 순위만 쓴다** — 순위는 두
축에서 뜻이 같다("이 축에서 몇 번째냐").

**공식은 한 줄이다.** 각 문서에 대해:

```
점수 = 1.0 / (RRF_K + dense순위)  +  LEXICAL_WEIGHT / (RRF_K + 렉시컬순위)
     = 1.0 / (60 + dense순위)     +  0.3 / (60 + 렉시컬순위)
```

한 축에만 나온 문서는 없는 쪽 항이 0 이다(SQL 의 `FULL OUTER JOIN` + `COALESCE(…, 0)` 이
그 일을 한다). 이 점수로 다시 정렬한 것이 최종 결과다.

**`RRF_K` 는 순위에 더하는 완충 상수다.** 이것이 없으면(`K = 0`) 어떻게 되는지가 이
상수의 존재 이유다:

| 순위 | `1 / rank` (K=0) | `1 / (60 + rank)` (K=60) |
| --- | --- | --- |
| 1위 | **1.000** | 0.01639 |
| 2위 | 0.500 | 0.01613 |
| 10위 | 0.100 | 0.01429 |
| 100위 | 0.010 | 0.00625 |

**`K = 0` 이면 1위와 2위의 차이가 절반이다.** 한 축에서 1등을 한 문서가 다른 모든 신호를
압도해 버린다. `K = 60` 이면 1위와 2위가 **1.6% 차이**라, *"한 축에서 아주 잘함"* 보다
*"두 축 모두에 나옴"* 이 이긴다. **그것이 RRF 의 핵심 아이디어다 — 두 축이 동의하는
문서를 위로 올린다.**

- `K` 를 **키우면** → 순위 차이가 평평해져 "양쪽에 다 나옴"이 더 중요해진다
- `K` 를 **줄이면** → 각 축의 1등이 세진다

`60` 은 RRF 원논문(Cormack et al. 2009)의 값이고, `RAG-003` 이 제안한 그대로 **한 번도
안 바뀌었다.** 근거 없이 안 바꾼 것은 아니다 — `RAG-057` 이 가중치 × `RRF_K` 를
**2차원 전수**(w 0~1.5 × K 10~200)로 훑었고 **최대가 19 로 지금과 같았다.**

⚠ **이 상수는 구조를 하나 만든다.** `LEXICAL_WEIGHT` 가 1.0 이 아니라 0.3 이라,
렉시컬 1위의 기여(`0.3/61 = 0.004918`)가 **dense 100위의 기여(`1/160 = 0.006250`)보다
작다.** 그래서 렉시컬 축은 dense 후보의 순서를 바꿀 뿐 **새 후보를 데려오지 못한다** —
§4.8 이 그 이야기다.

**곁가지 — 화면에 찍히는 `score` 는 여전히 코사인이다** (`RAG-035` ④). 순서는 RRF 가
정하는데 점수 칸은 코사인이라 **둘이 단조롭지 않을 수 있다.** 바꾸지 않은 이유 둘 —
점수의 뜻을 바꾸면 옛 랩과 비교가 안 되고, `0.02` 같은 RRF 값은 사람이 읽어도 정보가
없다. 그리고 **그 불일치 자체가 "렉시컬이 끌어올렸다"는 신호**로 읽힌다.

#### 🚫 기각 — BM25 확장 (ParadeDB · VectorChord)

착수 전 오프라인 프로토타입으로 **진짜 BM25(IDF 사용)** 와 **`ts_rank` 근사(IDF 없음)** 를
12문항에 같이 돌렸다:

| | 필수 재현율 |
| --- | --- |
| `ts_rank` (PG 내장) | **7/18** |
| BM25 | 6/18 |

**`ts_rank` 쪽이 오히려 나았다.** BM25 는 S4 를 1/1 → 0/1 로 깨뜨렸고 `ts_rank` 는 안 깨뜨렸다.
그래서 **컨테이너 이미지를 갈아탈 이유가 없다** — `pgvector/pgvector` 를 그대로 쓴다.

### 4.2 형태소 토크나이저 — 과분할이 질의를 통째로 지웠다 (`RAG-035` ③ⓐ)

PostgreSQL 기본 FTS 는 한국어에 약해서 Kiwi(kiwipiepy)로 형태소 토큰화해
`tsvector('simple')` + GIN 을 쓴다. 그런데:

```
맹견 → 맹 + 견        ← 둘 다 한 글자라 한 글자 필터에 걸려 질의에서 통째로 사라진다
```

"맹견 사육 허가 필요한가요?"(Q5)의 렉시컬 축이 `사육 | 허가 | 필요` 라는 **일반어만** 보게
되고, 정답 조문을 **오히려 밀어냈다**(1/1 → 0/1). 붙어 있던 체언 조각을 복합어로 되붙이되
**조각과 복합어를 둘 다** 낸다 — 원문 띄어쓰기가 제각각이라("동물등록" vs "동물 등록")
한쪽만 내면 띄어쓰기 하나에 매칭이 어긋난다.

**같은 필터가 부정 표현도 지운다** (`RAG-072` ①):

```
보험금을 지급하지 않는 사유  →  보험금 지급 사유          ← `않`(VX)이 한 글자 필터에 걸린다
보험금의 지급사유           →  보험금 지급 사유 지급사유
```

**DB 실측 — `content_tokens` 에 `않` 이 든 청크가 9,838개 중 0개다.** 문서 쪽에서도 전부
지워졌으므로 렉시컬 축은 **부정을 볼 수단이 애초에 없다.** 한 글자 필터의 근거는
*"'수' '것' '때' 같은 의존명사가 대부분이라 노이즈"* 였는데 그 논거는 **체언에 대한 것이지
부정 보조용언에 대한 것이 아니다.**

⏸ **그런데 고쳐도 목표 문항이 안 열려서** 토크나이저를 안 고쳤다:

| | 지금 | `않` 을 살린 뒤 |
| --- | --- | --- |
| 목표 청크 A | 최종 94위 | 최종 63위 |
| 목표 청크 B | 최종 110위 (렉시컬 14위) | 최종 108위 (렉시컬 11위) |
| top-5 안의 면책 조 | 없음 | **여전히 없음** |

### 4.3 렉시컬 가중치 — 두 번 스윕했고 두 번 다 안 옮겼다

**1차 (`RAG-035` ③ⓑ, 12문항 · 필수 재현율, dense 단독 = 6):**

```
w_lex   0.05  0.10 │ 0.15  0.20  0.30  0.35  0.45 │ 0.50  0.75  1.00
합계       7     7 │    8     8     8     8     8 │    7     7     7
```

`0.15~0.45` 가 평평하고 그 구간에서 회귀가 없다. **가운데인 0.3** 을 잡았다.

**균등 가중(1.0)이 왜 나쁜가** — Q5 의 정답은 dense 2위인데 렉시컬 49위였고,
**dense 15위·렉시컬 1위 문서에 밀려 top-5 밖으로 나갔다.** `ts_rank` 는 IDF 를 안 쓰므로
흔한 단어가 많은 짧은 청크가 쉽게 1위가 된다 — 그 잡음이 좋은 dense 신호를 이기면 안 된다.

**2차 (`RAG-057` ②, 25문항 · 36요구):** `search.py` 주석이 *"문항이 늘거나 코퍼스 성격이
바뀌면 다시 재라"* 고 못 박아 뒀고 조건이 둘 다 성립했다(12→25문항, 8,990문서).

| w | 0.00 | 0.05 | 0.10~0.35 | **0.40** | 0.45~0.50 | 0.60 | 0.75~1.00 | 1.50 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 요구충족 / 36 | 15 | 17 | **18** | **19** | 18 | 17 | 16 | 15 |

**0.40 이 1 더 얻는다. 그런데 안 옮겼다.** 19 를 내는 구간이 `0.37~0.44` 로 **폭이 0.08 인
턱**이고, 옛 결정이 0.3 을 고른 기준이 *"평평한 구간의 가운데 — 양끝은 한쪽이 무너지는
자리"* 였다. 그 기준을 그대로 적용하면 안 옮기는 쪽이다. 가중치 × `RRF_K` **2차원 전수**
(w 0~1.5 × K 10~200)에서도 최대가 19 이고, 19 가 나오는 칸은 평평한 구간이 아니라
**흩어진 점**이었다 — 어느 점을 고르든 25문항에 맞추는 일이 된다.

### 4.4 🚫 기각 — `ts_rank_cd` (`RAG-057` ③)

`ts_rank` 의 편향(짧은 청크가 쉽게 1위)을 흔들 후보였다. 실측:

- **25문항 중 24문항에서 렉시컬 순위가 완전히 같다.** 요구충족은 모든 가중치에서 한 칸도 안 다르다
- 정규화 플래그를 붙이면 오히려 나빠진다:

| | `ts_rank` | `ts_rank_cd` | `cd/1` | `cd/2` | `cd/16` | `cd/32` |
| --- | --- | --- | --- | --- | --- | --- |
| 최대 요구충족 | 19 | 19 | 16 | 16 | 16 | 19 |

**플래그가 전부 긴 문서를 깎는 방향**이기 때문이다(1=1+log(길이) · 2=길이 ·
16=1+log(고유낱말수)). 여기서 고치려던 편향은 **짧은 청크가 쉽게 1위가 되는 반대쪽**이라
이 축에는 쓸 플래그가 없다. (`cd/32` 는 `rank/(rank+1)` 단조변환이라 순위가 안 바뀐다 —
하네스가 제대로 도는지 보는 눈금으로 목록에 남겨 뒀다.)

### 4.6 필터 둘 — 전부 인자가 아니라 질의에서 읽는다

#### 교통수단 배제 (`RAG-052`)

"**기차에** 반려동물은 몇 kg까지"의 top-5 에 항공 청크 둘(이스타 9kg · 에어프레미아 7kg)이
4·5위로 들어와, 조항 번호를 실어 나르던 easylaw 청크를 밀어냈다. 답은 안 틀렸고
(SRT 10kg) **잃은 것은 KPI 다.**

크기부터 쟀다 — **22문항 중 2, KPI 에 닿는 것은 하나.** *"한 문항이면 안 하는 것도 정답"*
이라고 카드가 미리 적어 뒀고, 그래도 넣은 이유는 지하철·버스 소스가 들어오면 넓어지는
자리이고 되돌리기가 싸서다(파일 하나 + `search()` 다섯 줄).

⚠ **"남기기"가 아니라 "배제"다.** *"수단이 맞는 subcategory 만 남기기"* 로 하면
`category=policy` 인 easylaw 가 **통째로 빠져** 고치려던 청크가 사라진다. 규칙 셋:

1. 신호가 **정확히 하나**일 때만 건다 ("기차나 비행기"면 아무것도 안 뺀다)
2. 신호가 없으면 아무것도 안 뺀다 — 기본값은 "전부"
3. 뺄 수 있는 것은 교통 subcategory 뿐. 교통이 아닌 소스는 손대지 않는다

#### 지역 `org` 사전필터 (`RAG-063`)

`S3`(부산 동래구 내장형 등록 비용)를 **19개 랩 전수**로 추적한 표다:

| 랩 | 4 | 5~9 | 10~15 | 16~22 |
| --- | --- | --- | --- | --- |
| `cited` | ✅ | ✅ | ✅ | ❌ |
| `grounded` | ❌ | ✅ | ❌ | ❌ |

**하이브리드가 들어온 뒤로도 13랩 연속 실패다.** 그리고 `RAG-057` 이 순위 상수로도
못 고침을 증명했다 — **S3 는 `w ≥ 1.35` 를 요구하는데 DP1 은 `w ≤ 0.20` 을 요구한다.**
전역 상수로는 동시에 만족할 수 없다. 그래서 사전필터로 갔다.

⚠ **`org` 이 없는 문서는 남긴다.** "부산 동래구에서 목줄 안 하면 과태료?"의 답은 조례가
아니라 **동물보호법**에 있고 법령에는 `org` 이 없다. 지역 신호가 있다고 `org` 없는 문서를
빼면 고치려던 것보다 큰 것이 사라진다:

```sql
AND (metadata->>'org' IS NULL OR metadata->>'org' = ANY(:orgs))
```

> 🔴 **이 필터가 한 번 조용히 죽었다** (`RAG-066` ①). `rag load` 한 번에 `org` 백필
> **2,592행이 통째로 지워졌다** — `UPSERT` 가 `metadata` 를 병합이 아니라 **갈아끼우기**
> 때문이다. **적재도 성공하고 스모크도 통과하고 예외도 안 났다.** 랩을 두 번 돌 때까지
> 아무도 몰랐다. 이후 `load.metadata_loss()` 가드가 생겼다 — 판정은 *"있던 키가 통째로
> 사라지는가"* 하나로 좁혔다(규칙이 넓으면 사람이 `--allow-metadata-loss` 를 반사적으로
> 붙이게 되고, 그러면 가드가 없는 것과 같다).

### 4.7 어휘 다리 — 사람 말과 법 말이 한 낱말도 안 겹친다 (`RAG-066` · `RAG-070`)

**이 프로젝트에서 검색 품질을 가장 크게 움직인 것이 이것이다.**

정찰 실측(2026-09-06):

| 문항 | 지금 | 렉시컬만 확장 | **질의를 다시 인코딩** |
| --- | --- | --- | --- |
| `HS1` 아파트 반려견 동의 | 없음 | **없음** | **1위** (dense 1) |
| `FW3` 동물 화장장 | 없음 | 7위 | **1위** (dense 1) |
| `DP1` 비행기 태우기 | 6위 | 3위 | **2위** (dense 2) |

**dense 가 후보를 정하기 때문에 렉시컬만 확장해서는 `HS1` 이 아예 안 온다.** 그래서
별칭을 tsquery 에 더하는 것으로는 부족하고, **질의 문장을 넓혀 다시 인코딩해야 한다.**
그래서 `search.encode()` 를 **질의 벡터를 만드는 유일한 입구**로 모았고,
`test_vocabulary.py` 가 **AST 로 `encode_query` 직접 호출을 세서** 입구가 다시 갈라지는 것을 막는다.

가장 극적인 한 줄은 `목줄` → `안전조치` 였다 (`RAG-070`):

```
Q3  목줄 안 하면 과태료 얼마인가요?
답  "제공된 참고자료에는 목줄 미착용에 관한 과태료 규정이 포함되어 있지 않습니다."
```

**`lap19` 부터 `lap29` 까지 21랩 동안 한 번도 답한 적이 없다.** 그런데 답은 코퍼스에 있다 —
`동물보호법 시행령 별표 4-2-아`(1차 20 · 2차 30 · 3차 이상 50만원). 법이 쓰는 말은
`안전조치` 이고, `목줄` 은 두 다리 건너 **시행규칙 제11조**에 있다. 코퍼스 전체에서
`목줄` 이 든 청크는 49개인데 **별표에는 0개**다.

| | 붙이기 전 | `안전조치` 한 낱말 붙인 뒤 |
| --- | --- | --- |
| `별표 4-2-아` | dense **106위** | **1위** |
| 인용 확장 | — | `제101조④` · `제16조` = Q3·B1 의 `must` 둘 |

⚠ **이미 그 낱말이 있는 질의에는 안 더한다.** `QA5`("목줄 착용 외에 다른 안전조치
방법은?")는 질문에 이미 `안전조치` 가 있어 `aliases()` 가 아무것도 안 더한다 —
그 규칙이 여기서 값을 냈다.

> ⚠ **진단이 한 번 틀렸다는 것도 기록돼 있다.** `RAG-057` ⑤ 는 같은 실패를 **청킹 문제**로
> 보고 *"별표 행에 위반행위 이름과 근거 법조문을 실어야 한다"* 는 처방을 남겼는데,
> **그 처방은 이미 돼 있었다.** 공통 머리를 걷어 내도 **질의 벡터에 `안전조치` 가 아예
> 없으므로** 안 올라온다. 관찰(공통 머리는 실재한다)은 맞았고 **원인 지목이 틀렸다.**

### 4.8 구조적 사실 — 렉시컬은 후보를 **못 들여온다** (`RAG-072` ③)

이 문서에서 가장 중요한 한 줄이다. §4.1 의 RRF 공식이 만든 구조인데, **아무도 그것을
의도하지 않았다.** 어떤 청크가 **렉시컬 14위인데 최종 110위**인 것이 이상해서 산수를 해 봤다:

```
렉시컬 1위 · dense 후보 밖 :  0.3 / (60 + 1)    = 0.004918
dense 100위 · 렉시컬 밖    :  1   / (60 + 100)  = 0.006250   ← 이쪽이 크다
```

**렉시컬 1위여도 dense 꼴찌를 못 이긴다.** 이기려면 `LEXICAL_WEIGHT > 0.381` 이어야 하는데
지금은 0.3 이다(렉시컬 14위면 `> 0.463`).

즉 **지금 구조에서 렉시컬 축은 dense 가 뽑아 온 100개의 순서를 바꾸는 도구이지,
새 후보를 데려오는 도구가 아니다.** `RAG-057` 이 가중치를 스윕해 0.3 을 고른 자리인데
그 구조적 귀결은 그때 안 적혔다.

⚠ **이것은 "0.3 이 틀렸다"가 아니다.** 스윕에서 0.50 이상은 실제로 더 나빴다. 렉시컬이
후보를 들여오게 만들면 **그 잡음도 같이 들어온다.** `w` 를 4.0(13배)까지 올리면 목표 청크가
17위까지 오지만, 그때 top-3 가 무관한 조문으로 무너진다.

#### 이 한 줄이 §4 전체를 설명한다

검색은 **후보를 뽑는 단계**와 **뽑힌 것을 줄 세우는 단계**로 나뉜다. 위 산수가 말하는 것은
**dense 가 후보를 혼자 정한다**는 것이고, 그러면 뒷단계를 아무리 만져도 앞단계가 안 데려온
문서는 영영 안 나온다. §4 에서 안 통한 것과 통한 것이 정확히 그 선으로 갈린다:

| | 어느 단계를 만졌나 | 결과 |
| --- | --- | --- |
| §4.4 `ts_rank_cd` | 줄 세우기 (렉시컬 점수 함수) | 🚫 재정렬만 바뀐다 |
| §4.3 렉시컬 가중치 | 줄 세우기 (융합 계수) | 🚫 0.4 로 +1, 폭 0.08 짜리 턱 |
| §4.5 `CANDIDATE_N` | 후보 뽑기 — **양만** | 🚫 늘려도 dense 순위 낮은 건 여전히 낮다 |
| §4.7 렉시컬만 확장 | 줄 세우기 | 🚫 `HS1` 이 안 온 이유가 정확히 이것 |
| §5.1 리랭커 | 줄 세우기 (후보 안에서 재정렬) | 🚫 **똑같이 걸린다** |
| **§4.6 필터 둘** | **후보 뽑기 — 볼 문서를 줄인다** | ✅ |
| **§4.7 질의 재인코딩** | **후보 뽑기 — 벡터를 바꾼다** | ✅ |

**실제로 통한 둘은 dense 가 후보를 뽑는 단계 자체에 개입한다.** 필터는 볼 문서를 줄이고
어휘 다리는 질의 벡터를 바꾼다. 순위 상수를 만지는 시도는 전부 그 뒤 단계라 한계가 있었다.
⚠ `CANDIDATE_N` 이 후보 단계인데도 안 통한 것은 **양을 늘렸을 뿐 뽑는 기준을 안 바꿨기**
때문이다 — 그래서 이 표의 선은 "앞단계냐 뒷단계냐"가 아니라 **"후보 집합의 구성이 바뀌느냐"** 다.

**그리고 같은 제약이 리랭커에도 그대로 걸린다** — 다음 절이 그 이야기다.

## 5. 안 쓴 것 둘 — 리랭커와 HNSW

### 5.1 🚫 리랭커 — 하나 얻고 둘~셋 잃는다 (`RAG-076`)

`RAG-003` 이 v1 설계에 리랭커를 넣어 두고 *"평가셋 recall@5 를 재고 도입 결정"* 으로
유보했다. 하이브리드로 recall 이 6 → 8 로 움직인 뒤 실제로 쟀다.

**게이트 ① — 리랭커의 상한이 문항 2개다.** 도입을 재기 전에 *"후보 안에 답이 얼마나
들어와 있나"* 부터 셌다. `must` 요구 45개를 네 칸에 넣으면:

| 칸 | 뜻 | 수 |
| --- | --- | --- |
| A | 이미 top-5 안 | 34 |
| A+ | 인용 확장으로 들어옴 | 4 |
| **B** | **후보 안 · 근거 밖 — 리랭커의 사정거리** | **4** |
| C | 후보 밖 (>100) | 3 |
| D | 코퍼스에 없음 | 0 |

⚠ **요구 단위로 세면 리랭커의 몫이 부풀려진다.** `grounded` 는 `must` 주소가 **하나만**
근거에 실려도 성립하므로 문항 단위로 다시 세면 **31/33 이 이미 서 있고, 리랭커가 살릴 수
있는 것은 두 문항뿐**이다. 그리고 실측 `grounded` 가 **30/33** 이었다 —
**남은 여지가 1 이고, 그것이 이 카드의 천장이었다.**

**게이트 ② — 실제로 재정렬해 봤다** (`bge-reranker-v2-m3` · fp32 · GPU · 5,932쌍):

| | 근거에 `must` 가 있는 문항 | `must` 가 top-5 안 |
| --- | --- | --- |
| 지금 (RRF) | **31 / 33** | **30 / 33** |
| 리랭크 · 본문만 | 30 / 33 — `+I4` `−Q4 −Q6` | 28 / 33 |
| 리랭크 · 제목+본문 | 29 / 33 — `+I4` `−Q4 −Q6 −FW3` | 27 / 33 |

**리랭커는 제 일을 했다** — `I4` 를 **94위 → 2위**로 살려냈다. `RAG-072` ④ 가 N×w 아홉 칸을
훑어 *"최선이 26위"* 라고 적은 그 벽을 넘는다. **그런데 서 있던 문항을 둘~셋 무너뜨린다.**

**제목 가설도 재고 기각했다** — 무너진 넷이 전부 법령 문항이라 *"법령명이 본문에 없어서
리랭커가 어느 법인지 못 본 것"* 이 의심됐다(법령 청크 본문은 `제2조(정의) …` 로 시작하고
법령명은 `document_title` 에 있다). `document_title`·`section` 을 같이 넣어 다시 재니
**총계가 더 나빠졌다.** 측정이 리랭커에게 불리했을 가능성이라 그냥 넘기지 않은 자리다.

**🔴 결정적인 것은 비용 구조다.** 리랭커가 유일하게 고치는 문항의 정답이 **후보 94위**에
있다. 그것을 잡으려면 후보 100개를 **다 재정렬해야 하고**, 그 비용이 질의당 **약 21초**다
(GPU · fp32 · 후보 평균 180). 얕게(top-20 만) 재정렬하면 비용은 내려가지만
**94위는 애초에 안 들어온다. 값과 비용이 같은 손잡이에 묶여 있다.**
그리고 **서빙은 CPU 고정**이라 21초보다 나쁘다.

곁가지 둘:

- **리랭커는 인용 확장과 상호작용한다** — 확장은 top-20 이 가리키는 조문을 끌어오므로
  재정렬하면 확장의 입력이 통째로 달라진다. `Q6` 이 그렇게 잃었다. **top-5 만 비교하면
  안 보이는 손실**이라 프로브는 두 축을 다 냈다
- **fp16 은 공짜가 아니다** — 7.9 → 31.7 쌍/s 로 4배인데 **같은 후보에서 top-2 순서가 뒤집혔다**

**안 잰 것도 적어 둔다** — Cohere Rerank 3.5 는 안 쟀다. 이유가 판단이 아니라 **권한**이다:
키가 없고 **코퍼스 본문을 외부로 보내는 일**이라 사람이 정할 자리였고, 사람이 로컬 판
결과를 보고 닫기로 했다. 검색기를 `bge-m3` 로 되돌려 재지도 않았다(재인코딩 55분이 든다).

### 5.2 ⏸ HNSW 인덱스 — 만들어도 지금은 안 쓰인다 (`RAG-084` + 2026-09-10 서버 실측)

dense 검색은 지금 **전수 스캔**이다. `documents` 에 인덱스가 여섯 있는데 `embedding` 에
걸린 것은 하나도 없다.

**1차 측정 (`RAG-084`, 2026-09-09, 개발 PC · `pgvector:pg17` 컨테이너 · 189질의):**

| `ef_search` | dense recall@100 | 최종 recall@8 | top-8 이 전수 스캔과 같은 질의 |
| --- | --- | --- | --- |
| 40 (pgvector 기본값) | 39.0% | 88.5% | 66.7% |
| 100 | 90.8% | 96.7% | 83.1% |
| 200 | 96.6% | 99.0% | 89.9% |
| **400 (골랐다)** | **99.1%** | **99.8%** | **96.3%** |

| | 전수 스캔 | HNSW + `ef_search=400` |
| --- | --- | --- |
| p50 | 69.7ms | 43.1ms (−38%) |
| p95 | 88.2ms | 57.1ms (−35%) |

**2차 측정 (2026-09-10, 서버 `vectordb` · PostgreSQL 18.6 · pgvector 0.8.6 · 60질의).**
트랜잭션 안에서 인덱스를 만들고 재고 **롤백**했다 — `CONCURRENTLY` 를 안 쓰는 덕에 가능했고,
팀에 하나뿐인 DB 에서 파괴적 측정을 하는 유일한 길이다.

빌드 **1.5초**, 크기 **77MB**. dense 단독:

| | p50 | p95 |
| --- | --- | --- |
| 전수 스캔 (지금) | 36.0ms | 41.9ms |
| **HNSW 강제 (`ef_search=400`)** | **5.0ms** | **7.9ms** |

**7.2배**이고 top-8 은 60질의 **전부 전수 스캔과 동일**했다.

**🔴 그런데 플래너가 인덱스를 안 고른다:**

| `ef_search` | 플래너가 고른 것 | 그 비용 | 인덱스 강제 시 비용 |
| --- | --- | --- | --- |
| 40 | HNSW | 2,786 | 2,786 |
| 64 | HNSW | 3,683 | 3,683 |
| 100 | HNSW | 4,941 | 4,941 |
| 200 | Seq | 6,392 | 8,163 |
| **400 (배포된 값)** | **Seq** | **6,392** | 14,058 |
| 1000 | Seq | 6,392 | 30,092 |

pgvector 의 인덱스 비용 추정이 `ef_search` 에 따라 커지는데 전수 스캔은 6,392 로 고정이다.
**100 을 넘는 순간 플래너가 전수 스캔으로 돌아선다.**

⚠ **`RAG-084` 가 적은 *"300~500 에서 추정이 2,152 로 다시 떨어져 인덱스를 고른다"* 는
서버에서 재현되지 않는다.** 서버는 **PG 18.6 / pgvector 0.8.6** 이고 1차 측정은
`pgvector:pg17` 컨테이너였다 — 비용 모델이 다르다. **환경을 안 적었으면 틀린 결론이
그대로 남았을 자리다.**

**그래서 지금 상태를 세 줄로 적으면:**

| | 디스크 | dense 검색 | |
| --- | --- | --- | --- |
| 인덱스 없음 | 0 | 36ms | ← **지금** |
| 인덱스를 만들어만 둠 | +77MB | **36ms (그대로)** | ← 마이그레이션만 적용하면 여기 |
| 인덱스를 쓰게 만듦 | +77MB | 5ms | 설정을 더 손봐야 한다 |

**결론: 마이그레이션만 적용하는 것은 값이 0 이다.** 켠다면 "쓰게 만드는 것"까지 같이
가야 하고, 길이 둘이다 — `ef_search` 를 100 이하로 내리거나(정확도가 내려간다),
400 을 두고 플래너를 눌러 쓰게 하거나(`search.py` 가 이미 질의마다 설정 한 줄을 거는
자리가 있다).

⚠ **어느 쪽으로 가든 먼저 재야 하는 것이 있다** — 위 60질의는 **필터가 없는** 질의였다.
실제 `/life/ask` 는 지역·카테고리·부칙 필터를 건다. HNSW 는 필터가 붙으면 후보를 못 채워
**결과가 조용히 나빠지는** 성질이 있다.

**순서 제약도 하나 있다** — GCP 잡은 `backend/src` 를 이미지에 구워 돌기 때문에,
인덱스를 켠 채 잡이 옛 코드(증분화 전)로 돌면 **매일 그래프를 통째로 간다.**
**인덱스 적용과 GCP 이미지 재빌드는 같이 간다.**

## 6. 재는 쪽 — 무엇으로 재는지가 없으면 위의 모든 수가 의미가 없다

### 6.1 무엇을 커밋하고 무엇을 버리나

- **골든셋은 `rag/stages/goldenset.yaml` 에 커밋된다.** 기계 산출물(top-k 덤프)은 미추적이고
  **사람이 만든 판단**만 추적한다. 기준은 *"없어지면 다시 만들 수 있나, 아니면 판단이 유실되나"*
- **랩(`data/processed/answers/lapN.jsonl`)은 `data/` 미추적의 예외**다 — 같은 질문에도 LLM
  출력이 매번 달라 **옛 랩이 곧 유일본**이고, 코퍼스가 바뀐 뒤에는 재생성이 아예 불가능하다

### 6.2 지표를 바꾸면 재는 것이 달라진다

- `Hit@5` vs `Recall@5` — §3.2. 지표를 **탈락선의 성격에 맞췄다**
- **경계 문항을 총계에서 뺀다** (`RAG-062`) — 기권·거절 문항은 `must` 가 비어 재현율이
  정의되지 않는다. 25문항 스윕에서 30문항 중 다섯을 뺀 이유가 이것이다
- **KPI 를 두 축으로 가른다** (`RAG-070` ③):

| | 문항 | `cited` | `grounded` |
| --- | --- | --- | --- |
| 조 번호가 **있는** 소스 | 20 | **15 (75%)** | 16 |
| 조 번호가 **없는** 소스 | 13 | **1** | **13 (전부)** |

조 번호가 없는 13문항은 **전부 근거를 옳게 잡았다.** 보조금24 · SRT 약관 · 항공사 안내 ·
easylaw 해설에는 **인용할 조 번호가 애초에 없다.** `cited` 0 은 실패가 아니라 그 소스의
성질인데 **헤드라인은 두 축을 한 수에 섞고 있었다.**

### 6.3 평가 문항 집합을 세 번 바꿨다

위의 모든 수는 **어떤 질문 목록에 대고 잰 것이냐**에 딸려 있다. 그 목록이 세 번 바뀌었고,
바뀔 때마다 이전 랩과 직접 비교가 끊긴다.

| 언제 | 문항 집합 | 크기 |
| --- | --- | --- |
| `RAG-022` | 골든셋 v1 | 15문항 |
| `RAG-055`~ | hand 확장 | 30문항 (재현율이 정의되는 것은 25) |
| `RAG-079`·`RAG-080` | **`life_v1` 층화 문항 집합** | **140문항** |

`life_v1` 을 만든 이유는 **기존 문항 집합이 포화됐기 때문**이다 — 그 세트에서는 고칠 것이
안 남았는데 실제 답변 품질에는 구멍이 있었다. **못 재는 것을 못 고친다.** LLM judge(`RAG-074`·`RAG-075`)를 세우고 사람 라벨 30건으로
캘리브레이션해(`RAG-082`) 통과시킨 것이 그 자리다.

### 6.4 재는 법에서 배운 것 둘

- **랩 비교는 총계가 아니라 문항 단위로** (`RAG-071`). 총계가 같아도 안이 바뀐다 —
  §4.1 의 S3 이 그 실물이다
- **순위를 재는 정찰은 운영 SQL 을 복제해야 한다** (`RAG-072` ⑦). 비슷하게 짜면 안 된다.
  `row_number()` 를 매칭 안 된 행까지 포함해 매겼다가 같은 청크가 한 번은 14위, 한 번은
  83위로 나왔다. `ts_rank` 는 **동점이 흔해 tie-break 하나에 수십 등이 흔들린다**

## 부록. 이 프로젝트가 반복해서 배운 것

수치가 아니라 **일하는 방식**에서 반복된 것들이다. 검색과 무관해 보여도 위의 결정
대부분이 여기서 나왔다.

1. **조용히 틀리는 것이 가장 비싸다.** `org` 2,592행 소실 · 임베딩 모델 혼입(차원이 같아
   예외가 안 난다) · `content_tokens` 빈 값 · 배치 구성 섭동 — 전부 **예외가 안 나고
   로그도 조용하다.** 그래서 가드가 `NOT NULL`(기본값 없음) · `metadata_loss()` ·
   기동 시 모델 불일치 경고처럼 **실패시키는 쪽**으로 붙었다.
2. **먼저 재고, 안 오르면 나머지를 안 한다.** `RAG-072`·`RAG-076` 둘 다 **파일을 하나도
   안 고치고** 닫혔다. 정찰 스크립트만 남기고 게이트에서 멈춘 것이 여섯 번이다.
3. **결과를 보기 전에 규칙을 적는다.** §3.2 의 사전 등록이 실제로 판정을 뒤집었다.
4. **진단이 틀릴 수 있다는 것을 기록에 남긴다.** `RAG-057` ⑤ 의 청킹 진단, `RAG-076` ②의
   `CANDIDATE_N` 가설, `RAG-072` ⑦의 시뮬레이션 오류 — 셋 다 **자기가 뒤집은 것을 지우지
   않고** 남겼다. 지우면 다음 사람이 같은 것을 다시 시도한다.
5. **수치에는 잰 환경을 붙인다.** §5.2 가 그 값을 하루 만에 회수한 자리다.
