# 산책 파트 슬롯 미리보기

후속 사용자 결정과 그 경위는 **[장면 서술 상세 인계](https://github.com/rkbuhtig/DAENGS_geo/blob/2345c5b3d2b24f5754f55b802aab59905b807eb9/docs/explorations/walk/diary/narrative-design/README.md)**를 읽는다.
특별한 순간은 기록마다 별도 장면이며 AI가 자유 서술 본문에 관여하지 않고 공간·환경만 보조한다.
행동 핀은 가까운 시선으로 담으며 어디서·누가·무엇을·어떻게·환경 α를 구별한다.
[상권·공원·피복 정규화](space-normalization.md)는 실제 저장 응답으로 이식 동등성을 확인했다.
최신 서술 품질은 별도 검증 대상이다.

기획 기준은 [산책 장면과 일기 생성](https://github.com/rkbuhtig/DAENGS_geo/blob/2345c5b3d2b24f5754f55b802aab59905b807eb9/docs/explorations/walk/diary/plan.md)
([GEO #266](https://github.com/rkbuhtig/DAENGS_geo/pull/266))이다.
아래는 기존 슬롯 선정·배경 작성 구현이다. 장면의 완결성, 시스템 판정용 시간과 작성 입력의
분리, 표현 선택의 자유를 새 기획에 맞추는 작업은 별도다. 기존 슬롯 수치와 원본 보존은 유지한다.

[DEV #474](https://github.com/SAJOYO/DAENGS_dev/pull/474)의 장면 결합 구조를 재사용해
상권·공원·토지피복 정규화를 실제 생성 경로에 연결한다. 이전 비교 실험의 작성 지시는
새 정규화 계약으로 이어받지 않는다.

저장된 DEV 입력 → 기존 기본 보드 선정 → 공간·환경·동선 조건과 용량 →
장면별 스탬프 → Gemini 배경 서술 → 원문과 조립하는 워킹 스켈레톤이다.
`POST /app/walks/{walk_id}/diary-slots/preview`에서 실행한다.
`storyboard`의 기본 보드 생성도 같은 슬롯 계산과 서술·인용 검사를 사용한다.
미리보기 API를 거치지 않고, 고정한 스탬프를 서비스 writer에 직접 전달한다.

## 현재 연결 범위

`collect_backgrounds: true`를 미리보기 요청에 명시하면 읽기 트랜잭션을 끝낸 뒤
고정 장면에 상권·공원·피복의 정규화 재료를 결합한다. 상세 범위·시간 한도·실제 발행 활성화는
[공간 정규화 계약](space-normalization.md)을 따른다. 요청 기본값은 false다.
아래 CLI와 Place/Kakao 비교 결과는 이전 수집 실험 기록이다.
확인된 위치가 없으면 조회하지 않는다. 동시 조회 4개, 장면 12개, 수집 20초 한도가 있다.
일반 storyboard 발행에 이 외부 조회를 자동 추가한 것은 아니다.

`SceneBackgroundSnapshot`은 이미 고른 보드와 코어 버전·좌표에 묶인 일회 수집본이다.
기록별 `DiaryInput.backgrounds`의 계약을 바꾸거나 경로 지점을 가짜 사용자 기록으로
만들지 않는다. 공통 projector → 중복/충돌·조건 판정 → 파트 용량 → writer를 재사용한다.
환경·동선도 기존 판정을 통과한 근거만 쓰며, 누락된 당시 날씨를 현재 날씨로 채우지 않는다.

### 휴대폰의 고정 장면 비교 재현

`backend/`에서 다음 명령을 실행한다. `request.json`은 APP Debug의 v2 내보내기이고,
`source.json`은 실제 저장 입력의 `DiaryInput`, `points.json`은 그 분석에 사용한 업로드
좌표다. 모델에는 raw GPS를 전달하지 않는다. 개인 자료와 생성 결과는 Git 밖에 둔다.

```powershell
uv run tools/compare_diary_scenes.py --request <개인폴더>/request.json --source <개인폴더>/source.json --points <개인폴더>/points.json --target-scenes 5 --env-file <설정폴더>/.env --output <개인폴더>/새실행폴더
```

`--target-scenes`는 원래 보드의 중간 장면 목표값이다. 업로드 좌표의 fingerprint와
계정·산책을 검증하고, 재현한 공개 장면의 코어·위치·시각·관측 전체를 앱 원본과 대조한다.
보이는 장면만 원래 표시 순서와 편집 원문으로 투영하며 비교 전용 plan revision을 만든다.
발행본을 새로 만들거나 저장하지 않는다. 공통 writer의 계약 때문에 현재 CLI는
본문이 비어 있지 않은 2~12개 보드 장면만 받는다. 범위를 벗어나면 조회 전에 중단하며
원문을 채우거나 숨긴 장면을 되살리지 않는다. 다른 일기 형식도 자동 변환하지 않는다.

새 폴더에 보드, 수집 원응답·해시, 슬롯 선정/제외 사유, 실제 모델 입력·스키마·응답,
프롬프트·정책과 receipt, 앱 결과를 남긴다. `--backgrounds <이전실행>/backgrounds.json`은
같은 고정 장면의 수집본을 재사용한다. 키는 복사하지 않는다. 구조상 `accepted`여도
문장 의미는 별도 검토해야 한다. 이번 실제 비교는 다음과 같았다(2026-09-12).

- 폰에서 보존한 실제 산책: 원본 6개 장면의 ID·좌표·시각·순서·본문이 이전 비교와 동일.
  canonical 입력 hash와 공개 장면 전체도 재현본과 일치했다. 재계산한 plan hash는
  과거 발행 plan hash와 달라 같은 발행 영수증으로 취급하지 않았다.
- 위치 있는 4개: Place 0건 → 실제 Kakao 조회. 공간 슬롯 각 3개, 위치 참고 각 1개.
  동선 관측 장면 1개에는 실제 상대 저속 슬롯 1개. 환경은 모두 0개.
- 위치 없는 시작/종료 2개는 외부 조회·추가 서술 없이 원문 유지.
- 동일 수집본으로 3회 작성했다. 첫 2회에는 근거 없는 번화함/상점가 또는 산책로 표현이
  있어 적용하지 않았다. 현재 조회 정보와 등록 거리의 표현을 구체화한 세 번째 결과만
  검토·적용했다. 장소 나열은 대표 시설 하나로 줄었지만 문체는 여전히 설명문에 가깝다.
  지역 특성·날씨·감각을 풍부하게 쓴 일기가 완성됐다는 근거는 아니다.
- `uv run pytest tests/walk/diary -q -rs`: 345 passed, 9 skipped. 공통 슬롯·작성·보존 경계를
  바꿔 일기 패키지를 확인했다. 9건은 disposable DB 미설정으로 실행하지 못한 DB 통합 검사다.
  최종 프롬프트/표시·비정상 공급자 응답 보완 후 비교·수집·writer 32건 재확인.
  변경 파일 ruff와 `uv run check` 통과.
  Windows check는 프로세스에만 `PSExecutionPolicyPreference=Bypass`, `PYTHONUTF8=1`을 적용했다.

공개 서버의 슬롯 API는 기존 확인에서 기능 미제공 404였고, 이 PR을 배포하지 않았다.
폰 결과는 PC에서 동일 DEV 코드와 실제 외부 API를 실행한 비교다. 서버 활성화·운영 배포,
수집 근거가 더 풍부한 산책에서의 일기 문체 평가는 별도로 남는다.

| 단계 | 동작 |
| --- | --- |
| 실제 입력 | 기존 `read_input`의 소유자 확인·저장된 기록/사진/맥락·확정 동선 재생을 재사용 |
| 장면 | 기존 records-first 기본 보드. 사용자 기록을 보존하고 동선 보충·시작/종료 포함 |
| 공간 | 기존 projector에서 검증된 스키마·reference로 등록 지점/형상 거리·영역 집계·주소를 구분 |
| 환경 | 기록별 수집 큐 → 기존 Life `weather_at` → 기상청 격자 기온 관측. 실험용 `regional-weather-v1` 입력도 유지 |
| 동선 | canonical 관측을 재생하고 실제 연결 구간의 시간·위치 대응 확인 |
| 서술 | `gemini-3.1-flash-lite` 1회. writer 상한 15초와 서비스 요청의 남은 예산(최대 20초) 중 짧은 쪽을 적용. 장면·슬롯 선택은 코드, Gemini는 배경 문장만 작성 |
| 출력 | 기본 보드·파트 스탬프·조건/적재 판정과 실제값/기준값·생성 문장·인용 ID·입력/정책 revision |

파트 스탬프는 **장면마다 다시 계산하는 스냅샷**이다. 장면 사이의 변경은
각 장면의 후보와 조건을 다시 적용해 반영한다. 실시간 공유 캐시의 TTL/퇴출 상태나
영속 슬롯 테이블, 발행된 스탬프 교체 트랜잭션까지 구현한 것은 아니다.
공간 저장 거리를 다른 장면으로 이월하거나 새 장면의 거리로 해석하지 않는다.
시작/종료·동선 보충 장면은 대응하는 공간·환경 자료가 없으면 그 파트를 비워 둔다.

## 조건과 용량

`SlotPolicy`의 기본값은 초기 매개변수다. 미리보기 요청마다 변경할 수 있다.
서비스 생성 준비는 서버의 기본 정책을 사용하며, 일반 API 요청에서 변경할 수 없다.
현재 정책 버전은 `diary-part-slots-v3`다. 이전 v1/v2 실험 정책 JSON을 재사용할 때는
이 버전으로 명시적으로 바꾼다. 새 정책에는 실제 기온 관측의 나이 상한이 추가됐다.
이미 저장한 발행 영수증의 과거 정책 값은 재해석하지 않는다.

| 항목 | 기본값 | 처리 |
| --- | ---: | --- |
| 공간 용량 / 거리 | 3 / 250m | 위치가 유효한 해당 코어의 근거만. 등록 지점/형상 거리 초과 제외 |
| 환경 용량 / 관측 나이 | 1 / 7200초 | 실제 기온은 조회 기록·좌표 일치 및 기록 이전 관측. 실험 입력은 `[from, until)`과 선언된 지역 범위 확인 |
| 동선 용량 / 직전 허용 | 1 / 30초 | 현재 구간 우선, 다음으로 가까운 직전 구간. 단절을 건너지 않음 |
| 위치 샘플 시차 / 동선 대응 거리 | 30초 / 30m | 낡거나 대응 불명인 위치에 현재 맥락을 부여하지 않음 |
| 전체 용량 | 8 | 각 파트 순위 큐를 공간→환경→동선 순으로 한 개씩 순회 |
| 위치 설명 포함 | true | `include_location_reference`: 주소 최대 1개를 별도 메타데이터로 보존 |

조건 결과 `pass/fail/unknown`과 적재 결과 `kept/excluded/duplicate/conflict/part_capacity/total_capacity`를
분리한다. 공간은 **등록 지점 거리 → 형상 거리 → 영역 집계**의 비어 있지 않은 큐에서
하나씩 꺼내고 반복한다. 각 거리 큐 안에서만 가까운 순이며, 집계 반경은 거리 순위에 쓰지 않는다.
같은 종류만 있어도 남는 용량을 채울 수 있으며 종류별 필수 개수는 없다. 거리가 없는 집계끼리는
안정적인 ID로 순서를 정한다. 서로 다른 공간 의미 사이의 순환 순서는 이 실험 정책의 명시적 선택이다.
주소는 `location_reference`에 따로 담아 공간/전체 슬롯 용량과 경쟁하지 않는다. 최대 1개이며
writer의 입력 바이트 예산에는 포함되고 인용도 가능하다. 세 파트 근거가 최대 16개이므로
주소까지 포함한 장면별 인용 상한은 17개다. `space_slots:0`과 주소 비활성화는 독립적이다.
환경은 적용 가능한 최신 관측 구간, 동선은 현재/가까운 직전 구간을 우선한다.
`space_radius_m`을 키워도 기존 공급자가 저장한 250m 검색 결과 밖의 자료가 새로 생기지는 않는다.

**중복/충돌은 순위·용량보다 먼저 처리한다.** 대상(`entity_key`), 장면·관계·적용 범위
(`claim_scope`), 정규화한 주장 내용(`claim_key`)을 분리한다. 조회 시각과 단순 숫자 표기 차이
(`40`/`40.0`)는 다른 주장이 아니다. 같은 주장은 하나로 묶고 모든 `sources`의 ID·버전을 유지한다.
관계나 적용 범위가 다르면 별도 근거로 판단한다. 동일 조건에서 값이 다르면 모두 `conflict`로
제외하고 경쟁한 원자료와 값들을 `details`에 남긴다. 현재 어댑터에는 우선권을 입증할 버전 순서가
없으므로 조회 시각·가까운 거리로 승자를 고르지 않는다. 공간 반경 필터보다도 충돌 확인이 먼저여서
40m/200m 상충 입력에서 정책을 60m로 낮춰도 40m 주장만 조용히 살아남지 않는다.

판정의 `details`에는 계산 가능한 실제값·정책 기준값·단위를 담는다. 예: 거리 190m,
정책 100m, `outside_space_radius`. HTML의 ‘판정값과 기준값’ 표에서 확인한다.
직전 동선은 ‘이 기록에 앞선 구간’이며 장소 도착을 뜻하지 않는다. `interpretation`과
`temporal_relation`을 함께 전달해 상대 저속을 정지로 바꾸지 않도록 서술 의미를 명시한다.

환경 예제는 기온과 풍속만 포함한다. 맑음·현장의 감각을 추론할 근거가 아니다.
자료에 명시된 `area_center/area_radius_m`은 공급자가 보장한 관측 적용 범위를 뜻하며,
수집기 연결 시 해당 보장이 가능한지 확인해야 한다. 전체 스키마는 `RegionalWeather`에 있다.

## 실행

backend에서 Python 3.12와 기존 uv 의존성을 사용한다. DB 없이 합성 입력으로 실행:

```powershell
uv run python tools/run_diary_slots.py --output evals/diary-slots/rules
uv run python tools/run_diary_slots.py --generate --env-file C:/path/to/.env --output evals/diary-slots/gemini
```

키는 `GEMINI_API_KEY` 또는 `GOOGLE_API_KEY`를 사용한다. 로컬 메모의 `gemini: ...` 형식도
읽을 수 있다. 파일에서 해당 키 한 줄만 읽으며 결과에 복사하지 않는다.
`preview.html`에 장면과 근거가 나오며 `input.json`, `policy.json`, `preview.json`도 저장된다.
합성 예제의 기록 3개 모두 세 파트가 들어가고 시작/종료 포함 5개 장면이 나온다.
동선은 합성 GPS를 실제 DEV 측정 커널에 통과시켜 만든다.

저장된 입력이나 조건을 바꿔 다시 실행:

```powershell
uv run python tools/run_diary_slots.py --input evals/diary-slots/rules/input.json --policy evals/diary-slots/rules/policy.json --generate --output evals/diary-slots/variant
```

CLI 입력은 로컬 실험용 `source: DiaryInput`, `points: WalkEvidencePoint[]`이다.
서버의 소유권 증명이 아니다. `points`가 없으면 동선 배경과 지점 보충을 수행하지 않는다.

실제 저장 산책은 앱 회원 인증 및 **두 플래그 모두 true**일 때만 접근 가능하다:
`DAENGS_WALK_DIARY_ENABLED`, `DAENGS_WALK_DIARY_SLOTS_PREVIEW_ENABLED`.
미리보기 전용 플래그는 기본 false이며 일반 일기 활성화만으로 이 경로가 열리지 않는다.
이 플래그가 별도 사용자 허용 목록이나 호출 빈도 제한을 구현한 것은 아니다.

```http
POST /app/walks/{walk_id}/diary-slots/preview
Content-Type: application/json

{"target_scene_count":3,"generate":true,"policy":{"space_slots":3,"environment_slots":1,"motion_slots":1,"total_slots":8}}
```

원본을 요청으로 받지 않고 저장소에서 읽는다. DB 읽기 잠금은 LLM 호출 전에 해제하며
생성 예약이나 발행 보드를 저장하지 않는다. `generate:false`는 조건 결과만 반환한다.
`context_pending`과 `excluded_backgrounds`로 저장 자료 준비 상태도 반환한다.
공간·환경에 자료가 없으면 파트를 비운다. LLM 실패 시 기본 보드가 그대로 반환된다.
12개 초과 작성 장면, 32KB 초과 입력은 `budget_exceeded`; 모든 원본 장면은 유지된다.

## 확인과 다음 연결

### 서비스 연결 1단계: 장면별 근거 고정

`prepare_board_slots(source, board, policy, route=...)`는 **이미 선정된 기본 보드**에
규칙을 적용한다. 장면을 다시 고르지 않고, 각 장면 ID 순서대로 `PartStamp`를 만든다.
`BoardSlotSnapshot`은 세션·입력 revision·보드 계획 revision·정책·스탬프를 묶으며,
다른 세션이나 입력 revision의 보드와 섞으면 거절한다. 자료가 없는 장면도 빈 스탬프로 남는다.

`assemble_saved_base_board`가 장면 조립 직후 이를 계산해 `PreparedSavedBaseBoard.slots`에
보관한다. 기존 `storyboard`의 기본 보드 생성 경로가 사용하는 준비 객체에 들어가므로,
서비스 writer가 이 근거를 그대로 받는다. 전체 스탬프는 현재 호출의 메모리 객체이며
장면 사이의 영속 슬롯은 아니다. 발행할 때 실제 인용된 근거만 아래 3단계의 영수증에 남긴다.

기본 보드의 생성 revision은 슬롯 정책과 결과 revision도 포함한다. 생성 중 그 내용이
바뀌면 기존 완료 검사의 대상이 되며, 이미 발행한 보드는 기존 보존 규칙을 따른다.
구형 `walk-diary-bundle-v1` 생성 revision과 미리보기 v1의 revision 계산은 유지한다.
전체 슬롯·선정/탈락 사유·실제값/기준값은 일반 서비스 응답이나 발행 JSON에 추가하지 않는다.

### 서비스 연결 2단계: 고정 근거로 서술

기본 보드 요청은 `write_board(source, PreparedSavedBaseBoard)`로 연결된다. 구형
`walk-diary-bundle-v1`은 기존 writer를 사용한다. 기본 보드에서는 이전의 제한된 배경 목록을
재선정하지 않고 `slots.stamps`의 근거와 해당 장면의 원문만 전달한다. 선정 사유·순위·
진단값은 모델 입력에도 포함하지 않는다.

공통 `write_slot_stamps`는 `SlotWritingResult`를 반환한다. 결과에는 슬롯 revision과
writer 버전, 장면별 배경 문장과 인용 ID만 있으며 원문·위치·장면을 변경할 필드는 없다.
입력 장면의 누락/추가/중복, 다른 장면의 근거 인용, 인용 ID 없는 배경 문장은 구조 검사에서 거절한다.
조립 시 다시 같은 스탬프에 묶였는지 확인하고 배경 문장을 원문 앞에 붙인다.
인용 ID가 있다는 사실만으로 문장의 사실성을 자동 판정하는 것은 아니다.

미리보기와 서비스는 같은 작성·인용·조립 함수를 사용한다. 일반 응답은 완성된 `title/body`
등 기존 공개 계약 그대로다. 서술 영수증은 서버 내부 저장에만 포함하며 공개 응답에는 없다.
판정 사유는 미리보기에서만 제공한다.
기본 보드의 생성 revision에는 새 writer의 프롬프트·모델·예산 버전이 포함되며, 구형 v1의
버전 계산은 유지한다. 기존 발행 일기를 자동으로 다시 쓰지 않는다.

외부 호출은 기존 예약 commit 이후 한 번만 한다. 근거가 없으면 호출하지 않는다.
12개 작성 장면/UTF-8 입력 32KB/응답 64KB 상한을 초과하거나 응답이 잘못되면 기본 보드를
유지한다. writer 내부 상한은 15초지만, 서비스의 `preparation_budget_ms`가 있으면 기존
요청 시작 시각 기준의 마감이 우선한다. #443 병합 이후 요청 상한은 20초이며 기존 10초
요청도 계속 유효하다. writer 내부 상한 15초는 그대로다. 시간 초과·취소 뒤 늦은 응답은
기존 완료 경계를 통과할 수 없다. 예산을 생략한 기존 클라이언트의 15초 writer 상한도 유지한다.

`observed_slow`는 ‘다른 구간보다 이동 속도가 느렸다’처럼 표현하도록 지침을 보완했다.
[서비스 writer 실제 실행 기록](../../backend/evals/diary_slots/service-writer-v1.json):
같은 합성 산책의 첫 호출은 10초 마감을 넘었고, 두 번째 호출은 **6.203초**에 성공했다.
이 두 호출은 #443 반영 전의 10초 조건으로 실행한 기록이다.
세 기록 모두 세 파트를 입력받았으며, 첫 두 기록은 공간·환경·동선을, 세 번째는 환경·직전
동선을 인용했다. 두 저속 기록은 이번 출력에서 ‘머물렀다’로 바뀌지 않았다. 이는 단일
입력의 두 번 실행 결과이며 지연 안정성이나 의미 오류 해결을 보장하는 수치는 아니다.

직접 영향 테스트는 `uv run pytest tests/walk/diary/test_diary_slots.py tests/walk/diary/test_diary_slot_claims.py tests/walk/diary/test_diary_slots_api.py -q`.

판정하지 않는다. 실제 출력과 근거는 [v2 실행 기록](../../backend/evals/diary_slots/review-fixes-v2.json)에 남긴다.

### 서비스 연결 3단계: 발행 당시 인용 근거 보관

`walk-diary-board-storage-v2`는 기존 `walk_storyboards.bundle` JSONB 안에 완성 보드와
`writing_receipt`를 함께 저장한다. 테이블·컬럼은 추가하지 않는다. 영수증에는 생성·입력·
계획·슬롯 revision, 당시 슬롯 정책 값, writer의 프롬프트 해시·모델·예산 버전이 들어간다.
장면별로 원문 해시, 추가한 배경 문장, **실제 인용한 근거의 ID·파트·역할·사실·출처 ID/버전**을
남긴다. 동일 주장으로 묶인 출처는 모두 유지한다. 인용하지 않은 후보와 순위·탈락 사유는 저장하지 않는다.

저장 시 고정 스탬프와 작성 결과로 보드를 다시 조립해 일치하는지 확인한다. 재조회 시에는
저장된 해시·세대·장면 순서와 `배경 문장 + 원문`의 결합을 검사한다. 현재 슬롯 정책이나
writer 설정으로 과거 자료를 다시 선정하지 않는다. 배경 원자료가 없어지거나 새 자료가
수집돼도 당시 인용 사실을 보존한다. 원문 편집은 기존 `source_revision` 비교로 stale이 된다.
체크섬은 저장값의 일관성 검사이며 문장 의미의 사실성 판정이나 전자서명이 아니다.

문장과 영수증은 기존 완료 검사 아래 JSONB 한 값으로 확정한다. 중복 요청은 같은 저장값을
읽으며 늦은 writer가 새 세대의 문장이나 근거를 덮지 못한다. 마감 예약에도 인용이 빈 기본
보드 영수증이 들어가고, 만료 시 예약 당시의 값을 그대로 발행한다. 이전 storage-v1과 그
형식의 마감 예약도 읽되 영수증을 사후 생성하지 않는다. 공개 API 형식은 계속 board-v1이다.
이전 서버 버전은 storage-v2를 읽지 못하므로 롤백할 때 이 읽기 호환을 유지해야 한다.

`test_diary_board_receipt.py`는 실제 인용만 보관하는지, 과거 버전 보존·훼손·다른 세대 결합
거절·구형 저장 호환을 확인한다. `test_diary_board_db.py`는 별도 PostgreSQL 연결로
저장/재조회, 중복 요청, 마감 복구, 원문 수정 후 새 세대와 늦은 writer의 경합을 확인한다.

### 서비스 연결 4단계: 실제 기온 관측

기존 `environment.weather` context job이 `lookup_walk_weather`를 통해 Life의 과거 조회를
실행한다. `DAENGS_REALTIME_URL`이 있으면 기존 HTTP 경계, 없으면 기존 로컬 Life 경계를
사용한다. DB 세션을 닫은 뒤 최대 15초 안에 조회하며 실패는 기존 3회 시도 규칙을 따른다.
일기 생성 요청이나 GET에서 새 날씨 호출을 하지 않는다.

`kma-grid-temperature-v1`에는 요청한 기록 시각·좌표, 응답 격자, 관측 시각, 공급자 기준 시각,
조회 시각, 섭씨 기온과 출처를 저장한다. Life 경계에서 **요청 좌표를 변환한 격자 = 응답 격자
= 기온 원자의 격자**인지 확인한다. 초단기실황 기온 하나와 섭씨 단위, 성공 출처만 허용하며
예보·다른 시각의 응답·중복 기온 원자는 쓰지 않는다. 기존 finalize용 환경 값은 그대로다.

[기상청 자료 설명](https://data.kma.go.kr/data/rmt/rmtList.do?code=400&pgmNo=570&tabNo=2)에 따르면
초단기실황은 5km 격자의 대표 AWS 관측값이다. 현장 체감이나 사용자의 직접 측정으로 해석하지
않는다. 실험용 원형 반경·`valid_until`을 공급자가 보장한 것으로 새로 만들지 않는다.
슬롯은 저장 자료가 **조회한 바로 그 기록/좌표**에 묶였는지 확인하고, 관측 시각이 기록보다
앞서면서 `weather_max_age_s` 이내일 때 사용한다. 기본 7200초는 **우리의 서술 허용 정책**이며
기온이 그동안 유지됐다는 뜻이 아니다. 0~7200초에서 조정하며 실제값/기준값은 미리보기에 남긴다.

writer에는 `grid_temperature_observation` 역할과 관측 시각·나이·해석 정보를 전달한다.
기온이 인용되면 기존 storage-v2 영수증에도 그대로 남는다. 자료 없음·부정확한 위치·미래
기록·허용 나이를 넘은 관측은 환경 슬롯을 비운다. 값이 없다고 0도나 현재 날씨로 대체하지 않는다.

현재 자동 수집 대상은 기존 **행동·글 기록(walk_entry)** 이다. v2는 확정된 핀 좌표를 사용한다.
사진 전용·경로 보충·시작/종료 장면의 별도 기온 수집은 추가하지 않았다. 이전에 공급자 미연결로
완료된 job을 자동 재수집하지 않으며, 새 기록/revision의 큐부터 연결된다. 늦은 수집 결과는
이미 발행한 일기를 바꾸지 않는다.

운영에서는 기존 context worker/Beat와 `DAENGS_WALK_ENTRY_CONTEXT_ENABLED`가 필요하다.
로컬 Life의 키 이름은 **`DATA_GO_KR_KEY`**이며 기상청 단기예보 조회서비스의 활용 권한이
필요하다. 공간 수집용 `DAENGS_DATA_GO_KR_SERVICE_KEY`와 별도 설정이다. 원격 분기는 해당
Life 서비스의 기존 키와 캐시 예산을 사용한다. 새 SQL·환경 변수 이름·의존성은 없다.

`SERVICE_KEY_IS_NOT_REGISTERED_ERROR`를 확인했다. 실제 기온 확보와 그 기온을 사용한 Gemini
호출은 아직 확인하지 못했으며, 실측 성공으로 간주하지 않는다.
