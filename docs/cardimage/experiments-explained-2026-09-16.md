# 2026-09-16 FLUX.2-klein-4B 실험 읽는 법 (#557)

결과 숫자만 보면 무슨 말인지 모르는 표가 많아서, **용어와 실험 설계를 먼저 풀어 쓴 문서**다.
잰 값 자체는 `compare-2026-09-16-klein-e1.md`(E1) 와 `compare-2026-09-16-klein-e2-e3.md`(E2·E3) 에 있고, 여기서는 그것을 해석한다.

## 0. 한 문장 요약

FLUX.2-klein-4B 로 도감 카드를 만들 때 **틀에 적힌 글씨가 가끔 깨지는 문제**를 고치려고 세 가지를 바꿔 봤는데 전부 실패했고,
대신 **깨짐이 무엇으로 정해지는지**를 알아냈다 — 사진이 아니라 **틀 · seed · 생성 크기**다. 그래서 고칠 곳은 프롬프트가 아니라 **seed 를 고르는 방식**이다.

## 1. 카드가 만들어지는 과정 (용어의 바탕)

1. **틀(template)**: 달마다 하나씩 있는 완성된 카드 그림. 강아지(푸들)와 배경, 그리고 **글씨가 이미 그려져 있다** — 아래 패널의 `PETAL PAUSE`, `One petal. Perfect timing.`, `SPRING`, `920`, `Bloomed right on schedule.` 같은 것들.
2. **사진**: 사용자의 강아지 사진 한 장.
3. **모델**: 틀과 사진을 같이 주고 "틀의 강아지만 이 사진의 강아지로 바꾸고 **나머지는 그대로 두라**"고 시킨다. 여기서 모델이 그림 전체를 다시 그리기 때문에, 건드리지 말라고 한 글씨까지 조금씩 다시 그려져 **깨진다**.
4. **제목만 따로**: 맨 위 검은 제목판(`BLOSSOM MOMO`)은 AI 가 아니라 코드(Pillow)가 나중에 얹는다. 그래서 제목은 절대 안 깨진다. 깨지는 것은 **틀에 구워진 나머지 글씨**다.

> 즉 "글씨 깨짐"은 모델이 글자를 잘못 쓰는 문제가 아니라, **원래 있던 글자를 그대로 복사하지 못하는 문제**다.

## 2. E1 의 네 조건 — base / panel / 2048 / both

E1 은 "글씨를 덜 깨지게 하려면?"을 시험했다. 격자 이미지의 열 이름이 이 넷이다.

| 이름 | 한글 | 무엇을 바꿨나 | 왜 해 봤나 |
| --- | --- | --- | --- |
| **base** | 기준 | 아무것도 안 바꾼 지금 상태. 생성 크기 1024×1632, 프롬프트도 그대로 | 비교 기준. 09-15 에 만든 카드를 그대로 씀(새로 안 만듦) |
| **panel** | 문구 | 프롬프트에 **아래 패널 글자를 그대로 적어 줌** — `keep the text "PETAL PAUSE", "One petal. Perfect timing." … letter for letter` | 모델이 무슨 글자인지 알면 똑같이 그릴 것이라는 기대 |
| **2048** | 해상도 | 그림을 **1280×2048 로 더 크게** 생성(받은 뒤 카드 크기로 줄임). 프롬프트는 기준과 같음 | 작게 그리면 글자가 뭉개지니, 크게 그리면 획이 살아날 것이라는 기대 |
| **both** | 둘 다 | 문구 명시 + 1280×2048 | 두 방법이 서로 도울 수 있으니 |

### 결과 (사진 3장 × 4월·9월, seed 는 1 로 고정)

| 조건 | 4월 카드 | 9월 카드 | 판정 |
| --- | --- | --- | --- |
| base | 제목 줄이 `PETL PPAUSE` 로 깨짐(3장 전부) | 전부 깨끗(3장) | — |
| panel | `PE'AL PAUSE` + 맨 아래 줄이 `on scchhredeb.` 로 뭉개짐 | `SONPPYEON`, `surprive` | **더 나빠짐** |
| 2048 | 제목 줄은 정상, 대신 작은 글씨가 `Pérfect`·`Blcomed` | `SWEEꟼ`, `A warn Chuseok` | 자리만 옮김 + 40% 느림 |
| both | 제목 정상, 맨 아래 `cn sccheduie` | `SWWEEP`, `srack` | 자리만 옮김 |

**해석**
- **panel 이 나빠진 이유(추정):** 프롬프트에 글자를 적으면 모델이 그 글자를 "새로 쓰는" 작업으로 받아들인다. 복사가 아니라 작문이 되니 더 틀린다.
- **2048 이 안 통한 이유(추정):** 크기를 바꾸면 모델 내부에서 그림을 다루는 격자가 통째로 달라진다. 그래서 깨지는 자리가 이동할 뿐, 깨지는 양은 비슷하다.

## 3. 가장 중요한 발견 — 깨짐은 사진이 아니라 seed 가 정한다

### seed 가 뭔가

모델은 **무작위 잡음에서 시작해** 그림을 만든다. 그 잡음을 정하는 숫자가 **seed** 다.
같은 입력 + 같은 seed → **항상 똑같은 그림**. 실제로 이번에 이미지를 새로 빌드한 뒤 만든 카드가 09-15 카드와 픽셀까지 같았다(제목판 글자만 다름).

### 관찰

같은 조건에서 **사진 3장이 같은 글자를 같은 모양으로 깨뜨렸다.**
예를 들어 panel 조건 4월은 세 장 모두 맨 아래 줄이 `scchhredeb`, 2048 조건 9월은 세 장 모두 제목 끝 `P` 가 뒤집혔다.
E2 에서 seed 를 1~4 로 바꿔 보니 이렇게 갈렸다.

| seed | 4월 아래 패널 | 9월 아래 패널 |
| --- | --- | --- |
| 1 | `PETL PPAUSE` (깨짐) | 깨끗 |
| 2 | `Perrfect` (작은 오타) | `SWVEEP` |
| 3 | 깨끗 | `SIEEEP`, `Full rnoon` |
| 4 | 깨끗 | 깨끗 |

→ **글씨 품질은 (틀, seed, 생성 크기)의 함수**다. 사용자의 사진은 거의 영향이 없다.
→ 그래서 제품에서는 **달 틀마다 "글씨가 안 깨지는 seed" 목록을 미리 만들어 두고 그 안에서 뽑으면** 된다. 사용자마다 사진이 달라도 그 목록은 계속 유효하다.

## 4. E2 — "4장 뽑아 고르기" 가 되는가

### 두 방식

| 방식 | 뜻 | 결과 |
| --- | --- | --- |
| **순차(seq)** | 서비스를 4번 부른다. 한 번에 한 장씩, seed 를 1·2·3·4 로 | **된다.** 장당 약 16초 → 4장에 GPU 약 65초 |
| **한 번에(batch)** | 서비스를 1번 부르고 모델에게 4장을 동시에 그리게 한다(`count=4`) | **안 된다.** 2장부터 GPU 메모리 부족(CUDA OOM) |

GPU(L4)의 메모리 22GiB 중 대부분을 모델 자체가 차지해서, 두 장을 동시에 그릴 여유가 없다. 한 번에 뽑기는 더 큰 GPU 나 모델 경량화가 있어야 가능하다.
서비스에는 `count` 를 계약으로 남겨 뒀다(지금은 1 만 사용).

### 4장 중 몇 장이 쓸 만한가

기준: 제목·아래 패널 글씨 정상 + 사진 속 강아지와 닮음 + 목줄 같은 군더더기 없음.

| 사진 | 4월 | 9월 | 메모 |
| --- | --- | --- | --- |
| 정면(`_03`) | 1~2장 | 2장 | 가장 잘 나옴(닮음 4~5) |
| 옆 각도(`…335`) | 1장 | 1장 | 닮음 3~4 |
| 엎드린 옆모습(`_08`) | 0장 | 0장 | 4월은 4장 모두 **틀의 푸들 그대로** — 교체 자체가 실패 |

또 4장끼리 차이가 **작다**. 포즈·배경은 틀이 고정하니 털·귀·표정 정도만 달라진다. "고르는 재미"로 개인화를 기대하기는 약하고,
개인화는 과일·채소 카드에서 포즈·소품에 자유도를 주는 쪽이 실제 손잡이다.

## 5. E3 — 첫 요청이 느린 문제(콜드 스타트)

서비스는 평소 0대로 내려가 있고, 요청이 오면 인스턴스를 띄워 **15GB짜리 모델을 버킷에서 읽어 GPU 에 올린다.** 이게 6~7분이다.

| 설정 | 모델 로드 | 판정 |
| --- | --- | --- |
| 기본 | 340.7 / 374.9 / 403.1초 (세 번) | 기준 |
| `enable-buffered-read=true` (미리 읽어 두기) | 735.6초 | **2배 느림** — 탈락 |
| 파일 캐시를 메모리에 두기 | 잴 수 없음 | 컨테이너가 아예 못 떴다. 설정 원인 미확정이라 추측으로 다시 배포하지 않았다 |

**덤으로 알게 된 것:** `gcloud run deploy`/`update` 로 새 버전을 올리면 요청이 없어도 인스턴스가 떠서 모델을 올린다.
즉 **설정만 바꿔 보는 실험도 배포할 때마다 L4 약 7분 + 유휴 10분이 과금된다.**

## 6. 검수 점수를 왜 그대로 믿지 않았나

카드마다 Gemini 검수가 세 가지를 매긴다.
- `likeness` 1~5: 사진 속 강아지와 얼마나 닮았나
- `text_ok`: 글자가 멀쩡한가
- `avatar_ok`: 왼쪽 위 동그란 얼굴이 바뀌었나

그런데 이번에도 헛다리를 짚었다. 예를 들어 `'SWEEP' instead of 'SWEEP'`(같은 단어), 정상 카드에 "오타 있음" 판정 같은 것들이다.
그래서 **판정은 카드의 아래 패널을 원본 크기로 잘라 눈으로** 했고, 검수 점수는 참고로만 썼다. 격자 이미지는 `cardimage/out/_cardgen/` 에 있다.

## 7. 그 밖의 숫자 읽는 법

| 이름 | 뜻 |
| --- | --- |
| `service.seconds` | 서비스가 그림 한 장을 만든 시간(GPU). 1024×1632 는 16초대, 1280×2048 은 23초대 |
| `seconds` | 도구 기준 한 장 전체 시간 — 위 시간 + 사진 전처리 + 제목 얹기 + 검수 호출 |
| `load_seconds` | 인스턴스가 켜진 뒤 모델을 GPU 에 올리는 데 걸린 시간 |
| `drift` | 결과 카드가 틀에서 얼마나 밀렸는지(테두리 위치 비교) |
| `plate_shift` | 제목판 위치가 얼마나 어긋났는지. 못 재면 비워 둔다 |
| `gen_size` | 모델에게 요청한 생성 크기(`1024x1632` 또는 `1280x2048`) |
| `panel_text` | 프롬프트에 아래 패널 문구를 적었는지(E1 의 panel·both 조건) |
| `batch` | 한 번에 몇 장을 요청했는지. 비어 있으면 한 장씩 |

## 8. 결론과 정할 것

**확인된 것**
1. 프롬프트에 글자를 적는 방식은 쓰지 않는다(더 깨진다).
2. 1280×2048 은 이득이 없다(깨짐이 옮겨 가고 40% 느리다).
3. 한 번에 여러 장은 L4 에서 불가능하다 — 4장이 필요하면 순차로 약 1분.
4. 콜드 스타트는 설정으로 못 줄였다 — 6~7분은 그대로다.

**사람이 정할 것**
1. 달 틀마다 **검증된 seed 목록**을 만들어 그 안에서 뽑을지(권함 — 가장 싸고 효과 확실).
2. 순차 4장(요청당 GPU 약 1분 + 콜드 스타트)을 제품에서 받아들일지, 아니면 장수를 줄일지.
3. 엎드린 옆모습 사진은 4장을 뽑아도 못 건지니, 업로드 화면에 **사진 안내 문구**를 넣는 것으로 갈지.
4. E3 메모리 캐시 설정을 한 번 더 파 볼지, 콜드 스타트는 운영(사용 시간대 최소 인스턴스)으로 풀지.
