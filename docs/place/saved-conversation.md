# 찜 범위 대화 검색 — 2단계

서버 [#448](https://github.com/SAJOYO/DAENGS_dev/pull/448), 앱
[#317](https://github.com/SAJOYO/DAENGS_APP/pull/317).
[기존 회원 찜 검색](bookmarks-api.md)과 [명시적 찜 명령](bookmark-commands.md)을 연결한다.
새 회원 저장소나 AI 전용 찜은 없다.

후속 [공통 검색 정책 1단계](search-policy.md)는 집합 변경과 이전 화면 복원을 분리한다.
아래는 #448의 구현·검증 기록이며, 새 계약과 평가 기준은 후속 문서를 따른다.

## 대상·공간·조건

| 축 | 의미 | 유지 규칙 |
| --- | --- | --- |
| 검색 대상 | 일반 장소 / 회원의 전체 찜 키 | “찜에서 찾아줘”는 대상만 변경 |
| 공간 범위 | 기준 위치와 반경 / 지역 제한 없음 | “멀어도 돼, 지역 제한 없이”일 때만 반경 해제 |
| 검색 조건 | 업종·이름·필수 조건·선호·선택 반려견 | 언급하지 않은 조건 보존 |

`required_true`는 `hard`의 필수 조건이다. false와 미확인은 통과하지 않는다.
`preferred_true`는 기존 `parking` 우선 정렬이며 false·미확인을 제외하지 않는다.
좌표가 없으면 주차 확인 장소를 먼저 두고 그룹 안의 저장 순서를 유지한다.
좌표가 있으면 기존 거리 구간 안에서 주차를 우선한다. 지역 제한 해제는 기준 좌표를
지우지 않으므로 기준이 있을 때 거리 표시는 계속 가능하다.

일반·찜 검색은 같은 조건 컴파일의 AND/OR 편집을 사용한다. 일반 검색의 최대 6업종과
찜의 전체 18업종은 각각의 계약으로 검증한다. 찜 API로 표현할 수 없는 업종 한정 선호는
전체 업종 선호로 확대하지 않고 명확화를 요청한다.

## 호출 경로

일반 검색의 대화 요청은 `saved_search: "v1"`으로 찜 검색 실행 능력을 협상한다.
모델의 `search_scope=bookmarks`를 검증한 서버는 `receipt.saved_search_filters`를 준비한다.
일반 검색의 필터·목록·탐색 이력은 그대로이며, 준비 응답은 찜 조회 완료를 주장하지 않는다.
앱이 기존 회원 `/app/places/bookmarks/search`를 호출해 성공한 뒤 찜 탭에 결과를 표시한다.

찜 탭에서는 현재 조건과 발화만 `POST /app/places/bookmarks/interpret`에 보낸다.
활성 회원을 확인하고 트랜잭션을 끝낸 뒤 Place의 `/internal/place/bookmarks/interpret`에
조건과 발화만 전달한다. 회원 식별자·인증 정보·저장 키는 해석 요청에 전달하지 않는다.
해석은 DB 쓰기·검색 실행 권한이 없으며 `search / clarify / explain / return_search`를 반환한다.
앱은 `search`의 조건으로 기존 회원 검색 API를 실행하고 실제 결과 수로 답한다.
해석의 좌표·반려견 변경이나 알 수 없는 실행 동작은 앱에서 거절한다.

별도 채팅 기억은 추가하지 않았다. 현재 찜 조건이 다음 발화의 단서다. 단순 피드백이나
모호한 요청은 현재 목록·조건을 변경하지 않는다. 조회 실패도 이전 결과를 유지한다.
“더 보여줘”에는 조건에 맞는 전체 찜을 이미 한 번에 조회한다는 범위를 설명한다.

## 앱 상태

처음 찜 탭에 들어갈 때만 일반 검색의 적용 조건을 이어받는다. 이후 탭 전환은 마지막
찜 조건을 유지한다. 필터 창의 **현재 검색 조건으로 찜 보기**는 명시적으로 다시 복사한다.
자연어로 일반 검색에서 “이 조건으로 찜에서”를 요청해도 그 시점의 조건을 가져간다.

같은 댕댕이 UI에 찜 범위·반경/지역 제한·업종·필수/선호 조건을 표시한다.
탭·필터·계정·저장 목록이 바뀌면 늦은 찜 검색 응답은 적용하지 않는다. 화면 조건은 조회
성공 후 반영하며, 찜 검색 때문에 일반 검색의 목록·입력 중 문장·지도 선택을 복원/변경하지 않는다.
단일 장소 저장 명령의 충돌 순서는 1단계 계약을 그대로 쓴다. 읽기 응답 순서와는 별개다.

## 확인과 남은 범위

고정 입력은 [saved-search-cases.json](../../backend/evals/place_conversation/saved-search-cases.json),
실제 관측은 [출력 평가](saved-conversation-evaluation.md)에 있다.

- 서버는 조건 컴파일·합성 사실의 필수/선호 판정·내부 HTTP·회원 인증·기존 대화 회귀의
  고유 78개 테스트를 통과했다. 최초 70개, 정렬 회귀 1개와 해석 HTTP 7개를 추가하고
  변경한 파일만 재검증했다. 전체 스위트는 실행하지 않았다. `uv run check`와 변경 Python
  19개 파일의 Ruff 검사/포맷 검사도 통과했다.
- 앱은 계정 경계, 탭 조건 보존, 늦은 해석/검색, 실패 시 보존, HTTP 계약과 실제 Compose 연결의
  고유 41개 테스트를 통과했다. 최초 대상 32개 후 새 연결·명확화·HTTP·화면 검증을 추가하고
  관련 클래스만 재실행했다. debug APK 빌드와 지도 SDK를 끈 390dp 화면·말풍선을 확인했다.
- DB 쿼리·마이그레이션·회원 쓰기를 변경하지 않았다. 실제 운영 DB/회원·기기 종단 검증은 별도다.
- 서버의 Place와 APP backend를 먼저 반영한 뒤 앱을 반영한다. 새 키·의존성은 없다.
- 찜 탭의 장소별 정보 질문·번호 지칭·자연어 해제/결과 제외는 이번 범위에서 실행하지 않고
  카드/하트 사용을 안내한다. 일반 검색의 기존 명시적 찜 명령은 유지한다.
- #448에서 남긴 집합 변경+조건 변경의 명확화는 [#451 공통 정책](search-policy.md)에서
  search_places와 화면 복원으로 분리한다.
- 피드백을 받은 뒤 상태를 소비하지 않는 사전 조회·제안과 “찜하고 다음” 조합 실행은 3단계다.
