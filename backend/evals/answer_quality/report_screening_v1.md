# 판정이 답을 가르는가 — 실측 (#314)

`#283` 이 판정을 Life 프롬프트까지 이었다. 이 리포트는 **그것이 답을 바꾸는지, 바꾼다면
좋은 쪽인지**를 잰 기록이다. 2026-09-07, dev `822428c` + #283 `950565e` 임시 머지(미푸시).

## 결론

**바꾼다. 그리고 좋은 쪽이다 — 다만 표본이 14건이고 게이트가 없다.**

| | 판정 없음 `off_t0` | 판정 있음 `on_t0` |
| --- | --- | --- |
| 자격을 단정하지 않은 답 (`usable`) | 12/14 (0.857) | **14/14 (1.000)** |
| 자격 단정 (`eligibility_claim=0`) | **2** | **0** |
| 갈래 선택 평균 (`usable` 안에서) | 1.083 | **1.500** |
| 갈래 분포 (0 / 1 / 2) | 5 / 1 / 8 | 1 / 5 / 8 |

**안전 쪽이 먼저다.** 판정을 넣으니 자격 단정이 2 → 0 이 됐다. 이것은 이 카드가 시작할 때
걱정하던 것의 **반대** 결과다 — 판정을 쥐여 주면 "이상 소견이 있으니 지원 대상입니다" 를
말하게 될까 봐 별도 루브릭까지 만들었는데, 실제로는 판정이 있는 쪽이 **덜** 단정했다.
프롬프트 블록의 본문이 "무엇이었다" 보다 "무엇을 하지 말라" 가 긴 것이 이유로 보인다(#283).

**갈래 선택은 0 → 1 구간에서 올랐다.** `branch_selected=2`(시점 조건 조항을 실제로 짚음)는
**양쪽 다 8건으로 같다.** 오른 것은 0(판정과 무관한 일반론) 5 → 1 이고, 그 넷이 1 로 옮겨
갔다. 즉 판정은 **이미 잘 답하던 것을 더 잘 답하게 한 것이 아니라, 아무 상관 없는 답을
하던 것을 덜 하게 했다.**

## 인과가 확정된 근거 — 대조쌍

같은 조건으로 두 번 돌린 대조쌍이 있다. 이것이 없으면 아래 숫자는 못 읽는다.

| 짝 | 답변 문장이 같은 건수 |
| --- | --- |
| **대조쌍** `off_t0` 대 `off_t0_ctl` (완전 동일 조건) | **14/14** |
| **실험쌍** `off_t0` 대 `on_t0` (판정만 다름) | **0/14** |

대조쌍이 완전 일치하므로 **노이즈 플로어가 0** 이고, 실험쌍의 차이는 전부 판정 때문이다.

⚠️ **이 대조쌍은 `--life-temperature 0` 이라서 성립한다.** 온도를 안 고정하고 돌린 첫
사이클에서는 **같은 프롬프트로도 답이 14/14 전부 달랐다.** `generate.answer` 의
`GenerateContentConfig` 에 temperature 가 없어 Gemini 기본값으로 돌기 때문이다. 그 상태의
"0/14 동일" 은 아무 뜻이 없었고, 온도를 고정한 지금의 "0/14 동일" 은 결정적이다 —
**같은 숫자가 한 번은 무의미, 한 번은 증거다.**

## 믿을 수 있는 만큼만 — 이 숫자의 한계 넷

1. **표본 14건.** 자격 단정 2 → 0 은 두 건이 움직인 것이다. 방향은 맞지만 크기는 못 말한다.
2. **앵커 게이트가 없다.** 이 루브릭에는 앵커가 아직 없어서(`anchor_gate: none` 이 판정
   파일 메타에 남는다), #277 의 게이트를 통과한 84건 점수와 **같은 신뢰도가 아니다.**
3. **판정 조합이 하나뿐이다** — `abnormal:3`. `normal` 이나 오래된 판정(`abnormal:200`)에서
   같은 방향인지는 안 쟀다. 면책 조항이 30일을 조건으로 걸므로 **경과일이 갈래를 가르는
   자리**이고, 거기를 안 건드린 것은 이 측정의 큰 구멍이다.
4. **판정기 변형이 하나다.** 일치율(A·B)을 안 쟀다.

### 판정 프롬프트를 v1 → v2 로 고친 뒤 숫자가 바뀌었다

v1 은 판정 없는 쪽에 `"(판정 기록 없음 — 이 답은 판정을 못 받은 쪽이다. ⓑ 는 0 이 정상이다.)"`
라고 적었다. **그것은 유도였다** — 판정 없는 쪽의 갈래 점수를 낮추라고 판정기에게 미리
일러 준 셈이라, off/on 차이가 배선 효과가 아니라 프롬프트 효과가 된다.

| 갈래 선택 평균 | v1 (유도 있음) | v2 (유도 제거) |
| --- | --- | --- |
| `off_t0` | 0.727 | **1.083** |
| `on_t0` | 1.500 | 1.500 |
| 차이 | 0.773 | **0.417** |

**차이가 절반 가까이 줄었다.** 위 결론은 v2 숫자로 쓴 것이고, v1 숫자는 쓰지 않는다.

## 재현

`#283` 이 dev 에 없으면 **`--screening` 이 멈춘다** (`require_screening_wiring`). 아래는
#283 을 얹은 뒤의 절차다.

```powershell
# backend/ 에서. rag 는 POSTGRES_* 를 읽는데 그 값이 backend/.env 에 없다 (아래 함정)
$env:POSTGRES_IP = "<서버>"; $env:POSTGRES_USER = "..."; $env:POSTGRES_PASSWORD = "..."
$env:POSTGRES_DB = "vectordb"; $env:POSTGRES_PORT = "5432"

uv run python -m tools.answer_quality.generate_questions --question-set screening `
    --out evals/answer_quality/questions_screening_v1.jsonl
foreach ($run in @(@("off_t0",@()), @("off_t0_ctl",@()), @("on_t0",@("--screening","abnormal:3")))) {
    uv run python -m tools.answer_quality.collect --flag on --adapters real `
        --label $run[0] --questions evals/answer_quality/questions_screening_v1.jsonl `
        --strata pet_insurance_skin --life-temperature 0 @($run[1])
}
uv run python -m tools.answer_quality.judge screening `
    --answers evals/answer_quality/answers_on_t0.jsonl `
    --questions evals/answer_quality/questions_screening_v1.jsonl
```

### ⚠️ 함정 — 개발 PC 에서 `--adapters real` 은 `POSTGRES_IP` 를 셸에 올려야 한다

첫 실행이 14건 전부 `ERROR` 로 끝났다. 원인은 라우터가 아니라 **Life 의 DB 연결
타임아웃**(`OperationalError`, 59초)이었다. `rag` 는 `POSTGRES_*` 를 읽는데 서버 주소는
`backend/.env` 의 `DAENGS_DB_HOST` 에만 있고, 루트 `.env` 에는 `POSTGRES_IP` 가 없어
localhost 로 붙는다.

**이 둘을 통일하지 말 것** — 루트 CLAUDE.md 가 막아 둔 자리다. 셸에 올리는 것이 맞다.
서버 쪽의 같은 종류 함정은 #299 가 적었다.

## 남은 것

- **경과일 축을 안 쟀다.** 면책 조항이 30일을 조건으로 거는데 `abnormal:3` 하나만 봤다.
  `abnormal:200`(면책 기간 밖) 을 같이 재야 "경과일이 갈래를 가른다" 는 코퍼스 조사의
  주장이 실제로 확인된다. **다음 사이클의 1순위.**
- 앵커를 만들어 이 루브릭에도 게이트를 건다. 그전까지 이 점수는 #277 것과 같은 축이 아니다.
- 판정기 변형 B 를 만들어 일치율을 잰다.
- 표본 14 → 문체당 3~4 건으로.
- `normal` 판정에서 답이 어떻게 달라지는지. "특이 소견 없음" 이 면책 이야기를 꺼내게 하면
  그것은 과잉이다.
