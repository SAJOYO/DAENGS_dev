## D-001
### 백엔드는 Python 3.12 로 고정

`requires-python = ">=3.12,<3.13"`.

3.14 가 이미 설치돼 있었지만 3.12 를 골랐습니다. 데이터/AI 쪽 패키지 생태계가
최신 버전을 따라오는 데 시간이 걸리고, 이 프로젝트는 pgvector·임베딩 관련 의존성이
늘어날 예정이라 wheel 이 확실히 준비된 버전이 안전합니다.

상한(`<3.13`)을 둔 이유는 uv 가 조용히 상위 버전을 골라 로컬과 컨테이너가
갈라지는 것을 막기 위해서입니다.

**바꾸려면**: `pyproject.toml` 과 `backend/.python-version` 을 함께 고치고
`uv lock` 을 다시 돌려야 합니다.

## D-002
### uv 기본 src 레이아웃(패키지 형태)을 그대로 사용

`backend/src/daengs_backend/` 구조. `[build-system]` 과 `[project.scripts]` 를 둡니다.

예전 uv 는 애플리케이션을 비패키지(루트에 `main.py` 하나)로 만들었지만,
현재 버전은 패키지 형태가 기본입니다. 한 번 평평한 구조로 바꿔봤다가 되돌렸습니다.

패키지 형태의 실질적 이득은 **실행 위치에 의존하지 않는다**는 점입니다.
`uv sync` 가 `src` 를 경로에 등록해 주므로 어느 디렉터리에서든
`daengs_backend.main` 으로 import 됩니다. 평평한 구조에서는 현재 작업 디렉터리에
의존해 `from src.config import ...` 가 되고, 컨테이너에서 깨지기 쉽습니다.

패키지 안의 폴더 구분(MVC 등)은 **아직 정하지 않았습니다.** 당분간 평평하게 둡니다.

## D-003
### uv 베이스 이미지를 직접 빌드 (`uv:1`)

`docker/uv/Dockerfile` — `python:3.12.13-slim` + uv 바이너리.

공식 `ghcr.io/astral-sh/uv:python3.12-bookworm-slim` 을 먼저 써 봤고 동작도 했지만,
그 이미지의 uv 가 0.9.30 으로 개발 PC(0.12.3)보다 낮았습니다.
**uv 버전이 다르면 `uv.lock` 형식이 어긋나 배포 때만 실패할 수 있습니다.**
지금은 우연히 호환됐을 뿐입니다.

설치 스크립트를 돌리는 대신 공식 스크래치 이미지에서 바이너리만
`COPY --from` 으로 가져와 버전을 정확히 고정했습니다.

| | 크기 |
| --- | --- |
| `python:3.12.13` | 1.62GB |
| `python:3.12.13-slim` | 179MB |
| `uv:1` | 253MB |

풀 이미지가 아니라 slim 을 쓴 이유는 현재 의존성이 전부 wheel 이라 컴파일러가
필요 없기 때문입니다. 소스 빌드가 필요한 패키지를 넣게 되면 그때 `build-essential`
을 추가하거나 binary wheel 쪽을 씁니다.

**바꾸려면**: Dockerfile 의 `ARG UV_VERSION` 을 올리고 태그도 `uv:2` 로 올립니다.

## D-004
### backend 컨테이너에 폴더가 아닌 파일별로 마운트

`./backend/pyproject.toml`, `uv.lock`, `README.md`, `src` 를 각각 마운트합니다.

`./backend` 를 통째로 마운트하면 **호스트의 `backend/.venv` 가 함께 들어갑니다.**
그 안에는 Windows 용 `Scripts/python.exe` 가 있어 리눅스 컨테이너에서 실행되지
않습니다. `uv run` 이 그것을 쓰려다 깨지거나, 조용히 다시 만들면서 호스트 쪽
venv 를 망가뜨립니다.

두 가지를 놓고 골랐습니다.

- **A. 폴더째 마운트 + `/app/.venv` 에 익명 볼륨을 씌워 가리기** — 설정은 짧지만
  그 한 줄의 의미를 모르면 지웠다가 다시 깨집니다.
- **B. 파일별 마운트** — 줄 수는 늘지만 **무엇이 컨테이너로 들어가는지 목록만 봐도
  드러납니다.**

오래 유지할 설정이라 B 를 택했습니다.

여기에 더해 venv 자체를 마운트 경로 밖(`UV_PROJECT_ENVIRONMENT=/opt/venv`)으로
빼고 uv 캐시와 함께 볼륨에 두었습니다. 콜드 기동 4초, 웜 재시작 2초입니다.

**주의**: `pyproject.toml` 의 `readme = "README.md"` 때문에 `README.md` 도
마운트해야 합니다. 없으면 `uv sync` 가 패키지 빌드 단계에서 실패합니다.

## D-005
### backend 를 nginx 뒤에 두고 포트를 열지 않음

```
daengs.~     :80   → nginx → host.docker.internal:3000  (PM2 Next, 호스트)
daengback.~  :8000 → nginx → backend:8000               (FastAPI, 컨테이너)
```

backend 컨테이너를 8000 에 직접 노출하는 쪽이 지금 당장은 작업이 적습니다.
그래도 nginx 를 앞에 둔 이유는 두 가지입니다.

1. **HTTPS 를 붙일 자리가 한 곳으로 모입니다.** 지금은 http 라 체감이 없지만,
   인증서를 애플리케이션 안에서 처리하게 하면 훨씬 번거로워집니다.
2. **재현성.** 최종 목표가 "소스 받아서 `docker compose up -d` 하나"인데,
   직접 노출하면 라우팅이 compose 의 `ports:` 와 nginx 설정 두 군데로 흩어집니다.

포트포워딩(`daengback.~` → 8000)은 그대로 두고 nginx 가 8000 을 받게 했습니다.
외부 설정을 바꾸지 않아도 됩니다.

**CORS 는 이 결정과 무관하게 필요합니다.** 브라우저에게 `daengs.~` 와
`daengback.~` 는 다른 오리진이라, 앞에 무엇이 있든 상관없습니다.
`DAENGS_CORS_ORIGINS` 에 넣는 값은 **부르는 쪽인 프론트 도메인**입니다.

**남은 것**: 프론트가 아직 PM2 로 호스트에서 돕니다. 이것까지 컨테이너로 옮기면
`host.docker.internal` 이 사라지고 전부 compose 안으로 들어옵니다.

## D-006
### 배포도 개발 모드(reload)로 운영

컨테이너 명령이 `uv sync --frozen && exec uv run dev` 입니다.

학습·개발용 프로젝트라 코드 반영 속도를 우선했습니다. 배포 시 `git checkout` 이
마운트된 파일을 갱신하면 uvicorn 이 알아서 리로드하므로, 컨테이너를 재시작하지
않아도 새 코드가 뜹니다.

**대가**: `uv sync` 는 컨테이너가 뜰 때만 돕니다. 의존성을 바꾼 커밋을 배포하면
소스만 반영되고 패키지는 없어서 `ModuleNotFoundError` 가 납니다.
워크플로우를 건드리지 않기로 해서, **의존성을 바꾼 날만 서버에서 수동으로**
`docker compose restart backend` 를 실행합니다(웜 2초).

리로드 감시는 `src` 로 범위를 좁혔습니다. Windows 바인드 마운트에서는
inotify 가 전달되지 않아 폴링(`WATCHFILES_FORCE_POLLING`)을 써야 하는데,
폴링은 대상이 넓으면 CPU 를 계속 씁니다.

**바꿔야 할 때**: 실제 사용자 트래픽을 받게 되면 `uv run run` + 워커 여러 개로
가야 합니다. 그때는 소스를 마운트가 아니라 `COPY` 로 굽는 이미지가 필요합니다.

## D-007
### Postgres 5432 를 LAN 에 개방

`"${POSTGRES_PORT:-5432}:5432"` — `0.0.0.0` 바인딩입니다.

같은 네트워크의 팀원이 각자 PC 에서 DB 에 붙어야 해서 의도적으로 열어 둡니다.
`127.0.0.1` 로 묶으면 이 PC 안에서만 접속됩니다.

**조건**: `POSTGRES_PASSWORD` 를 `.env` 에서 반드시 기본값이 아닌 값으로
지정해야 합니다. 기본값 `postgres` 를 그대로 두면 네트워크의 누구나 들어옵니다.

pgAdmin(`tools` 프로파일)은 `PGADMIN_CONFIG_SERVER_MODE: "False"` 라
로그인이 없습니다. 띄워 두는 동안에는 인증 없는 DB 관리 콘솔이 열려 있는 셈이니
필요할 때만 켜세요.

## D-008
### DB collation 을 `C` 로 유지

`POSTGRES_INITDB_ARGS: "--encoding=UTF-8 --locale=C"`.

처음엔 한글 정렬이 깨질 거라 생각했지만, 실제로 확인해 보니 아니었습니다.

```
C collation : Zebra < apple < 가방 < 나무 < 하늘 < 힘
ICU (ko-KR) : 가방 < 나무 < 하늘 < 힘 < apple < Zebra
```

**한글끼리의 순서는 C 에서도 정확합니다.** 현대 한글 완성형(가~힣)이 유니코드
코드포인트 순서와 가나다 순서가 일치하도록 배치돼 있기 때문입니다.

실제 차이는 영문 대소문자 순서, 한글·영문 혼합 순서, NFD(자모 분리) 문자열입니다.
검색·저장·pgvector 동작에는 영향이 없고, `LIKE 'foo%'` 인덱스는 오히려 C 가
유리합니다.

정렬이 필요한 곳에서는 쿼리나 컬럼 단위로 붙이면 됩니다.

```sql
SELECT ... ORDER BY name COLLATE "ko-KR-x-icu";
```

**바꾸려면**: initdb 인자는 최초 생성 때만 반영되므로 볼륨을 지우고 다시
만들어야 합니다. 데이터가 쌓인 뒤에는 번거로우니, 필요해지면 컬럼 단위로
붙이는 쪽을 권합니다.

## D-009
### 환경 변수 파일을 compose 용과 앱 용으로 분리

| 파일 | 읽는 주체 | 내용 |
| --- | --- | --- |
| `.env` | docker compose | `POSTGRES_*`, `PGADMIN_*` |
| `backend/.env` | FastAPI 앱 | `DAENGS_*` |

한 파일에 몰아두면 "이 값을 누가 읽는지"가 흐려집니다. 특히 DB 접속 정보는
컨테이너를 만드는 쪽 설정이지 앱 설정이 아닙니다.

`backend/.env` 의 경로는 `config.py` 가 자기 위치 기준으로 잡습니다.
상대 경로(`env_file=".env"`)로 두면 실행 디렉터리에 따라 파일을 못 읽습니다.

compose 에서는 파일 마운트 대신 `env_file` + `required: false` 를 씁니다.
파일 마운트로 두면 **파일이 없을 때 도커가 그 자리에 폴더를 만들어 버립니다.**

**서버 준비**: `.env` 는 gitignore 대상이라 체크아웃에 없습니다. 러너 작업 폴더에
두 파일을 한 번 만들어 두세요. `checkout` 의 `clean: false` 덕분에 이후 배포에서
지워지지 않습니다.

## D-010
### pg_trgm 은 지금 넣지 않음

초기 스크립트에서 `CREATE EXTENSION pg_trgm` 을 뺐습니다.

현재 스키마는 순수 벡터 검색입니다. `pg_trgm`(문자 3-gram 유사도)을 쓰는 곳이
없고, 확장만 깔아 둔다고 성능이 달라지지도 않습니다.

**필요해지는 시점**: 하이브리드 검색을 붙일 때입니다. 벡터 검색만으로는
고유명사·숫자·정확한 표현에 취약해서 키워드 검색 점수와 합쳐야 합니다.
PostgreSQL 내장 full-text search 에는 **한국어 형태소 분석기가 없어서**
`to_tsvector('simple', ...)` 는 공백 단위로만 쪼갭니다("훈련을" ≠ "훈련").
그래서 형태소 분석 없이도 동작하는 `pg_trgm` 이 현실적인 선택지가 됩니다.

그때 필요한 것은 두 줄입니다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_documents_content_trgm ON documents USING gin (content gin_trgm_ops);
```

인덱스는 `db/indexes.sql` 에 넣습니다(적재 후 생성 원칙).
**주의**: `db/init/` 은 볼륨이 비어 있을 때만 실행되므로, 이미 만들어진 DB 에는
psql 로 직접 실행해야 합니다.

## D-011
### 백엔드 DB 층은 SQLAlchemy 2.0 async, 패키지 안은 MVC2 계층

`sqlalchemy[asyncio]` + `asyncpg`. `src/daengs_backend/` 안을
`core / models / schemas / repositories / services / routers` 로 나눕니다.

D-002 에서 "폴더 구분은 아직 정하지 않았다"고 미뤄 둔 것을, 관리자 인증을 붙이면서
정했습니다.

**드라이버·ORM.** 생 SQL(psycopg3)도 후보였습니다. 지금 스키마 원본이 손으로 쓴
`db/init/*.sql` 이라 그쪽이 결이 맞는 면도 있습니다. 그래도 ORM 을 고른 이유는
**Repository 계층을 두기로 했기 때문**입니다. 생 SQL 로 Repository 를 만들면
결국 손으로 ORM 을 다시 쓰게 됩니다. 인증만 해도 테이블 서넛이 서로 엮입니다.

asyncpg 를 고른 것은 pgvector 파이썬 패키지가 asyncpg 를 지원해서,
나중에 벡터 검색을 ORM 으로 붙일 때 드라이버를 갈아엎지 않아도 되기 때문입니다.

**계층 구분.** 후보는 셋이었습니다.

| | |
| --- | --- |
| 계층 우선 (MVC2) | 폴더가 `routers/ services/ ...`. 어디에 넣을지 고민이 없고 자바 배경이면 바로 읽힘 |
| 기능 우선 | 폴더가 `auth/ documents/ ...`. 기능 하나가 한 폴더라 팀원끼리 안 부딪힘 |
| 헥사고날 | 도메인이 프레임워크를 모름. 이 규모에선 보일러플레이트가 로직보다 많아짐 |

**계층 우선을 골랐습니다.** 팀에 자바 배경이 있어 이해 비용이 가장 낮습니다.
기능 우선이 팀 작업에는 유리하지만, 지금 기능이 하나뿐이라 이득이 안 보입니다.

**되돌리기 쉽습니다.** 계층 우선 → 기능 우선은 파일 이동과 import 경로 수정이
전부입니다. 다만 시간이 지나면 비싸지는 건 이동이 아니라 **얽힘**입니다.
계층 우선에서는 `services/a.py` 가 `repositories/b.py` 를 불러도 경계를 넘었다고
말해 주는 것이 없어서, 쌓이고 나면 옮기는 게 아니라 푸는 작업이 됩니다.
파일 20~30개가 넘어가면 다시 보세요.

**Alembic 은 넣지 않습니다.** 스키마 원본은 계속 `db/init/*.sql` 이고, `models/` 는
그것을 따라갑니다. 둘이 어긋날 수 있다는 게 이 선택의 대가입니다.
마이그레이션 도구는 **여러 명이 스키마를 각자 고치기 시작할 때** 값이 생깁니다.
그때 `documents` 를 초기 리비전으로 잡고 도입하면 됩니다.
`Base.metadata.create_all` 은 부르지 마세요 — SQL 파일과 원본이 둘로 갈립니다.

**접속 정보.** (D-013 에서 URL 한 줄 → 조각으로 바뀌었습니다. 아래는 당시 기록입니다.)
`backend/.env` 의 `DAENGS_DATABASE_URL` 은 **로컬에서 `uv run dev`**
로 띄울 때 쓰는 값입니다. 컨테이너 안에서는 `localhost` 가 컨테이너 자신이라
닿지 않으므로, compose 의 `environment:` 가 같은 이름으로 덮어씁니다
(`environment` 가 `env_file` 보다 우선). 컨테이너 쪽 값은 최상단 `.env` 의
`POSTGRES_*` 로 조립하므로 **접속 정보가 두 군데로 갈리지 않습니다** (D-009).

**`/health` 는 DB 가 죽으면 503 입니다.** 200 에 `db: "down"` 만 넣으면 모니터링이
실패를 못 잡습니다. compose 의 backend 에는 healthcheck 를 걸지 않았으니
이 503 으로 컨테이너가 재시작되지는 않습니다.
연결 실패는 `SQLAlchemyError` 로 감싸이지 않고 asyncpg 예외나 `OSError` 가
그대로 올라오므로, 상태 확인에서는 예외를 넓게 잡아야 합니다.

## D-012
### 개인정보는 앱단 AES-256-GCM, 키는 용도별로 셋

`core/crypto.py` (AES-256-GCM · HMAC blind index) 와 `core/password.py` (Argon2id).
키는 `DAENGS_AES_KEY` · `DAENGS_BLIND_INDEX_KEY` · `DAENGS_JWE_KEY` 셋으로 나눠
`backend/.env` 에서 받습니다.

| 데이터 | 처리 | 왜 |
| --- | --- | --- |
| 관리자 비밀번호 | Argon2id (단방향) | 되꺼낼 일이 없고, 되꺼내지면 안 됩니다 |
| 앱 회원 이메일 | AES-GCM + blind index | 원문이 필요하고, 중복가입도 막아야 합니다 |
| 전화번호 · 이름 | AES-GCM | 원문이 필요하고, 이 값으로 조회하지는 않습니다 |
| `kakao_id` | 평문 | 로그인 경로의 조회 키입니다 |

**비밀번호에 AES 를 쓰지 않습니다.** 복호화가 되는 순간 키를 쥔 사람이 전원의
비밀번호를 읽습니다. 반대로 AES 는 "나중에 원문을 다시 꺼내 봐야 하는" 값에만 씁니다.
해시 라이브러리는 `argon2-cffi` 를 직접 씁니다 — passlib 은 관리가 멈춰 최신 bcrypt 와
깨집니다.

**DB 가 아니라 앱에서 암호화합니다.** pgcrypto 로 하면 키가 SQL 문에 들어가서
`pg_stat_statements` 와 로그에 남고, DB 에 붙을 수 있는 사람이 곧 복호화할 수 있는
사람이 됩니다. 지금 DB 는 LAN 에 열려 있고(D-007) pgAdmin 은 로그인이 없어서,
그 둘이 갈라져 있는 편이 낫습니다. 대가는 **DB 안에서는 그 컬럼으로 검색·정렬이
안 된다**는 것입니다. 그래서 조회가 필요한 이메일에만 blind index 를 답니다.

**blind index 는 단순 SHA-256 이 아니라 HMAC 입니다.** 이메일은 후보가 뻔해서
키 없는 해시는 사전공격으로 다 맞힐 수 있습니다. 소문자로 정규화한 뒤 해시하며
(`A@x.com` 과 `a@x.com` 이 갈리면 중복가입을 못 막습니다), hex 64자라 `CHAR(64)` 에
그대로 들어갑니다.

**암호문 맨 앞에 키 버전 1바이트를 붙입니다.** `[버전 1B][nonce 12B][암호문+태그]`.
지금은 1 하나뿐이라 아무 값도 아니지만, 키를 갈 때 없으면 전수 재암호화 도중에
어느 키로 암호화된 행인지 알 방법이 없습니다. 나중에는 못 넣습니다.

**키를 셋으로 나눈 이유는 잃었을 때의 결과가 전부 다르기 때문입니다.**

| 키 | 잃으면 | 복구 |
| --- | --- | --- |
| JWE | 전원 로그아웃 | 새로 만들면 끝 |
| blind index | 해시 조회 불가 | AES 키가 살아 있으면 전부 재계산 |
| AES | 암호문이 영구히 안 열림 | 아래 |

**AES 키만 진짜 조심하면 됩니다.** 다만 이 설계에서는 잃어도 서비스가 죽지 않습니다 —
로그인 경로에 암호화 컬럼이 없고(`kakao_id` 는 평문), 개인정보 원본이 카카오에 있어
회원이 다시 로그인하면 채워집니다. 복구가 안 되는 것은 탈퇴자와 **앱에서 직접
입력받은 값**(반려견 정보 등 — 유일본)입니다.

키는 `SecretStr` 로 받아 로그·예외에 값이 찍히지 않게 하고, 기본값은 두지 않습니다.
개발용 기본값을 하나 박아 두면 그게 그대로 서버에 올라갑니다. **키가 없으면 앱이
뜨지 않는 것이 맞습니다.**

**되돌리기**: 암호화를 걷어내는 것은 컬럼 전수 복호화라 데이터가 쌓이기 전이 쌉니다.
키 교체는 버전 바이트 덕에 언제든 되지만, 재암호화가 끝날 때까지 옛 키를 `_KEYS` 에
남겨 둬야 합니다.

## D-013
### DB 접속 정보는 URL 한 줄이 아니라 조각으로

`db_host` · `db_port` · `db_user` · `db_password` · `db_name` 을 따로 받고,
`config.py` 의 `database_url` property 가 SQLAlchemy `URL.create` 로 조립합니다.
D-011 의 `DAENGS_DATABASE_URL` 을 대체합니다.

**개발 PC 와 서버는 호스트만 다릅니다.** 개발 PC 는 서버 IP, 서버 컨테이너는 compose
네트워크의 `pgvector`. URL 한 줄로 받으면 그 한 조각 때문에 접속 정보 **전체**를
`backend/.env` 와 `docker-compose.yml` 두 군데에 각각 적게 됩니다. 조각으로 받으면
compose 는 `DAENGS_DB_HOST: pgvector` 만 덮어쓰면 됩니다.

**이어 붙인 URL 은 비밀번호에 `@` `/` `#` 가 들어가면 깨집니다.** compose 가
`postgresql+asyncpg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@pgvector:...` 로 문자열을
만들고 있었는데, D-007 때문에 `POSTGRES_PASSWORD` 는 기본값이 아닌 값을 쓰게 되어
있어서 언제든 밟을 수 있었습니다. `URL.create` 는 조각을 받아 이스케이프까지 합니다.

**접속 정보의 원본은 여전히 최상단 `.env` 하나입니다** (D-009 유지). 전달 방식만
바뀝니다. compose 가 `POSTGRES_*` 를 읽어 `DAENGS_DB_*` 로 넘깁니다.

**옛 `DAENGS_DATABASE_URL` 은 조용히 무시하지 않습니다.** `extra="ignore"` 라 그냥
두면 무시되는데, 그러면 개발 PC 가 기본 호스트로 붙어 인증 실패를 봅니다 — 원인이
`.env` 의 옛 줄이라는 걸 알아채기 어렵습니다. 그 변수가 보이면 뜨지 않고 무엇을
바꿔야 하는지 알려 줍니다. 팀 전원이 `.env` 를 옮기고 나면 지워도 되는 코드입니다.

**계기.** `#8` 배포 때 `password authentication failed for user "daengs"` 로 backend 가
DB 에 못 붙었습니다. 원인은 최상단 `.env` 의 `POSTGRES_USER` 를 바꿨는데 pgvector
볼륨은 이미 `postgres` 로 초기화된 뒤였던 것입니다 (이 값들은 `db/init/` 과 마찬가지로
볼륨이 빌 때 한 번만 반영됩니다). 접속 정보 자체와는 다른 원인이었지만, 값이 어디서
어떻게 조립되는지 한눈에 안 보인다는 게 그때 드러났습니다.

**대가.** 설정 항목이 하나에서 다섯으로 늘었고, `sqlite://` 같은 다른 URL 을 통째로
넣는 길이 막혔습니다. 테스트에서 그럴 일이 생기면 그때 `database_url` 을 덮어쓰는
탈출구를 두면 됩니다. **지금 미리 두지는 않습니다** — 두 방식이 공존하면 어느 쪽이
이겼는지 매번 확인해야 합니다.

## D-014
### 관리자 권한 5단계를 PG ENUM 이 아닌 `VARCHAR + CHECK` 로

`admin_users.role` 을 이렇게 잡았습니다.

```sql
role VARCHAR(20) NOT NULL
    CHECK (role IN ('ADMIN','OPERATOR','CURATOR','ANALYST','VIEWER'))
```

**다섯 단계.**

| | |
| --- | --- |
| `ADMIN` | 계정·권한 관리까지 전부 |
| `OPERATOR` | 운영 데이터 CRUD + 개인정보 복호화 (계정 관리 제외) |
| `CURATOR` | 지식베이스 문서 + 검색 점검. 개인정보 접근 없음 |
| `ANALYST` | 지표·검색 점검 조회. 쓰기 없음 |
| `VIEWER` | 조회만. 개인정보는 마스킹 |

**지금 실제로 발급하는 것은 `ADMIN` 하나입니다.** 나머지 넷은 자리만 잡아 둔 것이고,
권한 체크 로직도 아직 없습니다. 그런데도 미리 적어 두는 이유는, 나중에 단계를 넣을 때
바뀌는 것이 값 목록이 아니라 **"이 화면은 누가 볼 수 있나"라는 판단 전부**이기 때문입니다.
축을 미리 정해 두면 그때 제약만 갈아끼우면 됩니다.

**왜 ENUM 이 아닌가.** PG ENUM 은 값 추가(`ALTER TYPE ... ADD VALUE`)는 되는데
그 다음이 불편합니다.

- 값 삭제가 없습니다. 쓰지 않게 된 값이 타입에 영원히 남습니다.
- 이름 변경(`RENAME VALUE`)은 되지만 순서 변경은 안 됩니다.
- `ADD VALUE` 는 PG 12 부터 트랜잭션 안에서 되지만, 추가한 값을 **같은 트랜잭션 안에서
  바로 쓸 수는 없습니다.** 마이그레이션 스크립트를 두 번에 나눠야 합니다.

이 컬럼의 목적 자체가 "나중에 구성을 바꿀 여지를 남긴다"인데 ENUM 은 그 반대 방향입니다.
`CHECK` 은 제약을 떨구고 다시 거는 것이 전부입니다.

```sql
ALTER TABLE admin_users DROP CONSTRAINT admin_users_role_check;
ALTER TABLE admin_users ADD CONSTRAINT admin_users_role_check
    CHECK (role IN (...));
```

**대가**는 두 가지입니다. 값 목록이 타입 하나가 아니라 제약 안에 문자열로 들어가서
`\dT` 같은 것으로 한눈에 볼 수 없고(그래서 `COMMENT ON COLUMN` 에 적어 뒀습니다),
같은 목록을 쓰는 컬럼이 여러 개가 되면 제약을 각각 고쳐야 합니다.
지금은 `role` 하나뿐이라 후자는 문제가 아닙니다.

같은 이유로 `admin_users.status` / `app_users.status` 도 `VARCHAR + CHECK` 입니다.
`documents.category` 가 이미 이 방식이라 저장소 전체가 한 가지 방식으로 통일됩니다.

**파이썬 쪽은 문자열입니다.** `models/admin_user.py` 의 `ADMIN_ROLES` 튜플이 같은 값을
들고 있지만, 이것은 리터럴을 흩뿌리지 않으려는 상수일 뿐 `Enum` 타입이 아닙니다.
SQLAlchemy 의 `Enum` 타입을 쓰면 DB 에 타입을 만들려 들기 때문에 쓰지 않았습니다.
**SQL 의 CHECK 을 고치면 이 튜플도 손으로 맞춰야 합니다** (D-011 - Alembic 이 없어
모델이 SQL 을 따라가는 구조의 대가입니다).

**관련**: 관리자(`admin_users`)와 앱 회원(`app_users`)을 한 테이블로 합치지 않은 것,
`app_users` 의 개인정보 컬럼을 암호문 + blind index 로 나눈 것은 PR `#7` 본문의
`## 컨텍스트 메모` 에 적었습니다.

## D-015
### access 는 JWE, refresh 는 DB 에 두는 불투명 토큰

관리자 로그인의 토큰을 두 종류로 나누고, 성격을 정반대로 잡았습니다.

| | 형식 | 수명 | DB |
| --- | --- | --- | --- |
| access | JWE (`alg="dir"` + `enc="A256GCM"`) | 5분 | 안 봅니다 |
| refresh | 뜻 없는 난수 32바이트 | 7일 (절대 만료) | SHA-256 해시로 매번 조회 |

**refresh 를 토큰 안에 담지 않는 이유는 강제 로그아웃입니다.** 계정을 잘랐는데 토큰이
살아 있으면 곤란한데, 무상태 토큰은 만료 전까지 서버가 손쓸 방법이 없습니다.
어차피 DB 를 봐야 한다면 암호화할 이유도 없어서 그냥 난수입니다.
원문은 저장하지 않고 해시만 둡니다 — DB 가 통째로 새어도 그것만으로 유효한 토큰이
되지는 않게.

**access 를 JWS(서명)가 아니라 JWE(암호화)로 한 이유**는 role 과 만료를 클라이언트가
읽지 못하게 하기 위해서입니다. JWT 는 base64 디코딩만으로 내용이 보입니다.
대신 프론트는 자기 권한을 `GET /auth/me` 로 받아와야 하는데, role 은 원래 서버에
물어봐야 하는 값이라 손해가 아닙니다.

**GCM 은 AEAD 라 서명을 따로 얹지 않습니다.** JWS 로 감싼 뒤 JWE 로 또 싸는(nested)
구성이 흔한 실수인데, 발급도 검증도 우리 서버뿐이라 불필요합니다.

**`joserfc` 의 함정**: `jwt.encode`/`jwt.decode` 는 `registry` 가 `JWERegistry` 일 때만
JWE 로 가고, 안 넘기면 **조용히 JWS 경로로 빠집니다.** 에러가 나지 않아서, role 이
평문으로 읽히는 토큰이 나가도 아무도 모릅니다. 토큰이 5조각인지 확인하는 테스트로
고정해 뒀습니다 (JWS 는 3조각).

#### 수명을 5분 / 7일로 잡은 것

access 는 발급 후 취소할 수 없어서, 그 구멍의 크기가 곧 수명입니다. 계정을 정지시켜도
이미 나간 토큰은 5분간 살아 있습니다. 쓰는 사람이 개발자뿐이라 길 이유가 없습니다.

**회전해도 refresh 의 만료는 갱신하지 않습니다(절대 만료).** 슬라이딩으로 하면 매일
쓰는 사람은 영원히 재로그인을 안 하게 되어 상한이 사라집니다.

#### 재사용 감지와 10초 유예 창

refresh 는 쓸 때마다 새 것으로 갈아 끼우고 옛 것을 폐기합니다(회전). 그러면 **이미
폐기된 토큰이 다시 들어왔을 때 탈취를 의심**할 수 있습니다 — 정상 사용자는 새 것을
받아 갔으니 옛 것을 쓸 이유가 없습니다. 그때는 그 계정의 세션을 전부 끊습니다.

문제는 오탐입니다. 한 브라우저의 탭 두 개가 같은 쿠키로 거의 동시에 재발급하면
한쪽은 반드시 방금 폐기된 토큰을 쓰게 됩니다. access 가 5분이라 재발급이 잦고,
30분일 때보다 6배 자주 걸립니다. **폐기된 지 10초 이내면 탈취가 아니라 탭 경합으로
보고 통과**시킵니다.

여기서 "로그아웃한 토큰"과 "회전으로 교체된 토큰"을 구분해야 합니다. 사유 컬럼을
더하는 대신 **폐기 방식을 나눴습니다.**

| 상황 | 행 처리 | 그 토큰이 다시 오면 |
| --- | --- | --- |
| 회전 | `revoked_at` 을 찍고 행은 남김 | 10초 이내면 통과, 이후면 탈취 |
| 로그아웃 | 행을 지움 | 못 찾음 → 즉시 거부 |
| 강제 로그아웃 · 탈취 대응 | 행을 지움 | 못 찾음 → 즉시 거부 |

이렇게 하면 **`revoked_at` 이 있다는 것 자체가 "회전으로 교체됨"을 뜻합니다.**
`db/init/03_auth.sql` 을 고치지 않아도 되고, 서버에 `ALTER TABLE` 을 돌릴 일도 없습니다.

**대량 폐기를 `revoked_at` 으로 하면 안 됩니다.** 다른 세션들이 10초 안에 재발급을
시도하면 유예 창을 타고 새 토큰을 받아 가서, 끊으려던 것이 안 끊깁니다.

**만료된 refresh 는 탈취로 올리지 않습니다.** 만료된 토큰은 쓸모가 없어서, 오래
잠들어 있던 탭 하나 때문에 팀 전체를 로그아웃시킬 이유가 없습니다.

#### 쿠키와 `/api/` 프록시

관리자 웹은 httpOnly 쿠키(`SameSite=Lax`), 네이티브 앱은 `Authorization: Bearer` 입니다.
**토큰 형식과 발급기는 하나를 공유**하고 전달 방식만 다릅니다.
httpOnly 는 JS 가 못 읽는 쿠키라, XSS 가 들어와도 토큰을 퍼가지 못합니다
(`localStorage` 에 두면 그대로 털립니다). 같은 이유로 **응답 본문에도 토큰을 담지
않습니다** — 담으면 httpOnly 로 둔 의미가 없어집니다.

`daengs.~`(:80) 와 `daengback.~`(:8000) 은 브라우저에게 다른 오리진이라 쿠키가 그냥은
실리지 않습니다. 오리진을 유지한 채 보내려면 `SameSite=None + Secure` 인데 `Secure` 는
HTTPS 필수이고 지금은 http 입니다. 그래서 **nginx 의 `/api/` 블록으로 같은 오리진을
만듭니다.** 로컬에서는 `next.config.ts` 의 `rewrites()` 가 같은 모양을 만들어,
프론트 코드는 양쪽에서 똑같이 `fetch("/api/auth/login")` 을 씁니다.

같은 이유로 **CORS 는 사실상 불필요해집니다.** `DAENGS_CORS_ORIGINS` 는 남겨 두되
프록시 경유가 기본 경로입니다.

**HTTPS 로 옮기면 `DAENGS_COOKIE_SECURE=true` 를 켜야 합니다.** 지금 켜면 http 에서
쿠키가 아예 안 실려 로그인하자마자 로그아웃됩니다.

#### 권한은 role 이 아니라 '무엇을 할 수 있는가'로

엔드포인트는 `require(Perm.PII_READ)` 처럼 **권한**을 선언합니다. role 을 직접 비교하면
role 구성을 바꿀 때마다 코드 전체를 뒤지게 되므로, `core/deps.py` 의
`ROLE_PERMISSIONS` 한 곳만 고치면 되도록 한 겹을 둡니다.
이 표는 `03_auth.sql` 의 role 주석(D-014)과 같은 내용이라 **같이 고쳐야 합니다.**

`current_admin` 은 **DB 를 보지 않습니다** — 토큰을 푸는 것으로 끝이고, 그게 무상태
토큰을 쓰는 이유 전부입니다. 대가로 role 변경과 계정 정지가 최대 5분 늦게 반영됩니다.
지금 DB 상태가 필요한 `GET /auth/me` 만 다시 조회합니다.

#### 로그인 실패 제한

`(login_id, IP)` 쌍으로 5회 실패 시 10분 잠급니다. **계정 단위로 세지 않습니다** —
계정 하나를 팀이 공유하고 있어서, 계정으로 세면 한 명이 5번 틀릴 때 전원이 잠기고
아이디만 아는 사람은 누구나 일부러 잠글 수 있습니다.

IP 를 믿을 수 있는 근거는 backend 가 포트를 열지 않는다는 것입니다 (D-005).
nginx 의 `proxy_set_header X-Real-IP $remote_addr` 가 클라이언트가 보낸 같은 이름의
헤더를 덮어쓰므로 위조할 수 없습니다.

**카운터 확인이 계정 조회보다 먼저입니다.** 순서가 바뀌면 잠기는지 여부로 계정 존재가
드러납니다. 같은 이유로 없는 아이디로 두드릴 때도 똑같이 셉니다.

상태는 **프로세스 메모리**입니다. DB 에 두면 `admin_users` 에 컬럼이 늘고 서버에서
`ALTER TABLE` 을 돌려야 합니다. backend 가 단일 프로세스라 지금은 이걸로 충분하고,
**재시작하면 카운터가 풀리는 것이 한계**입니다. Redis 는 쓰지 않습니다 — compose 에
없고, 이것 하나 때문에 서비스를 늘릴 이유가 없습니다.

#### 최초 관리자 계정

`db/init/*.sql` 에 넣지 못합니다. **Postgres 로는 Argon2id 해시를 만들 수 없습니다** —
`pgcrypto` 의 `crypt()` 는 bcrypt / md5 / des 만 지원하고, 지금 켜는 확장은 `vector`
하나뿐입니다. SQL 파일에 넣으려면 해시를 git 에 커밋해야 하는데, 그러면 비밀번호를
바꿔도 히스토리에 옛 해시가 남습니다.

그래서 `uv run seed-admin` 이 **SQL 을 출력만 하고 DB 는 건드리지 않습니다.**
여러 번 돌려도 부작용이 없고, 같은 아이디를 두 번 붙여넣으면 `login_id` 의 UNIQUE
제약이 막습니다. `getpass` 를 쓰므로 **컨테이너에서는 `-it` 가 필요합니다.**

## D-016
### 관리자와 앱 회원이 토큰·세션 테이블을 공유하고, 종류는 `typ` 로 가른다

앱 회원의 카카오 로그인을 붙이기 전에, 관리자용으로 만들어 둔 인증 기반(D-015)을
두 종류의 사람이 같이 쓰도록 넓혔습니다. 정한 것은 셋입니다.

| | 결정 |
| --- | --- |
| 토큰 | 발급기·키를 공유하고, access 클레임 `typ` 로 종류를 구분 |
| 세션 저장 | `refresh_tokens` 한 테이블. 소유자 FK 를 둘 두고 CHECK 로 배타 |
| 검증 | 각 의존성이 **자기 종류가 아닌 토큰을 401 로 거부** |

#### `typ` 클레임이 없으면 앱 회원이 관리자가 됩니다

발급기가 하나이므로 앱 회원의 access token 도 **우리 키로 서명·암호화된 진짜
토큰**입니다. 위조가 아니라서 검증은 전부 통과하고, `sub` 는 어느 쪽이든 UUID
한 개라 그것만으로는 구분되지 않습니다.

지금은 우연히 막힙니다 — 앱 회원 토큰의 role 이 `ROLE_PERMISSIONS` 에 없어서
권한이 빈 집합이 되고 `require(...)` 가 403 을 냅니다. **그 우연에 기대지 않습니다.**
`CurrentAdmin` 만 받고 권한을 안 거는 엔드포인트가 하나라도 생기면 그 자리로
그대로 들어옵니다. 테스트로 고정해 뒀습니다.

`typ` 가 모르는 값이면 **아무 쪽으로도 넘기지 않고 거부**합니다. 기본값을 관리자로
두면 클레임을 지운 토큰이 관리자로 통과합니다.

role 의 유무도 종류가 정합니다 — 관리자 토큰에 role 이 없거나 앱 토큰에 role 이
붙어 있으면 발급도 검증도 거부합니다.

#### 세션은 한 테이블, 소유자 컬럼은 둘

`03_auth.sql` 이 미뤄 뒀던 '컬럼을 더할지 / 테이블을 나눌지'의 답입니다.

    admin_user_id UUID REFERENCES admin_users(id) ON DELETE CASCADE,
    app_user_id   UUID REFERENCES app_users(id)   ON DELETE CASCADE,
    CHECK (num_nonnulls(admin_user_id, app_user_id) = 1)

**`subject_type` + `subject_id` 한 쌍으로 하지 않은 이유**는 FK 를 걸 수 없기
때문입니다. 계정을 지워도 세션이 남고, 그것을 지우는 책임이 DB 에서 앱으로 넘어옵니다.

**테이블을 나누지 않은 이유**는 회전과 재사용 감지 규칙(D-015)이 양쪽 똑같기
때문입니다. 10초 유예 창, 로그아웃은 삭제·회전은 `revoked_at` 이라는 불변식,
절대 만료 — 이 미묘한 규칙이 두 벌이 되면 그중 한쪽만 고치는 날이 옵니다.
대신 repositories 가 컬럼 이름 대신 주체를 받고, 분기는 `_SUBJECT_COLUMN`
한 곳에만 둡니다.

인덱스는 부분 인덱스입니다. 각 행이 둘 중 한 컬럼만 채우므로, 그냥 걸면 인덱스마다
반대쪽 주체의 행이 전부 NULL 로 들어갑니다.

#### 딸려 온 것 — `db/migrations/`

`db/init/` 은 볼륨이 빌 때만 실행되므로 **이미 돌고 있는 서버 DB 에는 아무 일도
일어나지 않습니다.** 지금까지는 그때그때 손으로 SQL 을 만들어 적용했는데, 이번에
`ALTER` 가 다섯 줄이라 파일로 남겼습니다. Alembic 은 여전히 쓰지 않습니다 —
버전 테이블이 없어서 **무엇이 적용됐는지 DB 가 기억하지 않으므로**, 각 파일을
여러 번 돌려도 안전하게 씁니다.

#### 대가

- **이 변경 전에 발급된 access token 은 전부 무효**입니다 (`typ` 가 없어서).
  수명이 5분이고 refresh 는 그대로 살아 있어서 재발급 한 번이면 복구됩니다.
- `refresh_tokens.admin_user_id` 의 NOT NULL 이 CHECK 제약으로 바뀌었습니다.
  **마이그레이션에서 NOT NULL 만 풀고 CHECK 를 빠뜨리면 주인 없는 세션 행이
  만들어질 수 있습니다.** 한 트랜잭션에 묶어 뒀습니다.

## D-017
### 카카오 로그인은 OIDC `id_token` 을 서버가 직접 검증한다

앱이 카카오에서 받은 **`id_token`** 을 우리 서버로 보내고, 서버는 카카오 공개키(JWKS)로
서명을 검증합니다. access token 을 받아 `/v2/user/me` 로 되묻는 방식은 쓰지 않습니다.

#### 왜 access token 방식이 아닌가

| | `id_token` | access token |
| --- | --- | --- |
| 로그인당 카카오 호출 | **없음** (공개키만 캐시) | 있음 — 카카오가 느리면 우리 로그인도 느림 |
| "우리 앱 토큰인가" | `aud` 검증으로 **자동** | `/v1/user/access_token_info` 로 직접 대조해야 함 |
| 허용 IP 설정 | 불필요 | 서버 공인 IP 를 콘솔에 등록해야 함 |

**두 번째 줄이 결정적입니다.** access token 방식에서 `app_id` 대조를 빠뜨리면, 다른
카카오 앱에서 발급된 토큰으로도 우리 서비스에 계정이 생깁니다. 그 토큰의 회원번호는
그 앱 기준이라 엉뚱한 새 회원이 됩니다. 빠뜨려도 **정상 로그인은 멀쩡히 되기 때문에**
뚫린 줄 모릅니다. `id_token` 은 `aud` 가 그 역할을 대신하고, 이건 표준 검증 절차라
빠뜨리기 어렵습니다.

세 번째 줄도 이 프로젝트에서는 무겁습니다. 카카오는 키 유출에 대비해 호출 허용 IP 설정을
권장하는데, 우리 서버는 자체 PC 라 공인 IP 가 고정이라는 보장이 없습니다. 바뀌면 로그인이
통째로 죽습니다. `id_token` 검증은 앱 키로 카카오 API 를 부르지 않아 이 문제가 없습니다
(JWKS 는 키가 필요 없는 공개 엔드포인트입니다).

**대가**: 앱이 카카오 개발자 콘솔에서 **OpenID Connect 를 켜야 하고**, 로그인 요청의
`scope` 에 **`openid` 를 넣어야** 합니다. 토글만 켜고 scope 를 빠뜨리면 `id_token` 이
아예 안 나옵니다. 우리 서버 혼자 정할 수 없는 유일한 부분입니다.

#### 검증에서 빠뜨리면 안 되는 것

    iss   https://kauth.kakao.com 정확히
    aud   우리 앱 키 목록 중 하나    ← 없으면 남의 앱 토큰이 통과합니다
    exp   만료
    alg   RS256 하나로 고정         ← 없으면 알고리즘 혼동 공격이 열립니다

**`alg` 고정이 특히 조용한 구멍입니다.** 열어 두면 공격자가 헤더의 alg 를 HS256 으로
바꾸고 **공개키를 HMAC 비밀키 삼아** 서명할 수 있습니다. 공개키는 누구나 가져올 수
있으므로 서명 없이 토큰을 만드는 것과 같아집니다. 카카오도 RS256 하나만 씁니다
(`openid-configuration` 과 실제 JWKS 둘 다 확인).

넷 다 테스트로 고정해 뒀습니다 (`tests/test_kakao.py`). **하나라도 빠져도 정상 로그인은
되기 때문에**, 테스트가 없으면 뚫린 것을 알 방법이 없습니다.

#### `aud` 는 앱 키 하나가 아니라 **목록**입니다 (2026-08-27 추가)

처음에는 REST API 키 하나와 대조했습니다. **앱이 네이티브 SDK 로 붙는 순간 로그인이
전부 401 이 되었습니다.**

카카오는 **인가 요청에 쓴 앱 키를 그대로 `aud` 에 넣습니다.** 같은 애플리케이션이라도
들어온 경로마다 값이 다릅니다:

| 로그인 경로 | `aud` 에 오는 값 |
| --- | --- |
| Android / iOS SDK | 네이티브 앱 키 |
| JavaScript SDK | JavaScript 키 |
| REST API (`uv run kakao-token`) | REST API 키 |

그래서 `DAENGS_KAKAO_APP_KEYS` 로 **목록**을 받습니다 (`config.py` 의 `kakao_app_keys`).
`.env` 만 고쳐서는 안 되는 변경이었습니다 — `Settings` 가 `extra="ignore"` 라, 새 이름을
넣어도 아무 데서도 읽지 않고 조용히 무시됐습니다. 옛 이름만 남아 있으면 backend 가 뜨지
않고 무엇으로 바뀌었는지 알려 줍니다 (D-013 의 `DAENGS_DATABASE_URL` 과 같은 방식).

**목록을 늘려도 D-017 의 취지는 유지됩니다.** "우리 앱인가"가 "우리 앱들 중 하나인가"로
바뀔 뿐이고, 한 애플리케이션의 키만 넣으면 회원번호(`sub`)가 같아 계정도 갈라지지
않습니다. 반대로 **다른 애플리케이션의 키를 섞으면** 같은 사람이 서로 다른 회원이 됩니다
— 회원번호는 앱 단위이기 때문입니다. 어드민 키는 `aud` 로 오지 않으므로 넣지 마세요.

##### 빈 목록이 가장 위험합니다

`joserfc` 의 `JWTClaimsRegistry.check_value` 는 `values` 가 빈 목록이면
`if not option_values: return` 으로 빠져나가 **`aud` 검사를 통째로 건너뜁니다.**
즉 `DAENGS_KAKAO_APP_KEYS=[]` 는 "앱 키가 없다"가 아니라 **"아무 카카오 앱의 토큰이나
통과"** 입니다 — 정확히 D-017 이 막으려던 그 구멍이 설정 한 줄로 열립니다.

필수 필드로 두는 것만으로는 `[]` 를 못 막으므로 `config.py` 의 validator 가 거부합니다.
빈 문자열이 섞인 경우도 같이 막습니다 (`[""]` 는 목록이 비지 않았지만 어떤 `aud` 와도
맞지 않아 전원 로그인 불가를 조용히 만듭니다).

`tests/test_kakao.py` 에 **통과하는 것이 정답인 거부 테스트**를 하나 두었습니다 —
목록을 비우면 남의 앱 토큰이 실제로 통과한다는 것을, 즉 `verify_id_token` 이 스스로
막을 수 없고 config 의 validator 가 유일한 방어선이라는 것을 못박아 둔 것입니다.

##### CLI 만 REST 키를 따로 압니다

`cli/kakao_token.py` 는 REST 흐름이라 `client_id` 자리에 **REST API 키**가 필요합니다.
허용 목록에서 아무거나 집으면 안 됩니다 — 넣은 순서에 기대는 코드가 되고, 네이티브 키를
`client_id` 로 보내면 authorize 단계에서 거절당합니다. 그래서 `DAENGS_KAKAO_REST_API_KEY`
는 **그 CLI 전용 설정**으로 남겨 두었습니다 (없어도 backend 는 정상, `--client-id` 로도
넘길 수 있음). 이 CLI 로 검증까지 확인하려면 허용 목록에 REST API 키도 들어 있어야
합니다 — 네이티브 키만 넣어 두면 앱은 되는데 CLI 만 막힙니다.

#### 시계 오차를 60초까지 봐줍니다

**없으면 우리 시계가 카카오보다 1초만 뒤처져도 모든 로그인이 실패합니다.** `id_token` 의
`iat`(발급 시각)가 우리 기준으로 미래가 되어 "미래에 발급된 토큰"으로 거부됩니다.
실제로 개발 PC 에서 만났고, 응답이 "우리 앱의 것이 아님"으로 보여서 `aud` 를 한참
들여다봤습니다. 서버도 같은 Windows PC 라 똑같이 겪습니다.

NTP 동기화가 근본 해법이지만, 동기화가 잠깐 어긋난다고 로그인이 통째로 죽으면 안 됩니다.

같은 60초가 `exp` 에도 적용됩니다 — 만료된 토큰을 1분 더 받아 주는 셈인데, 카카오
`id_token` 은 로그인 직후 한 번 쓰고 버리는 값이라 위험이 거의 없습니다.
**우리가 발급하는 access token(D-015)에는 이 여유를 주지 않습니다.**

#### 공개키 캐시

6시간 캐시하고, **모르는 `kid` 가 오면 한 번 다시 받아옵니다.** 영원히 캐시하면 카카오가
키를 가는 순간 전원이 로그인 불가가 되고, 매번 받아오면 카카오 장애에 끌려갑니다.
다시 받아오는 데에도 최소 간격(1분)을 둡니다 — 없으면 엉터리 `kid` 를 계속 보내는
것만으로 우리 서버가 카카오를 두드리게 만들 수 있습니다.

`joserfc` 는 모르는 `kid` 에 `InvalidKeyIdError`(= `JoseError` 갈래)를 냅니다.
`KeyError` 로 잡으면 **재요청 경로를 영영 안 타서**, 키 교체 때 조용히 전원 로그인
불가가 됩니다. 실제로 이 실수를 했고 테스트가 잡았습니다.

#### 저장하는 것과 안 하는 것

- **카카오 access/refresh 토큰은 저장하지 않습니다.** 남의 서비스 자격증명이라
  로그인 시점에 검증만 하고 버립니다. 나중에 카카오 API 를 다시 불러야 하면 그때
  AES 로 암호화해서 저장합니다.
- 동의 항목은 **회원번호 하나**입니다. 이메일도 받지 않습니다 — 받지 않기로 한 것이
  아니라 **개인 개발자 앱에서는 `account_email` 이 "권한 없음"이라 켤 수가 없습니다**
  (비즈 앱 전환이 있어야 열립니다). 콘솔에서 안 켠 항목을 `scope` 에 넣으면 로그인
  화면 대신 KOE205 가 뜨므로, 요청하는 scope 는 `openid` 하나입니다.
  `app_users` 의 이메일 컬럼은 **그대로 둡니다** — 나중에 비즈 앱으로 가면 채울 수
  있고, 지금 지우면 그때 마이그레이션이 또 필요합니다. 값은 계속 NULL 입니다.
- **닉네임(`profile_nickname`)은 콘솔에서 필수 동의로 켜져 있지만 저장하지 않습니다.**
  로그인할 때 사용자가 동의는 하게 되는데, 우리 DB 에 넣는 순간 암호화·파기 책임이
  생기고 얻는 것이 없습니다. 화면에 이름이 필요하면 **앱이 SDK 에서 직접** 가져다 쓰세요.
- 전화번호·실명은 추가 심사(영업일 3~5일) 대상이기도 합니다.
- **어드민 키는 서버에 두지 않습니다.** 탈퇴 시 카카오 연결 끊기는 앱이 SDK 로 합니다.
  그 키 하나로 전 회원을 조작할 수 있어서, 편의를 위해 늘릴 물건이 아닙니다.
- `app_users.name_enc` 는 비워 둡니다. 카카오 기본 제공은 닉네임이고 실명은 별도 심사
  대상인데, 닉네임은 카카오 밖에서 의미가 옅어 암호화해 보관할 이득이 적습니다.


## D-018
### 생활비서 RAG·실시간 산책은 `src/daengs_life/` 한 겹으로 들여온다

`choiyc05/daengs-life` 의 백엔드(패키지 5개 · 테스트 36파일)를 이 레포로 옮기면서
`backend/src/daengs_life/` 를 새로 만들고 **`crawler` · `rag` · `realtime` · `tasks` · `app`
다섯을 형제 그대로** 그 안에 넣었습니다. `daengs_backend` 안에 섞지 않았습니다.

#### 왜 한 겹인가

이름 후보는 `daengs_rag` 였습니다. 그런데 옮기는 다섯 중 `realtime`(3,348줄)이
`rag`(3,621줄)와 덩치가 같아서, 전부를 rag 라 부르면 절반을 잘못 부르는 것이 됩니다.

그렇다고 `daengs_rag` + `daengs_realtime` 으로 쪼개면 **둘 다 `crawler` 에 의존한다**는
문제가 걸립니다. `crawler` 를 어느 쪽에 둘지, 아니면 세 번째 패키지로 뺄지를 정해야 하고,
무엇보다 **의존 방향 가드 두 개가 패키지를 가로지르게 되어 다시 설계해야 합니다.**
그 가드는 `rag` 가 `crawler.core.{config,textutil}` 까지만, `realtime`·`tasks`·`app` 은
`crawler.core.config` 하나만 보도록 강제하는 장치이고 — "실시간은 저장하지 않는다"(RAG-012)를
사람의 규율이 아니라 코드로 지키는 물건입니다.

한 겹으로 묶으면 다섯이 형제로 남아 **그 가드의 뜻이 그대로 보존**됩니다. import 는
접두사 한 겹만 붙고(`from rag.stages.x` → `from daengs_life.rag.stages.x`, 33파일),
가드는 스캔 경로와 접두사 벗기기 두 군데만 고치면 됩니다.

경계선을 다시 긋는 것 — `controllers`→`routers`, `dto`→`schemas`, psycopg 직접 SQL 을
SQLAlchemy 로 옮길지 — 은 **이 카드에서 하지 않았습니다.** 그건 이 레포의 MVC2 규약(D-011)과
저쪽 RAG-027 을 맞추는 별도의 작업이고, 한 PR 에 같이 넣으면 리뷰가 불가능해집니다.

이름을 원본 레포와 같게 둔 것은 의도입니다. 핸드오프 노트와 `RAG-`·`RT-` ADR 들이 전부
"daengs-life" 로 적혀 있어, 그대로 두면 서류 자국이 번역 없이 이어집니다.

#### 서빙은 아직 앱에 붙이지 않았습니다

`daengs_backend` 는 `daengs_life` 를 **어디에서도 import 하지 않습니다.** `dev` 머지가
곧 배포인데, 저쪽 서빙은 lifespan 에서 임베딩 모델을 CPU 로 상주시킵니다(RAG-028 ①).
그대로 등록하면 **돌고 있는 API 프로세스가 모델 로드분(수 초 + 메모리)을 같이 뭅니다.**
같은 프로세스에 둘지 워커·별도 서비스로 뺄지는 붙이기 전에 정할 일이라 다음 카드로 뺐습니다.

#### 곁딸린 결정 넷

- **ADR 접두사는 `RAG-`·`RT-` 로 갈라 둡니다.** 원래 저쪽도 `D-` 에 `docs/decisions.md` 라
  파일명·번호가 같은데 뜻이 남남이었습니다(이 레포 `D-011`=SQLAlchemy·MVC2 / 저쪽
  `D-011`=법령 웹 원문 경로). 저쪽이 이관 직전에 개명했고 **번호는 유지**했습니다
  (`D-027`=`RAG-027`). ⚠ 그 이전의 저쪽 커밋 메시지와 PR 본문은 옛 `D-` 표기입니다.
- **env 이름에 `DAENGS_` 접두사를 붙이지 않았습니다.** `rag` 는 최상단 `.env` 의
  `POSTGRES_*` 를 **compose 값 그대로** 읽는데, 그 이름은 pgvector 컨테이너와 공유하는
  것이라 접두사를 붙이면 DB 를 못 찾습니다. API 키도 발급 기관이 부르는 이름 그대로가
  `docs/data-sources.md` §9 와 1:1 입니다. 두 Settings 는 `extra="ignore"` 라 한 `.env`
  안에 섞여 있어도 서로를 무시하고, 실제로 겹치는 이름은 **하나도 없습니다**(확인함).
  통일이 필요해지면 `AliasChoices` 로 두 이름을 다 받는 쪽이 맞습니다 — 지금 바꾸면
  서버 `.env` 를 손으로 고쳐야 하는데 얻는 것이 이름 모양뿐입니다.
- **`data/` 는 새로 크롤링합니다.** 통째로 복사하지 않았습니다(RAG-017). ⚠ **복사와
  재수집을 섞으면 안 됩니다** — `chunk_id` 에 수집 날짜가 박혀 있어
  (`crawler/core/store.py`, `easylaw-pet-1-1-1__20260819#note-1`) 오늘 받으면 모든 ID 가
  바뀌고 옛 parquet 3종과 `documents` 행이 함께 무효가 됩니다. 골든셋 라벨은 수집 날짜를
  뺀 논리 주소라 안전합니다(RAG-022 ⑥). `data/processed/answers/lap1.jsonl` 만 예외로
  추적합니다 — LLM 출력이라 재현이 안 되는데 RAG-028 ⑥ 이 1랩↔2랩 비교 축으로 정했습니다.
- **저쪽 `.gitattributes` 는 가져오지 않았습니다.** `* text=auto eol=lf` 라 이 레포 전체를
  LF 로 재정규화해 버립니다. `tests/fixtures/.gitattributes`(`* -text`, API 응답 바이트
  보존용)만 남겼습니다.

#### 옮기면서 실제로 어긋난 것 셋

전부 "개발 모드에서는 안 드러나는" 종류였습니다.

1. **`PACKAGE_ROOT` 가 `parents[2]`** 였습니다. `backend/` 를 가리키던 것이 `src/daengs_life/`
   두 겹이 끼면서 `parents[4]` 가 됐습니다. 안 고치면 `backend/.env` 를 못 찾습니다.
2. **휠에 `daengs_life` 가 빠졌습니다.** `uv_build` 는 프로젝트 이름에서 유추한 모듈
   하나(`daengs_backend`)만 담습니다. `[tool.uv.build-backend] module-name` 에 둘 다
   적었습니다 — 컨테이너가 `backend/src` 를 마운트해 도는 지금은 안 드러납니다.
3. **`test_cache.py` 가 `realtime/cache.yaml` 경로를 손으로 조립**하고 있었습니다.
   모듈이 쥔 `CACHE_FILE` 을 쓰게 바꿨습니다.

#### 한 줄 처방 하나

`psycopg.connect` 에 `connect_timeout=3` 을 넣었습니다(`rag/stages/load.py`). 없으면 DB 가
안 떠 있을 때 libpq 기본 타임아웃을 통째로 무는데, `_conn_or_skip()` 은 **실패한 뒤에야**
skip 하므로 DB 테스트 수만큼 그 시간이 곱해져 "멈춘 것처럼" 보입니다. 저쪽 실측이
DB 기동 35초 / 미기동 사실상 정지였고, **이 레포는 DB 가 원격(서버 PC)이라 더 자주 겪습니다.**

## D-019
### Redis 를 compose 에 올리고, LAN 에 열되 비밀번호를 건다

`/walk` 를 배포되는 API 에 붙이면서(#23) `redis:8.2-alpine` 서비스를 compose 에 넣었습니다.
지금까지는 `daengs_life` 안에 Redis 를 쓰는 코드가 있는데 서비스가 없어서, 실제 경로가 늘
**프로세스 메모리 폴백**이었습니다 (RT-001 ④-c).

#### 왜 메모리 폴백으로 두면 안 되는가

캐시 값이 아니라 **일 예산 카운터** 때문입니다. data.go.kr 개발계정은 **1,000회/일**이고
`Cache` 가 그 횟수를 세서 한도에 닿으면 호출을 멈춥니다. 카운터가 프로세스 메모리에 있으면
재시작마다 0 으로 돌아가, 제약이 있는 척만 하고 실제로는 넘겨 부릅니다.
(활성 키 집합도 같은 이유입니다 — 별도 프로세스인 Celery Beat 가 그것을 읽어야 합니다.)

#### 포트를 LAN 에 연다

`0.0.0.0:6379` 바인딩입니다. pgvector 와 같은 판단이되 이유는 다릅니다 — 팀원이 붙어서가
아니라, **개발 PC 에서도 서버 Redis 를 봐야 카운터가 하나로 모이기** 때문입니다. 개발 PC 가
각자 메모리로 세면 같은 API 키의 1,000회를 여럿이 따로 세다가 조용히 초과합니다.

그래서 **`--requirepass` 를 함께 겁니다.** Postgres 와 달리 Redis 는 기본이 무인증이라,
열어 두고 비밀번호가 없으면 같은 네트워크의 누구나 `FLUSHALL` 할 수 있습니다.
`REDIS_PASSWORD` 가 비면 `--requirepass ""` 가 되어 인증이 꺼집니다. 그래서 compose 에
`${REDIS_PASSWORD:?...}` 가드를 걸어 **값이 없으면 아예 안 뜨게** 했습니다 — #26 이
`DAENGS_TRAINING_RAG_BASE_URL` 에 쓴 것과 같은 장치이고, 저기가 "빈 값이면 restart loop"
를 막듯이 여기는 "인증 없는 Redis 가 LAN 에 열리는 것"을 막습니다. 컨테이너가 안 뜨는 편이
열린 채로 뜨는 것보다 낫습니다. compose 는 파일 전체를 해석하고 나서 컨테이너를 만들므로
가드 한 곳이면 `REDISCLI_AUTH` 와 backend 의 `REDIS_URL` 까지 같이 지켜집니다.

접속은 `REDIS_URL` **한 줄**입니다. `DAENGS_DB_*` 를 조각으로 받은 D-013 과 반대인데,
`realtime` 이 `redis.from_url` 을 쓰고 Celery 브로커도 같은 문자열을 받기 때문입니다.
대가로 D-013 이 피하려던 함정이 그대로 남습니다 — **비밀번호에 `@` `/` `#` 이 들어가면
깨집니다.** `.env.example` 에 영숫자로만 짓도록 적어 두는 것으로 대신합니다.

#### `maxmemory` 를 걸지 않습니다

캐시라고 `allkeys-lru` 를 거는 것이 반사적인 선택이지만, 여기서는 **틀립니다.**
`tasks/celery_app.py` 가 `realtime.config.REDIS_URL` 을 **그대로** 브로커로 씁니다.
즉 나중에 워커를 띄우면 같은 인스턴스·같은 DB 0 을 쓰게 되고, eviction 정책은 DB 번호가
아니라 **인스턴스 단위**라 큐에 들어간 태스크가 조용히 지워집니다.

지금은 안 걸어도 됩니다 — 캐시 항목은 전부 TTL(`ttl_periods` 4주기)이 붙어 스스로 사라집니다.
브로커를 별도 DB(`/1`)로 가르는 것은 **Celery 를 실제로 띄우는 카드**에서 합니다. 다만 DB 를
갈라도 eviction 문제는 안 풀리므로, 그때도 `maxmemory` 는 재검토 대상입니다.

#### 영속성은 RDB 만

`--save 900 1 --appendonly no` + `redis-data` 볼륨. 캐시 값은 잃어도 다시 받으면 되지만
예산 카운터는 잃으면 그날 한도를 넘깁니다. AOF 까지 갈 이유는 없습니다 — 카운터의 해상도가
"몇 분 전 값"이면 충분하고, 어차피 48시간 TTL 로 사라지는 키입니다.

#### backend 가 redis 의 healthcheck 를 기다립니다

Redis 가 없어도 앱은 뜹니다(④-c). 그런데도 `condition: service_healthy` 를 건 이유는
**그 판단이 프로세스 생애에 한 번뿐**이기 때문입니다 — `deps.get_cache` 가 `lru_cache` 라
lifespan 에서 연 결과가 그대로 굳습니다. backend 가 먼저 뜨면 Redis 가 1초 뒤에 올라와도
그 프로세스는 재시작 전까지 메모리 폴백이고, 그러면 이 결정의 목적이 통째로 사라집니다.

#### 비밀번호가 틀려도 조용히 메모리로 떨어집니다

④-c 가 연결 실패를 예외가 아니라 저하로 다루기 때문에, `REDIS_URL` 의 비밀번호가 틀려도
앱은 아무 말 없이 뜨고 카운터만 안 쌓입니다 — **인증 실패와 연결 실패가 구분되지 않습니다.**
그 설계를 바꾸지는 않았습니다(앱이 Redis 때문에 못 뜨는 것이 더 나쁩니다). 대신 확인할
자리를 만들었습니다:

```powershell
uv run python -m daengs_life.realtime config
```

실제로 붙여 보고 `[x] Redis 에 붙었다` / `[ ] 메모리 폴백` 을 찍습니다. `REDIS_URL` 은
비밀번호를 `***` 로 가려 출력합니다 (터미널이 곧 로그입니다 — RAG-012).

#### 그래서 연결 타임아웃을 걸었습니다

`open_store()` 는 `redis-py` 의 기본 타임아웃(무제한)을 쓰고 있었습니다. 판단이 lifespan 에서
일어나므로 그동안 **앱이 안 뜹니다** — 닫힌 포트에 4.2초(실측), 응답 없는 호스트면 OS 의 SYN
타임아웃(윈도우 20초대)을 통째로 뭅니다. "없어도 돈다"가 "없으면 20초 늦게 돈다"가 되면
같은 약속이 아닙니다. `socket_connect_timeout=1.0` · `socket_timeout=2.0` 을 걸어 저하까지
1초로 줄였습니다 (`realtime/cache.py`). 붙어 있을 때는 밀리초 단위라 영향이 없습니다.

## D-020
### nginx 는 backend 를 매 요청 다시 DNS 로 푼다

`daengback.~:8000` 과 `daengs.~/api/` 가 502 였습니다 (#31). backend 컨테이너가
재생성될 때마다 재발했고, 서버 PC 에서 `docker compose restart nginx` 를 해야 풀렸습니다.

원인은 nginx 가 `upstream` 블록의 이름을 **기동할 때 딱 한 번** 풀고 그 IP 를 프로세스가
죽을 때까지 쓰기 때문입니다. `daengs-backend` 는 compose 가 재생성할 때마다 IP 가 바뀌는데
(`environment` 를 고치면 재생성됩니다) nginx 는 그것을 모릅니다. 프론트가 멀쩡했던 것이
진단의 근거였습니다 — 그쪽 업스트림은 `host.docker.internal`, 즉 **안 바뀌는 게이트웨이
IP** 라 같은 파일 안에서 한쪽만 깨졌습니다.

```nginx
resolver 127.0.0.11 ipv6=off valid=10s;   # Docker 내장 DNS

set $fastapi_upstream backend:8000;
proxy_pass http://$fastapi_upstream;      # 변수가 있어야 매 요청 다시 푼다
```

`resolver` 와 **`proxy_pass` 의 변수는 세트**입니다. 변수 없이 `resolver` 만 적으면
아무 일도 일어나지 않습니다. 그래서 `fastapi` upstream 블록은 지웠습니다 — 이름이
upstream 으로 정의돼 있으면 변수가 DNS 보다 그 블록을 먼저 집어서, 변수를 써도 옛 IP 를
그대로 씁니다.

#### 대신 `/api` 접두사 제거가 `rewrite` 로 옮겨졌습니다

**이 결정의 값은 대부분 여기 있습니다.** 전에는 `proxy_pass http://fastapi/;` 의 **끝
슬래시**가 `/api/auth/login` → `/auth/login` 을 했습니다. `proxy_pass` 에 변수를 쓰면
그 규칙이 적용되지 않아, 끝 슬래시를 붙여도 접두사가 안 떨어지고 백엔드가
`/api/auth/login` 을 받아 404 를 냅니다. 그래서 명시적으로 바꿨습니다:

```nginx
location /api/ {
    set $fastapi_upstream backend:8000;   # rewrite 보다 **먼저**
    rewrite ^/api/(.*)$ /$1 break;
    proxy_pass http://$fastapi_upstream;
}
```

`set` 이 `rewrite` 앞에 와야 합니다. 둘 다 rewrite 모듈이고 `break` 가 그 단계를 거기서
끊기 때문에, 뒤에 두면 `set` 이 아예 실행되지 않습니다. 변수가 빈 채로 남아 500 이 나고
로그에 `invalid URL prefix in "http://"` 가 찍힙니다 — 작업 중 실제로 밟았습니다.

**여기를 틀리면 관리자 로그인이 통째로 깨집니다** (D-015). 그 블록이 프론트와 API 를
같은 오리진으로 묶어 httpOnly 쿠키를 보내는 유일한 길입니다. `:8000` 쪽 `location /` 은
접두사를 안 떼므로 변수만 바꿨습니다.

#### 프론트 업스트림은 그대로 둡니다

`upstream nextjs { server host.docker.internal:3000; }` 는 안 건드렸습니다. 게이트웨이
IP 는 컨테이너 재생성으로 바뀌지 않아 이 문제를 겪지 않고, 굳이 같이 바꾸면 멀쩡한 경로에
변경 위험만 얹습니다.

#### 기각: 배포마다 nginx 재시작

`deploy.yml` 에 `docker compose restart nginx` 한 줄이면 되고 더 간단합니다. 그런데
**원인이 아니라 증상을 미는 것**이라, 컨테이너를 손으로 재생성할 때는 (`docker compose up
-d --force-recreate backend`) 여전히 깨집니다. 배포마다 프론트까지 잠깐 끊기는 것도 대가입니다.

#### 검증

일회용 네트워크에 가짜 backend 와 nginx 를 띄우고, backend 를 재생성해 IP 를 바꾼 뒤
(옛 IP 는 다른 컨테이너가 물려받게 해서 #31 의 "즉시 502" 까지 재현) nginx 를 **재시작하지
않고** 불렀습니다. 같은 이벤트에서 **옛 설정은 502, 새 설정은 200** 이었습니다.

**되돌리려면**: `upstream fastapi` 블록을 되살리고 `proxy_pass http://fastapi/;` 로 돌린 뒤
`/api/` 의 `rewrite` 와 `set` 두 줄을 지웁니다. 세 가지가 한 묶음이라 일부만 되돌리면
로그인이 깨집니다.

## D-021
### `/ask` 의 임베딩 모델을 배포되는 API 프로세스에 상주시킨다

`POST /ask`(제도·문서형 질의응답)를 `daengs_backend` 에 붙이면서 정해야 했던 것은
엔드포인트 하나가 아니라 **임베딩 모델을 어느 프로세스에 둘 것인가** 였습니다. `#23` 이
`/walk` 만 붙이고 `/ask` 를 남겨 둔 이유가 이것이었습니다.

**결론: 지금은 한 프로세스입니다.** 배포되는 API 프로세스(로그인·`/walk`·`/training` 과
같은 곳)에 `qwen3-embedding-0.6b` 를 CPU 로 상주시킵니다. 상시 비용은 **RAM 약 2.4GB** 하나입니다.

이 결정이 싼 이유는 모델이 앞 카드에서 `bge-m3`(6.5GB) → `qwen3-embedding-0.6b`(1.2GB)로
바뀌어 상주 부담이 1/5 이 됐기 때문입니다. 차원은 셋 다 1024 라 스키마는 그대로입니다.

#### 기각: 사이드카 (compose 서비스 / 호스트 프로세스)

`/ask` 만 별도 프로세스로 띄우고 `daengs_backend` 는 게이트웨이만 갖는 안입니다.
**나중에 갈 곳이지 지금 갈 곳이 아닙니다** — 같은 서버 PC 안에서 프로세스만 나누면
**상주 RAM 이 줄지 않습니다.** 오히려 프로세스가 하나 늡니다. 버는 것은 격리이고,
RAM 은 다른 PC 로 옮길 때 벌립니다. 지금 그 격리를 사려고 배포 대상을 하나 늘리는 것은
이릅니다.

#### 기각: Gemini 임베딩 API

torch 를 아예 안 싣는 안입니다. 질의 인코딩이 네트워크 왕복이 되어 `/ask` 의 지연이
늘고, **문서 쪽 벡터를 만든 모델과 달라집니다** — 코퍼스를 통째로 다시 임베딩해야 합니다.
평가(RAG-024)가 고른 승자를 버리는 것이기도 합니다.

#### 그래서 무엇이 딸려 왔는가

- **컨테이너에 `ml` 그룹이 깔립니다.** compose 의 `command` 가
  `uv sync --frozen --group ml && exec uv run --no-sync dev` 입니다.

  카드를 열 때는 *"`uv run` 이 기본 그룹 기준으로 다시 맞춰 방금 깐 `ml` 을 걷어낸다"* 고
  적어 뒀는데, **재 보니 그렇지 않았습니다** (uv 0.12.5). `uv run` 은 **inexact** 동기화라
  남는 패키지를 지우지 않습니다. 지우는 것은 **인자 없는 `uv sync`**(exact)입니다.

  그래서 조심할 자리가 옮겨집니다 — 위험한 것은 `uv run` 이 아니라 **사람이 컨테이너 안에서
  손으로 돌리는 `uv sync`** 입니다. 그러면 torch 가 빠져 `/ask` 만 503 이 되는데, 다른 API 는
  멀쩡해서 로그에 아무 문제도 안 보입니다. `uv sync --group ml` 로 부르세요.
  `--no-sync` 는 방어선이 아니라 중복 제거로 남깁니다.
- **리눅스용 CPU torch 인덱스를 추가했습니다.** PyPI 기본 휠은 NVIDIA 런타임을 동봉해서,
  마커가 win32 뿐이면 GPU 를 안 쓰는 컨테이너가 수 GB 를 받습니다. `uv lock` 재생성으로
  `nvidia-*` 패키지가 전부 빠졌습니다.
- **HF 캐시 볼륨**(`hf-cache`). 없으면 컨테이너를 다시 만들 때마다 1.2GB 를 다시 받습니다.
- **`POSTGRES_*` 를 backend 컨테이너에 넘깁니다.** `daengs_life.rag` 는 자기 Settings 를 갖고
  `DAENGS_DB_*` 를 **모릅니다.** 안 넣으면 컨테이너 안에서 `localhost:5432` 로 가서
  `/ask` 만 502 가 됩니다. 두 이름 체계를 통일하지 않은 것은 D-018 이 미뤄 둔 규약 정합
  작업이고, 2단계에서 프로세스를 떼면 그쪽이 자기 접속을 가져야 해서 지금 합치면 되돌립니다.

#### 예열은 백그라운드로, 예열 중의 `/ask` 는 **기다리지 않고 503**

모델 로딩(실측 5~7초)을 lifespan 에서 **동기로** 하면 그동안 로그인도 `/walk` 도 502 입니다.
컨테이너가 `reload=True` 로 돌고 배포가 마운트된 소스를 갈아 끼우므로(D-006), 그 일은
**backend 코드가 바뀌는 배포마다** 일어납니다. 그래서 `asyncio.to_thread` 로 돌립니다.

두 벌이 올라가는 것을 막는 장치는 lifespan 이 아니라 `deps._ENCODER_LOCK` 입니다. `lru_cache` 는
캐시만 스레드 안전하고 **동시 미스는 막지 않아서**, 락이 없으면 예열 중에 들어온 `/ask` 가
두 번째 1.2GB 를 올립니다 — 상주 RAM 이 유일한 상시 비용인데 그 순간 2배가 됩니다.

**처음에는 그 락을 `/ask` 가 기다리게 뒀는데, 첫 배포에서 그 대가를 실측했습니다** (`#37`).
`#35` 를 머지한 배포(2026-08-27), `hf-cache` 볼륨이 비어 있는 상태입니다.

| | |
| --- | --- |
| backend 재생성 다운타임 | 약 20초 (전체 API 502 — 컨테이너가 `ml` 그룹을 설치) |
| **1차 `/ask`** | **504 at 60.06s** — 본문이 nginx 의 `<title>504 Gateway Time-out</title>` |
| 2차 | 200 at 22.5s |
| 3·4차 | 200 at 1.82s / 1.77s |

버그가 아니라 **설계한 대로 동작한 결과**입니다. 콜드 캐시에서는 로드에 가중치 1.2GB
다운로드가 얹혀 60초를 넘고, nginx 의 `proxy_read_timeout`(60초)이 먼저 끊습니다.
**기다린 대가가 나쁩니다** — 사용자는 60초를 물고서 우리가 내지 않은 HTML 오류 페이지를
받고, 상태 코드도 본문도 우리 손을 떠나 프론트(`lib/life-rag.ts`)가 읽을 것이 없습니다.

**그래서 예열이 도는 중이면 기다리지 않고 즉시 503 + `Retry-After` 입니다.** `ml` 이 없을 때
`/ask` 만 503 이 되는 규칙(*"요청이 틀린 게 아니라 환경이 덜 갖춰졌다"*)과 같은 자리이고,
프론트가 *"모델을 올리는 중입니다"* 를 띄우고 다시 물을 수 있습니다.

- **락은 없애지 않았습니다.** 락의 목적은 두 벌 적재를 막는 것이고 그건 여전히 필요합니다.
  바뀐 것은 *"기다린다"* 가 *"안 기다리고 503"* 이 된 것뿐입니다.
- **nginx 의 60초를 늘리는 것은 답이 아닙니다.** 늘리면 사용자가 60초보다 **더** 기다립니다.
  문제는 타임아웃 값이 아니라 기다리게 한 쪽이고, 늘려도 브라우저·프론트의 타임아웃이
  그다음에서 같은 일을 합니다.
- **예열이 꺼져 있으면(`DAENGS_WARM_UP_ENCODER=false`) 기다리는 것이 맞습니다.** 그때는 아무도
  예열하지 않아 첫 요청이 로드를 무는 것이 설계입니다. 그래서 `_ENCODER_LOCK.locked()` 로
  *"락이 잡혀 있다"* 만 보면 안 되고 **누가 잡고 있는지**를 갈라야 합니다
  (`deps._WARM_UP_IN_PROGRESS`) — 안 그러면 그 PC 에서 동시 요청 중 뒤엣것이 엉뚱하게 503 을
  받고, 예열이 꺼져 있는 한 계속 그렇습니다. 여기가 이 변경의 유일한 함정입니다.
- **1회성이지만 매번은 아닙니다.** `hf-cache` 가 채워진 뒤에는 재현되지 않습니다. 다만
  **볼륨을 지우거나 모델을 바꾸면 다시** 옵니다 — 그때 이 503 경로가 실제로 값을 합니다.
- **배포 다운타임 20초는 별개입니다.** 컨테이너가 `ml` 그룹을 설치하는 동안 전체 API 가
  502 인 것은 이 결정이 다루는 범위가 아니고, `backend-venv` 볼륨이 채워진 뒤에는 짧아집니다.

`tests/test_ask_warm_up.py` 의 **단언이 아니라 뜻을 바꿨습니다** — 전에 지킨 것은 *"예열 중에
들어온 요청이 기다렸다가 같은 한 벌을 받는다"* 였고, 이제는 *"기다리지 않고 503, 그래도 두
벌은 아니다"* 입니다. 두 벌을 안 올린다는 원래 목적은 같은 테스트가 그대로 지킵니다.

`DAENGS_WARM_UP_ENCODER=false` 로 끌 수 있습니다. `tests/conftest.py` 가 그렇게 합니다 —
안 끄면 `ml` 이 깔린 개발 PC 에서 `TestClient` 를 여는 테스트마다 모델이 올라오고
**실서버 DB 에까지 붙습니다.**

#### `ml` 이 없으면 `/ask` 만 503

개발 PC 는 `uv sync` 만 해도 backend 가 떠야 합니다. `get_encoder` 는 로드 실패를
**503** 으로 옮깁니다(500 이 아닙니다 — 요청이 틀린 게 아니라 환경이 덜 갖춰진 것이고,
`GEMINI_API_KEY` 없음을 503 으로 보내는 것과 같은 규칙입니다).

`tests/test_main_stays_light.py` 의 **단언은 그대로 두고 뜻만 바꿨습니다.** 전에 지킨 것은
*"컨테이너가 `ml` 없이 떠야 한다"* 였고, 이제는 *"`ml` 없는 개발 PC 에서도 backend 가 뜨고
`/ask` 만 503 이어야 한다"* 입니다. 단언이 그대로 통과하는 이유는 `daengs_life` 가 무거운
것을 전부 함수 안에서 import 하기 때문입니다 — 무거워지는 것은 import 가 아니라 예열입니다.

#### 조용히 틀리는 자리 하나

**서빙 키와 코퍼스의 임베딩 모델이 다르면 검색이 에러 없이 무의미한 순위를 냅니다.**
두 벡터가 다른 공간에 있어 코사인이 무의미해지는데, 세 모델의 차원이 전부 1024 라 예외가
하나도 안 납니다. 그래서 기동 때 `documents.metadata->>'embedding_model'` 과 대조해
경고를 남깁니다. **막지는 않습니다** — 교체는 정상 경로이고, 조용한 것만이 문제입니다.

#### Gemini 호출

모델은 `gemini-3.1-flash-lite`, 타임아웃은 **30초**입니다. 안 걸면 무제한이라 상류가 물리면
`/ask` 를 돌리는 스레드풀 워커를 그대로 잡고 있습니다(FastAPI 가 `def` 컨트롤러를
스레드풀에서 돌립니다). nginx 기본 `proxy_read_timeout`(60초) 안쪽이라 **우리가 먼저**
504 를 냅니다.

⚠ `HttpOptions.timeout` 은 초가 아니라 **밀리초**입니다. 설정 이름이 `gemini_timeout_ms`
인 것과 `tests/test_ask_api.py` 의 단위 고정 테스트가 한 쌍입니다.

에러 코드는 **일부러 갈라 둡니다** — 404(근거 없음) / 502(상류가 죽음) / 503(키·모델 없음)
/ 504(우리가 건 타임아웃). 2단계에서 게이트웨이를 두게 되면 이것을 뭉개면 안 됩니다.

#### 2단계 — 언제 프로세스를 뗄 것인가

ⓐ `docker stats daengs-backend` 실측이 서버 여유를 위협하거나 스왑이 보일 때
ⓑ backend 배포마다의 5~7초가 실제로 거슬릴 때
ⓒ 동시 요청에서 torch 스레드 경합이 관찰될 때
ⓓ 임베딩을 GPU 로 돌리고 싶어질 때(= 개발 PC 로의 이사)

`daengs_life.app.main:app` 이 **이미 독립 ASGI 앱**이라 하는 일은 등록 두 줄과 예열 한 줄을
게이트웨이로 바꾸는 것뿐입니다. **그래서 그 접점을 이 카드에서 흐리면 안 됩니다** — 특히
DB 접속을 `DAENGS_DB_*` 로 통일하고 싶어지는 자리에서 통일하면 나중에 되돌립니다.
호스트 프로세스가 아니라 **compose 서비스**를 권합니다(재부팅 후 사람이 안 띄워도 됩니다).

**되돌리려면**: `main.py` 의 `include_router(ask...)` 와 예열 한 줄, compose 의 `--group ml`
· `hf-cache` · `POSTGRES_*`, `pyproject.toml` 의 `pytorch-cpu` 인덱스를 지우고 `uv lock` 을
다시 만듭니다. `/ask` 는 `uv run uvicorn daengs_life.app.main:app --port 8100` 으로 계속 돕니다.

## D-022
### 스크리닝 모델을 `backend/` 가 아닌 최상위 폴더로

피부 병변 스크리닝을 `skin-screening/` 최상위 폴더에 독립 서비스로 두었습니다.

`backend/` 는 MVC2 계층 규칙(D-011)이 걸려 있는 자리이기도 합니다. 이 폴더는

그래서 원본 구조를 그대로 두고, 대신 어느 쪽이 원본인지를 못 박아 두었습니다
(`skin-screening/CLAUDE.md`). **고칠 일이 생기면 원본을 고치고 다시 복사합니다.**

`ai-assistant/`(#14)도 같은 모양입니다 — 최상위 폴더, 자체 `pyproject.toml` 과
`uv.lock`, 자체 정적 화면.

**지금은 배포에 안 붙어 있습니다.** compose·nginx·`deploy.yml` 어디에도 없어서
`dev` 에 머지돼도 서버에서 아무것도 안 돕니다. 붙일 때 정할 것:

* **가중치는 git 에 안 들어갑니다.** `best.pt` 가 163MB / 189MB 이고 GitHub 은
  파일당 100MB 가 하드 리밋입니다. AI Hub 데이터는 재배포 금지이기도 합니다.
  → 서버 PC 디스크에 한 번 두고 `read_only` 볼륨으로 마운트합니다.
  `.env` 와 암호화 키(D-012)를 다루는 방식과 같습니다 — **재배포해도 안 지워집니다.**
* 서버 PC 에 GPU 가 있는지. 없으면 CPU 로 사진 한 장에 0.6~3초입니다 (실측 615ms).
* nginx 경로. backend 와 마찬가지로 포트를 직접 열지 않습니다 (D-005).

## D-024
### 스크리닝은 별도 컨테이너로, profile 로 꺼둔 채 들여온다

`skin-screening` 을 compose 서비스로 정의하되 `profiles: ["screening"]` 을 걸어
**기본 `docker compose up -d` 에서는 안 뜨게** 했습니다. nginx 에는 `daengback`
아래 `location /screen/` 을 얹었습니다 — **새 포트를 열지 않습니다.**

#### backend 에 넣지 않은 이유

backend 프로세스에는 이미 임베딩 모델이 상주합니다 (D-021). 거기에 1·2단계
가중치를 더 얹으면 메모리도 늘지만, 진짜 문제는 **한 프로세스가 죽을 때 같이
죽는 범위**입니다 — 스크리닝이 넘어지면 로그인과 `/ask` 까지 같이 넘어집니다.
스크리닝은 요청이 올 때만 도는 별개의 일이라 같은 프로세스에 있을 이유가 없습니다.

`skin-screening/` 은 **외부 저장소([gayeoniee/deeplearning_test](https://github.com/gayeoniee/deeplearning_test),
공개)의 사본**이기도 합니다 (D-022). `backend/src/` 의 MVC2 계층(D-011)에 맞춰
구조를 바꾸면 재동기화가 diff 로 안 됩니다.

#### profile 로 꺼두는 이유

`.github/workflows/deploy.yml` 이 배포 때 **`docker compose up -d` 를 직접 돌립니다.**
켜진 채로 머지하면 가중치가 없는 서버에서 컨테이너가 재시작 루프에 빠집니다.
profile 뒤에 두면 머지가 서버 상태를 **하나도 안 바꿉니다.**

#### 앱은 `daengback` 아래 경로로 붙인다 — 새 포트를 안 쓴다

앱이 부르는 주소는 **`http://daengback.~/screen/v1/screen`** 입니다.
`nginx/default.conf` 의 `listen 8000` 블록에 `location /screen/` 하나를 얹었습니다.

처음에는 별도 포트(8001)로 잡았다가 되돌렸습니다. **한 번도 열린 적은 없습니다.**
포트를 쓸 이유는 웹 데모 화면 하나뿐이었는데, 실측해 보니 값이 안 맞았습니다.

* **밖에서 열려 있는 포트는 80 뿐입니다.** `daengback` 은 그 80 을 서버 PC 의 8000
  으로 넘겨받고 있습니다. 8001 을 쓰려면 **공유기 포트포워딩 + 서버 방화벽**이
  새로 필요한데, 경로로 붙이면 이미 열린 길을 그대로 씁니다.
* **HTTPS 를 붙일 때 한 번에 됩니다.** 지금 전부 평문 http 이고(앱은 디버그
  빌드에서만 `usesCleartextTraffic` 으로 통과시키는 중), 언젠가 TLS 를 붙여야
  합니다. 별도 포트였으면 인증서를 따로 매야 합니다.
* 앱 입장에서도 `apiBaseUrl` 과 **같은 호스트**라 다룰 주소가 하나 줄어듭니다.

대가는 **웹 데모 화면이 서버에서는 안 돈다**는 것입니다. `demo/index.html` 이
`fetch('/healthz')` 로 오리진 루트를 부르는데 접두사 아래에서는 어긋나고, 그 파일은
위에서 말한 **사본이라 고칠 수 없습니다**. 그 화면은 개발·명세용이라 각자 PC 에서
`serve.py` 로 띄워 보면 됩니다 — 제품은 앱입니다.

#### 설정 반영은 `reload` 로 한다

`nginx/default.conf` 는 컨테이너에 **얹혀만** 있습니다. 내용이 바뀌어도 컨테이너
명세가 그대로라 `docker compose up -d` 가 nginx 를 다시 만들지 않고, nginx 는
설정을 **뜰 때 한 번** 읽으므로 스스로 다시 읽지도 않습니다. **그래서 이 설정이
들어간 커밋을 머지해도 서버는 그대로입니다** — 켤 때 한 번 알려주면 됩니다.

```powershell
docker compose exec nginx nginx -t          # 문법 검사
docker compose exec nginx nginx -s reload   # 무중단 반영
```

`restart` 가 아니라 `reload` 인 이유: 끊기지 않고, **새 설정이 깨져 있으면 바꾸지
않고 옛 설정으로 계속 돕니다.** `restart` 는 그 경우 nginx 가 못 떠서 사이트가
통째로 내려갑니다.

#### 그래도 켜는 시점은 사람이 고른다

`serve.py` 는 **인증·레이트 리밋이 없는 데모 서버**입니다. profile 을 켜는 순간
`daengback/screen/` 이 인증 없는 업로드 엔드포인트가 됩니다. 인증을 붙이는 것은
별도 카드이고, 그전까지는 켜는 시점을 사람이 정합니다.

#### 가중치는 코드와 따로 간다

`best.pt` 가 163MB / 189MB 라 **GitHub 의 파일당 100MB 하드 리밋**에 걸립니다
(라이선스 문제가 아닙니다 — AI 허브 약관상 학습 결과물의 배포는 자유롭습니다).
서버 디스크에 두고 `SCREENING_RELEASE_DIR` 로 가리켜 `:ro` 로 물립니다.
`releases/<커밋해시>/` **바깥**이라 재배포해도 안 지워집니다 — `.env` 와 암호화
키(D-012)를 다루는 방식과 같습니다.

추론 경로에 파일 쓰기가 없어서 읽기 전용으로 충분하고, `Engine.load` 가
`pretrained=False` 로 부르므로 **기동할 때 네트워크도 안 씁니다** (backend 가
`hf-cache` 볼륨을 둔 이유가 여기에는 없습니다).

## D-025
### 홀로그램 도감을 조직 public 저장소 + GitHub Pages 로 분리

`frontend/public/neo-hologram/` 을 **`SAJOYO/DAENGS_CARDS`** 로 옮기고 이 저장소에서
지웠습니다. 서빙은 GitHub Pages 이고 주소는 <https://cards.weareithero.cloud/> 입니다.

**이 기록은 "뺐다"는 사실입니다.** 어떻게 서빙하는지·왜 public 인지는 저쪽
`docs/decisions.md` 의 `CARDS-001` 이하에 있습니다. 접두사가 달라(`CARDS-` / `D-`)
번호가 부딪히지 않습니다.

#### 왜 뺐나

도감은 DAENGS 제품의 일부가 아니라 **프레임워크 없이 만든 카드 데모**입니다.
그런데 `public/` 안에 있는 동안은 세 가지가 따라붙었습니다.

- 도감의 CSS 한 줄만 고쳐도 `dev` 머지가 **DAENGS 전체를 재배포**했습니다.
- 자체 서버가 nginx `:80` 평문이라 **자이로(DeviceOrientation)가 영영 안 켜졌습니다.**
  그 API 는 secure context 를 요구합니다. Pages 는 HTTPS 라 이 제약이 그냥 사라집니다.
- PM2·러너·nginx 중 아무거나 죽으면 도감도 같이 죽었습니다. 지금은 무관합니다.

#### 복붙이 아니라 `git subtree split` 으로 옮겼다

폴더를 건드린 커밋만 뽑아 히스토리를 살린 채 넘겼습니다. 절차의 정본은 저쪽
`docs/migration.md` 이고, 여기 다시 적지 않은 것은 의도입니다 — 두 군데가 되면 어긋납니다.

#### 링크 교체와 폴더 삭제를 한 PR 에 묶은 이유

`dev` 머지가 곧 배포라, 나눠서 머지하면 그 사이에 랜딩이 없는 주소를 가리키는
**404 구간**이 생깁니다.

#### 여기 남은 것

`tools/neo-hologram-layers.py` 와 `tools/art-src/` 는 이 저장소에 남습니다. 원화 원본이
수 MB 라 `.gitignore` 로 빠져 있어서 **새 저장소로 간 것은 결과물인 `art/*.webp` 뿐**이고,
스크립트의 입력이 여기 있기 때문입니다. 결과물의 목적지만 `DAENGS_CARDS/art/` 로 바뀌었습니다.
webp 변환기는 개인 저장소 `choiyc05/gohome` 에만 있습니다 — 원화를 새로 받으면
이 셋의 위치부터 확인해야 합니다.

## D-026
### Place 검색은 별도 컨테이너 + 별도 PostGIS 로, profile 로 꺼둔 채 들여온다

DAENGS_geo 에서 검증을 마친 Place 검색을 최상위 `place-search/` 로 들여옵니다 —
D-022(최상위 폴더)·D-024(compose profile 로 꺼둔 착륙)와 같은 방식입니다.
`profiles: ["place"]` 라 기본 `docker compose up -d` 에서는 아무것도 안 뜹니다.

현재 착륙 범위는 이렇습니다.

```
place-search → place-db
DAENGS_APP  -X→ 공개 경로 없음
```

#### backend 에 넣지 않은 이유

- 선행 조건이 이미 코드로 증명돼 있습니다. 원본 쪽 정리(rkbuhtig/DAENGS_geo#148:
  profile 역참조 제거, #149: provider/walk/journey 없는 전용 진입점)로 이 유닛은
  **PostGIS 만 있으면 뜹니다.** 별도 컨테이너의 비용이 사실상 사라진 상태입니다.
- in-process 로 넣으면 패키지 이름·설정·세션 체계를 이관과 **동시에** 갈아야 하고,
  장애 도메인도 합쳐집니다 (D-024 가 스크리닝을 밖에 둔 이유와 같습니다).
  나중에 정말 필요하면 in-process 로 접는 것은 쉽고, 반대는 비쌉니다.
- backend 는 place-search 기동에 **종속되지 않습니다**. place profile 을 켜지 않아도
  auth/ask 를 포함한 기존 서비스는 이전과 똑같이 떠야 합니다.

#### place-db 를 pgvector 와 합치지 않은 이유

place 스키마는 `CREATE EXTENSION postgis` 부터 시작하는 자기 역사(Alembic 리비전
0001~0020)를 갖고 있습니다. 최초 통합에서 DB 통합·이미지 교체·마이그레이션 번역을
코드 이관과 동시에 하면 문제가 났을 때 원인 축이 늘어납니다. 합치는 것은 서버 PC 의
메모리가 실측으로 부족해질 때 다시 봅니다.

**"스키마 원본은 `db/init/`, Alembic 안 씀" 규칙은 dev DB(pgvector) 한정입니다.**
place-db 의 스키마 원본은 `place-search/alembic` 이고, 리비전 히스토리를 개조하지
않고 통째로 가져왔습니다 (walk 용 빈 테이블 몇 개가 생기는 것이 히스토리 분기보다
쌉니다 — `place-search/UPSTREAM.md`).

#### API 는 아직 nginx 에 노출하지 않았다

D-024 의 profile 패턴만 차용하고 `/screen/` 같은 public ingress 는 복제하지 않습니다.
place-search 의 `/v2/places/search` 는 **내부 계약**입니다 — 인증이 없고, 개의
identity 가 아니라 선택적인 값(size/weight/age)을 받으며, 값이 없어도 검색합니다.
이번 착륙에서는 공개 연결을 만들지 않았습니다. APP 이 어떤 경로로 호출할지는 실제
클라이언트 계약을 확인한 별도 PR 에서 정하며, backend 나 반려견 프로필을 선행 조건으로
두지 않습니다.

#### 이관 이후의 소유권

Place 검색의 canonical 구현은 **이 저장소**입니다. geo 쪽 사본은 동결이며(그쪽 산책
연구가 facility corpus 를 참조해 삭제하지 못함), 검색 수정은 여기서만 합니다.
경계를 지키는 것은 문서가 아니라 `place-search/tests/test_boundary.py` 입니다 —
진입점 closure 화이트리스트와 "backend 를 import 하지 않는다"를 CI 가 잽니다.

## D-027
### APP의 기존 Place 요청은 nginx가 place-search로 그대로 전달한다

D-026에서 착륙만 끝낸 Place 검색을 DAENGS_APP의 현재 계약에 연결합니다. APP과
place-search가 이미 같은 `POST /v2/places/search` 요청·응답을 쓰므로 nginx는 URI나
본문을 번역하지 않습니다.

```
DAENGS_APP → daengback:8000/v2/places/search → nginx → place-search → place-db
                                                    backend -X→
                                                Dog Profile -X→
```

- `location /v2/places/`만 place-search로 보내며 나머지 8000번 경로는 계속 backend로 갑니다.
- 요청에 `conditions`가 없어도 되는 기존 browse-mode 계약을 유지합니다. Dog Profile을
  조회하거나 검색 입력으로 만들어 주는 중계 계층은 두지 않습니다.
- 실제 배포에서 요청을 받을 수 있도록 place-search와 place-db의 `place` profile을
  해제합니다. 스키마는 place-search가 뜨기 전에 기존 Alembic 이력을 적용합니다.
- place-db는 호스트 포트를 열지 않습니다. 검색 서비스는 compose 네트워크에서만 DB에
  붙고, 외부 진입점은 nginx 하나뿐이라는 기존 인프라 경계를 따릅니다.
- 공공데이터 키는 여전히 적재 배치에만 필요합니다. 빈 DB에서도 검색 서버와 공개 API는
  정상 기동하며, 데이터 적재 시점이나 추천 정책을 이 연결 PR에서 새로 정하지 않습니다.
