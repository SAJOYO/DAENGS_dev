## 2. 오케스트레이션 안에서 이 파트의 자리

계약·상태·라우팅은 `docs/orchestration/contracts.md` · `docs/orchestration/routing.md`(#80) 가 원본이다. 여기서는 **이 파트가 그 틀에
꽂히려면 무엇을 내야 하는가**만 적는다.

```
/assistant/query → LangGraph
   라우터(분류기) → RoutePlan{requests[], handoffs[], clarify}
   → LifeCapabilityAdapter.run(LifePayload)  ─in-process→ daengs_life.app.services.ask.ask()
     WalkCapabilityAdapter.run(WalkPayload)  ─in-process→ daengs_life.app.services.walk.walk()
   → CapabilityResult{OK | ABSTAINED | REFUSED | PENDING | ERROR | TIMEOUT}
   → 결정적 집계 → AssistantResponse
```

**용어 — Walk 가 둘이다.** 위 `WalkCapabilityAdapter` 와 능력 이름 `walk` 는 Life 의 **산책 적합도**(`daengs_life.realtime`, RT-)다.
`backend/src/daengs_walk/`(D-045 · D-046 · D-047)는 GPS 산책 **기록**·Cellophane·Capsule 이고 `/app/walks` 로 나가며, 오케스트레이션의
실행 대상이 아니다. 이 문서에서 "Walk" 는 전자다. HTTP 경로는 A4(#176)로 `/life/walk-conditions` 가 됐지만 **능력 이름 `walk` 는 09-21 전에
바꾸지 않는다** — 벤치마크 골드 80문항 · 앱이 읽는 `results[].capability` 가 그 값에 묶여 있다 (§5).

### 경계 — 주제가 아니라 **근거의 종류**로 긋는다

"생활"은 주제로는 끝이 없다. 이 파트의 실제 경계는 처음부터 하나였다: **출처를 인용할 수 있는 답만 한다** (KPI · `/life/ask` 의 404 ·
RAG-008 ③ 이 `care`·`emergency` 를 뺀 이유).

| Life 가 답한다 | 근거의 종류 |
| --- | --- |
| 규정 · 제도 · 절차 · 조건 · 요금 · 기한 | 법령 · 조례 · 고시 · 약관 · 기관 공식 안내 (`trust_level`: `law` > `official` > `guideline` — **`guideline` 은 아직 0건이다**, RAG-060 ⑥) |
| 지금/오늘의 조건 판정 | 공공 API 직조회 — `/life/walk-conditions`, (앞으로) 분실 조회 |

| Life 가 답하지 않는다 | 이유 | 어떻게 거절·넘기나 (2026-09-03 계약 실물에 맞춤) |
| --- | --- | --- |
| **이 개의 몸**에 대한 판단 — 증상 · 진단 · 용량 · 응급 | 문서가 아니라 판단 (RAG-008 ③) | **Life 가 REFUSED** — `refusal.code` = `medical_boundary` / `emergency_boundary` (A3a). 능력은 handoff 를 낼 수 없다 — `CapabilityResult` 에 그 필드가 없다 (contracts §4) |
| **이 개의 행동**을 바꾸는 계획 — 짖음 · 배변 · 입질 교정 | 〃 | 라우터가 `training` 을 EXECUTE 로 같이 고른다(다중 선택). Life 는 근거 없으면 `no_evidence` 기권 — **별도 핸드오프 불필요** |
| **어디** — 병원 · 카페 · 숙소 위치 | 장소 데이터는 place 소유 (D-026) | **라우터가 `place` 를 EXECUTE 로 고른다** — ✅ **선다** (D-051 · 2026-09-04). #196 이 능력·어댑터·planner 를 넣었고 v7 이 `ExecuteName` 에 `place` 를 더했다. 옛 상태(*"빈 선택 → 최상위 FAILED"*)는 2026-09-04 에 끝났다 — `A3b`(§3 A) |
| 근거 문서가 코퍼스에 없는 것 | — | 기권 `no_evidence` (넘길 곳 없음) |

### 🔴 위는 **데이터** 이야기다 — 코드는 따로 간다 (2026-09-09)

**GCP 에 닿는 길이 셋인데 위 절은 둘만 말한다.** `#325` 뒤로 "GCP 동기화 손작업은 없다"가 맞지만
그건 **코퍼스에만** 맞고, `daengs_life` **코드**는 그 길로 안 간다.

| 무엇을 고쳤나 | GCP 에 어떻게 닿나 |
| --- | --- |
| backend 코드 (`daengs_backend` 등) | VM `git pull` → 컨테이너 재생성 (`runbook.md` §6) |
| 코퍼스 데이터 | **자동** — 잡이 매일 04:00 에 스스로 크롤~적재 |
| **잡이 도는 코드** (`daengs_life`) | ✅ **`bash infra/gcp/pipeline.sh`** — 버킷에 rsync 한다 (몇 초). 굽지 않는다 |

첫 줄에 `[entrypoint] 코드 <해시>` 를 찍으므로 **어느 코드로 돌았는지 실행 하나만 열면 보인다.**

🔴 **네 번째 줄이 새로 드러났다.** `EF_SEARCH` 는 `daengs_life` 에 있지만 **serving 이 읽는 것은
잡의 코드가 아니라 VM 워크트리(`main`)** 다. 그래서 잡을 아무리 갱신해도 `/life/ask` 의 설정은
스냅샷을 내야 바뀐다 — #427 이 GCP 인덱스를 미룬 이유가 이것이다 (RAG-086 ①-ⓒ).

### ✅ **GCP 잡은 이제 새 코드로 돈다** (2026-09-10 · #427 · RAG-086)

2026-09-10 오전까지 이 절의 제목은 *"지금 GCP 잡은 옛 코드로 돈다 — 그렇게 두기로 했다"* 였다.
`RAG-085` 가 그렇게 판정한 근거는 **비용**이었다: 태그가 `backend/src` 전체의 내용 해시라 잡이
쓰지도 않는 패키지를 고쳐도 **CPU 2.3GB + CUDA 9GB 를 다시 굽고**, 코드를 고칠 때마다 그 비용이
붙는다. 조건은 *"해시 입력 좁히기가 먼저"* 였다.

**#427 은 좁히는 대신 원인을 없앴다.** 코드를 이미지에서 빼서 버킷(`code/` prefix)에 두고
entrypoint 가 `/app/src` 로 복사해 `python -m` 으로 부른다. 그러면 **코드 배포에 굽기가 0 분**이고
이미지는 의존성이 바뀔 때만 굽는다. 좁히기 안을 안 고른 이유는 하나다 — 그것은 *관계없는
패키지를 고쳤을 때만* 굽기를 없애는데, **이 카드가 배포하려던 것이 바로 `daengs_life`** 였다.
근거 셋과 대가는 RAG-086 ②.

| 카드 | 지금 |
| --- | --- |
| **`D16`**(#384) | ✅ **닿았다.** 잡이 새 `load.py` 로 돌아 증분 적재가 GCP 에서도 값을 낸다. 검증은 수동 트리거 1회(`--dry-run`)이고 로그 첫 줄이 `[entrypoint] 코드 a358d860` 이었다 |

⚠ **새 실패 모양이 하나 생겼다: rsync 를 잊는 것.** 옛 판의 *굽기를 잊는 것*과 같은 자리다.
`pipeline.sh` 가 rsync 를 자기 안에 들고 있어 사람이 치는 명령은 하나지만, **다른 길로 코드를
올리면 그 보호가 없다.** 확인은 잡 로그 첫 줄의 `코드 <해시>` 다.

⚠ **`RAG-085` 가 걸어 둔 조건(*"HNSW 를 켜는 순간 이 판단을 되돌려라"*)은 이제 무의미하다.**
그 조건의 위험은 *인덱스를 켠 채 잡이 옛 `load.py` 로 돌면 매일 그래프를 통째로 간다* 였는데,
잡이 새 코드로 돌게 되면서 사라졌다. 그리고 **집 서버 인덱스는 실제로 켰다** (§1 적재 행).
