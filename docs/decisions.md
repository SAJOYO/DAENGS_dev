## D-001
### 백엔드는 Python 3.12 로 고정

`requires-python = ">=3.12,<3.13"`.

3.14 가 이미 설치돼 있었지만 3.12 를 골랐습니다. 데이터/AI 쪽 패키지 생태계가
최신 버전을 따라오는 데 시간이 걸리고, 이 프로젝트는 pgvector·임베딩 관련 의존성이
늘어날 예정이라 wheel 이 확실히 준비된 버전이 안전합니다.

상한(`<3.13`)을 둔 이유는 uv 가 조용히 상위 버전을 골라 로컬과 컨테이너가
갈라지는 것을 막기 위해서입니다.

**바꾸려면**: `pyproject.toml` 과 `backend/.python-version` 을 함께 고치고
`uv lock` 을 다시 돌려야 합니다.

## D-002
### uv 기본 src 레이아웃(패키지 형태)을 그대로 사용

`backend/src/daengs_backend/` 구조. `[build-system]` 과 `[project.scripts]` 를 둡니다.

예전 uv 는 애플리케이션을 비패키지(루트에 `main.py` 하나)로 만들었지만,
현재 버전은 패키지 형태가 기본입니다. 한 번 평평한 구조로 바꿔봤다가 되돌렸습니다.

패키지 형태의 실질적 이득은 **실행 위치에 의존하지 않는다**는 점입니다.
`uv sync` 가 `src` 를 경로에 등록해 주므로 어느 디렉터리에서든
`daengs_backend.main` 으로 import 됩니다. 평평한 구조에서는 현재 작업 디렉터리에
의존해 `from src.config import ...` 가 되고, 컨테이너에서 깨지기 쉽습니다.

패키지 안의 폴더 구분(MVC 등)은 **아직 정하지 않았습니다.** 당분간 평평하게 둡니다.

## D-003
### uv 베이스 이미지를 직접 빌드 (`uv:1`)

`docker/uv/Dockerfile` — `python:3.12.13-slim` + uv 바이너리.

공식 `ghcr.io/astral-sh/uv:python3.12-bookworm-slim` 을 먼저 써 봤고 동작도 했지만,
그 이미지의 uv 가 0.9.30 으로 개발 PC(0.12.3)보다 낮았습니다.
**uv 버전이 다르면 `uv.lock` 형식이 어긋나 배포 때만 실패할 수 있습니다.**
지금은 우연히 호환됐을 뿐입니다.

설치 스크립트를 돌리는 대신 공식 스크래치 이미지에서 바이너리만
`COPY --from` 으로 가져와 버전을 정확히 고정했습니다.

| | 크기 |
| --- | --- |
| `python:3.12.13` | 1.62GB |
| `python:3.12.13-slim` | 179MB |
| `uv:1` | 253MB |

풀 이미지가 아니라 slim 을 쓴 이유는 현재 의존성이 전부 wheel 이라 컴파일러가
필요 없기 때문입니다. 소스 빌드가 필요한 패키지를 넣게 되면 그때 `build-essential`
을 추가하거나 binary wheel 쪽을 씁니다.

**바꾸려면**: Dockerfile 의 `ARG UV_VERSION` 을 올리고 태그도 `uv:2` 로 올립니다.

## D-004
### backend 컨테이너에 폴더가 아닌 파일별로 마운트

`./backend/pyproject.toml`, `uv.lock`, `README.md`, `src` 를 각각 마운트합니다.

`./backend` 를 통째로 마운트하면 **호스트의 `backend/.venv` 가 함께 들어갑니다.**
그 안에는 Windows 용 `Scripts/python.exe` 가 있어 리눅스 컨테이너에서 실행되지
않습니다. `uv run` 이 그것을 쓰려다 깨지거나, 조용히 다시 만들면서 호스트 쪽
venv 를 망가뜨립니다.

두 가지를 놓고 골랐습니다.

- **A. 폴더째 마운트 + `/app/.venv` 에 익명 볼륨을 씌워 가리기** — 설정은 짧지만
  그 한 줄의 의미를 모르면 지웠다가 다시 깨집니다.
- **B. 파일별 마운트** — 줄 수는 늘지만 **무엇이 컨테이너로 들어가는지 목록만 봐도
  드러납니다.**

오래 유지할 설정이라 B 를 택했습니다.

여기에 더해 venv 자체를 마운트 경로 밖(`UV_PROJECT_ENVIRONMENT=/opt/venv`)으로
빼고 uv 캐시와 함께 볼륨에 두었습니다. 콜드 기동 4초, 웜 재시작 2초입니다.

**주의**: `pyproject.toml` 의 `readme = "README.md"` 때문에 `README.md` 도
마운트해야 합니다. 없으면 `uv sync` 가 패키지 빌드 단계에서 실패합니다.

## D-005
### backend 를 nginx 뒤에 두고 포트를 열지 않음

```
daengs.~     :80   → nginx → host.docker.internal:3000  (PM2 Next, 호스트)
daengback.~  :8000 → nginx → backend:8000               (FastAPI, 컨테이너)
```

backend 컨테이너를 8000 에 직접 노출하는 쪽이 지금 당장은 작업이 적습니다.
그래도 nginx 를 앞에 둔 이유는 두 가지입니다.

1. **HTTPS 를 붙일 자리가 한 곳으로 모입니다.** 지금은 http 라 체감이 없지만,
   인증서를 애플리케이션 안에서 처리하게 하면 훨씬 번거로워집니다.
2. **재현성.** 최종 목표가 "소스 받아서 `docker compose up -d` 하나"인데,
   직접 노출하면 라우팅이 compose 의 `ports:` 와 nginx 설정 두 군데로 흩어집니다.

포트포워딩(`daengback.~` → 8000)은 그대로 두고 nginx 가 8000 을 받게 했습니다.
외부 설정을 바꾸지 않아도 됩니다.

**CORS 는 이 결정과 무관하게 필요합니다.** 브라우저에게 `daengs.~` 와
`daengback.~` 는 다른 오리진이라, 앞에 무엇이 있든 상관없습니다.
`DAENGS_CORS_ORIGINS` 에 넣는 값은 **부르는 쪽인 프론트 도메인**입니다.

**남은 것**: 프론트가 아직 PM2 로 호스트에서 돕니다. 이것까지 컨테이너로 옮기면
`host.docker.internal` 이 사라지고 전부 compose 안으로 들어옵니다.

## D-006
### 배포도 개발 모드(reload)로 운영

컨테이너 명령이 `uv sync --frozen && exec uv run dev` 입니다.

학습·개발용 프로젝트라 코드 반영 속도를 우선했습니다. 배포 시 `git checkout` 이
마운트된 파일을 갱신하면 uvicorn 이 알아서 리로드하므로, 컨테이너를 재시작하지
않아도 새 코드가 뜹니다.

**대가**: `uv sync` 는 컨테이너가 뜰 때만 돕니다. 의존성을 바꾼 커밋을 배포하면
소스만 반영되고 패키지는 없어서 `ModuleNotFoundError` 가 납니다.
워크플로우를 건드리지 않기로 해서, **의존성을 바꾼 날만 서버에서 수동으로**
`docker compose restart backend` 를 실행합니다(웜 2초).

리로드 감시는 `src` 로 범위를 좁혔습니다. Windows 바인드 마운트에서는
inotify 가 전달되지 않아 폴링(`WATCHFILES_FORCE_POLLING`)을 써야 하는데,
폴링은 대상이 넓으면 CPU 를 계속 씁니다.

**바꿔야 할 때**: 실제 사용자 트래픽을 받게 되면 `uv run run` + 워커 여러 개로
가야 합니다. 그때는 소스를 마운트가 아니라 `COPY` 로 굽는 이미지가 필요합니다.

## D-007
### Postgres 5432 를 LAN 에 개방

`"${POSTGRES_PORT:-5432}:5432"` — `0.0.0.0` 바인딩입니다.

같은 네트워크의 팀원이 각자 PC 에서 DB 에 붙어야 해서 의도적으로 열어 둡니다.
`127.0.0.1` 로 묶으면 이 PC 안에서만 접속됩니다.

**조건**: `POSTGRES_PASSWORD` 를 `.env` 에서 반드시 기본값이 아닌 값으로
지정해야 합니다. 기본값 `postgres` 를 그대로 두면 네트워크의 누구나 들어옵니다.

pgAdmin(`tools` 프로파일)은 `PGADMIN_CONFIG_SERVER_MODE: "False"` 라
로그인이 없습니다. 띄워 두는 동안에는 인증 없는 DB 관리 콘솔이 열려 있는 셈이니
필요할 때만 켜세요.

## D-008
### DB collation 을 `C` 로 유지

`POSTGRES_INITDB_ARGS: "--encoding=UTF-8 --locale=C"`.

처음엔 한글 정렬이 깨질 거라 생각했지만, 실제로 확인해 보니 아니었습니다.

```
C collation : Zebra < apple < 가방 < 나무 < 하늘 < 힘
ICU (ko-KR) : 가방 < 나무 < 하늘 < 힘 < apple < Zebra
```

**한글끼리의 순서는 C 에서도 정확합니다.** 현대 한글 완성형(가~힣)이 유니코드
코드포인트 순서와 가나다 순서가 일치하도록 배치돼 있기 때문입니다.

실제 차이는 영문 대소문자 순서, 한글·영문 혼합 순서, NFD(자모 분리) 문자열입니다.
검색·저장·pgvector 동작에는 영향이 없고, `LIKE 'foo%'` 인덱스는 오히려 C 가
유리합니다.

정렬이 필요한 곳에서는 쿼리나 컬럼 단위로 붙이면 됩니다.

```sql
SELECT ... ORDER BY name COLLATE "ko-KR-x-icu";
```

**바꾸려면**: initdb 인자는 최초 생성 때만 반영되므로 볼륨을 지우고 다시
만들어야 합니다. 데이터가 쌓인 뒤에는 번거로우니, 필요해지면 컬럼 단위로
붙이는 쪽을 권합니다.

## D-009
### 환경 변수 파일을 compose 용과 앱 용으로 분리

| 파일 | 읽는 주체 | 내용 |
| --- | --- | --- |
| `.env` | docker compose | `POSTGRES_*`, `PGADMIN_*` |
| `backend/.env` | FastAPI 앱 | `DAENGS_*` |

한 파일에 몰아두면 "이 값을 누가 읽는지"가 흐려집니다. 특히 DB 접속 정보는
컨테이너를 만드는 쪽 설정이지 앱 설정이 아닙니다.

`backend/.env` 의 경로는 `config.py` 가 자기 위치 기준으로 잡습니다.
상대 경로(`env_file=".env"`)로 두면 실행 디렉터리에 따라 파일을 못 읽습니다.

compose 에서는 파일 마운트 대신 `env_file` + `required: false` 를 씁니다.
파일 마운트로 두면 **파일이 없을 때 도커가 그 자리에 폴더를 만들어 버립니다.**

**서버 준비**: `.env` 는 gitignore 대상이라 체크아웃에 없습니다. 러너 작업 폴더에
두 파일을 한 번 만들어 두세요. `checkout` 의 `clean: false` 덕분에 이후 배포에서
지워지지 않습니다.

## D-010
### pg_trgm 은 지금 넣지 않음

초기 스크립트에서 `CREATE EXTENSION pg_trgm` 을 뺐습니다.

현재 스키마는 순수 벡터 검색입니다. `pg_trgm`(문자 3-gram 유사도)을 쓰는 곳이
없고, 확장만 깔아 둔다고 성능이 달라지지도 않습니다.

**필요해지는 시점**: 하이브리드 검색을 붙일 때입니다. 벡터 검색만으로는
고유명사·숫자·정확한 표현에 취약해서 키워드 검색 점수와 합쳐야 합니다.
PostgreSQL 내장 full-text search 에는 **한국어 형태소 분석기가 없어서**
`to_tsvector('simple', ...)` 는 공백 단위로만 쪼갭니다("훈련을" ≠ "훈련").
그래서 형태소 분석 없이도 동작하는 `pg_trgm` 이 현실적인 선택지가 됩니다.

그때 필요한 것은 두 줄입니다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_documents_content_trgm ON documents USING gin (content gin_trgm_ops);
```

인덱스는 `db/indexes.sql` 에 넣습니다(적재 후 생성 원칙).
**주의**: `db/init/` 은 볼륨이 비어 있을 때만 실행되므로, 이미 만들어진 DB 에는
psql 로 직접 실행해야 합니다.

## D-011
### 백엔드 DB 층은 SQLAlchemy 2.0 async, 패키지 안은 MVC2 계층

`sqlalchemy[asyncio]` + `asyncpg`. `src/daengs_backend/` 안을
`core / models / schemas / repositories / services / routers` 로 나눕니다.

D-002 에서 "폴더 구분은 아직 정하지 않았다"고 미뤄 둔 것을, 관리자 인증을 붙이면서
정했습니다.

**드라이버·ORM.** 생 SQL(psycopg3)도 후보였습니다. 지금 스키마 원본이 손으로 쓴
`db/init/*.sql` 이라 그쪽이 결이 맞는 면도 있습니다. 그래도 ORM 을 고른 이유는
**Repository 계층을 두기로 했기 때문**입니다. 생 SQL 로 Repository 를 만들면
결국 손으로 ORM 을 다시 쓰게 됩니다. 인증만 해도 테이블 서넛이 서로 엮입니다.

asyncpg 를 고른 것은 pgvector 파이썬 패키지가 asyncpg 를 지원해서,
나중에 벡터 검색을 ORM 으로 붙일 때 드라이버를 갈아엎지 않아도 되기 때문입니다.

**계층 구분.** 후보는 셋이었습니다.

| | |
| --- | --- |
| 계층 우선 (MVC2) | 폴더가 `routers/ services/ ...`. 어디에 넣을지 고민이 없고 자바 배경이면 바로 읽힘 |
| 기능 우선 | 폴더가 `auth/ documents/ ...`. 기능 하나가 한 폴더라 팀원끼리 안 부딪힘 |
| 헥사고날 | 도메인이 프레임워크를 모름. 이 규모에선 보일러플레이트가 로직보다 많아짐 |

**계층 우선을 골랐습니다.** 팀에 자바 배경이 있어 이해 비용이 가장 낮습니다.
기능 우선이 팀 작업에는 유리하지만, 지금 기능이 하나뿐이라 이득이 안 보입니다.

**되돌리기 쉽습니다.** 계층 우선 → 기능 우선은 파일 이동과 import 경로 수정이
전부입니다. 다만 시간이 지나면 비싸지는 건 이동이 아니라 **얽힘**입니다.
계층 우선에서는 `services/a.py` 가 `repositories/b.py` 를 불러도 경계를 넘었다고
말해 주는 것이 없어서, 쌓이고 나면 옮기는 게 아니라 푸는 작업이 됩니다.
파일 20~30개가 넘어가면 다시 보세요.

**Alembic 은 넣지 않습니다.** 스키마 원본은 계속 `db/init/*.sql` 이고, `models/` 는
그것을 따라갑니다. 둘이 어긋날 수 있다는 게 이 선택의 대가입니다.
마이그레이션 도구는 **여러 명이 스키마를 각자 고치기 시작할 때** 값이 생깁니다.
그때 `documents` 를 초기 리비전으로 잡고 도입하면 됩니다.
`Base.metadata.create_all` 은 부르지 마세요 — SQL 파일과 원본이 둘로 갈립니다.

**접속 정보.** (D-013 에서 URL 한 줄 → 조각으로 바뀌었습니다. 아래는 당시 기록입니다.)
`backend/.env` 의 `DAENGS_DATABASE_URL` 은 **로컬에서 `uv run dev`**
로 띄울 때 쓰는 값입니다. 컨테이너 안에서는 `localhost` 가 컨테이너 자신이라
닿지 않으므로, compose 의 `environment:` 가 같은 이름으로 덮어씁니다
(`environment` 가 `env_file` 보다 우선). 컨테이너 쪽 값은 최상단 `.env` 의
`POSTGRES_*` 로 조립하므로 **접속 정보가 두 군데로 갈리지 않습니다** (D-009).

**`/health` 는 DB 가 죽으면 503 입니다.** 200 에 `db: "down"` 만 넣으면 모니터링이
실패를 못 잡습니다. compose 의 backend 에는 healthcheck 를 걸지 않았으니
이 503 으로 컨테이너가 재시작되지는 않습니다.
연결 실패는 `SQLAlchemyError` 로 감싸이지 않고 asyncpg 예외나 `OSError` 가
그대로 올라오므로, 상태 확인에서는 예외를 넓게 잡아야 합니다.

## D-012
### 개인정보는 앱단 AES-256-GCM, 키는 용도별로 셋

`core/crypto.py` (AES-256-GCM · HMAC blind index) 와 `core/password.py` (Argon2id).
키는 `DAENGS_AES_KEY` · `DAENGS_BLIND_INDEX_KEY` · `DAENGS_JWE_KEY` 셋으로 나눠
`backend/.env` 에서 받습니다.

| 데이터 | 처리 | 왜 |
| --- | --- | --- |
| 관리자 비밀번호 | Argon2id (단방향) | 되꺼낼 일이 없고, 되꺼내지면 안 됩니다 |
| 앱 회원 이메일 | AES-GCM + blind index | 원문이 필요하고, 중복가입도 막아야 합니다 |
| 전화번호 · 이름 | AES-GCM | 원문이 필요하고, 이 값으로 조회하지는 않습니다 |
| `kakao_id` | 평문 | 로그인 경로의 조회 키입니다 |

**비밀번호에 AES 를 쓰지 않습니다.** 복호화가 되는 순간 키를 쥔 사람이 전원의
비밀번호를 읽습니다. 반대로 AES 는 "나중에 원문을 다시 꺼내 봐야 하는" 값에만 씁니다.
해시 라이브러리는 `argon2-cffi` 를 직접 씁니다 — passlib 은 관리가 멈춰 최신 bcrypt 와
깨집니다.

**DB 가 아니라 앱에서 암호화합니다.** pgcrypto 로 하면 키가 SQL 문에 들어가서
`pg_stat_statements` 와 로그에 남고, DB 에 붙을 수 있는 사람이 곧 복호화할 수 있는
사람이 됩니다. 지금 DB 는 LAN 에 열려 있고(D-007) pgAdmin 은 로그인이 없어서,
그 둘이 갈라져 있는 편이 낫습니다. 대가는 **DB 안에서는 그 컬럼으로 검색·정렬이
안 된다**는 것입니다. 그래서 조회가 필요한 이메일에만 blind index 를 답니다.

**blind index 는 단순 SHA-256 이 아니라 HMAC 입니다.** 이메일은 후보가 뻔해서
키 없는 해시는 사전공격으로 다 맞힐 수 있습니다. 소문자로 정규화한 뒤 해시하며
(`A@x.com` 과 `a@x.com` 이 갈리면 중복가입을 못 막습니다), hex 64자라 `CHAR(64)` 에
그대로 들어갑니다.

**암호문 맨 앞에 키 버전 1바이트를 붙입니다.** `[버전 1B][nonce 12B][암호문+태그]`.
지금은 1 하나뿐이라 아무 값도 아니지만, 키를 갈 때 없으면 전수 재암호화 도중에
어느 키로 암호화된 행인지 알 방법이 없습니다. 나중에는 못 넣습니다.

**키를 셋으로 나눈 이유는 잃었을 때의 결과가 전부 다르기 때문입니다.**

| 키 | 잃으면 | 복구 |
| --- | --- | --- |
| JWE | 전원 로그아웃 | 새로 만들면 끝 |
| blind index | 해시 조회 불가 | AES 키가 살아 있으면 전부 재계산 |
| AES | 암호문이 영구히 안 열림 | 아래 |

**AES 키만 진짜 조심하면 됩니다.** 다만 이 설계에서는 잃어도 서비스가 죽지 않습니다 —
로그인 경로에 암호화 컬럼이 없고(`kakao_id` 는 평문), 개인정보 원본이 카카오에 있어
회원이 다시 로그인하면 채워집니다. 복구가 안 되는 것은 탈퇴자와 **앱에서 직접
입력받은 값**(반려견 정보 등 — 유일본)입니다.

키는 `SecretStr` 로 받아 로그·예외에 값이 찍히지 않게 하고, 기본값은 두지 않습니다.
개발용 기본값을 하나 박아 두면 그게 그대로 서버에 올라갑니다. **키가 없으면 앱이
뜨지 않는 것이 맞습니다.**

**되돌리기**: 암호화를 걷어내는 것은 컬럼 전수 복호화라 데이터가 쌓이기 전이 쌉니다.
키 교체는 버전 바이트 덕에 언제든 되지만, 재암호화가 끝날 때까지 옛 키를 `_KEYS` 에
남겨 둬야 합니다.

## D-013
### DB 접속 정보는 URL 한 줄이 아니라 조각으로

`db_host` · `db_port` · `db_user` · `db_password` · `db_name` 을 따로 받고,
`config.py` 의 `database_url` property 가 SQLAlchemy `URL.create` 로 조립합니다.
D-011 의 `DAENGS_DATABASE_URL` 을 대체합니다.

**개발 PC 와 서버는 호스트만 다릅니다.** 개발 PC 는 서버 IP, 서버 컨테이너는 compose
네트워크의 `pgvector`. URL 한 줄로 받으면 그 한 조각 때문에 접속 정보 **전체**를
`backend/.env` 와 `docker-compose.yml` 두 군데에 각각 적게 됩니다. 조각으로 받으면
compose 는 `DAENGS_DB_HOST: pgvector` 만 덮어쓰면 됩니다.

**이어 붙인 URL 은 비밀번호에 `@` `/` `#` 가 들어가면 깨집니다.** compose 가
`postgresql+asyncpg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@pgvector:...` 로 문자열을
만들고 있었는데, D-007 때문에 `POSTGRES_PASSWORD` 는 기본값이 아닌 값을 쓰게 되어
있어서 언제든 밟을 수 있었습니다. `URL.create` 는 조각을 받아 이스케이프까지 합니다.

**접속 정보의 원본은 여전히 최상단 `.env` 하나입니다** (D-009 유지). 전달 방식만
바뀝니다. compose 가 `POSTGRES_*` 를 읽어 `DAENGS_DB_*` 로 넘깁니다.

**옛 `DAENGS_DATABASE_URL` 은 조용히 무시하지 않습니다.** `extra="ignore"` 라 그냥
두면 무시되는데, 그러면 개발 PC 가 기본 호스트로 붙어 인증 실패를 봅니다 — 원인이
`.env` 의 옛 줄이라는 걸 알아채기 어렵습니다. 그 변수가 보이면 뜨지 않고 무엇을
바꿔야 하는지 알려 줍니다. 팀 전원이 `.env` 를 옮기고 나면 지워도 되는 코드입니다.

**계기.** `#8` 배포 때 `password authentication failed for user "daengs"` 로 backend 가
DB 에 못 붙었습니다. 원인은 최상단 `.env` 의 `POSTGRES_USER` 를 바꿨는데 pgvector
볼륨은 이미 `postgres` 로 초기화된 뒤였던 것입니다 (이 값들은 `db/init/` 과 마찬가지로
볼륨이 빌 때 한 번만 반영됩니다). 접속 정보 자체와는 다른 원인이었지만, 값이 어디서
어떻게 조립되는지 한눈에 안 보인다는 게 그때 드러났습니다.

**대가.** 설정 항목이 하나에서 다섯으로 늘었고, `sqlite://` 같은 다른 URL 을 통째로
넣는 길이 막혔습니다. 테스트에서 그럴 일이 생기면 그때 `database_url` 을 덮어쓰는
탈출구를 두면 됩니다. **지금 미리 두지는 않습니다** — 두 방식이 공존하면 어느 쪽이
이겼는지 매번 확인해야 합니다.

## D-014
### 관리자 권한 5단계를 PG ENUM 이 아닌 `VARCHAR + CHECK` 로

`admin_users.role` 을 이렇게 잡았습니다.

```sql
role VARCHAR(20) NOT NULL
    CHECK (role IN ('ADMIN','OPERATOR','CURATOR','ANALYST','VIEWER'))
```

**다섯 단계.**

| | |
| --- | --- |
| `ADMIN` | 계정·권한 관리까지 전부 |
| `OPERATOR` | 운영 데이터 CRUD + 개인정보 복호화 (계정 관리 제외) |
| `CURATOR` | 지식베이스 문서 + 검색 점검. 개인정보 접근 없음 |
| `ANALYST` | 지표·검색 점검 조회. 쓰기 없음 |
| `VIEWER` | 조회만. 개인정보는 마스킹 |

**지금 실제로 발급하는 것은 `ADMIN` 하나입니다.** 나머지 넷은 자리만 잡아 둔 것이고,
권한 체크 로직도 아직 없습니다. 그런데도 미리 적어 두는 이유는, 나중에 단계를 넣을 때
바뀌는 것이 값 목록이 아니라 **"이 화면은 누가 볼 수 있나"라는 판단 전부**이기 때문입니다.
축을 미리 정해 두면 그때 제약만 갈아끼우면 됩니다.

**왜 ENUM 이 아닌가.** PG ENUM 은 값 추가(`ALTER TYPE ... ADD VALUE`)는 되는데
그 다음이 불편합니다.

- 값 삭제가 없습니다. 쓰지 않게 된 값이 타입에 영원히 남습니다.
- 이름 변경(`RENAME VALUE`)은 되지만 순서 변경은 안 됩니다.
- `ADD VALUE` 는 PG 12 부터 트랜잭션 안에서 되지만, 추가한 값을 **같은 트랜잭션 안에서
  바로 쓸 수는 없습니다.** 마이그레이션 스크립트를 두 번에 나눠야 합니다.

이 컬럼의 목적 자체가 "나중에 구성을 바꿀 여지를 남긴다"인데 ENUM 은 그 반대 방향입니다.
`CHECK` 은 제약을 떨구고 다시 거는 것이 전부입니다.

```sql
ALTER TABLE admin_users DROP CONSTRAINT admin_users_role_check;
ALTER TABLE admin_users ADD CONSTRAINT admin_users_role_check
    CHECK (role IN (...));
```

**대가**는 두 가지입니다. 값 목록이 타입 하나가 아니라 제약 안에 문자열로 들어가서
`\dT` 같은 것으로 한눈에 볼 수 없고(그래서 `COMMENT ON COLUMN` 에 적어 뒀습니다),
같은 목록을 쓰는 컬럼이 여러 개가 되면 제약을 각각 고쳐야 합니다.
지금은 `role` 하나뿐이라 후자는 문제가 아닙니다.

같은 이유로 `admin_users.status` / `app_users.status` 도 `VARCHAR + CHECK` 입니다.
`documents.category` 가 이미 이 방식이라 저장소 전체가 한 가지 방식으로 통일됩니다.

**파이썬 쪽은 문자열입니다.** `models/admin_user.py` 의 `ADMIN_ROLES` 튜플이 같은 값을
들고 있지만, 이것은 리터럴을 흩뿌리지 않으려는 상수일 뿐 `Enum` 타입이 아닙니다.
SQLAlchemy 의 `Enum` 타입을 쓰면 DB 에 타입을 만들려 들기 때문에 쓰지 않았습니다.
**SQL 의 CHECK 을 고치면 이 튜플도 손으로 맞춰야 합니다** (D-011 - Alembic 이 없어
모델이 SQL 을 따라가는 구조의 대가입니다).

**관련**: 관리자(`admin_users`)와 앱 회원(`app_users`)을 한 테이블로 합치지 않은 것,
`app_users` 의 개인정보 컬럼을 암호문 + blind index 로 나눈 것은 PR `#7` 본문의
`## 컨텍스트 메모` 에 적었습니다.

## D-015
### access 는 JWE, refresh 는 DB 에 두는 불투명 토큰

관리자 로그인의 토큰을 두 종류로 나누고, 성격을 정반대로 잡았습니다.

| | 형식 | 수명 | DB |
| --- | --- | --- | --- |
| access | JWE (`alg="dir"` + `enc="A256GCM"`) | 5분 | 안 봅니다 |
| refresh | 뜻 없는 난수 32바이트 | 7일 (절대 만료) | SHA-256 해시로 매번 조회 |

**refresh 를 토큰 안에 담지 않는 이유는 강제 로그아웃입니다.** 계정을 잘랐는데 토큰이
살아 있으면 곤란한데, 무상태 토큰은 만료 전까지 서버가 손쓸 방법이 없습니다.
어차피 DB 를 봐야 한다면 암호화할 이유도 없어서 그냥 난수입니다.
원문은 저장하지 않고 해시만 둡니다 — DB 가 통째로 새어도 그것만으로 유효한 토큰이
되지는 않게.

**access 를 JWS(서명)가 아니라 JWE(암호화)로 한 이유**는 role 과 만료를 클라이언트가
읽지 못하게 하기 위해서입니다. JWT 는 base64 디코딩만으로 내용이 보입니다.
대신 프론트는 자기 권한을 `GET /auth/me` 로 받아와야 하는데, role 은 원래 서버에
물어봐야 하는 값이라 손해가 아닙니다.

**GCM 은 AEAD 라 서명을 따로 얹지 않습니다.** JWS 로 감싼 뒤 JWE 로 또 싸는(nested)
구성이 흔한 실수인데, 발급도 검증도 우리 서버뿐이라 불필요합니다.

**`joserfc` 의 함정**: `jwt.encode`/`jwt.decode` 는 `registry` 가 `JWERegistry` 일 때만
JWE 로 가고, 안 넘기면 **조용히 JWS 경로로 빠집니다.** 에러가 나지 않아서, role 이
평문으로 읽히는 토큰이 나가도 아무도 모릅니다. 토큰이 5조각인지 확인하는 테스트로
고정해 뒀습니다 (JWS 는 3조각).

#### 수명을 5분 / 7일로 잡은 것

access 는 발급 후 취소할 수 없어서, 그 구멍의 크기가 곧 수명입니다. 계정을 정지시켜도
이미 나간 토큰은 5분간 살아 있습니다. 쓰는 사람이 개발자뿐이라 길 이유가 없습니다.

**회전해도 refresh 의 만료는 갱신하지 않습니다(절대 만료).** 슬라이딩으로 하면 매일
쓰는 사람은 영원히 재로그인을 안 하게 되어 상한이 사라집니다.

#### 재사용 감지와 10초 유예 창

refresh 는 쓸 때마다 새 것으로 갈아 끼우고 옛 것을 폐기합니다(회전). 그러면 **이미
폐기된 토큰이 다시 들어왔을 때 탈취를 의심**할 수 있습니다 — 정상 사용자는 새 것을
받아 갔으니 옛 것을 쓸 이유가 없습니다. 그때는 그 계정의 세션을 전부 끊습니다.

문제는 오탐입니다. 한 브라우저의 탭 두 개가 같은 쿠키로 거의 동시에 재발급하면
한쪽은 반드시 방금 폐기된 토큰을 쓰게 됩니다. access 가 5분이라 재발급이 잦고,
30분일 때보다 6배 자주 걸립니다. **폐기된 지 10초 이내면 탈취가 아니라 탭 경합으로
보고 통과**시킵니다.

여기서 "로그아웃한 토큰"과 "회전으로 교체된 토큰"을 구분해야 합니다. 사유 컬럼을
더하는 대신 **폐기 방식을 나눴습니다.**

| 상황 | 행 처리 | 그 토큰이 다시 오면 |
| --- | --- | --- |
| 회전 | `revoked_at` 을 찍고 행은 남김 | 10초 이내면 통과, 이후면 탈취 |
| 로그아웃 | 행을 지움 | 못 찾음 → 즉시 거부 |
| 강제 로그아웃 · 탈취 대응 | 행을 지움 | 못 찾음 → 즉시 거부 |

이렇게 하면 **`revoked_at` 이 있다는 것 자체가 "회전으로 교체됨"을 뜻합니다.**
`db/init/03_auth.sql` 을 고치지 않아도 되고, 서버에 `ALTER TABLE` 을 돌릴 일도 없습니다.

**대량 폐기를 `revoked_at` 으로 하면 안 됩니다.** 다른 세션들이 10초 안에 재발급을
시도하면 유예 창을 타고 새 토큰을 받아 가서, 끊으려던 것이 안 끊깁니다.

**만료된 refresh 는 탈취로 올리지 않습니다.** 만료된 토큰은 쓸모가 없어서, 오래
잠들어 있던 탭 하나 때문에 팀 전체를 로그아웃시킬 이유가 없습니다.

#### 쿠키와 `/api/` 프록시

관리자 웹은 httpOnly 쿠키(`SameSite=Lax`), 네이티브 앱은 `Authorization: Bearer` 입니다.
**토큰 형식과 발급기는 하나를 공유**하고 전달 방식만 다릅니다.
httpOnly 는 JS 가 못 읽는 쿠키라, XSS 가 들어와도 토큰을 퍼가지 못합니다
(`localStorage` 에 두면 그대로 털립니다). 같은 이유로 **응답 본문에도 토큰을 담지
않습니다** — 담으면 httpOnly 로 둔 의미가 없어집니다.

`daengs.~`(:80) 와 `daengback.~`(:8000) 은 브라우저에게 다른 오리진이라 쿠키가 그냥은
실리지 않습니다. 오리진을 유지한 채 보내려면 `SameSite=None + Secure` 인데 `Secure` 는
HTTPS 필수이고 지금은 http 입니다. 그래서 **nginx 의 `/api/` 블록으로 같은 오리진을
만듭니다.** 로컬에서는 `next.config.ts` 의 `rewrites()` 가 같은 모양을 만들어,
프론트 코드는 양쪽에서 똑같이 `fetch("/api/auth/login")` 을 씁니다.

같은 이유로 **CORS 는 사실상 불필요해집니다.** `DAENGS_CORS_ORIGINS` 는 남겨 두되
프록시 경유가 기본 경로입니다.

**HTTPS 로 옮기면 `DAENGS_COOKIE_SECURE=true` 를 켜야 합니다.** 지금 켜면 http 에서
쿠키가 아예 안 실려 로그인하자마자 로그아웃됩니다.

#### 권한은 role 이 아니라 '무엇을 할 수 있는가'로

엔드포인트는 `require(Perm.PII_READ)` 처럼 **권한**을 선언합니다. role 을 직접 비교하면
role 구성을 바꿀 때마다 코드 전체를 뒤지게 되므로, `core/deps.py` 의
`ROLE_PERMISSIONS` 한 곳만 고치면 되도록 한 겹을 둡니다.
이 표는 `03_auth.sql` 의 role 주석(D-014)과 같은 내용이라 **같이 고쳐야 합니다.**

`current_admin` 은 **DB 를 보지 않습니다** — 토큰을 푸는 것으로 끝이고, 그게 무상태
토큰을 쓰는 이유 전부입니다. 대가로 role 변경과 계정 정지가 최대 5분 늦게 반영됩니다.
지금 DB 상태가 필요한 `GET /auth/me` 만 다시 조회합니다.

#### 로그인 실패 제한

`(login_id, IP)` 쌍으로 5회 실패 시 10분 잠급니다. **계정 단위로 세지 않습니다** —
계정 하나를 팀이 공유하고 있어서, 계정으로 세면 한 명이 5번 틀릴 때 전원이 잠기고
아이디만 아는 사람은 누구나 일부러 잠글 수 있습니다.

IP 를 믿을 수 있는 근거는 backend 가 포트를 열지 않는다는 것입니다 (D-005).
nginx 의 `proxy_set_header X-Real-IP $remote_addr` 가 클라이언트가 보낸 같은 이름의
헤더를 덮어쓰므로 위조할 수 없습니다.

**카운터 확인이 계정 조회보다 먼저입니다.** 순서가 바뀌면 잠기는지 여부로 계정 존재가
드러납니다. 같은 이유로 없는 아이디로 두드릴 때도 똑같이 셉니다.

상태는 **프로세스 메모리**입니다. DB 에 두면 `admin_users` 에 컬럼이 늘고 서버에서
`ALTER TABLE` 을 돌려야 합니다. backend 가 단일 프로세스라 지금은 이걸로 충분하고,
**재시작하면 카운터가 풀리는 것이 한계**입니다. Redis 는 쓰지 않습니다 — compose 에
없고, 이것 하나 때문에 서비스를 늘릴 이유가 없습니다.

#### 최초 관리자 계정

`db/init/*.sql` 에 넣지 못합니다. **Postgres 로는 Argon2id 해시를 만들 수 없습니다** —
`pgcrypto` 의 `crypt()` 는 bcrypt / md5 / des 만 지원하고, 지금 켜는 확장은 `vector`
하나뿐입니다. SQL 파일에 넣으려면 해시를 git 에 커밋해야 하는데, 그러면 비밀번호를
바꿔도 히스토리에 옛 해시가 남습니다.

그래서 `uv run seed-admin` 이 **SQL 을 출력만 하고 DB 는 건드리지 않습니다.**
여러 번 돌려도 부작용이 없고, 같은 아이디를 두 번 붙여넣으면 `login_id` 의 UNIQUE
제약이 막습니다. `getpass` 를 쓰므로 **컨테이너에서는 `-it` 가 필요합니다.**

## D-016
### 관리자와 앱 회원이 토큰·세션 테이블을 공유하고, 종류는 `typ` 로 가른다

앱 회원의 카카오 로그인을 붙이기 전에, 관리자용으로 만들어 둔 인증 기반(D-015)을
두 종류의 사람이 같이 쓰도록 넓혔습니다. 정한 것은 셋입니다.

| | 결정 |
| --- | --- |
| 토큰 | 발급기·키를 공유하고, access 클레임 `typ` 로 종류를 구분 |
| 세션 저장 | `refresh_tokens` 한 테이블. 소유자 FK 를 둘 두고 CHECK 로 배타 |
| 검증 | 각 의존성이 **자기 종류가 아닌 토큰을 401 로 거부** |

#### `typ` 클레임이 없으면 앱 회원이 관리자가 됩니다

발급기가 하나이므로 앱 회원의 access token 도 **우리 키로 서명·암호화된 진짜
토큰**입니다. 위조가 아니라서 검증은 전부 통과하고, `sub` 는 어느 쪽이든 UUID
한 개라 그것만으로는 구분되지 않습니다.

지금은 우연히 막힙니다 — 앱 회원 토큰의 role 이 `ROLE_PERMISSIONS` 에 없어서
권한이 빈 집합이 되고 `require(...)` 가 403 을 냅니다. **그 우연에 기대지 않습니다.**
`CurrentAdmin` 만 받고 권한을 안 거는 엔드포인트가 하나라도 생기면 그 자리로
그대로 들어옵니다. 테스트로 고정해 뒀습니다.

`typ` 가 모르는 값이면 **아무 쪽으로도 넘기지 않고 거부**합니다. 기본값을 관리자로
두면 클레임을 지운 토큰이 관리자로 통과합니다.

role 의 유무도 종류가 정합니다 — 관리자 토큰에 role 이 없거나 앱 토큰에 role 이
붙어 있으면 발급도 검증도 거부합니다.

#### 세션은 한 테이블, 소유자 컬럼은 둘

`03_auth.sql` 이 미뤄 뒀던 '컬럼을 더할지 / 테이블을 나눌지'의 답입니다.

    admin_user_id UUID REFERENCES admin_users(id) ON DELETE CASCADE,
    app_user_id   UUID REFERENCES app_users(id)   ON DELETE CASCADE,
    CHECK (num_nonnulls(admin_user_id, app_user_id) = 1)

**`subject_type` + `subject_id` 한 쌍으로 하지 않은 이유**는 FK 를 걸 수 없기
때문입니다. 계정을 지워도 세션이 남고, 그것을 지우는 책임이 DB 에서 앱으로 넘어옵니다.

**테이블을 나누지 않은 이유**는 회전과 재사용 감지 규칙(D-015)이 양쪽 똑같기
때문입니다. 10초 유예 창, 로그아웃은 삭제·회전은 `revoked_at` 이라는 불변식,
절대 만료 — 이 미묘한 규칙이 두 벌이 되면 그중 한쪽만 고치는 날이 옵니다.
대신 repositories 가 컬럼 이름 대신 주체를 받고, 분기는 `_SUBJECT_COLUMN`
한 곳에만 둡니다.

인덱스는 부분 인덱스입니다. 각 행이 둘 중 한 컬럼만 채우므로, 그냥 걸면 인덱스마다
반대쪽 주체의 행이 전부 NULL 로 들어갑니다.

#### 딸려 온 것 — `db/migrations/`

`db/init/` 은 볼륨이 빌 때만 실행되므로 **이미 돌고 있는 서버 DB 에는 아무 일도
일어나지 않습니다.** 지금까지는 그때그때 손으로 SQL 을 만들어 적용했는데, 이번에
`ALTER` 가 다섯 줄이라 파일로 남겼습니다. Alembic 은 여전히 쓰지 않습니다 —
버전 테이블이 없어서 **무엇이 적용됐는지 DB 가 기억하지 않으므로**, 각 파일을
여러 번 돌려도 안전하게 씁니다.

#### 대가

- **이 변경 전에 발급된 access token 은 전부 무효**입니다 (`typ` 가 없어서).
  수명이 5분이고 refresh 는 그대로 살아 있어서 재발급 한 번이면 복구됩니다.
- `refresh_tokens.admin_user_id` 의 NOT NULL 이 CHECK 제약으로 바뀌었습니다.
  **마이그레이션에서 NOT NULL 만 풀고 CHECK 를 빠뜨리면 주인 없는 세션 행이
  만들어질 수 있습니다.** 한 트랜잭션에 묶어 뒀습니다.

## D-017
### 카카오 로그인은 OIDC `id_token` 을 서버가 직접 검증한다

앱이 카카오에서 받은 **`id_token`** 을 우리 서버로 보내고, 서버는 카카오 공개키(JWKS)로
서명을 검증합니다. access token 을 받아 `/v2/user/me` 로 되묻는 방식은 쓰지 않습니다.

#### 왜 access token 방식이 아닌가

| | `id_token` | access token |
| --- | --- | --- |
| 로그인당 카카오 호출 | **없음** (공개키만 캐시) | 있음 — 카카오가 느리면 우리 로그인도 느림 |
| "우리 앱 토큰인가" | `aud` 검증으로 **자동** | `/v1/user/access_token_info` 로 직접 대조해야 함 |
| 허용 IP 설정 | 불필요 | 서버 공인 IP 를 콘솔에 등록해야 함 |

**두 번째 줄이 결정적입니다.** access token 방식에서 `app_id` 대조를 빠뜨리면, 다른
카카오 앱에서 발급된 토큰으로도 우리 서비스에 계정이 생깁니다. 그 토큰의 회원번호는
그 앱 기준이라 엉뚱한 새 회원이 됩니다. 빠뜨려도 **정상 로그인은 멀쩡히 되기 때문에**
뚫린 줄 모릅니다. `id_token` 은 `aud` 가 그 역할을 대신하고, 이건 표준 검증 절차라
빠뜨리기 어렵습니다.

세 번째 줄도 이 프로젝트에서는 무겁습니다. 카카오는 키 유출에 대비해 호출 허용 IP 설정을
권장하는데, 우리 서버는 자체 PC 라 공인 IP 가 고정이라는 보장이 없습니다. 바뀌면 로그인이
통째로 죽습니다. `id_token` 검증은 앱 키로 카카오 API 를 부르지 않아 이 문제가 없습니다
(JWKS 는 키가 필요 없는 공개 엔드포인트입니다).

**대가**: 앱이 카카오 개발자 콘솔에서 **OpenID Connect 를 켜야 하고**, 로그인 요청의
`scope` 에 **`openid` 를 넣어야** 합니다. 토글만 켜고 scope 를 빠뜨리면 `id_token` 이
아예 안 나옵니다. 우리 서버 혼자 정할 수 없는 유일한 부분입니다.

#### 검증에서 빠뜨리면 안 되는 것

    iss   https://kauth.kakao.com 정확히
    aud   우리 REST API 키          ← 없으면 남의 앱 토큰이 통과합니다
    exp   만료
    alg   RS256 하나로 고정         ← 없으면 알고리즘 혼동 공격이 열립니다

**`alg` 고정이 특히 조용한 구멍입니다.** 열어 두면 공격자가 헤더의 alg 를 HS256 으로
바꾸고 **공개키를 HMAC 비밀키 삼아** 서명할 수 있습니다. 공개키는 누구나 가져올 수
있으므로 서명 없이 토큰을 만드는 것과 같아집니다. 카카오도 RS256 하나만 씁니다
(`openid-configuration` 과 실제 JWKS 둘 다 확인).

넷 다 테스트로 고정해 뒀습니다 (`tests/test_kakao.py`). **하나라도 빠져도 정상 로그인은
되기 때문에**, 테스트가 없으면 뚫린 것을 알 방법이 없습니다.

#### 공개키 캐시

6시간 캐시하고, **모르는 `kid` 가 오면 한 번 다시 받아옵니다.** 영원히 캐시하면 카카오가
키를 가는 순간 전원이 로그인 불가가 되고, 매번 받아오면 카카오 장애에 끌려갑니다.
다시 받아오는 데에도 최소 간격(1분)을 둡니다 — 없으면 엉터리 `kid` 를 계속 보내는
것만으로 우리 서버가 카카오를 두드리게 만들 수 있습니다.

`joserfc` 는 모르는 `kid` 에 `InvalidKeyIdError`(= `JoseError` 갈래)를 냅니다.
`KeyError` 로 잡으면 **재요청 경로를 영영 안 타서**, 키 교체 때 조용히 전원 로그인
불가가 됩니다. 실제로 이 실수를 했고 테스트가 잡았습니다.

#### 저장하는 것과 안 하는 것

- **카카오 access/refresh 토큰은 저장하지 않습니다.** 남의 서비스 자격증명이라
  로그인 시점에 검증만 하고 버립니다. 나중에 카카오 API 를 다시 불러야 하면 그때
  AES 로 암호화해서 저장합니다.
- 동의 항목은 **회원번호 + 이메일(선택)** 뿐입니다. 동의를 늘릴수록 암호화·보관 책임이
  늘어납니다. 전화번호·실명은 추가 심사(영업일 3~5일) 대상이기도 합니다.
