## E2 — 4장 뽑기

### 방식

| 방식 | 명령 | 결과 |
| --- | --- | --- |
| 순차 4회 | `cardgen_compare.py --seeds 1,2,3,4` → `e2-seq/` 24장 | **성공** — 서비스 16.2~16.4초/장, 24장 02:31~02:40 |
| 한 번에 4장 | `--seeds 1 --batch 4` (서비스 `count=4`) | **실패** — 500, 서비스 로그 `torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 354.00 MiB … 81.12 MiB is free` |
| 한 번에 2장 | `--batch 2` | **실패** — 같은 OOM(`706.00 MiB … 561.12 MiB is free`) |

두 OOM 모두 첫 transformer 블록의 attention(`apply_rotary_emb`)에서 났다. bf16 모델만으로 GPU 22GiB 의 대부분이 차 있어 배치 활성값이 못 들어간다(추정).
실패 뒤에도 서비스는 살아 있었다(`/health` ready). `count` 는 계약으로 남기되 L4 에서는 1 만 쓴다 — 더 큰 GPU 나 양자화에서 다시 볼 수 있다.

### 닮음 · 목줄 · 쓸 만한 장 (눈 + 검수 likeness, `e2-seq_card_4.png` · `_9.png`)

"쓸 만함" = 제목·패널 글씨 정상 + 닮음(검수 4 이상, 눈으로 확인) + 목줄 없음. 작은 오타는 감점.

| 사진 | 4월 (4장 중) | 9월 (4장 중) | 메모 |
| --- | --- | --- | --- |
| `_03` 정면 | **1~2** (s3, s2 는 작은 오타) | **2** (s1, s4) | 닮음 4~5. 목줄은 4월 s1 에만 |
| `…335` | **1** (s4) | **1** (s4) | 닮음 3~4. 목줄 s1·s3 |
| `_08` 엎드린 옆모습 | **0** | **0** | 4월은 4장 모두 틀의 푸들로 돌아감(닮음 1). 9월 최고 3 |

- 4장끼리의 차이는 **털·귀·표정 정도로 작다** — 포즈·구도는 틀이 고정한다(월 스페셜의 "무대 고정" 규칙대로).
- 시간: 순차 4장 = GPU 약 65초, 도구 기준(검수 포함) 약 90초.

### 3번 카드에 주는 근거

1. **순차 생성**을 전제로 한다(L4 에서 배치 불가). 4장이면 요청 하나에 GPU 약 1분 + 콜드 스타트.
2. **seed 는 달 틀마다 미리 검증한 목록에서** 고른다 — 무작위 4장이면 글씨가 깨진 장이 1~2장 섞인다. 목록은 이번처럼 사진 2~3장 × seed N 으로 한 번 만들어 둔다.
3. **사진 안내 문구**(정면·앉은 사진)는 필요하다 — 엎드린 옆모습은 4장을 뽑아도 고를 게 없었다(E5 대신, 09-16 사용자 결정과 일치).
4. 4장 차이가 작으므로 "고르는 재미"는 약하다 — 과일·채소 카드(4번)의 **포즈·소품 자유도**가 개인화의 실제 손잡이다.

## E3 — 콜드 스타트

공식 문서(docs.cloud.google.com/run/docs/configuring/services/gpu-best-practices, 09-16 조회)가 권하는 FUSE 옵션 둘을 기준과 비교했다.
변형마다 `gcloud run services update` 로 새 리비전을 만들었다 — **배포만 해도 인스턴스가 떠서 로드를 시작하므로** 그 시각부터 잰다.

| 변형 | 설정 | 인스턴스 시작 → ready | 모델 로드(`load_seconds`) |
| --- | --- | --- | --- |
| V0 기준 | 기본 GCS FUSE 마운트 | 383초 (17:23:16Z → 17:29:39Z) | 374.9초 |
| V1 buffered read | `mount-options=enable-buffered-read=true` (리비전 `00003-rt5`) | 약 736초 (배포 17:42:19Z → load 로그 17:54:26Z) | **735.6초 — 약 2배 느림** |
| V2 파일 캐시 in-memory | in-memory 볼륨 `fcache` 16Gi + `mount-options=cache-dir=cr-volume:fcache` (리비전 `00004-vsp`) | **기동 실패** — 1초 안에 `Application exec likely failed` 반복, GCSFuse 마운트 로그 없음 | — |

- **V1:** 비동기 선읽기가 safetensors 를 여는 방식(추정: 필요한 부분만 여기저기 읽는 접근)과 맞지 않아 오히려 느려진 것으로 보인다. 한 번만 쟀다.
- **V2:** 메모리 초과가 아니라 **마운트 설정 단계에서 컨테이너가 못 떴다**(확인: 앱 로그·FUSE 마운트 로그가 한 줄도 없음). 문서에 완전한 예시가 없어
  in-memory 볼륨을 컨테이너에도 마운트해야 하는지 등 원인을 확정하지 못했다(추정). 추측으로 GPU 배포를 반복하지 않으려고 **다시 시도하지 않았다.**
  설정을 확정해 다시 잴 가치는 있다 — 다만 파일 캐시는 원래 두 번째 읽기부터 빨라지는 장치라, 매번 새 인스턴스인 콜드 스타트에서 효과가 클지는 불확실하다.
- 실패 뒤 서비스는 기준 설정(리비전 `00005-rhn`)으로 되돌렸고, V1·V2 리비전은 지웠다.
- 가중치를 이미지에 굽기(15GB — 공식 권장 10GB 미만을 넘고 빌드·풀이 커진다)와 시작 CPU boost(GPU 문서에 언급 없음, `--no-cpu-throttling` 이미 켬)는 재지 않았다.
