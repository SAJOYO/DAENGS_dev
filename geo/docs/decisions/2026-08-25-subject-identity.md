# 세션을 묶는 식별자는 프로필이 아니다 — 그리고 우리가 만들지도 않는다

결정 #4 는 반려견 프로필을 이 레포가 소유하지 않는다고 정했다. 그 결정이 산책 저장에서
이렇게 나타났다 — Android 는 `dogId` 를 **null 로 저장**했다. "가짜 id 를 넣어 baseline 을
오염시키지 않는다" 는 이유였고 맞는 판단이었다.

그런데 서버 `WalkSession.dog_id` 는 필수(`min_length=1`)다. 업로드를 붙이는 순간 이 둘이
정면으로 부딪힌다.

## 두 요구는 다른 것이다

```
프로필   이름 · 견종 · 나이 · 체중 · 건강     → 이 레포 소유 아님 (결정 #4)
식별     "이 세션과 저 세션이 같은 개다"      → 반드시 필요
```

결정 #4 가 금지한 것은 **프로필을 소유하는 것**이지 세션을 묶는 것이 아니다. baseline 은
개별 개에 붙어야 의미가 있다 — 두 마리를 키우는 집에서 섞인 baseline 은 없느니만 못하다.

## 결정

**1. `dog_id` 는 불투명 키다 — 산책 저장·업로드 계층에서.** 그 계층에서는 프로필을 조회하는
근거로 쓰지 않고, 값의 형태에 의미를 두지 않으며, 세션을 묶는 것 외의 용도가 없다.

**레포 전체 규칙이 아니다.** 병원 검색과 `/journey` 는 실제로 `dog_id` 로 외부 프로필 계약을
조회한다(`profile_source().get(...)` · `owner_of(...)`). 결정 #4 가 정한 것은 프로필을
*소유하지 않는다* 이지 *조회하지 않는다* 가 아니다. 두 용법은 공존하며, 산책 쪽이 좁은
쪽이다 — 산책 사실은 프로필 내용에 의존하지 않고 묶이기만 하면 된다.
필드 이름은 `dog_id` 로 둔다 — `subject_id` 가 의미에 더 맞지만 서버 계약·DB 컬럼·
`walk-record.md`·Android 를 동시에 건드리는 개명이고, 지금 얻는 것이 이름 하나뿐이다.
두 번째 subject 종류가 생기면 그때 바꾼다.

**2. 식별자는 주입받는다. 이 레포도 앱도 만들지 않는다.** 지금 Android 는 `dogId` 를 null 로
저장한다. 업로드 경로를 붙일 때 빌드 설정으로 주입하고, release 기본값은 빈 값으로 둔다.

기기가 UUID 를 생성하는 안을 기각한 이유가 이것이다: **재설치·기기 변경마다 새 개가 되고,
조각난 baseline 을 나중에 합칠 근거가 없다.** 사용자가 "이거랑 저거 같은 개예요" 라고
말해줄 표면도 없다. 조용히 조각나는 것보다 **업로드가 꺼져 있는 게 낫다.**

**3. 식별자가 비어 있으면 업로드하지 않는다.** 미완성이 아니라 게이트다. 산책 사실이 어느
개에 귀속되는지 모르는 채로 서버에 쌓지 않는다. release 기본값을 빈 값으로 두는 이유다.

**이 게이트는 결정 #57 의 보관 정책 게이트와 별개다.** 여기서 묻는 것은 *누구의 산책인지
아는가* 뿐이다. 팀 프로필이 붙어 이 게이트가 열려도 실사용 업로드는 #57 이 따로 막는다.
하나로 묶으면 식별자가 채워지는 날 보관 정책 게이트까지 같이 열린다.

**4. 로컬 세션 행도 자기 `dogId` 를 안다.** 업로드 시점에 붙이지 않고 세션을 열 때 저장한다.
행이 누구 것인지 모르면 **그 subject 의 데이터를 지우라는 요청을 로컬에서 실행할 수 없다**
(결정 #57 의 삭제 단위). 지금은 null 이 저장되므로, 주입을 붙이는 변경이 이것도 같이 한다.

## 미뤄지는 것

팀 프로필이 붙으면 그 id 를 주입하면 된다. 그 전에 debug 로 쌓인 페르소나 세션과 실제
프로필 id 를 이어붙일지는 **그때 정한다** — 개발 데이터를 실사용 baseline 에 섞는 것은
기본적으로 하지 않는 쪽이 맞다고 보지만, 그건 이 결정의 범위가 아니다.

## 알면서 받는 손해

기기를 바꾸면 서버의 과거 세션과 새 기기의 세션을 이을 방법이 지금은 없다. 주입되는 id 가
기기 밖에서 오면(팀 프로필) 자동으로 해결되고, 그게 2 번을 고른 또 하나의 이유다.
