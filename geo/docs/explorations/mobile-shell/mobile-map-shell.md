# 모바일 셸 — 지도는 등뼈지만 산책의 주인공 화면은 아니다

이 문서는 `/dev`만 있던 시점에서 출발했다. 현재는 Android 위치→병원 검색→NAVER 지도·카드→
action·전화와 선택형 trail/territory 레이어가 구현돼 있다. 아래 브리핑·트리거·회고 화면은
결정 #51 이후 소비자 옵션이며 현재 제품 약속이 아니다.

## 정의부터: "지도가 메인"의 뜻

> 모든 화면에서 지도가 가장 커야 한다는 뜻이 **아니다**.
> 모든 위치 기반 경험이 **같은 공간 상태를 공유한다**는 뜻이다.

이 구분이 없으면 산책이 "지도 위 GPS 로거"가 된다. 표면은 두 종류다.

| 표면 | 화면 | 지도 |
|---|---|---|
| **공간 표면** | 병원·약국 검색 · 산책 진행 · 산책 중 병원 인사이트 · 경로 확인 | 주인공 |
| **에피소드 표면** | 출발 전 브리핑 · 종료 후 회고 | 조연 또는 없음 |

`overview.md`의 3단 루프가 이 구분의 근거다 — 비중이 **높음**인 두 순간(출발 전·종료 후)은
지도 화면이 아니다. 이동 중은 "최소"고, 그때만 지도가 주인공이다.

```
앱 실행
 └─ 내 위치 중심 지도 (공간 표면)
     ├─ 병원·약국 → 마커 + 하단 시트 → 후보 선택 → Why/How 상세
     └─ 산책 시작
          ├─ 출발 전 브리핑          (에피소드 표면)
          ├─ 진행 중 최소 HUD         (공간 표면, 지도 유지)
          │   └─ 병원 질문 → 병원 레이어 → 닫으면 산책으로 즉시 복귀
          └─ 종료 후 회고            (에피소드 표면)
```

병원은 지도 안에서 완결하고, 산책은 브리핑–최소 진행–회고로 완결한다.

## 시안 목록 (6장)

병원 4장을 그리면 병원 앱이 나온다. 3단 루프 비중대로 배분한다.

1. **출발 전 브리핑** — 오늘 목표, 날씨·어제 산책량 반영, 시작 버튼
2. **산책 진행 중 최소 HUD** — 지도 + 거리·시간. 화면을 보게 만들지 않는다
3. **이동 중 짧은 트리거** — 알림 한 줄. 빈도 상한이 곧 설계
4. **산책 종료 회고** — 경로 요약, 에피소드. 여기서만 길게 써도 된다
5. **병원 검색** — 지도 + 하단 시트 (가까운 후보 2~3개 먼저)
6. **병원 상세** — Why / How / 안전 통지 / 전화·경로

`/dev`처럼 왼쪽에 20개를 늘어놓지 않는다. 마커와 하단 카드는 선택 상태를 공유한다.

## 위치 계약 — follow_device / pinned

서버 계약은 [condition-schema](../hospital-search/condition-schema.md#위치는-두-경로로-들어온다)에
있다. 앱은 위치를 **두 개** 들어야 한다.

```text
deviceLocation   실제 GPS. 계속 갱신
searchOrigin     현재 검색 기준점
locationMode     follow_device | pinned
```

| 행동 | 검색 요청에 싣는 값 | 모드 |
|---|---|---|
| 내 위치에서 검색 | `origin` = 최신 GPS | follow_device |
| GPS 위치 fix 수신 | **검색 요청 없음**. `deviceLocation`만 기기 안에서 갱신 | 현재 모드 유지 |
| follow_device에서 검색·필터 요청 | `origin` = 최신 `deviceLocation` | follow_device 유지 |
| 지도 팬 후 재검색 | `edits:[set_origin]`, **`origin` 생략** | pinned |
| pinned 에서 필터 변경 | **`origin` 생략** | pinned 유지 |
| 내 위치 버튼 | `origin` = 최신 GPS | follow_device 복귀 |

센서 이벤트는 병원 검색의 트리거가 아니다. 위 전송 규칙은 사용자가 검색·필터 변경·재검색을
일으킨 **그 요청의 payload**를 말한다. 산책 세션의 위치 배치 업로드는 아래 소유권 갈래의
별도 계약이다.

**pinned 에서 `origin` 을 실어 보내면 팬해서 보던 지역이 매 턴 사라진다.** 서버 API 는 안
바꾼다. 서버 쪽 "origin 생략 시 state 좌표 유지"는
`test_omitting_origin_keeps_the_pinned_search_location`가 잡는다. 앱 쪽 "pinned 면 origin 필드
자체를 생략"은 Android 요청 빌더가 생길 때 직렬화 테스트로 따로 고정해야 한다.

## 안전 표면은 선택이 아니다

`trace.py`: *"상황이 사용자 설정을 눌렀으면 말해줘야 한다. 사용자는 자기가 건 조건이 살아
있다고 믿는다."* 화면에 **자리가 있어야** 한다.

| 응답 필드 | 자리 | 규칙 |
|---|---|---|
| `show_call_cta` | 하단 시트 위 고정 배너 | 조건을 좁히는 대신 전화를 권한다 |
| `call_reasons` | 배너 안 한 줄 | 원시 코드 금지. **모르는 코드는 문장을 만들지 말고 생략** |
| `resolution[].overrode` | 접지 않는 통지 | 눌린 설정 이름과 이유를 같이 |
| 나머지 `resolution[]` | 상세 접기 | 디버깅용. 주인공 아님 |

`/dev` 구현이 참조 렌더링이다 (`app/static/dev.html` `renderSafety`).

## 불확실성 행렬 — 시안이 반드시 덮어야 할 상태

이 제품의 정체성은 **모르는 것을 모른다고 말하는 것**이다. 그런데 시안은 기본적으로
happy path 를 그리고, 그러면 앱은 이 상태들을 그릴 자리 없이 만들어진다.

모든 화면마다 하나씩 억지로 넣을 필요는 없다. **시안 전체가 아래를 전부 덮으면 된다.**

- [ ] 영업시간 `unknown` (인허가 원천에 시간이 없다 — 실데이터 대부분)
- [ ] 경로 `estimate` (추정임이 보여야 한다)
- [ ] 경로 `unavailable` (`min`·`m` 이 null — 0 이 아니라 없음)
- [ ] 이름에서 추정한 태그 ("병원명에서 치과 관련 표현 감지")
- [ ] 근거 없음
- [ ] 정책 override 통지
- [ ] 전화 CTA
- [ ] 결과 0곳
- [ ] 네트워크 지연·실패

## Android / Web 역할

README 확정 사항("웹 메인 + Android 전용 앱")과 충돌하지 않게 역할로 가른다.

| 기능 | Android | Web |
|---|---|---|
| 병원·약국 검색 | 전체 | 전체 |
| 인터랙티브 지도 | **기준 구현** | 모바일 웹 지원 |
| 산책 세션 | 전체 | 미지원 |
| 화면 꺼진 위치 추적 | 지원 | 불가 |
| 챗봇 카드·공유 | 지원 | 지원 |
| 개발 검증 | — | `/dev` |

Android 가 유일한 화면은 아니다. **산책과 현재 위치 중심 지도의 기준 구현이 Android** 다.
PR #12 의 웹 지도는 병원 검색과 실험 표면으로 남는다.

## 위치 권한 단계

앱을 켜자마자 "항상 허용"을 요구하지 않는다. 경쟁 조사가 짚은 "가입 장벽" 불만과 같은 결이다.

1. 내 주변을 볼 때 → foreground 위치
2. `산책 시작`을 누를 때 → location foreground service
3. 화면이 꺼져도 지속 알림으로 산책 중임을 드러냄
4. 종료하면 추적 중단
5. **세션 밖 상시 백그라운드 추적은 v1 에 없다**

## 미결 — Android 스켈레톤 전에 정해야 하는 것

### ① 산책 판정의 소유권과 업로드 주기

[session-engine-draft](../walk/README.md) 는 서버 판정을 전제한다:
`POST /walks/{id}/locations` 업로드 → 판정 → **트리거 서술이 업로드 응답으로** 온다.

그래서 **이동 중 트리거의 지연 = 업로드 주기**다. 구조적으로 묶여 있다.

```text
업로드 주기 ↔ 트리거 신선도 ↔ 배터리
  10초  즉각적    배터리·데이터 부담
  60초  최대 1분 늦음   무난
```

기기가 소유할 것(수집·smoothing·임시 진행도 표시·오프라인 큐·중복 알림 억제)과 서버가
소유할 것(정식 거리·구역·새 길 판정, 트리거 확정, 보상, 빈도 상한의 최종 권한, LLM 서술)을
가르는 하이브리드가 유력하다. **수치보다 소유권을 먼저 고정한다.**

다행히 이 서비스의 원칙이 긴 주기를 허용하는 쪽이다 — *"이동 중 알림은 최소. 산책의
주인공은 개, 폰이 아니다"* (overview.md).

- [ ] 오프라인 동작 (기록·거리는 보여주고, 보상·에피소드는 동기화 후)

## 착지 — Android 첫 수직 절단면

구현은 `android/`에 있다. 단일 Compose 모듈에서 foreground 위치 단발 조회, NAVER 지도,
`POST /hospital/search`, 마커·카드, `actions[]` 재요청, 전화와 안전 통지를 끝까지 연결했다.
`state`와 action edits는 불투명 JSON으로 왕복하며 요청 빌더 테스트가 pinned origin 생략을 고정한다.

후속 절단면에서 병원 전용 화면을 단일 `MapHost`로 바꾸고 장소·트레일·territory를 명시적
레이어로 조립했다. 실제 Fused 위치와 가상 재생 경로가 같은 연속 `LocationSource` 계약을 쓰며,
트레일 기록과 표시 여부는 독립이다. territory는 기본으로 꺼져 있고 사용자가 켰을 때만 현재
육각 셀과 로컬 마킹을 그린다. 이 실험은 서버 소유권·공개 경쟁·사진·H3를 결정하지 않는다.

산책 foreground service도 여전히 미구현이다. 현재 연속 구독의 소유자는 ViewModel 범위의
`LocationTracker`이며, 화면을 벗어나면 구독을 끊고 화면 밖에서는 다시 켜지지 않는다
(`isForeground`). 피드 교체는 `switchFeed()` 한 곳만 통과한다.

service 착수 시 옮겨야 하는 것은 tracker 하나가 아니다. 지금은 `TrailRecorder`와 피드 정책이
ViewModel 안에 있어서 기록이 Activity와 같이 죽는다. 서비스가 구독을 가져가려면 recorder와
피드 소유권이 함께 앱 그래프로 나가고 ViewModel은 flow 조합만 남아야 한다. `MapHost` 소비
계약은 그대로 유지된다.

위치 값은 두 층이다. `deviceLocation`은 실제 GPS만 기록해 검색 `origin`과 "내 위치 기준"
문구를 책임지고, `feedSample`은 가상 이동을 포함해 지금 피드가 주는 위치라서 카메라·트레일·
territory만 읽는다. 가상 좌표가 병원 검색으로 새는 경로를 구조로 막는다.
