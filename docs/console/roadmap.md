## 0. 한 장 요약

- **콘솔은 코드 하나, 배포 두 곳이다.** 로컬 `daengs.~/console`(개발 DB) · GCP `daengapp.~/console`(운영 DB).
  "GCP 용 콘솔" 을 따로 만들지 않는다 — **운영 값이 있는 쪽이 운영 콘솔**이고, 로컬 콘솔은 그 화면을 배포 전에
  확인하는 자리다. 로컬 콘솔의 중요성이 덜해 보이는 이유가 그것이고, 그건 문제가 아니라 배치다 (§2 배포).
- **운영 콘솔이 `dev` 를 따라잡았다** (2026-09-07 · #289). 스냅샷이 나가면서 **운영 API 경로가
  40 → 72** 로 늘었고 관리자 API 다섯 갈래(신고 · 회원 · 감사 · 계정 · 지표)가 전부 운영에 섰다
  (같은 날 실측). **밀려 있던 마이그레이션 11장도 적용됐고 짝인 `verify_*.sql` 이 통과했다** —
  §2 의 "미적용 여덟" 이 그날 0이 됐고, **프론트 재빌드까지 사람이 로그인해서 확인했다.**
  "만들 것"은 이로써 다 닫혔다 — 남은 콘솔 작업은 **전부 남의 결정이나 남의 파트를 기다린다** (§5).
- **요청 하나가 남기는 것이 생겼다** (2026-09-07 · #297). `request_metrics` 표가 지연 ·
  실패 사유 · 라우터 종류를 담고 `/console/metrics` 가 그것을 그린다. **질문 원문도 회원
  식별자도 안 담는다**(D-037 · D-054) — verify 가 금지된 열 이름을 단언한다.
  ⚠ **GCP 미적용 마이그레이션이 이걸로 둘이 됐다** (§2 운영 DB 실측).
- **콘솔이 운영 도구로 넘어왔다.** 메뉴 아홉 가운데 둘(기능 점검 · 크롤)만 여전히 "우리 기능을 우리가 두들겨
  본다" 이고, 나머지는 운영 화면이다 — 상태(#180) · 관리자 계정(#207 · #222) · 감사 로그(#221) ·
  회원 · 반려견(#211 · #212 · #257) · 운영 지표(#223) · **신고(#235 · #237)**. **준비 중 카드는 지식 베이스
  하나만 남았고**, 그것은 지금 성립하지 않는다 (§6). **사용자가 남긴 것은 이제 전부 콘솔에 있다** (§3).
- **신고 경로가 둘이 됐다.** 서버 API(`POST /app/reports` → `/console/reports`, #235 · #237)가 생겼고,
  **메일 경로도 그대로 남는다** (2026-09-03 사람 결정) — 구버전 앱과 저장되지 않은 대화용이다. 콘솔은
  API 로 온 것만 본다. **남은 것은 앱이 그 API 를 부르는 일**이고, 그 전에 앱 화면의 고지 한 줄이
  필요하다 (D-053 ④). 그때까지 신고는 계속 메일로 온다 (§3).
- **A 트랙이 닫혔다.** 감사 로그(#203) · 역할별 계정 발급(#207) · 회원 조회(#211 · #212) · 감사 화면(#221) ·
  비밀번호(#222) · 신고(#235 · #237) 에 이어 **회원 목록(#257)까지 끝났다.** 마지막 전제였던 열람 범위는 D-053 이 닫았고,
  그 뒤 남아 있던 "운영 DB 적용" 은 2026-09-05 에 확인해 보니 **이미 끝나 있었다** (§2 "운영 DB 실측").
  **A5(감사 로그 보존)까지 2026-09-07 에 닫혔다 — A 트랙은 비었다.** 증가량을 실제로 재 보니
  하루 14행이라 **지우지 않기로 했다** (§4 A5 · §6).
- **09-21 전에도 DB 를 바꾼다** (사람 결정, §7). 대가는 카드마다 두 DB(로컬 · GCP) 손 적용이다
  (`docs/deploy/roadmap.md` §2-5).

## 1. 왜 필요한가

"있으면 좋다" 가 아니라 **지금 그 일을 어떻게 하고 있나** 로 잰다. 콘솔이 없어서 안 되는 일은 없다 — 전부
psql · Gmail · SSH 로 된다. 콘솔이 바꾸는 것은 **그 일을 할 수 있는 사람의 수**와 **흔적이 남는지**다.

### D. 보안 후속 — 콘솔 탭과 백엔드가 같이 간다

> 화면만 안 보이는 계정" 도 없다. 무인증인 것이 화면에 그대로 보이는 편이 오히려 정직하다.


**왜 그 순서였나** — 다음에 같은 판단을 할 때 쓰는 근거라 남긴다.

- **A4(감사 로그)가 A 트랙 맨 앞이었던 이유** — A2 의 복호화 · A3 의 발급 · A1 의 신고 처리가
  전부 "누가 했나" 를 남겨야 하는 일이다. 뒤에 넣었으면 세 카드를 다시 열었다.
- **A3 이 A2b 앞이었던 이유** — 복호화 화면을 열기 전에 그것을 **못 보는 계정**(VIEWER · ANALYST)이
  실제로 있어야 `pii:read` 가리기가 검증된다. #207 전까지는 전원 ADMIN 이라 권한 코드가 한 번도
  실행되지 않았다. A2a(#211)는 마스킹만이라 그 계정 없이도 섰다.
- **A1(신고)이 맨 뒤였던 이유** — 전제가 셋(#131 · A0 · A4)이었다. 마지막까지 남은 줄 알았던
  "운영 DB 적용"은 2026-09-05 에 확인해 보니 **이미 끝나 있었다** — 로드맵이 09-03 뒤로 실측되지
  않아 계속 "대기"로 적혀 있었을 뿐이다. **실측하지 않은 전제가 카드를 얼마나 오래 막는지**가
  이 줄의 교훈이다.
- **A2c(목록)가 §7 "역할 발급" 을 안 기다린 이유** — 목록 줄에서 개인정보를 아예 빼서, 기다릴
  이유였던 문장("VIEWER 까지 전 회원의 개인정보를 넘겨본다") 자체를 없앴다 (#257).
- **스냅샷이 1번이었던 이유 — 소유가 남에게 있어도 값이 크면 표에 둔다.** `dev → main` 은
  `deploy/roadmap.md` 소유인데 이 표의 맨 위였다. 빼면 표가 "콘솔은 할 게 없다" 로 읽히기
  때문이었고, 실제로 그 줄이 나가자(#289) **메뉴 여섯이 값 있는 쪽에 섰다.** 이 파트가 만든
  것이 아니라 **이 파트가 기다리던 것**이 1번인 상태는 앞으로도 생긴다.
- **B1 · C1 · C2 를 먼저 한 이유** — DB 도 결정도 필요 없고, 09-21 발표 화면에 바로 보인다.
