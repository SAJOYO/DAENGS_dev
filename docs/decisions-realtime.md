### ① 계층 — 전송 층과 provider 층을 나눈다 — ✅ 확정 (2026-08-24)

**"provider 를 기관 축으로 자르나 데이터 축으로 자르나"에서 출발했는데, 실제로 무엇이 다른지 세어 보니
둘 중 하나를 고르는 문제가 아니었다.**

| API | 호스트 | 인증 | 응답 | 에러 |
|---|---|---|---|---|
| 기상청 단기예보 | `apis.data.go.kr` | `serviceKey` 쿼리 | JSON `response.body.items.item[]` | `response.header.resultCode` |
| 기상청 특보 | `apis.data.go.kr` | 〃 | 〃 | 〃 |
| 기상청 생활기상지수 | `apis.data.go.kr` | 〃 | 〃 | 〃 |
| 에어코리아 실시간 | `apis.data.go.kr` | 〃 | 〃 | 〃 |
| 에어코리아 측정소 | `apis.data.go.kr` | 〃 | 〃 | 〃 |
| 카카오 Local | `dapi.kakao.com` | `Authorization: KakaoAK` **헤더** | JSON `documents[]` + `meta` | HTTP status |
| 기상청 API허브 | `apihub.kma.go.kr` | `authKey` 쿼리 | **텍스트/CSV** (`#` 주석 헤더) | 텍스트 |

**관찰 1 — 전송 계약은 기관과 일치하지 않는다.** 기상청이 data.go.kr(3종)과 API허브(1종) 양쪽에
걸쳐 있다. 기관 축으로 자르면 `kma.py` 안에 **인증 방식 2개·응답 포맷 2개**가 들어간다.
경계가 아무것도 막지 못하면 그건 경계가 아니다.

**관찰 2 — 데이터 축으로만 자르면 봉투를 5번 쓴다.** `resultCode` 분기, `items` 언랩, 빈 `items`,
에러 시 JSON 이 아니라 XML 로 돌아오는 폴백 — data.go.kr 계열의 그 처리가 5개 모듈에 복사된다.

**결정 — 두 축을 서로 다른 층에 둔다.** RAG-018 이 파서에서 푼 것과 같은 형태다.

| | RAG-018 파서 | 이번 realtime |
|---|---|---|
| 아래 층 | `extract/` **포맷** 층 (pdf·hwpx·html·xml) | `transport/` **전송** 층 (datagokr·kakao·kmahub) |
| 위 층 | `parsers/` **사이트** 층 (소스 1 = 모듈 1) | `providers/` **소스** 층 (API 1 = 모듈 1) |
| 위로 나가는 계약 | 공통 IR 6종 (`ir.py`) | 공통 관측 모델 (②) |

> **경로 정정 (2026-08-24, `feat/rag` 대조)** — 위 표의 `extract/`·`parsers/`·`ir.py` 는 RAG-018 당시의
> `rag/` 최상위 경로다. **RAG-023** 이 그 뒤 `rag/` 를 `core/`(순서 없음) + `stages/`(순서 있음) +
> `pipeline.py` 로 재배치해서 지금은 `rag/stages/parse/extract/` · `.../parsers/` · `rag/core/ir.py` 다.
> **유추는 그대로 유효하다** — RAG-023 이 "RAG-018 의 3층 자체는 그대로이고 위치만 parse 단계 안으로"라고
> 명시했다. 층의 순서도 역할도 안 바뀌었다.

```
backend/realtime/
├── __main__.py       CLI — crawler·rag 와 같은 방식 (RAG-001 원칙 1)
├── config.py         Settings — DATA_GO_KR_KEY · KAKAO_REST_KEY · KMA_HUB_KEY
├── transport/        ① 전송 층 — 인증·봉투·에러코드·재시도 (3 모듈)
│   ├── datagokr.py     serviceKey + response.header/body.items   ← 5종이 공유
│   ├── kakao.py        KakaoAK 헤더 + documents[]
│   └── kmahub.py       authKey + 텍스트/CSV
├── providers/        ② 소스 층 — API 하나 = 모듈 하나 (7 모듈)
│   ├── kma_vilage_fcst.py · kma_warning.py · kma_life_index.py · kma_apihub.py
│   ├── airkorea_realtime.py · airkorea_stations.py
│   └── kakao_local.py
├── geo.py            좌표 변환 — WGS84 → 격자(nx,ny) · TM
├── observation.py    ★ 공통 관측 모델 = provider 와 룰 사이의 계약 (②)
├── rules.py          산책 적합도 판정 (③)
└── cache.py          신선도·TTL (④)
```

- **provider 는 API *서비스* 하나 = 모듈 하나다. 오퍼레이션 단위가 아니다.** 단기예보 서비스의
  `getUltraSrtNcst`·`getUltraSrtFcst`·`getVilageFcst` 셋은 같은 봉투·같은 격자 입력이라 한 모듈 안의
  함수 셋이다. 그래서 provider 7개가 `docs/data-sources.md` §8 의 연동 체크 7개와 1:1 로 맞는다
- **`geo.py` 를 provider 밖에 둔 이유** — 격자·TM 변환은 어느 API 의 것도 아니다. 카카오 `transcoord`
  로도 되고 자체 계산으로도 되는데 **자체 계산이 기본이고 카카오는 대체재**다. 그래야 `KAKAO_REST_KEY`
  가 없어도 관통되고, 카카오는 "○○동" 표기라는 UX 역할만 남는다
- 크롤러의 `sources/law/_lawgokr.py`(사이트가 같은 두 소스의 공용 베이스)가 부분적 선례지만,
  그것은 **소스 층 안의 공유**였다. 여기서는 전송 계약이 기관을 가로지르므로 층을 하나 더 내려야 한다

**기각 — 기관 축 단독**: 관찰 1. 기상청이 두 전송 계약에 걸쳐 있어 경계가 실제 차이와 어긋난다.
**기각 — 데이터 축 단독**: 관찰 2. 봉투 처리가 5중복되고, 그 5개가 따로 늙는다.
**기각 — `core/` 를 두는 것**: 아래 ①-3.

### ①-3 `realtime/` 에는 `core/` 를 두지 않는다 — ✅ 확정 (2026-08-24)

**왜 물어야 했나** — `crawler/` 도 `rag/`(RAG-023 이후) 도 `core/` 가 있다. realtime 만 없으면
"셋 중 하나만 다른" 모양이 되고, 특히 `observation.py` 는 ②가 **provider 와 룰 사이의 계약**이라고
못박은 것이라 `rag` 에서 정확히 같은 역할을 하는 `ir.py` 가 `core/` 에 있다는 점이 걸린다.

**그런데 RAG-023 자신의 기준을 적용하면 두지 않는 쪽이 나온다.** `core/` 가 생긴 이유는 "**N 개가
공유하는 것**을 한자리에"였다 — 단계 7개가 `config`·`io`·`ir` 을 공유하고, crawler 는 소스 6개가
`core/` 5개를 공유한다.

realtime 에서 그 N 은 `providers/` 7개인데, **걔들이 공유하는 것은 이미 `transport/` 다.** 위 대조표가
그렇게 말하고 있다 — 아래 층 / 위 층. 즉 realtime 에서 `core/` 가 설 자리는 `transport/` 가 이미
차지했고, 하나 더 만들면 층이 겹친다.

남는 최상위 5개도 묶을 대상이 아니다. **"모두가 쓴다"가 아니라 각자 서로 다른 둘을 잇는다** —
`observation` 은 providers↔rules, `geo` 는 providers↔app, `cache` 는 transport 를 감싼다.
묶으면 `rules`·`cache` 만 폴더 밖에 남고, RAG-023 이 고치려던 바로 그 **"왜 얘는 폴더고 얜 파일인가"**
가 재현된다.

**`stages/` 는 애초에 이식 대상이 아니다.** realtime 은 파이프라인이 아니라 **요청 시점 엔진**이다.
단계별 산출물도, 단계별 CLI 서브커맨드도, "지금 어디까지 됐나"도 없다. `pipeline.py` 가 답할 질문이
realtime 에는 존재하지 않는다.

**재개 조건** — 최상위 파일이 늘어 분류가 필요해지면 그때 다시 본다. 지금 예상되는 증가는
`rules.py` 옆의 임계 설정 파일(③-d)과 `observation.py` 분할 정도라 기준을 넘지 않는다.

> **정정 (2026-08-24, 실측)** — 위 표는 API허브를 "텍스트/CSV" 한 줄로 적었다. 실제로는 **두 계열**이다:
> `typ01/url/*.php` 는 텍스트/CSV, `typ02/openApi/<서비스>/<오퍼레이션>` 은 data.go.kr 과 **같은
> 서비스명·오퍼레이션명 체계의 JSON** 이다. 실패 봉투는 두 계열 공통으로 `{result:{status,message}}` 라
> data.go.kr(`cmmMsgHeader`)·kakao(`errorType`)와 또 다르다. 그리고 **생활기상지수는 data.go.kr 이 아니라
> 이 typ02 계열에 있다** (`LivingWthrIdxServiceV3`, docs/realtime-apis.md §6.4).
>
> **①의 결정은 그대로 유효하고 근거는 오히려 강해졌다** — 기상청 하나가 이제 전송 계약 **셋**에 걸쳐 있다
> (data.go.kr · apihub typ01 · apihub typ02). 기관 축으로 자르면 `kma.py` 안에 인증 2종·응답 포맷 3종이
> 들어간다. `transport/kmahub.py` 가 두 계열을 다루되, 봉투 처리가 갈리면 파일을 갈라도 된다 —
> 그건 전송 층 **안쪽**의 문제이므로 층 경계를 건드리지 않는다.

### ①-2 `realtime` → `crawler` 참조 — ✅ 허용, 범위는 `crawler.core.config` 하나 (2026-08-24)

**왜 필요한가** — `airkorea-stations` 의 측정소 목록은 이전·증설이 있어 월 1회 갱신하는 정적 메타이고,
`docs/realtime-apis.md` §1 이 이미 `data/reference/` 에 두기로 했다. 그러려면 `DATA_DIR` 이 필요한데
그 탐색은 `crawler/core/config.py` 에만 있다 (RAG-014 "경로 탐색은 한 곳"). **`rag` 가 RAG-018 에서 정확히
같은 이유로 같은 예외를 받았다** — 두 번째 사례이므로 이제 일회성 예외가 아니라 **패턴**으로 기록한다.

**왜 좁혀야 하는가** — 넓히면 realtime 이 `Fetcher`·`store`·`seed_sources` 까지 끌어오게 되고,
그 순간 **"실시간은 저장하지 않는다"**(`data/README.md` §5, RAG-012)가 흐려진다. realtime 은 크롤 대상이
아니고 `.meta.json` 도 만들지 않는다. 캐시하는 것은 측정소 목록 같은 **정적 메타뿐**이다.

**가드를 말에서 기계로 옮긴다** — RAG-018 의 "`rag` 가 `crawler` 를 참조하는 것은 경로 탐색 하나뿐"은
지금까지 **문서에만 있는 규칙**이었다. `tests/test_import_direction.py` 는 `crawler/` 디렉터리만 훑어서
그 반대 방향을 아예 보지 않는다. 둘을 추가한다:

1. `FORBIDDEN` 에 `realtime` 추가 — `crawler` 가 `realtime` 을 import 하지 못하게 (기존 가드의 확장)
2. **새 테스트** — `rag/` 와 `realtime/` 이 `crawler` 를 import 할 때 **허용 목록 밖이면 실패**.
   허용 목록은 **패키지마다 다르다** (아래 ①-2 정정)

의존 방향은 여전히 한쪽이다: **app → (rag | realtime) → `crawler.core.*`(좁은 허용 목록)**

> **정정 (2026-08-24, `feat/rag` 대조)** — 위 2 는 원래 "`crawler.core.config` **외의 경로면 실패**.
> 지금 `rag` 가 이미 그 규칙을 지키고 있어 추가 즉시 통과한다"였다. **사실이 아니다.**
>
> ```
> rag/stages/parse/parsers/law/easylaw_pet.py:26   from crawler.core import textutil
> ```
>
> 그대로 짜면 feat/rag 머지를 기다릴 것도 없이 **이 브랜치에서 바로 실패한다** (같은 파일이
> 옛 경로 `rag/parsers/law/` 에 이미 있다). 그리고 이건 사고가 아니라 **의도된 확장**이다 —
> `feat/rag` 의 `rag/README.md` 가 근거를 적어 뒀다: *"`cites()` 는 허위 인용 19건을 잡아낸 규칙이
> 들어 있어 복사하면 그 지식이 갈라진다. RAG-018 이 정한 `rag → crawler` 의존은 경로 탐색까지였고
> 여기서 '한국 법령 문서 공통 텍스트 처리'까지 넓혔다"*.
>
> **허용 목록을 패키지별로 나눈다.** 한 줄로 뭉뚱그려 넓히면 realtime 을 좁힌 근거가 같이 사라진다.
>
> | 패키지 | 허용 | 근거 |
> |---|---|---|
> | `rag` | `crawler.core.config` · `crawler.core.textutil` | RAG-018 + 위 확장 |
> | `realtime` | `crawler.core.config` **하나** | ①-2 본문 — `Fetcher`·`store`·`seed_sources` 가 들어오면 "실시간은 저장하지 않는다"(RAG-012)가 흐려진다 |
>
> `textutil` 은 **법령 텍스트 처리**라 realtime 이 쓸 일이 애초에 없다. 목록이 갈려 있어야
> realtime 쪽에 그게 새로 들어오는 날 테스트가 잡는다.
>
> 가드 본체는 `crawler/` 만 훑는 지금 구조와 달리 `rglob` 로 대상 디렉터리를 훑으면 되므로
> **RAG-023 의 `rag/` 재배치와 무관하게 동작한다** — 경로를 하드코딩하지 않는다.

### ② 공통 관측 모델 — 🔶 진행중 (2026-08-24, ②-a 확정)

7개 API 응답을 무엇으로 정규화할 것인가. 재논의 비용이 🔴 라 여기서 시간을 쓴다.
**말로 정하지 않았다** — 키 3종을 넣고 실제로 호출해 응답 모양 5종을 확보한 뒤 시작했다
(`docs/realtime-apis.md` §6). 다섯 하위 결정으로 쪼갠다. 뒤가 앞을 되돌리지 않는 순서다.

| 순 | 하위 결정 | 상태 | 이 자리인 이유 |
|---|---|---|---|
| ②-a | **범위** — 무엇을 모델링하나 | ✅ 확정 | 담을 것이 몇 종인지 정해야 형태를 말할 수 있다 |
| ②-b | **형태** — 필드 고정 스냅샷이냐 측정값 목록이냐 | ✅ 확정 | 본체 |
| ②-c | **시간축** — 예보는 관측과 같은 타입인가 | ✅ 확정 | ②-b 가 정해져야 "같은 타입"이 뭔지 말이 된다 |
| ②-d-1 | **값의 표현** — `value` 에 무엇을 담나 | ✅ 확정 | 실측 값이 숫자만이 아니다. 필드 결정이라 🔴 |
| ②-d-2 | **등급** — provider 가 주나 룰이 만드나 | ✅ 확정 | 표현이 정해진 뒤 |
| ②-d-3 | **어휘** — `Q` 의 닫힌 목록과 각 양의 표현 | ✅ 확정 | 위 둘이 정해지면 표를 채우는 일 |
| ②-e | **메타의 자리** — 값마다인가 묶음마다인가 | ✅ 확정 | ④ 캐시·⑤ 저하와 맞물린다 |

#### ②-a 관측 모델은 세 종류를 갈라 담는다 — ✅ 확정 (2026-08-24)

provider 7개의 출력을 성격으로 세어 보면 하나가 아니라 셋이다.

| 종류 | 무엇 | 실물 | 자리 |
|---|---|---|---|
| **관측값** | 양 + 수치 | 실황·예보·PM·지수 | `observation.py` |
| **상태** | 구간 + 범주, **수치가 없다** | 특보, 미세먼지 예보통보 | `observation.py` (별도 타입) |
| **위치 해석** | 조회 키 | 격자 `(nx,ny)`·측정소·행정동·특보구역 | `geo.py` |

**근거 1 — 특보는 값이 없다.** `getPwnStatus` 는 `{other, t6, t7, tmEf, tmFc, tmSeq}` 이고 `t6` 에
전국 발효 현황이 **자연어 1,610자**로 들어온다 (§6.3). 이것을 measurement 로 넣으면
`value=None, grade="경보"` 라는 기형이 생기고, 그 `None` 을 **모든 룰이 특수 처리**하게 된다.

**근거 2 — 위치 해석은 방향이 반대다.** 프로브에서 실제로 돈 체인은
`transcoord → TM → getNearbyMsrstnList → stationName → getMsrstnAcctoRltmMesureDnsty` 다.
측정소 이름은 룰이 읽는 값이 아니라 **다음 호출의 인자**였다. 즉 관측 모델(provider→룰)이 아니라
그 앞단이다. 다만 "○○동 (측정소: △△) 기준" 표기 때문에 ⑥ 응답에는 실려야 하므로 버리지 않고
별도 타입으로 들고 간다.

**근거 3 — 셋의 신선도 단위가 다르다** (④ 예고). 관측값은 분·시간, 상태는 발표 시각,
위치 해석은 측정소 목록 월 1회 + 격자 변환은 영구다. 한 타입에 담으면 TTL 을 값마다 다르게 줘야 한다.

**기각 — 전부 한 타입**: 근거 1.
**기각 — 관측값만 모델링하고 특보는 룰이 API 응답을 직독**: 폭염특보는 "즉시 부적합"의 최우선
입력인데 하필 그것만 계약 밖에 두게 된다. 실측 당일이 정확히 그 케이스였다 (서울동남권 폭염경보 발효).

**따라 나오는 것** — `data/reference/` 캐시가 **둘**이 된다: 측정소 목록(월 1회) +
**특보구역명 ↔ 행정구역 매핑**. 후자는 `t6` 파싱에 필수다 — 강남구를 "서울동남권"으로 옮겨야 한다.

#### ②-b 관측값은 측정값 목록이다 — ✅ 확정 (2026-08-24)

provider 는 **`Measurement` 목록**을 내보낸다. 필드 고정 스냅샷이 아니다.

```python
class Q(StrEnum):                  # 닫힌 어휘. 내용은 ②-d
    TEMP = "temp_c"; HUMIDITY = "humidity_pct"; WIND = "wind_ms"
    PM10 = "pm10"; PM25 = "pm25"; UV = "uv_index"

@dataclass(frozen=True)
class Measurement:
    quantity: Q
    value: float
    observed_at: datetime
    source: str                    # 'kma-vilage-fcst' | 'airkorea-realtime' | ...
    spatial_ref: str               # '격자 61,125' | '측정소 강남대로'
    grade: int | None = None       # provider 가 준 등급. 누가 만드는지는 ②-d
```

> 위 스케치는 뒤에서 두 번 **세분됐다** (모순이 아니라 쪼갠 것이므로 ②-b 의 결정은 그대로 유효하다).
> `observed_at` → `valid_at` + `issued_at` (②-c) · `value: float` → `value: Value` (②-d-1).
> 최종 필드는 ②-d-1 을 볼 것.

§6.3 의 모양 A~E 를 두 후보로 표현해 대조했다.

| 기준 | 필드 고정 스냅샷 | **측정값 목록** |
|---|---|---|
| ① 룰 코드에 API 고유 이름 누출 | 없음 | 없음 (`Q` 가 막는다) |
| ② **값별 신선도·출처** | `temp_c`+`temp_at`+`temp_src` … **필드 3배** ❌ | 구조에 이미 있다 ✅ |
| ③ 부분 실패 | `None` 하나로 "장애"와 "미지원"이 안 갈린다 | 부재 = 없음, 이유는 따로 |
| 룰의 정적 타입 안전 | 강함 | 약함 — 키 조회 + `None` 체크 |
| 양 하나 추가 비용 | 모델·provider 스키마 변경 | `Q` 한 줄 |

**결정적인 것은 기준 ②였다.** 실측 시각이 값마다 다르다 — 취향이 아니라 사실이다:

| 값 | 시각 | 공간 |
|---|---|---|
| 기온 | 14:00 관측 (정각+40분 제공) | 격자 (61,125) |
| PM10 / PM2.5 | 14:00 (매시) | 측정소 강남대로 |
| 폭염경보 | **10:00 발표** | 특보구역 서울동남권 |
| 미세먼지 예보 | **11시 발표** | 권역 서울 |

스냅샷에 `observed_at` **하나**를 두면 그 필드는 거짓말이 된다. 정직하게 담으려면 필드가 3배가 되고,
그건 측정값 목록을 손으로 펼친 모양이다.

**함께 정한 것 — 룰이 읽는 편의 뷰는 지금 만들지 않는다.** 비용이 비대칭이다:

| | 나중에 바꾸면 | |
|---|---|---|
| provider 가 **내보내는** 형태 | provider 7개 + 룰 전부 | 🔴 |
| 룰이 **읽는** 편의 뷰 | 그 뷰 하나 (provider 무관) | 🟢 |

비싼 절반만 지금 정한다. 그 뷰가 하게 될 일 — **같은 양에 출처가 둘일 때 무엇을 고르나**
(API허브 AWS 분 단위 기온 ↔ 격자 실황 기온) — 은 정확히 ⑤ 저하 정책이라 거기서 함께 본다.

**아는 약점** — 룰이 `obs.latest(Q.TEMP)` 로 매번 `None` 체크를 한다. 스냅샷보다 정적 타입 안전이
약하다. 감수하는 이유는 기준 ②이고, 뷰를 얹으면 사라진다.

**선례** — RAG-018 이 파서에서 같은 형태를 썼다. 파서가 **공통 IR 6종**(narrow 한 요소 목록)을 내보내고
청커가 소비한다. 여기서는 provider 가 `Measurement` 목록을 내보내고 룰이 소비한다.

#### ②-c 예보와 관측은 한 타입이고, 시각을 둘 갖는다 — ✅ 확정 (2026-08-24)

`Measurement` 의 최종 시각 필드다. 예보를 위한 별도 타입을 만들지 않는다.

```python
@dataclass(frozen=True)
class Measurement:
    quantity: Q
    value: float
    valid_at: datetime          # 이 값이 말하는 시각    ← 판정(③)이 본다
    issued_at: datetime         # 발표·관측 시각         ← 신선도(④)가 본다
    source: str
    spatial_ref: str
    grade: int | None = None
```

> `value: float` 는 ②-d-1 에서 `value: Value`(합집합)로 세분됐다. 시각 필드에 대한 ②-c 의 결정은 그대로다.

**관측은 "리드타임 0인 측정값"이다.** 억지 일반화가 아니라 실측이 그렇다 — 5개 모양 중 4개가 시각을
둘 주고, 나머지 하나(실황)도 **14:00 관측값을 14:40에야 받는다**(정각+40분 제공). 별도 타입으로
가르면 오히려 그 40분을 담을 자리가 없어진다.

| 모양 | 발표·관측 | 대상 |
|---|---|---|
| 초단기실황 | `baseTime 1400` | 같음 (제공은 14:40) |
| 초단기예보 | `baseTime 1330` | `fcstTime 1400` |
| 단기예보 | `baseTime 1400` | `fcstTime 1500` ← 실측 33℃ |
| 특보 | `tmFc 202608241000` | `tmEf 202608241100` |
| 미세먼지 예보통보 | `dataTime "11시 발표"` | `informData "2026-08-24"` |

**기각 — 예보를 별도 타입(`Measurement` + `Forecast`).** 결정적인 이유는 **룰이 원하는 것이
"시각 슬라이스"**라는 점이다. 체감온도는 기온만으로 안 되고 습도·풍속이 **같은 시각**이어야 한다.
실측 당일 판정에 필요했던 것은 "**15시의** 기온·습도·풍속"이고 그 셋이 전부 단기예보에서 오는데,
"지금" 판정은 실황에서 온다. 두 타입이면 룰이 같은 계산을 두 경로로 쓰게 되고 —
**체감온도 산식이 두 곳에 생긴다.** 한 타입이면 `obs.at(15:00, Q.TEMP)` 로 통일된다.

**따라 나오는 것** — 같은 `(quantity, valid_at)` 에 발표가 여러 번 있을 수 있다
(단기예보는 1일 8회 발표). **최신 `issued_at` 이 이긴다**는 규칙이 조회 헬퍼에 들어간다.
그리고 실측 한 번이 872건(8 + 66 + 798)이므로 목록은 `(quantity, valid_at)` 색인이 필요하다.

**기각 — 예보를 ②에서 빼고 나중에.** 오늘 폭염 판정에 쓰인 33℃ 가 실황이 아니라 예보값이었다.
"지금 나가도 되나"에도 이미 예보가 섞이므로 예보 없이는 룰 자체를 못 쓴다.

#### ②-d-1 `value` 는 세 표현의 합집합이고, 어느 것인지는 `quantity` 가 정한다 — ✅ 확정 (2026-08-24)

②-b·②-c 는 `value: float` 로 스케치했다. **실측 값의 절반이 거기 안 맞는다.**

| 실측 도메인 | 예 (2026-08-24) | 표현 |
|---|---|---|
| 연속 실수 | `T1H '33.1'` `REH '57'` `WSD '1.7'` `TMP '33'` `POP '30'` `PM10 37` | `float` |
| 범주 코드 | `PTY '0'`(0~4) · `SKY '1'/'3'/'4'` | **`Code`** — provider 가 의미 enum 으로 번역 |
| 구간 서술 | `PCP '강수없음'` · `SNO '적설없음'` · 예보 `RN1 '강수없음'` | **`Interval`** — 원문 라벨 + `lo`/`hi` |
| 순서형 등급 | `pm10Grade1h '2'` `khaiGrade '2'` | `grade` 필드 (②-d-2) |

```python
Value = float | Code | Interval        # Code: PrecipKind.NONE, SkyState.CLEAR …
                                       # Interval: label='1.0mm 미만', lo=0.0, hi=1.0

@dataclass(frozen=True)
class Measurement:
    quantity: Q
    value: Value
    valid_at: datetime; issued_at: datetime
    source: str; spatial_ref: str
    grade: int | None = None
```

**`quantity` ↔ 표현이 1:1 로 못 박힌다.** 그래서 합집합이어도 룰에 `isinstance` 분기가 생기지 않는다 —
`Q.TEMP` 를 조회하는 자리는 `float` 임을 이미 안다. 그 표는 ②-d-3 에서 확정한다.

**근거 1 — 한 이름이 오퍼레이션에 따라 도메인이 바뀐다.** `RN1` 이 초단기실황에서는 `'0'`(숫자),
초단기예보에서는 `'강수없음'`(문자열)으로 온다. API 하나 안에서도 흔들리므로 **도메인 고정은
provider 층의 일**이라는 것이 실측으로 증명됐다.

**근거 2 — 구간은 점으로 바꾸지 않아도 판정할 수 있다.** 처음에는 "임의 수치를 만들지 않으려면
강수를 상태로 보내야 한다"고 봤는데 잘못된 이분법이었다. 구간을 구간으로 담으면 정보 손실도
임의 정밀도도 없다:

| 원문 | `lo` | `hi` | "비 오나?" `hi > 0` | "30mm 이상?" `lo >= 30` |
|---|---|---|---|---|
| `'강수없음'` | 0.0 | 0.0 | False | False |
| `'1.0mm 미만'` | 0.0 | 1.0 | True | False |
| `'30.0~50.0mm'` | 30.0 | 50.0 | True | True |

**기각 — `PTY`·`SKY`·강수를 ②-a 의 상태(state)로 보낸다** (이 ADR 의 첫 안이었다).
**②-c 를 되돌리기 때문이다.** ②-c 가 예보와 관측을 한 타입으로 묶은 이유는 "룰이 원하는 것은
시각 슬라이스이고, 두 타입이면 조회 경로가 갈려 같은 계산이 두 곳에 생긴다"였다. 그런데 `PTY` 를
상태로 보내면 `temp = obs.at(t, Q.TEMP)` 옆에 `rain = states.at(t, …)` 라는 **두 번째 경로**가 다시 생긴다.
`PTY` 는 특보와 성격이 다르다 — 특보는 (구간 · 특보구역 · 자연어 파싱)이고 `PTY` 는
(시점 · 격자 · 코드 하나)로 **기온과 완전히 같은 축**이다. 공유하는 것은 "숫자가 아니다" 하나뿐인데
그것만으로 같은 통에 넣은 것이 잘못이었다.

→ 따라서 **상태(state)에는 특보와 미세먼지 예보통보만 남는다.** ②-a 의 정의("구간 + 범주")가 그대로 맞다.

**기각 — 숫자로 강제 변환** (`'1.0mm 미만'` → `0.5`): 없는 정밀도를 만든다. `PTY=3`(눈)을 float 에 넣으면
평균·대소 비교가 성립하는 것처럼 보이는 거짓 구조가 된다.

**미실측 공백** — 실측 당일은 비가 오지 않아 `PCP`/`RN1` 이 `'강수없음'` 하나만 나왔다.
`'1.0mm 미만'` 같은 **구간 문자열의 실제 형태는 문서 기준이고 확인하지 못했다.** `Interval` 파서는
문서로 만들되 **모르는 문자열을 만나면 조용히 0 으로 떨어지지 말고 실패**하게 한다 —
비 오는 날 프로브를 다시 돌릴 때 그게 잡아 준다.

#### ②-d-2 등급은 provider 가 싣고, 판정은 룰이 값으로 한다 — ✅ 확정 (2026-08-24)

먼저 용어를 갈랐다. "등급"이 두 가지를 가리키고 있었다.

| | 무엇 | 누구 것 |
|---|---|---|
| **양 자체의 공식 등급** | PM2.5 29 = 보통(환경부) · 자외선지수 4 = 보통 | 관측의 속성 → **②** |
| 산책 적합도 등급 | 폭염 + 미세먼지 + 강수를 합쳐 판정 | ③의 산물 |

②-d-2 는 앞의 것만 다룬다. 결정:

| | |
|---|---|
| `grade` 를 채우는 주체 | **provider.** API 가 준 것만 싣는다. 없으면 `None` |
| `None` 의 의미 | **결함이 아니다** — 기온에는 공식 등급이 애초에 없다 |
| `grade` 의 용도 | **표시·설명용** ("PM10 37㎍/㎥ · 보통") |
| 판정 | 룰이 `value` 와 **자기 임계표**로 한다. 원칙적으로 `grade` 를 읽지 않는다 |
| 두 벌 중 무엇 | provider 가 **`Grade1h`(현재 기준)** 를 골라 흡수한다. 24h 등급은 싣지 않는다 |
| 재현 불가한 합성 지수 | `khaiValue`(통합대기환경지수)는 **값 자체를 하나의 양**으로 싣는다 (`Q.KHAI` + 그 등급) |

**근거 1 — 우리가 재현할 수 없는 등급이 있다.** PM10/PM2.5 등급은 환경부 구간표로 재계산 가능하지만
`khaiValue 91 / khaiGrade 2` 는 여러 오염물질을 합성한 값이라 공식 산식을 재현해야 한다.
"전부 룰이 만든다"가 성립하지 않는 이유다.

**근거 2 — 척도의 단계 수가 다르다.** 에어코리아 4단계(좋음/보통/나쁨/매우나쁨) vs 자외선지수
5단계(낮음/보통/높음/매우높음/위험). `grade: int` 에 룰이 `>= 3` 을 쓰면 **양에 따라 뜻이 달라진다.**

**근거 3 — 산책 임계가 기관 등급 경계와 같을 이유가 없다.** 환경부 등급은 성인 기준이다. 강아지는
지면 가까이서 호흡하고 체구가 작아 '보통' 구간 안에서도 제한하고 싶을 수 있다. 등급을 싣되 룰이
그것으로 판정하지 않으면, 기관 기준이 바뀌어도 표시는 따라가고 산책 임계는 독립적으로 움직인다.
붙여 놓으면 어느 쪽도 못 움직인다.

**근거 4 — 실측 함정을 provider 가 흡수한다.** 오늘 PM10 37 은 `Grade=1`(24h 평균 27 기준),
`Grade1h=2`(현재)였다. 룰이 등급을 읽으면 매번 "어느 등급이지"를 고민하게 되므로, 그 선택을
provider 층에서 한 번에 끝낸다.

**기각 — provider 가 공통 척도로 정규화해서 싣는다**: 4단계와 5단계를 억지로 맞춰야 하고 어느 쪽으로
눌러도 정보가 없어지거나 빈 칸이 생긴다. 정규화한 순간 룰이 그걸 쓰고 싶어져 근거 3이 무너진다.

**기각 — `grade` 를 없애고 룰이 전부 만든다**: 근거 1로 `khaiGrade` 를 잃는다. 그리고 표시에 쓸
공식 라벨("보통")을 우리가 지어내게 된다 — ⑥ 응답에서 "왜 부적합인지" 설명할 때 기관 공식 문구여야
설득력이 있고, 그건 만들어 쓰면 안 되는 종류의 문구다.

#### ②-d-3 `Q` 는 23개다 — ✅ 확정 (2026-08-24)

표를 채우다 나온 결정이 둘, 그리고 목록이다.

**결정 1 — 같은 양이 두 표현으로 오면 넓은 쪽으로 통일한다.** ②-d-1 이 "`quantity` ↔ 표현 1:1"을
못 박았는데 실측이 바로 어긴다. `RN1` 이 실황에서는 `'0'`(숫자 mm), 예보에서는 `'강수없음'`(구간)이다.
→ **`Q.PRECIP_MM` 의 표현은 `Interval`** 이고, 실황의 `2.5` 는 `Interval(lo=2.5, hi=2.5)` 로 올린다.
점은 폭 0 인 구간이라 정보 손실이 없고, 룰은 `hi > 0` 하나로 실황·예보를 똑같이 다룬다.
좁은 쪽(`float`)으로 맞추면 `'1.0mm 미만'` 을 임의 수치로 눌러야 해서 ②-d-1 이 기각한 짓이 된다.

**결정 2 — 파생량은 `Q` 에 넣지 않는다.** 체감온도는 기상청 API 가 2026-05-01 종료돼 기온·습도·풍속으로
자체 계산해야 하는데(`realtime-apis.md` §2.3), `Q.FEELS_LIKE` 로 넣지 않는다. `Measurement` 는
`source`(provider id)와 `spatial_ref` 를 갖는데 **파생값은 출처가 "우리"**라 섞으면 "이 값이 어디서
왔나"가 흐려진다 — ②의 존재 이유가 그것이다. 체감온도는 ③이 만들고 ⑥ 응답에 별도로 실린다.

| `Q` | 표현 | 단위 | `grade` | 출처 |
|---|---|---|---|---|
| `TEMP` | `float` | ℃ | — | `T1H` · `TMP` |
| `TEMP_MIN` / `TEMP_MAX` | `float` | ℃ | — | `TMN` · `TMX` |
| `HUMIDITY` | `float` | % | — | `REH` |
| `WIND` | `float` | m/s | — | `WSD` |
| `WIND_U` / `WIND_V` | `float` | m/s | — | `UUU` · `VVV` (동서·남북 성분) |
| `WIND_DIR` | `float` | deg | — | `VEC` — ⚠️ **순환값** |
| `PRECIP_KIND` | `Code` | — | — | `PTY` (0~4) |
| `PRECIP_MM` | `Interval` | mm | — | `RN1` · `PCP` |
| `SNOW_CM` | `Interval` | cm | — | `SNO` |
| `PRECIP_PROB` | `float` | % | — | `POP` |
| `SKY` | `Code` | — | — | `SKY` (1·3·4) |
| `LIGHTNING` | `float` | — | — | `LGT` ⚠️ 미실측 |
| `WAVE_M` | `float` | m | — | `WAV` |
| `PM10` / `PM25` | `float` | ㎍/㎥ | ✅ `Grade1h` | 에어코리아 |
| `SO2` / `NO2` / `CO` / `O3` | `float` | ppm | ✅ `Grade1h` | 에어코리아 |
| `KHAI` | `float` | — | ✅ `khaiGrade` | 에어코리아 (합성 지수, ②-d-2) |
| `UV` | `float` | — | ✅ | 생활기상지수 ⚠️ 미실측(403) |

**`WIND_DIR` 은 `float` 이지만 일반 실수가 아니다.** 359°와 1°가 인접한 순환값이라 평균·대소 비교가
다르게 동작한다. 표현을 `float` 로 두는 것은 원값을 보존하기 위해서이고, **룰은 이 양을 평균 내거나
임계 비교하지 않는다**는 것을 여기 못 박는다. 필요해지면 16방위 `Code` 를 추가한다.

**넓게 잡은 이유** — 처음에는 산책 판정에 쓰는 13개만 넣으려 했다. 전부 넣기로 한 근거는 비용이다:
빠진 것들이 **어차피 같은 응답에 실려 온다.** 매핑은 provider 에서 한 줄이고, ②-b 가 "양 추가 =
`Q` 한 줄"이라고 한 그대로다. 나중에 필요해질 때 provider 를 다시 여는 것보다 싸다.

**들어가지 않는 것** — 특보와 미세먼지 예보통보. ②-a 에서 **상태(state)** 로 간 구조적 결정이며,
값이 아니라 (구간 · 구역 · 자연어)이므로 `Q` 로 옮기지 않는다.

**미실측 둘** — `LGT`(낙뢰)는 실측값이 `'0'` 뿐이라 도메인이 숫자인지 코드인지 확인하지 못했고,
`UV` 는 apihub 403 이라 응답 자체를 보지 못했다. 표에 넣되 **확인 전**이고, 값이 잡히면 표현을 확정한다.

#### ②-e 값의 메타는 값마다, 조회의 메타는 묶음마다 — ✅ 확정 (2026-08-24)

원래 질문("신선도·출처를 값마다 붙이나 스냅샷마다 붙이나")은 ②-b·②-c 가 이미 답했다 —
`valid_at`·`issued_at`·`source`·`spatial_ref` 가 전부 `Measurement` 필드다. 남은 것은 반대쪽,
**`list[Measurement]` 만으로 충분한가**였고, 답은 아니다.

```python
@dataclass(frozen=True)
class ProviderResult:
    provider: str                 # 'airkorea-realtime'
    ok: bool
    reason: str | None            # 'SERVICETIMEOUT_ERROR' | 'not_subscribed' | 'no_key'
    attempts: int

@dataclass(frozen=True)
class Observations:
    location: ResolvedLocation    # ②-a 의 위치 해석이 앉는 자리
    fetched_at: datetime
    measurements: list[Measurement]
    states: list[State]           # 특보 · 미세먼지 예보통보
    providers: list[ProviderResult]
    # 조회 헬퍼: latest(q) · at(t, q) · series(q) — 최신 issued_at 우선 (②-c)
```

**근거 1 — 부분 실패는 값의 부재로 표현되지 않는다.** 실측 당일 에어코리아가 `05` 로 두 번 죽었다
(재시도로 복구). 복구 못 했다면 목록에 `PM10` 이 그냥 없는데, "없다"의 원인이 실측에서 이미 셋으로
갈렸고 ⑤의 대응이 각각 다르다:

| 원인 | 실측 | ⑤가 해야 할 대응 |
|---|---|---|
| 일시 장애 | 에어코리아 `05` | 재시도 → 실패 시 "대기질 확인 불가"로 저하 |
| 미신청·권한 | `UV` apihub 403 | 재시도 무의미. 기능을 켜지 않는다 |
| 경로 없음 | `12` | 버그. 조용히 넘기면 안 된다 |

`list[Measurement]` 는 셋을 전부 "그냥 없음"으로 뭉갠다.

**근거 2 — ⑥ 응답이 "기준"을 요구한다.** `realtime-apis.md` §0 이 "현위치 기준 UX 는
**'○○동 (측정소: △△) 기준'** 으로 정직하게 표기"라고 적어 뒀다. 그건 값 하나의 속성이 아니라
**조회 전체의 속성**이고, ②-a 의 위치 해석이 앉을 자리이기도 하다.

**기각 — 실패를 `Measurement` 로 표현** (`value=None` + 에러): ②-a 가 특보에서 기각한 기형이다.
게다가 죽은 provider 는 양이 여럿인데(`PM10`·`PM25`·`SO2`…) 실패는 provider 하나다 — **개수가 안 맞는다.**

**기각 — `list[Measurement]` 만 두고 ⑤가 실패 정보를 따로 들고 다닌다**: 룰이 관측과 실패를
**두 인자**로 받게 되고 둘의 짝이 어긋날 수 있다. 한 묶음이면 어긋날 수 없다.

**⑤를 미리 당기는 것이 아니다.** ②는 **자리만** 만든다. "PM 이 없을 때 판정을 어떻게 저하시키나",
"최소 필수 입력이 무엇인가"는 ⑤가 이 자리 위에서 정한다.

## ③ 산책 적합도 룰 — 🔶 진행중 (2026-08-24, ③-a 확정)

재논의 비용은 🟡(룰 파일 하나 + 검증 케이스 재작성)지만 **출력 모양만은 ⑥ 응답과 프론트로 새어
나가므로** 먼저 못 박는다.

| 순 | 하위 결정 | 상태 | 이 자리인 이유 |
|---|---|---|---|
| ③-a | **출력의 모양** | ✅ 확정 | 나머지가 전부 "무엇을 만드는가"에 달려 있다 |
| ③-b | **축과 결합** — 등급이 하나인가 축별인가, 합칠 때 최악 우선인가 · 미래 대기질을 무엇으로 대신하나 | ✅ 확정 | 출력이 정해져야 |
| ③-c | **체감온도 산식** | ✅ 확정 | 축이 정해져야 |
| ③-d | **임계표** — 강아지 기준 경계값 | ✅ 확정 | 마지막. 숫자는 언제든 조정 |

첫 시험 케이스는 실측으로 준비돼 있다 (`realtime-apis.md` §6.6): **서울동남권 폭염경보 발효 +
실황 33.1℃ + 예보 15시 33℃ + 강수 없음 + PM10 37(`Grade1h` 보통) + PM2.5 29(보통) + 통합지수 91(보통)**.
대기질만 보면 나갈 만하고 열만 보면 못 나가는 케이스다.

### ③-a 판정은 시각의 함수이고, 상한은 T+24h 다 — ✅ 확정 (2026-08-24)

```python
judge(obs: Observations, t: datetime) -> Verdict     # "지금"은 t = now 인 특수 경우
```

**근거 — ②-c 와 같은 통일이다.** ②-c 가 "관측은 리드타임 0인 예보"로 묶어 조회 경로를 하나로 만들었고,
`obs.at(t, q)` 가 이미 있다. 여기서는 **"지금 판정 = t=now 인 판정"** 으로 묶는다. 순간 판정만 만들면
나중에 시간축을 넣을 때 룰 시그니처와 ⑥ 응답 구조가 함께 바뀌지만, 반대 방향은 인자 하나를 고정하는
것이라 공짜다 — **비용이 한쪽으로만 든다.**

실측이 이 결정을 요구하기도 했다. 같은 격자의 단기예보가 `TMP` 33 → 32 → 31 → 29 → 28 → 27 로 내려간다.
**"지금 안 됨"과 "저녁엔 됨"이 같은 응답 안에 들어 있다.** G1(순간 판정)이면 앞의 절반만 답한다.

#### 범위 — 상한은 정책, 그 안의 판정 가능 여부는 데이터

**상한 = T+24h (1일).** 오늘 남은 시간 + 내일 아침 산책까지 — 산책 계획의 실제 수요 범위다.
정책 상수이므로 나중에 늘리는 비용은 🟢.

**그 안에서 t 마다 판정이 되는지는 `obs` 가 정한다.** 축마다 커버리지가 전혀 다르다는 것이
실측으로 확인됐기 때문에, `MAX_HORIZON` 하나로는 표현이 안 된다:

| 축 | 미래 커버리지 (2026-08-24 14시 발표) |
|---|---|
| 기온·습도·풍속·`PTY`·`SKY`·`POP`·강수량 | 초단기예보 T+6h(매시) + 단기예보 **T+58h 까지 매시간**, 이후 T+82h 까지 3시간 간격 |
| 일 최저/최고 | 3일치 3점 |
| **PM10·PM2.5 값** | **없다.** 실측은 과거 22시간(08-23 17시 ~ 08-24 14시)뿐 |
| 미세먼지 등급 (권역·일) | 오늘·내일 2일 (`PM10`/`PM25`/`O3`) |
| 폭염특보 | **현재 발효만.** 예비특보(`t7`)는 자연어 |
| 자외선 | 일 단위 (미실측) |

`MAX_HORIZON = 6h` 같은 상수는 **두 방향으로 동시에 틀린다** — 기상은 그보다 훨씬 멀리 가고
대기질은 그보다 훨씬 짧다. T+24h 안에서도 기상은 전부 1시간 간격으로 있지만 대기질 값은 t=now 뿐이다.

**그래서 `Verdict` 는 "판정 불가"와 "근거 부족(저하 판정)"을 1급 값으로 갖는다.** ②-e 의
`ProviderResult` 와 같은 정신이다 — 없는 것을 없다고 말할 자리를 만든다. 실측 기준으로 실제 나오는 모양:

| t | 기상 | 대기질 | 특보 | 판정 |
|---|---|---|---|---|
| 지금 | ✅ 실황 | ✅ 현재값 | ✅ 발효 | **완전** |
| ~T+6h | ✅ 매시 | ⚠️ 대용 | ⚠️ 현재 발효 유지 | 실용적 |
| ~T+24h (상한) | ✅ 매시 | ⚠️ 일 등급 | ❌ | **개략** |

미래 시각의 대기질을 무엇으로 대신할지(현재값 지속 / 권역 일 등급 / 축 제외)는 "무엇이 필수 축인가"와
함께 **③-b** 에서 정한다.

### ③-b 축 3개, 등급 3단계, 결합은 최악 우선 — ✅ 확정 (2026-08-24)

```python
class Grade(IntEnum):
    UNSAFE = 1; CAUTION = 2; GOOD = 3      # 순서 있는 척도에는 이 셋만

class Axis(StrEnum):
    HEAT = "heat"     # 체감온도 + 폭염·한파특보 (지열 보정은 P2)
    AIR  = "air"      # PM10 · PM2.5 · 통합지수 + 황사특보
    RAIN = "rain"     # PTY · 강수량 · 낙뢰 + 호우·대설·강풍·태풍특보

@dataclass(frozen=True)
class AxisVerdict:
    grade: Grade | None                    # None = 판정 근거 없음
    basis: list[Measurement | State]       # 그 등급의 근거가 된 값

@dataclass(frozen=True)
class Verdict:
    at: datetime
    grade: Grade | None                    # 아는 축들의 최악. 전부 모르면 None
    axes: dict[Axis, AxisVerdict]
    dominant: list[Axis]                   # 최악을 만든 축 — 동률이면 여럿 ← "왜"
    unknown_axes: list[Axis]               # 판정에 못 넣은 축 ← 신뢰도
    uv: AxisVerdict | None                 # 부가 표시. 등급에 영향 없음
```

**결합은 최악 우선.** 축들은 상쇄 관계가 아니다 — 대기질이 아주 좋다고 폭염경보가 지워지지 않는다.
**기각 — 가중합**: ① 가중치에 근거가 없다(왜 0.4인가를 설명할 수 없다) ② 상쇄가 성립하지 않는다
③ 실측 케이스에서 위험한 답이 나온다 — 열 `UNSAFE` + 대기질 `GOOD` 을 평균하면 `CAUTION` 이고,
폭염경보 발효 중에 "조심해서 다녀오세요"는 틀린 답이다.

**축별 등급을 버리지 않고 전부 들고 간다.** 답이 "부적합"이 아니라 "**폭염경보 때문에** 부적합"이어야
하기 때문이다. `dominant` 가 그 "왜"이고, 동률이 가능하므로 목록이다.

#### 첫 안에서 고친 것 넷

**① `UNKNOWN` 을 등급 척도에 넣은 것은 버그였다.** 처음에 `GOOD=3 … UNKNOWN=0` 으로 두고
"UNKNOWN 은 최악 우선에 참여하지 않는다"를 **말로** 막았다. 그러면 누군가 `min(axes.values())` 를
쓰는 순간 조용히 `UNKNOWN` 이 이긴다. → **등급은 3값이고 모름은 `None`.** 타입이 실수를 막는다
(`min()` 에 `None` 이 섞이면 터진다). `UNKNOWN` 축은 최악 우선에 참여하지 않고 `unknown_axes` 에
실려 신뢰도를 낮춘다 — 참여시키면 대기질 미래값이 없다는 이유만으로 T+1h 부터 전부 판정 불가가 된다.

**② 미래 대기질에 persistence 를 쓰지 않는다.** 첫 안은 "T+6h 까지 현재값 지속"이었는데,
**가중합을 기각한 논리에 스스로 걸린다** — 6시간 뒤 미세먼지가 지금과 같다는 근거가 없고,
근거 없는 외삽을 만들어 판정에 쓰는 것이다.

| t | 대기질 축 근거 | 표기 |
|---|---|---|
| `now` | 측정소 실측값 (`Grade1h`) | "측정소 △△ 기준" |
| 미래 | **권역 일 등급** (`informGrade`) | "서울 권역 예보 기준" |

실측이 `informGrade` 를 오늘·내일 2일치(`PM10`/`PM25`/`O3`) 주므로 T+24h 를 전부 덮는다. 해상도가
권역·일 단위로 떨어지지만 **기관이 실제로 예보한 값**이지 우리가 지어낸 값이 아니다.

**③ 자외선은 축이 아니다.** 첫 안은 4축이었다. 자외선은 **산책을 막지 않는다** — 개는 털이 있어
사람과 영향이 다르고 "UV 때문에 부적합"을 뒷받침할 기준이 없다. 게다가 그 데이터는 apihub 403 이라
**한 번도 보지 못했다.** → 3축으로 줄이고 자외선은 응답에 부가 표시로만 싣는다.

**④ 누적 보정은 "나중에"가 아니라 하지 않는다.** "세 축이 모두 `CAUTION` 이면 더 나쁜 것 아닌가"를
처음에는 미뤘는데, 미룰 문제가 아니다. **등급이 행동에 대응한다**(나간다 / 짧게 나간다 / 안 나간다).
하위 임계 요인이 겹쳐도 행동이 바뀌지 않으면 등급을 내릴 이유가 없다. 그리고 정말 의미 있는
상호작용인 **기온 × 습도는 이미 체감온도 산식 안에 있다**(③-c) — 축 사이가 아니라 축 안에서
처리되는 것이 맞다. "2개 이상이면 한 단계" 같은 규칙은 가중치와 똑같이 근거 없는 숫자다.

**단계를 3으로 둔 이유** — 사용자의 행동이 셋뿐이다. 4단계는 `CAUTION` 을 둘로 쪼개는 것인데 행동이
달라지지 않는다. ②-d-2 의 기관 등급(에어코리아 4단계·자외선 5단계)과는 **별개 척도**이므로 이름을
다르게 둔다.

**특보는 별도 축이 아니라 해당 축의 입력이다** — 폭염·한파 → `HEAT`, 황사 → `AIR`,
호우·대설·강풍·태풍 → `RAIN`. 매핑표 자체는 ③-d 에 들어간다.

### ③-c 두 산식을 기온으로 갈라 쓴다 — ✅ 확정 (2026-08-24)

기상청 "체감온도(대상·환경별)" 서비스가 2026-05-01 종료돼 직접 계산한다
(`realtime-apis.md` §2.3). 산식은 **손대지 않고 공식 그대로** 쓴다.

> **정정 (2026-08-24 저녁, 실측)** — "종료"는 **data.go.kr 쪽만** 맞았다. 기상청 API허브에
> `LivingWthrIdxServiceV3/getSenTaIdxV3` 가 살아 있고 활용신청도 승인된다
> (`realtime-apis.md` §6.8). **결정은 유지하되 근거가 바뀐다** — 자체 계산의 이유는 "API 가 없어서"가
> 아니라 **"행정구역·발표시각 단위라 ③-a 의 시각별 판정(`judge(obs, t)`)에 맞지 않아서"** 다.
> 그리고 이득이 하나 생겼다: **우리 산식을 기관 공식값과 대조할 수단**이 있다. 검산이 문서 대조가
> 아니라 실측 대조가 된다. (아직 `requestCode` 조합을 못 찾아 값 자체는 미확인)

```python
def wet_bulb_stull(ta, rh):            # 습구온도 근사 (Stull 2011)
    return (ta*atan(0.151977*(rh+8.313659)**0.5) + atan(ta+rh)
            - atan(rh-1.67633) + 0.00391838*rh**1.5*atan(0.023101*rh) - 4.686035)

def summer_feels(ta, rh):              # 기상청 여름철 체감온도 (2020~). 풍속 안 씀
    tw = wet_bulb_stull(ta, rh)
    return -0.2442 + 0.55399*tw + 0.45535*ta - 0.0022*tw**2 + 0.00278*tw*ta + 3.0

def winter_feels(ta, v_ms):            # 풍속냉각지수 (JAG/TI 2001). 습도 안 씀
    v = v_ms*3.6                       # m/s -> km/h
    return 13.12 + 0.6215*ta - 11.37*v**0.16 + 0.3965*ta*v**0.16
```

**적용 경계는 계절이 아니라 기온으로 가른다.**

| 조건 | 체감온도 |
|---|---|
| 기온 ≥ **25℃** | 여름식 |
| 기온 ≤ **10℃** 이고 풍속 > **1.3 m/s** | 겨울식 |
| 그 밖 | **기온 그대로** |

**기각 — 월로 가르기(기상청 운영 방식).** 기상청은 5~9월 / 11~3월로 계절 운영하지만 우리는
"지금 이 격자"를 판정한다. 월로 가르면 **10월 이상고온이나 4월 한파에서 엉뚱한 산식**을 쓴다.

겨울식의 `≤10℃ · >1.3 m/s` 는 **공식 적용 조건 그대로**다. 여름식은 기상청이 명시 하한 없이
계절로만 운영해서, **25℃ 는 우리가 고른 값**이다 — 회귀식이 고온에서 적합됐고 그 아래는 폭염 판정과
무관하기 때문인데, 근거가 공식이 아니라 우리 판단이라는 것을 여기 남긴다.

#### 실측 검산 (2026-08-24 14:00, 강남 격자)

| 입력 | 결과 |
|---|---|
| 기온 33.1℃ · 습도 57% | 습구온도 26.25℃ → **체감온도 33.27℃** |
| 기상청 폭염 기준 주의보 33℃ / 경보 35℃ | **주의보역** |

서울동남권에는 폭염**경보**가 발효 중이었는데 모순이 아니다 — 특보는 "**일 최고** 체감온도 35℃ 이상이
2일 지속될 것으로 **예상**"이라는 지역·예보 기반 판단이고, 우리 값은 격자의 14:00 순간값이다.
특보 응답의 `other` 필드가 그 근거를 스스로 적어 두었다: *"2023년 5월 15일부터 기온과 습도를 고려하는
체감온도 기반으로 폭염특보가 운영됨"*.

**왜 기온이 아니라 체감온도인가**도 같은 실측으로 나온다. 기온 33.1℃ 고정, 습도만 바꾸면:

| 습도 | 40% | 50% | 57% | 70% | 80% |
|---|---|---|---|---|---|
| 체감온도 | 31.5℃ | 32.6℃ | 33.3℃ | 34.4℃ | **35.3℃** |

습도만으로 **3.8℃**가 움직이고 주의보역과 경보역이 갈린다. ③-b 가 "축 사이 누적 보정을 하지 않는
대신 기온 × 습도 상호작용은 축 안에서 처리한다"고 한 것이 이 자리다.

**강아지 보정을 산식에 넣지 않는다.** ②-d-2 와 같은 원칙 — 기관 공식은 그대로, 우리 판단은
임계표(③-d)에서. 산식을 손대면 "이건 기상청 체감온도다"라고 말할 수 없어지고 위 검산 같은 대조도
불가능해진다.

**정직하게 남길 것 둘**
- 습구온도를 API 가 주지 않아 **Stull(2011) 근사**가 한 겹 낀다 (통상 오차 ±0.3℃ 수준)
- 여름식이 풍속을 쓰지 않으므로 **여름에는 바람이 판정에 반영되지 않는다.** 체감상 시원해도
  공식이 반영하지 않는데, 공식을 그대로 쓰는 원칙을 따른다

체감온도는 ②-d-3 결정 2(파생량 제외)에 따라 `Q` 에 넣지 않는다. ③이 계산해 `AxisVerdict.basis` 에
근거로 싣는다.

### ③-d 임계는 기관 기준을 앵커로 쓰고, 비인용 값은 표시한다 — ✅ 확정 (2026-08-24)

표를 채우려고 보니 진짜 결정은 숫자가 아니라 **출처 없는 숫자를 어떻게 다루는가**였다.

| 축 | 공공 기준 |
|---|---|
| 대기질 | ✅ 환경부 — PM10 30/80/150 · PM2.5 15/35/75 ㎍/㎥ |
| 열 | ✅ 기상청 — 폭염 33/35℃(체감) · 한파 −12/−15℃(기온) |
| 강수 | ✅ 기상청 특보 |
| **"강아지에게 몇 ℃부터 위험한가"** | ❌ **없다** |

이 레포 파트①의 KPI 가 "출처 링크 + 조항 번호 인용"이다. 파트②에서 근거 없는 숫자를 조용히 박으면
같은 기준을 스스로 어긴다. 그래서 원칙을 먼저 정한다.

**원칙 1 — 임계는 `rules.py` 가 아니라 설정에 두고, 값마다 출처를 한 줄 붙인다.** 출처가 없으면
`# 우리 선택` 이라고 **명시**한다 (③-c 의 25℃ 선례).
**원칙 2 — 앵커는 전부 기관 기준.** 새 숫자를 최소로 만든다.
**원칙 3 — 4단계 → 3단계 압축은 축마다 명시한다.**

#### AIR — 비인용 숫자 0개

| 환경부 4단계 | 우리 |
|---|---|
| 좋음 · 보통 | `GOOD` |
| 나쁨 | `CAUTION` |
| 매우나쁨 | `UNSAFE` |

**강아지 조정을 넣지 않는다.** 개가 지면 가까이 호흡한다는 것은 정성적으로 맞지만 측정소 값과의
차이를 **정량화할 근거가 없다.** 근거 없는 방향으로 숫자를 만들지 않는다.
→ 실측(PM10 37 · PM2.5 29, 둘 다 보통)은 `AIR = GOOD`.

#### RAIN — 비인용 숫자 0개

| 조건 | 등급 |
|---|---|
| 호우·대설·강풍·태풍 특보 발효, 또는 낙뢰 | `UNSAFE` |
| `PTY ≠ 0` 또는 강수량 `hi > 0` | `CAUTION` |
| 그 밖 | `GOOD` |

**강수량 자체로는 `UNSAFE` 를 만들지 않는다.** "몇 mm 부터 위험한가"를 우리가 정하는 대신
**호우특보가 곧 기관의 위험 판정**이므로 그것을 쓴다. ②-d-1 이 강수량을 `Interval` 로 둔 덕에
`hi > 0` 하나로 실황·예보가 같이 다뤄진다.

#### HEAT — 비인용 숫자 2개 (여름 31 · 겨울 0)

| 체감온도 | 등급 | 근거 |
|---|---|---|
| < 31℃ | `GOOD` | |
| 31 ~ 33℃ | `CAUTION` | **31 = 우리 선택** |
| ≥ 33℃ | `UNSAFE` | 기상청 **폭염주의보** 기준을 한 칸 당겨 씀 |
| 0 ~ 5℃ | `CAUTION` | **0 = 우리 선택** |
| ≤ −12℃ | `UNSAFE` | 기상청 **한파주의보** 기준 |

사람 기준이면 33~35℃ 가 주의보역(=`CAUTION`)인데 한 칸 당겨 `UNSAFE` 로 올린다. 근거는 정성적이지만
방향이 명확하다 — **개는 땀샘이 거의 없어 헐떡임으로만 체온을 낮추고, 그 효율이 습도에 급격히
무너진다.** 숫자 자체는 인용값이고 새로 만든 것은 경계 둘뿐이다.

> **정직하게** — 한파 기준 −12/−15℃ 는 **기온 기준**이다. 그것을 체감온도에 적용하는 것은
> 우리 매핑이고 안전 방향(체감온도가 기온보다 낮다)이다. 이것도 설정에 명시한다.

#### 특보 → 축 매핑

| 특보 | 축 | 결과 |
|---|---|---|
| 폭염 · 한파 | `HEAT` | `UNSAFE` |
| 황사 | `AIR` | `UNSAFE` |
| 호우 · 대설 · 강풍 · 태풍 | `RAIN` | `UNSAFE` |
| 풍랑 · 폭풍해일 · 지진해일 | — | 해상용, 무시 |
| 건조 | — | 축 없음, 무시 |

#### 검문소 — 확정 즉시 실측으로 돌린다

> 2026-08-24 14:00 강남: `HEAT = UNSAFE`(체감 33.27℃ + 폭염경보) · `AIR = GOOD`(둘 다 보통) ·
> `RAIN = GOOD`(`PTY=0`) → **`grade = UNSAFE`, `dominant = [HEAT]`**.
> 그리고 예보를 따라가면 저녁 어느 시각부터 `CAUTION` → `GOOD` 으로 바뀌는 시각이 나와야 한다.

**③ 산책 적합도 룰 — ✅ 확정 완료 (2026-08-24).** 네 하위 결정이 모두 닫혔다.

## ⑤ 부분 실패·저하 정책 — 🔶 진행중 (2026-08-24, ⑤-a 확정)

공공 API 는 실제로 죽는다 — 실측 당일 에어코리아가 두 번(`05`), apihub 가 여러 번 타임아웃.
②-e 가 `ProviderResult` 로, ③-a·③-b 가 `unknown_axes` 로 **자리는 이미 만들어 놨다.** ⑤는 정책이다.

| 순 | 하위 결정 | 상태 | ④ 의존 |
|---|---|---|---|
| ⑤-a | **필수 축** — 무엇이 없으면 답을 못 내나 | ✅ 확정 | 없음 |
| ⑤-b | **재시도** — 어느 실패에 몇 번, 백오프 | ✅ 확정 | 없음 |
| ⑤-d | **같은 양의 다중 출처 우선순위** | ✅ 확정 | 없음 |
| ⑤-c | **stale 허용** — 캐시된 옛 값을 얼마나 오래된 것까지 | ✅ 확정 | ④ 뒤에 닫았다 |

> **순서 주의** — 이 ADR 머리의 표는 ④를 ⑤보다 앞에 뒀다. ⑤-c(stale)만 ④의 TTL·저장소에
> 얹히므로 **그것만 ④ 뒤로 미루고** 나머지는 먼저 닫는다. ⑤-d 는 ②-b 가 "같은 양에 출처가 둘일 때
> 무엇을 고르나는 ⑤에서"라고 예고해 둔 자리인데, `nph-aws2_min`(AWS 분 단위 기온)이 실제로 열리면서
> **가정이 아니라 실물**이 됐다 (`realtime-apis.md` §6.8).

### ⑤-a 기상청 격자만 필수, 나머지가 없으면 `GOOD` 을 말하지 않는다 — ✅ 확정 (2026-08-24)

```
기상청 격자 provider 실패      -> grade = None            (판정 불가)
그 외 축이 UNKNOWN             -> 판정하되 상한 CAUTION    (GOOD 으로 올리지 않는다)
```

**근거 1 — 특보 provider 는 필수가 아니다.** ③-d 가 특보가 아니라 **값**으로 판정하도록 정한 덕이다.
실측 케이스에서 특보를 못 받아도 체감온도 33.27℃ ≥ 33 이라 `HEAT = UNSAFE` 가 그대로 나온다.
특보는 **보강**이지 필수가 아니다 — ③-d 의 설계가 ⑤의 견고성을 만들어 줬다.

**근거 2 — 축은 3개지만 실패 단위는 2개다.** `HEAT` 와 `RAIN` 은 **같은 provider**(기상청 격자)에서
온다. 그것이 죽으면 둘이 함께 죽고, 그때는 산책 판정 자체가 성립하지 않는다.

**근거 3 — "모르는 것을 좋다고 말하지 않는다."** 이것이 상한 규칙의 전부다.

| 상황 | 결과 |
|---|---|
| 에어코리아 죽음 + 열 `UNSAFE` | `UNSAFE` — 상한은 `GOOD` 만 막으므로 위험을 놓치지 않는다 |
| 에어코리아 죽음 + 열 `GOOD` + 비 없음 | **`CAUTION`** + `unknown_axes=[AIR]` → "대기질을 확인하지 못했습니다" |
| 기상청 격자 죽음 | `None` — 열도 강수도 모르면 답할 것이 없다 |

**기각 — 전부 필수(하나라도 `UNKNOWN` 이면 판정 불가)**: 에어코리아가 죽을 때마다 아무 답도 못 준다.
실측에서 한 번의 프로브 동안 두 번 죽었다. 너무 취약하다.

**기각 — 아는 것만으로 그대로 판정**: "대기질 모름 + 열 `GOOD`" 을 `GOOD` 으로 내면, 미세먼지가
매우나쁨인 날에 "좋음"이라고 말하게 된다. 상한 규칙은 정확히 이 구멍을 막는다.

### ⑤-b 재시도는 예산 안에서만 한다 — ✅ 확정 (2026-08-24)

| 실패 | 실측 | 재시도 |
|---|---|---|
| `resultCode 05` SERVICETIMEOUT | 에어코리아 2회 발생, **1회 재시도로 2/2 복구** | ✅ |
| 네트워크 예외 · HTTP 5xx (503·타임아웃) | apihub 에서 반복 발생, 재시도로 성공 | ✅ |
| HTTP 4xx(403) · `11` 파라미터 · `12` 경로 없음 · `30` 미신청 | 몇 번을 해도 동일 | ❌ 즉시 `ProviderResult(ok=False, reason=…)` |

| | |
|---|---|
| 횟수 | **2회** (총 3시도). 실측은 1회로 복구됐고 2회면 여유 |
| 백오프 | 0.5s → 1.5s + 지터 |
| provider 개별 타임아웃 | **5초** |
| **전체 예산** | **8초.** 넘으면 남은 provider 를 포기하고 `UNKNOWN` 으로 응답한다 |
| 호출 방식 | provider 는 서로 독립이므로 **병렬**. 측정소 → 실시간 같은 **체인만 순차** |

**전체 예산이 ⑤-b 의 핵심이다.** ⑤-a 가 "축 하나가 없어도 `CAUTION` 으로 답한다"를 만들어 줬으므로
**오래 기다리느니 저하 응답을 주는 것이 낫다.** "다 모일 때까지 기다린다"는 정책은 ⑤-a 를
무의미하게 만든다 — 저하 응답을 설계해 놓고 정작 저하될 기회를 주지 않는 셈이다.
8초는 실측 기준(개별 호출은 대개 1초 내, 최대가 단기예보 106KB)에서 재시도 한 바퀴를 감당하는 값이다.

**실패 분류가 두 축이라는 점을 명시한다** — data.go.kr 은 HTTP 200 안에 `resultCode` 로 실패를 숨기고
(`05`가 그렇다), apihub 는 **HTTP 레벨**로 죽는다(503·타임아웃). 둘 다 봐야 하며, HTTP status 만
보면 `05` 를 성공으로 오인한다 (`realtime-apis.md` §6.1 함정 2).

### ⑤-d 출처 우선순위 목록, "가까우면"이 아니라 "같은 격자면" — ✅ 확정 (2026-08-24)

②-b 가 미뤄 둔 자리다. `nph-aws2_min` 이 열리면서 가정이 아니라 실물이 됐다 — **기온이 네 곳에서 온다:**

| 출처 | 신선도 | 공간 |
|---|---|---|
| AWS 분 단위 지점 (`nph-aws2_min`) | **분** (실측 17:35) | 관측소 **지점** |
| 격자 초단기실황 (`T1H`) | 매시 정각, **+40분 제공** | **5km 격자** |
| 초단기예보 (`T1H`) | 매시 30분 발표 | 5km 격자 |
| 단기예보 (`TMP`) | 1일 8회 발표 | 5km 격자 |

**긴장은 신선도와 공간 대표성이 반대 방향이라는 것이다.** AWS 는 가장 신선하지만 그 지점이 내 위치를
대표한다는 보장이 없고, 격자는 최대 100분 지연되지만 **정의상 내 위치를 포함한다.**

같은 `(quantity, valid_at)` 에 여러 값이 있으면 이 순서로 고른다:

1. **같은 격자 안에 있는 AWS 지점 관측**
2. 격자 초단기실황 (`getUltraSrtNcst`)
3. 초단기예보 (`getUltraSrtFcst`)
4. 단기예보 (`getVilageFcst`)

**"가까우면 AWS" 가 아니라 "같은 격자면 AWS" 인 것이 핵심이다.** "5km 안" 같은 임계를 두면 ③-d 가
경계한 **비인용 숫자**가 또 생긴다. 격자 일치는 이미 정의된 단위라
`dfs_xy_conv(지점 위경도) == (nx, ny)` 로 판정되고 **새 숫자를 만들지 않는다.** 지점이 내 격자 안에
있으면 대표성 문제가 사라지고 신선도 이득만 남으므로 그때는 AWS 가 명백히 낫다.

#### ②-c 를 한 겹 다듬는다

②-c 는 "같은 `(quantity, valid_at)` 에 발표가 여럿이면 **최신 `issued_at` 이 이긴다**"고 했다.
그것만으로는 틀리는 경우가 실측에 있다:

> `valid_at = 15:00` 에 **초단기예보**(13:30 발표)와 **단기예보**(14:00 발표)가 둘 다 있다.
> 최신 발표만 보면 단기예보가 이기는데, **6시간 이내는 초단기예보가 더 정확하다.**

→ **출처 우선순위가 먼저, 같은 출처 안에서 최신 `issued_at`.** ②-c 의 규칙은 유지되되 그 아래로 들어간다.

**따라 나오는 것** — AWS 지점이 내 격자 안인지 판정하려면 지점 좌표가 필요하다.
`data/reference/` 캐시가 셋이 된다: 측정소 목록 · 특보구역 매핑 · **AWS 지점 목록**.

**한계를 명시한다** — 전국 AWS 는 500~600 지점이고 5km 격자는 수천 개라, **1순위는 실제로 도시 일부에서만
발동한다.** 그래도 두는 이유는 강남처럼 지점이 촘촘한 곳에서 분 단위 신선도를 공짜로 얻기 때문이다.

## ④ 신선도·캐시 — ✅ 확정 (2026-08-24)

### ④-a 캐시 키는 사용자 위치가 아니라 **API 조회 키**

위치 하나가 **다섯 개의 서로 다른 공간 단위**로 갈라진다:

| 조회 키 | 쓰는 곳 |
|---|---|
| 격자 `(61,125)` | 기상 3종 |
| 측정소 `강남대로` | 대기질 실시간 |
| 특보구역 `서울동남권` | 특보 |
| AWS 지점 | 분 단위 관측 |
| 권역 `서울` · 행정구역 `1168000000` | 미세먼지 예보통보 · 생활기상지수 |

"역삼동에 대한 캐시"로 두면 **강남 전역이 같은 격자를 쓰는데도 사람 수만큼 다시 받는다.**
조회 키로 캐시하면 한 번 호출이 그 격자의 모든 사용자를 덮는다.

```
rt:{provider}:{operation}:{조회키}
예) rt:kma-vilage-fcst:ncst:61,125   ·   rt:airkorea-realtime:dnsty:강남대로
```

### ④-b TTL(보관) · 재호출 시점(발표 주기) · 사용 가능 여부(`issued_at`) 를 **분리**

재호출 시점은 실측 발표 주기에서 **유도된다** (임의 숫자 없음):

| provider | 새 값이 생기는 시점 |
|---|---|
| 초단기실황 | 매시 정각 관측 → **`:40` 제공** |
| 초단기예보 | 매시 `:30` 발표 → `:45` 제공 |
| 단기예보 | 02·05·…·23시 발표 → `:10` 제공 |
| 대기질 실시간 | 매시 |
| AWS | **매분** |
| 특보 | **비정기** → 고정 5분 ← 이 절의 유일한 임의 숫자 |
| 측정소·AWS 지점 목록 | 월 1회 (30일) |

**셋을 한 숫자로 뭉치면 ⑤-c(stale)가 얹힐 자리가 없어진다** — 만료된 값이 남아 있어야 옛 값을 쓴다.
그래서 Redis TTL 은 넉넉히(보관), 재호출은 위 표로, "쓸 수 있는가"는 값의 `issued_at` 으로 판단한다.

### ④-c 저장소는 Redis, **없어도 돈다**

RAG-001 대로 Redis 를 쓰되 연결 실패가 판정을 막지 않는다. 캐시는 가속이지 정답의 원천이 아니다.
Redis 가 없으면 매번 호출하고 ⑤-b 의 8초 예산이 그 비용을 잡는다.

### ④-d 요청이 채우고(single-flight) Beat 가 **활성 키만** 데운다

pull 만으로는 실사용에서 둘이 깨진다 — **thundering herd**(만료 순간 동시 요청이 전부 미스 →
같은 API 를 N번)와 **cold start 가 사용자에게 그대로 노출**.

```
요청 → 히트면 즉시 응답
     → 미스면 single-flight 로 한 번만 호출 (나머지는 그 결과를 기다린다)
     → 조회 키를 "활성 키" 집합에 기록 (마지막 요청 시각)
Beat → 활성 키만 다음 발표 시각에 맞춰 미리 갱신 · 24시간 미요청이면 활성 집합에서 제거
```

전국을 미리 당기지 않고 **한 번이라도 쓰인 키만** 데운다. 활성 키 집합이 곧 실사용 지역이라
사용자가 늘면 자연스럽게 따라간다. RAG-001 의 Celery + Beat 를 실제로 쓰는 첫 자리다.

### ④-e ⚠️ 실제 제약 — data.go.kr **개발계정 일 1,000회** (2026-08-24 확인)

한도는 **API(활용신청)별**이다. 계산하면 병목이 하나로 좁혀진다:

| 서비스 | 조회 키 하나당 | 1,000 으로 가능한 수 |
|---|---|---|
| **기상청 단기예보** (실황+초단기예보+단기예보가 **한 서비스**) | 24+24+8 = **56회/일** | **약 17 격자** ← **병목** |
| 에어코리아 대기오염정보 | 24회/일 | 41 측정소 (서울 40개면 딱) |
| 기상청 특보 | 전국 1세트 288회/일 | 여유 |
| 에어코리아 측정소정보 | 월 1회 | 여유 |

**서울이 대략 30~40 격자다. 17개로는 서울 하나도 못 덮는다.** 대응 넷:

1. **AWS 로 초단기실황을 대체한다 (가장 큰 절감).** AWS 는 apihub 소속이라 **data.go.kr 한도를 안 쓰고**,
   `stn=0` 로 **전국 500~600 지점을 1회 호출**로 받는다(실측 97KB). ⑤-d 가 "같은 격자 안 AWS 지점이
   1순위"라고 이미 정했으므로, 지점이 있는 격자는 실황(24회/일)을 부르지 않아도 된다.
   → 그 격자는 24+8 = **32회/일** → 1,000 으로 **31 격자**. 서울이 들어온다
2. **프리페치는 활성 상위 N개만**, 나머지는 pull. `N` 은 예산에서 역산 (설정값)
3. **provider 별 일 호출 예산을 설정에 두고**, 초과하면 프리페치를 멈추고 pull 만 남긴다 —
   한도 초과로 전부 죽는 것보다 낫다
4. **운영계정 전환 신청** ← 근본 해결. 승인되면 10만/일. 실사용자를 상정하면 사실상 필수 (P0)

> 이 제약이 **⑤-c 의 가치를 키운다.** 호출을 아껴야 하므로 "발표 주기가 지났지만 아직 못 불렀다"가
> 정상 경로가 된다. ⑤-c 는 예외 처리가 아니라 **예산 정책의 일부**다.

#### ④-f 프리페치 활성 키 상한 `N` = **10 으로 시작**

기상청 단기예보 서비스 예산 1,000/일을 나눈 값이다:

| | 격자당 | `N`=10 | `N`=20 | `N`=31 |
|---|---|---|---|---|
| AWS 지점이 있는 격자 (실황 생략) | 32회/일 | 320 | 640 | 992 |
| AWS 지점이 **없는** 격자 | 56회/일 | 560 | 1,120 ❌ | ❌ |
| **pull 여유분** | | **440~680** | 0~360 | ~0 |

1. **혼재 비율을 아직 모른다.** 활성 격자 중 몇 %에 AWS 지점이 있는지는 실사용을 봐야 안다.
   보수적으로 56회/일 기준을 잡으면 10개가 상한에 가깝다
2. **pull 여유분이 있어야 한다** — 프리페치되지 않은 새 지역 요청이 들어올 자리다. `N`=20 은 여유가
   0이 될 수 있다
3. ④-e 3번(예산 초과 시 프리페치 중단)이 안전장치라 **틀려도 한도 초과로 전부 죽지 않는다**

**실제 소비량을 로그로 재서 조정한다.** `N` 은 설정값이라 되돌리는 비용 🟢 이고,
**운영계정(10만/일)이 승인되면 같은 식으로 재역산**하면 된다 — 그때는 수백 단위가 된다.

### ⑤-c stale 은 "갱신 주기를 몇 번 놓쳤는가"로 재고, 쓰되 `GOOD` 으로 올리지 않는다 — ✅ 확정 (2026-08-24)

④-e 가 성격을 이미 규정했다 — 일 1,000회 제약에서는 **"발표 주기가 지났지만 아직 못 불렀다"가
정상 경로**다. stale 은 에러 처리가 아니라 예산 정책의 일부다.

**언제 쓰나** — 새 값을 못 얻은 경우 전부다: ⑤-b 재시도 소진 · ④-e 예산 초과로 호출하지 않음 ·
single-flight 대기 타임아웃. 셋을 구분할 이유가 없다.

**어떻게 드러내나** — 자리가 이미 있다: `Measurement.issued_at`(②-c) · `ProviderResult`(②-e) ·
`AxisVerdict`(③-b).

| | |
|---|---|
| **stale 판정** | 그 양의 **갱신 주기를 한 번 이상 놓쳤으면** stale — 대기질 1시간, 실황 1시간, AWS 1분, 단기예보 1주기 (④-b 표) |
| **폐기 상한** | **갱신 주기 × 3** ← 이 절의 **유일한 비인용 숫자**, 설정에 `# 우리 선택` 표시 |
| **stale 값의 취급** | 버리지 않고 **쓰되 ⑤-a 의 상한 규칙을 적용한다 — `GOOD` 으로 올리지 않는다** |

**시간(분·시간)이 아니라 주기 횟수로 재는 것이 요점이다.** 갱신 주기는 ④-b 에 실측으로 다 있으므로
새 숫자가 거의 생기지 않는다. 그리고 마지막 줄이 핵심이다 — stale 은 "모름"과 "정상" 사이인데,
**그 중간을 표현할 장치를 ⑤-a 가 이미 만들어 뒀다.** 새 등급도 새 개념도 만들지 않고 재사용하며,
위험은 억제된다: 3시간 전 기온으로 "산책하기 좋아요"라고 말하지 않는다.

**예보는 자연히 다르게 동작한다.** 관측값은 `valid_at` 이 고정이라 시간이 지나면 `t=now` 를 덮지
못하지만, 예보는 `valid_at` 이 미래라 **발표가 좀 오래됐어도 여전히 그 시각을 덮는다.** ②-c 가 시각을
둘로 나눠 둔 덕에 이 구분이 규칙 없이 저절로 갈린다.

**하지 않는 것 — stale-while-revalidate**(옛 값으로 즉시 응답 + 백그라운드 갱신). ④-d 의 Beat 가
활성 키를 미리 데우므로 그 경로는 이미 항상 신선하고, 비활성 키는 어차피 동기 호출이 필요하다.
복잡도만 늘고 얻는 것이 없다.

**⑤ 부분 실패·저하 정책 — ✅ 확정 완료 (2026-08-24).** 네 하위 결정이 모두 닫혔다.

## RT-002. 8단계 캐시 — 조립 자리 · 인프라 범위 · AWS 지점표 — ✅ 확정 (2026-08-25)

RT-001 ④·⑤-c 를 구현으로 옮기려다 계획의 빈칸 셋이 드러났다. 셋 다 **RT-001 이 정한 것을
바꾸지 않는다** — 정해진 것을 어디에 놓느냐의 문제라 하위 결정으로 남긴다.

### ②-a 조립 함수는 `realtime/collect.py` 에 둔다

**빈칸** — 검문소 D 는 "에어코리아를 죽였을 때 `AIR=unknown` + 전체가 `GOOD` 으로 안 올라가는지"인데,
**판정 쪽은 7단계에서 이미 통과했다** (`test_an_unknown_axis_never_lets_the_answer_reach_good` ·
`test_the_cap_only_blocks_good_so_danger_is_not_hidden` · `test_a_failed_provider_is_visible_next_to_the_verdict`).
그러므로 D 가 새로 확인하는 것은 판정 규칙이 아니라 **전송 실패가 캐시를 거쳐 판정까지 전달되는
경로**다. 그러려면 provider 7개를 불러 `Observations` 하나로 묶는 함수가 있어야 하는데, 구현 계획은
그것을 9단계 `app/` 로 잡아 두었다. **검문소는 8단계에 있다.**

**결정** — `realtime/collect.py` 를 새로 둔다. `cache.py` 가 이것을 감싸고, 9단계 `app/` 는
`judge(collect_cached(...), now)` 세 줄짜리 껍데기가 된다.

**기준은 "검문소 D 를 FastAPI 없이 돌릴 수 있는가"였다.** 조립이 `app/` 에 있으면 D 를 보려고
9단계를 먼저 해야 하고 단계 순서가 뒤집힌다. `realtime/` 안에 있으면 `python -m realtime walk` 로
돈다. 기각한 대안은 `cache.py` 안에 함께 두는 것 — 파일 하나가 ④의 다섯 덩어리 + 조립까지
여섯 가지를 지고, **캐시를 끈 상태의 순수 조립을 따로 시험할 수 없게 된다.**

①-3(`core/` 를 두지 않는다)과 부딪히지 않는다. `core/` 를 기각한 이유는 "N 개가 공유하는 것"의
자리가 이미 `transport/` 라서였다. `collect.py` 는 공유물 창고가 아니라 **호출 순서를 아는 한 층**이고,
지금까지 아무도 그것을 몰랐다 — providers 는 서로를 모르고 rules 는 조회를 모른다.

### ②-b 8단계는 Celery Beat 프리페치까지 세운다. Celery 자리는 `backend/tasks/`

**빈칸** — RAG-001 이 "Celery + Beat + Redis" 를 확정했지만 **레포에 실물이 하나도 없다.**
`compose.yml` 은 `db` 하나뿐이고 `pyproject.toml` 에 `celery` 도 `redis` 도 없다. 8단계 ④-c·④-d 가
그것을 처음으로 실제로 쓰는 자리다.

**결정** — 8단계에서 Redis 어댑터와 Beat 프리페치까지 전부 세운다. ④가 통째로 닫힌다.

기각한 대안은 "메모리 구현만, 인프라는 나중"이었다. 짧고 검문소 D 는 그대로 통과하지만,
**④의 다섯 덩어리 중 프리페치(④-d)와 영속 예산(④-e 3)이 비어 8단계를 완료라고 부를 수 없다.**
그리고 일 예산 카운터가 프로세스 메모리에 있으면 재시작마다 리셋이라 ④-e 의 제약이 시험되지 않는다.

**자리는 RAG-009 가 이미 정해 두었다** — `backend/tasks/` 가 `crawler/`·`rag/`·`realtime/` 의 형제
패키지이고 의존 방향은 `tasks → …` 한쪽이다. `test_import_direction.py` 의 `FORBIDDEN` 에 `tasks` 가
이미 들어 있어 아래에서 위를 부르는 것은 이미 막혀 있다. **새로 막는 것은 범위다** —
`tasks` 를 `test_import_direction_packages.py` 의 `ALLOWED` 에 `realtime` 과 같은 폭
(`crawler.core.config` 하나)으로 추가한다. 넓히면 워커가 `store`·`Fetcher` 를 끌고 들어와
"실시간은 저장하지 않는다"가 워커 쪽에서 조용히 뚫린다.

### ②-c AWS 지점표는 `data/reference/` 의 정적 메타다 — 🔴 블로커 해제 (2026-08-25)

`stn_inf.php` 활용신청이 승인됐다. **같은 날 403 → 200.** 확인한 것:

```
AWS 지점 745개 · LON/LAT 실려 온다
역삼(37.4979, 127.0276) → 격자 (61,125) 안의 AWS 지점 = 1개 (401 서초, 37.48462/127.02601)
```

**⑤-d 1순위와 ④-e 1번이 둘 다 실제로 발동한다.** `kma_apihub.fetch` 는 좌표표를 인자로 받도록
이미 만들어져 있었으므로(6단계) 채울 것은 그 표를 만드는 함수뿐이다 —
`parse_stations`/`fetch_stations` 를 같은 모듈에 붙인다. **provider = API 서비스 하나 = 모듈 하나**
규칙 그대로다 (`stn_inf` 와 `nph-aws2_min` 은 같은 typ01 봉투·같은 인증).

신선도는 **월 1회**라 `airkorea_stations` 와 같은 취급이다 — `data/reference/` 캐시, 그것이
`realtime` 이 `crawler.core.config` 의 경로 탐색을 참조하는 (두 번째이자 마지막) 이유다.

**덤으로 얻은 것과 못 얻은 것** — 표에 `LAW_ID`(법정동코드, 서초 = `1165010800`)가 실려 있어
생활기상지수의 `areaNo` 재료가 된다. ⚠️ **정정 (§6.9)** — 그대로는 안 되고 **앞 5자리(시군구)만**
쓴다(`1165000000`). 법정동 코드로 부르면 `99 검색결과가 없습니다` 인데 그게 권한 문제처럼
안 보여서 원인을 찾는 데 오래 걸렸다. 자르는 규칙은 `kma_life_index.area_code()` 한 곳에 있다. 반면 `FCT_ID`(`11B10101`)는 **동네예보구역**이라 특보구역과
다르다 — 🟡 특보구역 매핑표는 여전히 필요하다.

**같이 정리된 것** — 대기 중이던 "apihub 생활기상지수 활용신청"은 **신청할 것이 없다.**
`LivingWthrIdxServiceV3` 아래 남은 403 은 `getAirDiffusionIdxV3`(대기확산지수) 하나뿐인데
`kma_life_index` 가 그것을 부르지 않는다. 우리가 부르는 `getSenTaIdxV3`·`getUVIdxV3` 는 둘 다 200 이다
(§6.8 이 403 이라고 적은 `getUVIdxV3` 도 8/25 재확인 결과 열려 있다. ③-b 가 UV 를 축에서 뺀 결정은
그대로 두고, **"미신청이라 못 쓴다"는 근거만 사실이 아니게 됐다**).
