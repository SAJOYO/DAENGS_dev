## 2번 — FLUX.2-klein-4B 실험 카드 (자세히)

**목적:** 3·4번을 설계할 때 필요한 숫자를 크레딧이 무료인 동안 모은다. 제품 코드(앱 경로)는 바꾸지 않는다.

**공통 규칙**
- 돈이 나가는 실행 전에 조건·장수·예상 비용을 설명하고 승인받는다. 실패는 매 시도 원인을 확인/추정으로 갈라 적는다.
- 판정은 검수 점수만 믿지 않고 격자 이미지를 눈으로 본다. 제목의 강아지 이름은 **영문**(예: `MOMO`) — 검수가 한글 이름을 깨진 글자로 오판한다.
- 비교할 때 seed 는 고정한다.
- 결과는 `docs/cardimage/compare-*.md` · `worklog.md`, 산출물은 `cardimage/out/_cardgen/<실험>/`(미추적). 끝나면 위 체크리스트를 체크한다.

### E1. 글씨 유지

| 조건 | 내용 |
| --- | --- |
| ① 프롬프트 | 아래 패널 문구를 그대로 적는다(예: "keep the text `PETAL PAUSE` exactly"). 달마다 문구를 `catalog` 에 두는 방식 검토 |
| ② 해상도 | 1024×1632 → **1280×2048**(2.6MP, FLUX.2-klein-4B 상한 4MP, 서비스는 2048 까지 받음) — 생성 시간 1.5~2배 예상 |
| ③ ① + ② | |
| 대상 | 깨졌던 조건(4월 · seed 1) × 사진 3장 → 조건당 3장, 이어서 9월 확인 |
| 판정 | 문구 정확 여부(눈) · 닮음 · 목줄 · 장당 시간 |
| 코드 | `HttpCardImageEngine` 에 생성 크기 인자, `tools/cardgen_compare.py` 에 `--gen-size`·`--prompt-extra` |
| 비용 (추정) | 콜드 스타트 7분 + 9장 + 유휴 10분 ≈ L4 22분 ≈ ₩500 |

**09-16 결과(잠정):** 문구 명시는 **더 깨졌다**, 1280×2048 은 깨지는 자리를 옮겼을 뿐이고 40% 느리다. 같은 틀·seed·크기면 사진이 달라도 같은 자리가 깨진다 →
조건을 바꾸지 말고 **달 틀마다 글씨가 안 깨지는 seed 를 미리 골라 둔다**. 상세 `compare-2026-09-16-klein-e1.md`.

### E2. 4장 뽑기

| 항목 | 내용 |
| --- | --- |
| 방식 비교 | 순차 4회 호출 vs 파이프라인 한 번에 4장(`num_images_per_prompt`) — GPU 메모리(L4 24GB, 실사용 22GiB) 안에 들어가는지, 총 시간 |
| seed | 카드별 파생값(예: `hash(요청 id, 장 번호)`) 이 결과를 충분히 다르게 만드는지 |
| 판정 | 사진 각도별(정면·옆·엎드림) "4장 중 쓸 만한 장" 수 — 고를 게 없는 경우가 얼마나 나오는지 |
| 서비스 | `/generate` 를 N장 계약으로 넓힐지(진행률 포함) 판단할 근거 |

**09-16 결과(잠정):** 서비스에 `count`(1~4)를 넣었지만 **L4 에서는 2장부터 CUDA OOM** — 순차만 된다(장당 약 16초, 4장 GPU 약 65초).
seed 1~4 × 사진 3: 글씨는 seed 로 갈리고(제목·아래 패널 기준 4월 {3,4}, 9월 {1,4} 깨끗, seed 4 는 둘 다), 쓸 만한 장은 정면 사진 1~2 · 엎드린 옆모습 0.
4장끼리 차이는 털·귀·표정 정도로 작다. 상세 `compare-2026-09-16-klein-e2-e3.md`.

### E3. 콜드 스타트 줄이기

지금 로드 425~430초(버킷 ~15GB, GCS FUSE). 후보:
- GCS FUSE 마운트 옵션(파일 캐시 · 병렬 다운로드) — 서비스 메모리 증가와 교환
- 가중치를 이미지에 굽기 — 09-15 새 이미지(~10GB) 첫 가져오기가 5분이었으니 오히려 느릴 수 있다(재야 안다)
- 시작 CPU boost

판정: `load_seconds` 와 인스턴스 기동~ready 전체 시간.

**09-16 결과(잠정):** 기준(기본 FUSE) 로드 374.9초 · 403.1초 · 340.7초. `enable-buffered-read=true` 는 **735.6초로 2배 느림**. in-memory 파일 캐시(`cache-dir=cr-volume:…`)는
컨테이너가 **마운트 단계에서 못 떠** 재지 못했다(문서에 완전한 예시가 없어 원인 미확정, 추측 재배포는 안 함). 가중치 굽기·CPU boost 는 이유만 적고 안 쟀다.
→ 설정은 기본 유지. 콜드 스타트는 3번 카드에서 "사용 시간대 최소 인스턴스" 같은 운영 쪽으로 푼다. 또 **배포만 해도 인스턴스가 떠서 로드한다**(배포 한 번 = L4 약 7분 + 유휴 10분).
⚠ 가중치를 다시 받게 되면 `fetch.py`(한 파일씩, `max_workers=1`) 경로는 **실제 잡으로 아직 안 돌려 봤다** — 09-15 성공은 잡 명령을 `hf download` 로 덮어쓴 실행이었다. 첫 실행은 로그를 지켜본다.

### E4. 비용 실측

결제 콘솔(Billing → 보고서)에서 Cloud Run GPU **서비스** 실제 청구액을 SKU 별로 확인한다. 지금 장당 비용(₩43 / ₩400)은
가중치 잡 단가를 옮겨 쓴 추정이다. 확인되면 비교 문서의 비용 칸을 바꾼다.

### 이미지 하나로 맞추기 (실험 중 처음 새로 빌드할 때) — ✅ 09-16 `07e7a55`

09-16 전에는 서비스가 `c917c96`, 잡이 `90a42ef` 를 써서 갈라져 있었다. 한 이미지로 둘 다 돌릴 수 있는 구조인데(잡은 실행 명령만
`python -m daengs_cardgen.fetch klein-4b` 로 바꿔 씀), 09-15 에 Qwen 수정·가중치 받기 수정으로 새로 빌드하면서
잡만 갱신하고 서비스는 재배포하지 않았기 때문이다.

- **왜 8GB 를 통째로 먹나:** Dockerfile 앞쪽 `ENV`(PYTORCH_CUDA_ALLOC_CONF)가 바뀌어 뒤의 설치 레이어가 전부 새로
  만들어졌다. 저장소 합계 28.2GB vs 이미지 크기 합 28.4GB — 공유분은 0.2GB 뿐(09-16 조회). 월 약 $0.8.
- **한 것 (09-16, #557):** Qwen 코드를 걷어내고 `count` 를 넣어 `07e7a55` 를 한 번 빌드 → 서비스·잡을 함께 그 태그로 → 서비스 스모크 확인 →
  `c917c96`·`90a42ef` 와 옛 리비전 삭제.
- **앞으로도 같다:** 빌드마다 8GB 가 새로 쌓인다. 배포가 끝나면 쓰지 않는 태그를 지운다.
  옛 리비전이 옛 이미지를 물고 있어도 트래픽 0% 이고 되돌릴 일이 없으면 지워도 된다.

**완료 기준:** E1~E3 결과가 문서에 있고(E4 는 보류), 3번 카드의 "정할 것" 각각에 근거 숫자가 붙어 있다.

## 3번 — 여러 장 생성 + 고르기 (제품화)

- backend: 한 요청에 N장, 조회 응답에 진행률(몇 장 완료), 고른 1장만 저장·나머지 폐기(또는 짧은 보관), 장별 seed 저장.
- 한도: 카드 장수 대신 "뽑기 횟수" 또는 GPU 시간 기준으로 다시 설계 — D-077 을 개정하거나 새 번호.
- 콜드 스타트 대응: E3 결과 + 사용 시간대 최소 인스턴스 여부.
- 앱 경로 정리 기준(`4 × cardimage_timeout_ms + 60초`)을 GPU 경로의 콜드 스타트에 맞게 고친 뒤에야 `DAENGS_CARDGEN_URL` 을 운영에 넣는다.
- 카드 종류별 엔진 선택(월 스페셜 = Nano Banana 2 한 장, 개인화 카드 = FLUX.2-klein-4B 여러 장) 여부.
