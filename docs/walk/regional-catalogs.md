# 지역별 공공자료 캐시와 자동 갱신

[#399](https://github.com/SAJOYO/DAENGS_dev/pull/399)는 [최초 운영 연결](runtime.md)의 다음 단위다.
기존 outbox와 일기 생성기를 유지하고, 상권·하천을 지역별로 준비한다. 앱의 화면, 원문 보존,
장면 선정·작성 계약은 바꾸지 않는다.

## 지역과 선택

좌표를 EPSG:5179의 1km 격자로 묶는다. 키는 `kr1k-x-y`이고 각 격자의 중심에서
반경 1,200m 자료를 수집한다. 격자 모서리까지 약 707m + 최대 검색 반경 250m +
제공자 거리 계산 차이를 위한 5m 여유가 모두 들어간다.

이는 내부 캐시 공유 단위이며 사용자에게 표시하는 행정동이나 셀로판 검색의 지역 정책이 아니다.
각 기록은 자기 지역의 캐시 하나만 사용한다. 겹치는 지역의 상가를 합산하지 않는다.
상권 125m·하천 250m의 **검색 원 전체**가 캐시에 포함돼야 한다.
범위 밖이거나 자료가 없는 경우를 시설/하천 0개로 표현하지 않는다.

- `DAENGS_WALK_PUBLIC_CATALOG_ROOT/<region>/commerce.json`
- `DAENGS_WALK_PUBLIC_CATALOG_ROOT/<region>/river.json`
- 공원은 기존 전국 등록점 파일 `DAENGS_WALK_PARK_CATALOG_PATH`를 공유한다.
- SGIS 동 주소는 기존 조회기를 그대로 사용한다.
- 이행 중에는 유효한 기존 단일 지역 파일을 fallback으로 사용할 수 있다.

## 준비와 갱신

기존 Beat가 매분 `walk-public-catalog` 큐로 작업을 보낸다. 전용 `walk-catalog-worker`만
이 큐를 소비하고 캐시 볼륨에 쓴다. 웹·장면 수집 worker·Beat는 읽기 전용이다.
정확 동선, 메모, 사용자 ID를 공공자료 API에 보내지 않는다. 지역 중심과 검색 반경으로 조회한다.

갱신 워커는 기존 DB의 현재 revision에 해당하는 위치 있는 기록을 읽는다.
확정 행동 핀을 우선하며, 임시 핀·삭제된 기록·폐기된 revision은 제외한다.
pending/running 작업을 우선하고, 최근 30일 산책의 지역도 만료 전 갱신 대상으로 본다.
한 번에 최대 3,000개의 자료 작업을 읽는다. 실제 부하가 이 범위를 넘으면 처리량과
페이지 순회를 확장해야 하며, 이를 전국 모든 기록의 즉시 처리 보장으로 해석하지 않는다.

자료 다운로드는 DB 트랜잭션과 장면 수집의 45초 lease **밖에서** 실행한다.
갱신 중복 방지는 Redis의 300초 소유 토큰 잠금이며 한 사이클의 전체 제한은 240초다.
대기열의 오래된 스케줄 메시지는 55초 후 만료돼 장기 중단 후 작업이 계속 쌓이지 않는다.

| 정책 | 값 |
| --- | --- |
| 갱신 시작 | 수집 후 20일, 또는 파일 없음/무결성·범위 오류 |
| 읽기 유효기간 | 기존과 같은 30일 |
| 사이클별 다운로드 시도 | 전국 공원 포함 최대 5개 캐시 |
| 사이클별 HTTP 요청 | 페이지·실패 요청 포함 최대 80회 |
| 자동 갱신 일일 요청 | KST 날짜별 기본 300회, 설정 허용 1~1,000회 |
| 제공자 실패 재시도 | 해당 캐시 1시간 뒤 |
| 하천 표준 메타데이터 | 한 사이클의 여러 지역에서 요청 결과 공유 |

`DAENGS_WALK_CATALOG_DAILY_REQUESTS`는 **이 자동 갱신기의 할당량**이다.
기존 시설/날씨 조회나 운영자의 수동 Prepare 호출까지 합친 제공기관 전체 한도는 아니다.
실패한 HTTP 요청도 전송 전에 원자적으로 계수한다. Redis가 연결되지 않으면 무제한 요청으로
전환하지 않는다.

새 파일은 기존 제공자의 페이지 검증·정규화가 끝난 후 원자적으로 교체한다.
갱신 실패 시 기존 파일을 덮어쓰지 않으며, 유효기간 안의 파일은 계속 사용한다.
30일을 넘긴 자료는 읽지 않는다. `partial` 자료를 완전한 자료로 승격하지 않는다.

## 장면 수집과 연결

새 지역의 캐시가 없으면 수집 결과를 `unavailable / catalog_preparing`으로 남기고
기존 세 번 재시도 범위 안에서 다음 시도를 5분 뒤에 예약한다.
갱신 워커가 실제 reader로 자료 준비를 확인하면, 해당 자료를 기다리던 pending 작업만
앞당긴다. 정상적으로는 다음 30초 수집 주기에 이어진다.

갱신 완료가 아직 running인 시도와 겹치면 다음 갱신 주기에서 pending 상태를 확인한다.
현재 revision, 마지막 시도의 대기 이유, 작업 상태를 함께 검사하며
completed/failed/cancelled 작업을 다시 열지 않는다.
장기간 제공자 장애나 요청 한도 소진으로 세 번 시도를 모두 쓴 기록은 그대로 unavailable이다.
[기존 기록 보강](context-backfill.md)은 명시적 명령으로 예약하며 이 갱신기가 대신하지 않는다.
저장된 일기의 재생성은 별도다.

## 운영

기존 공공자료 설정 파일에 아래 값이 들어간다. 새 키·DB migration은 필요 없다.

```dotenv
DAENGS_WALK_PUBLIC_CATALOG_ROOT=/data/walk-public/regions
DAENGS_WALK_CATALOG_REFRESH_ENABLED=true
DAENGS_WALK_CATALOG_DAILY_REQUESTS=300
```

기존 `Walk diary runtime → Start`가 지역 경로·자동 갱신 flag를 추가하고 사전 점검한 뒤
수집 worker → 갱신 worker → Beat → 웹 순서로 반영한다. 이전 설정의 키와 기타 값은 유지한다.
검사 실패 시 설정 파일을 복구한다. 새 worker도 별도 venv를 쓰므로 backend의 ML 환경을 건드리지 않는다.

일반 배포는 **이미 실행 중인** 갱신 worker만 재생성한다. 처음부터 자동 활성화하거나
정지한 worker를 다시 켜지 않는다. Stop은 Beat·수집 worker·갱신 worker를 함께 정지한다.
기존 자료/캐시/DB는 유지한다. 오랫동안 중지해 공원과 초기 지역 캐시가 만료됐다면 Prepare 후 Start한다.

실패 상태는 갱신 worker에 안전한 상태·건수·예외 종류만 경고로 남긴다.
URL, 키, 본문, 사용자·기록 ID는 기록하지 않는다.

## 검증

2026-09-10 로컬 검사:

- 지역/기존 제공자/수집/PowerShell/사전 검사 명시 파일: 99 passed.
- PostgreSQL 현재 핀·revision·대기 작업 재개, Redis 동시 요청 상한·소유 토큰 잠금,
  지역 캐시·기존 Smoke·수집 재시도: 43 passed. 앞 수치와 중복되어 합산하지 않는다.
- 모든 DB 검사는 localhost의 임시 schema, Redis 검사는 전용 임시 컨테이너에서 수행한다.
- 마지막 설정 경계·잘못된 지역 캐시·지역 Smoke 검사 보완 후 관련 파일 16 passed.
  변경 Python Ruff와 `uv run check`도 통과했다. 전체 저장소 pytest를 실행한 결과는 아니다.

운영 Smoke의 `regional_smoke=true`는 서로 다른 두 격자 중심에 합성 산책을 만든다.
별도 관리 CLI로 지역을 미리 채우지 않고 정상 API·Beat·갱신 worker·수집 worker를 거친다.
각 장면의 상권·하천 봉투가 자기 지역 캐시를 참조하는지, 실제 Gemini 생성·원문 보존·재조회가
성공하는지 확인한 뒤 임시 계정과 연결 자료를 삭제한다. 실행 전 캐시 존재 여부도 결과에 남긴다.
물리 폰 UI 검사나 장기 장애·실제 20일 경과의 운영 관찰을 수행한 것으로 보지 않는다.
