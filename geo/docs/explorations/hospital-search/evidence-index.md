# 근거 인덱스 — 실시간 호출 대신 배치 적재 (오프라인 enrichment)

> 용어 정정: 이건 RAG 가 아니다. LLM 이 문서를 회수해 생성하는 게 아니라 **오프라인 근거 수집 →
> 특징 저장 → SQL 랭킹**이다. topic 사전이 ~30개 규모라 pgvector 임베딩도 지금은 불필요하다 —
> 정확 일치로 시작하고, 어휘가 수백 개로 늘면 그때 검토한다.

## 원천 (약관 리스크 순으로 대체)

네이버 검색 API 결과의 장기 적재는 **막힌 것으로 취급** (위 parked-reason). 허용 가능한 원천:
1. DAENGS 자체 후기 (우리 데이터 — 무제한)
2. 병원이 직접 등록·확인한 진료 정보 (최고 신뢰도 — 유일하게 '역량'이라 불러도 되는 것)
3. 재사용 허가가 명확한 공공데이터
4. 정식 제휴 데이터
5. 외부 검색은 저장·가공 없이 **실시간 원문 링크 표시만** (허용 범위 재확인 후)

아래 파이프라인·실측은 원천이 무엇이든 동일하게 적용된다 — 실측에 쓴 검색은 검증용 대체였다.

**발상 (사용자)**: 검색 시마다 커뮤니티 API를 부를 게 아니라, **미리 수집해 적재해두고
RAG 방식으로 꺼내면** 된다.

공공데이터가 이미 이 원칙이다 — "공공 API는 사용자 검색 시 호출하지 않고 배치에서만
호출한다" (README). 근거도 같은 대접을 받을 이유:

| | 실시간 호출 (지금 community.py) | 배치 적재 + RAG |
|---|---|---|
| 검색 지연 | 검색마다 외부 API 왕복 | DB 조회뿐 — 사실상 0 |
| 쿼터 | 사용자 트래픽에 비례 (일 25,000회 상한) | 배치가 소진. 트래픽과 무관 |
| 순위 재현성 | 외부 코퍼스가 바뀌면 같은 state 도 순위가 흔들림 | 코퍼스 버전에 고정. 갱신 시점을 우리가 정함 |
| 커버리지 | 그 턴의 쿼리 2~3개가 전부 | 증상 어휘 사전 × 지역을 배치로 전부 훑음 |

## 수집은 크롤링이 아니라 **공식 검색 API 배치**

community-search.md 의 결정("공식 API, 크롤링 아님")을 유지한다. 카페·블로그 직접
크롤링은 약관·robots 위반이고, 일 25,000회 쿼터는 배치엔 충분하다 — 증상 어휘 ~30개
× 주요 지역 ~50개 × 코퍼스 3종 = 일 상한 안에서 며칠에 한 바퀴.

**저장 형태가 관건**: 스니펫 원문 장기 저장은 약관 확인 전엔 못 박는다 (community-search.md
에 이미 표시). 그래서 **파생 신호 우선** —

```sql
-- 원천 1행 = 근거 1건. 삭제 요청·만료·오매칭을 행 단위로 관리한다.
CREATE TABLE place_evidence_source (
    place_id     BIGINT REFERENCES place(id),
    topic        TEXT,          -- 증상 어휘 or 과목 ('슬개골', 'eye', ...)
    source_type  TEXT,          -- own_review | hospital_registered | public | partner
    source_url   TEXT,
    observed_at  TIMESTAMPTZ,
    expires_at   TIMESTAMPTZ,   -- 오래된 근거는 조용히 순위에서 빠진다
    match_method TEXT,          -- name_contain | addr_verified | llm_verified
    confidence   TEXT,
    corpus_ver   TEXT,
    status       TEXT           -- active | retracted | stale
);
-- mention_cnt 는 위를 집계한 파생값 (뷰/머티리얼라이즈드 뷰). 저장 원본이 아니다.
```

**표현 규칙**: 이 데이터는 "언급 근거"지 진료역량 인증이 아니다. 병원이 직접 등록한 것(source_type
= hospital_registered)만 능력이라 부를 수 있고, 나머지는 화면에서도 "커뮤니티 언급"으로 쓴다.

## 조회 루프 (검색 시점 — 외부 호출 0)

```
state.symptoms + state.specialty
 → topic 매칭 (정확 일치 → 없으면 pgvector 유사도)
 → place_evidence 에서 반경 안 병원의 신호 조회
 → 부스트 + 근거 표시 (지금과 동일한 자리: attach_evidence)
```

`CommunitySearch` 프로토콜 뒤에 구현이 하나 붙는 것뿐이다 — `attach_evidence` 의
호출자(hospital/api)는 안 바뀐다. state 에서 쿼리를 만드는 배선(2026-08-20)도 그대로:
증상이 state 에 있어야 topic 매칭이 재현 가능하다.

## 실측 (2026-08-20, 웹 검색 대체 — 네이버 키 발급 전)

**강남 × 슬개골·절뚝** (쿼리 2개): 스니펫 10건 → 전국 5,457곳 이름 매칭 4건 (예은
논현·권앤정 수원·수 센터 영등포·진주 오탐 1) · 미매칭 7건 자동 폐기 = 노이즈 전부.
강남역 반경 조회에서 예은은 **거리순 top-12 밖** — 근거 pull-forward 가 없으면 안 보인다.

**안동 × 슬개골 / 해남 × 눈 뿌옇** (같은 방식): 해당 지역 병원 **0건**. 코퍼스 중력이
수도권 2차 센터로 쏠린다 — 쿼리에 지역명을 넣어도 또 예은·수 센터·N 의료센터가 온다.

**안동동물의료센터 (병원명 직접 쿼리)**: 애그리게이터 병원 페이지에서 **진료 능력 목록**
(슬개골탈구·치과·피부·안과·정형), 당근마켓 동네생활에서 지역 후기 ("고양이 잘보세요",
이웃 예천군). 변방은 **역방향이 돈다.**

### 따라서 수집은 두 방향이다

| 방향 | 쿼리 | 잘 도는 곳 | 산출물 |
|---|---|---|---|
| 증상→병원 | 증상 어휘 × 지역 | 수도권·광역시 | 증상↔병원 연결 (FAQ·후기) |
| 병원→평판 | 병원명 (전 병원 1회씩) | **전국 균일** | 능력 목록·지역 후기 |

역방향 쿼터: 5,457곳 × 1콜 = 하루 한도(25,000) 안에서 전 병원 일 1회. 변방 병원도
근거 0 이 아니라 "능력 목록 + 동네 후기"까지는 갖게 된다.

### 실측이 확정한 리스크 둘
- **동명·유사명 오탐**: '24시수동물메디컬센터' 스니펫이 진주 '수동물메디컬센터'에 물렸고,
  '안동' 쿼리에 '안양' 병원들이 왔다. 매칭은 이름 포함만으론 안 되고 **주소·도메인 교차
  검증**이 필수다 (배치라 LLM 검증 비용이 고정이라는 게 다행인 지점).
- **접두어 미스**: 스니펫 '월드펫동물메디컬센터' ↔ DB '24시월드펫동물메디컬센터' 미매칭.
  포함 방향을 양방향으로.

변방 실측에서 변방이 **틀린 결과가 아니라 빈 결과**로 강등된 건 evidence 가 prefer 라서다
— must 였으면 변방 검색이 통째로 죽었다. 이 경계는 지켜야 한다.

주의: 이 실측은 웹 검색 대체라 네이버 카페·지식iN 의 변방 커버리지는 키 발급 후 재실측.
애그리게이터(핏펫 등) 페이지 수집은 약관 확인 전엔 후보일 뿐이다.
